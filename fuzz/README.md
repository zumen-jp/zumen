# fuzz

受け取ったバイト列を読む所を、cargo-fuzz で試します（#398・#501・#517）。登録したすべての形式と、L0 の ZIP・XML・ISO 10303-21 に target があります。API（`zumen` の `Session`）を通して、形式の判定から応答を作るまでと、形式でない入力を流す target もあります。どの target も、テストキットの fuzz の関数（`survives`・`survives_lift`・`survives_with`・`survives_calls`）を呼びます。小さい予算の中で止まり、2 回で同じ結果（読めたか・止まった理由・診断・使った量、API では応答のバイト列）になることを確かめます。パニック・止まらない繰り返し・メモリの使い過ぎは、libFuzzer が見つけます。

## target

| target | 試すこと |
| --- | --- |
| `zip` | ZIP を読み、項目を展開し、`.zip` の項目はアーカイブとして辿る。展開した量（ZIP 爆弾）と入れ子が予算で止まり、読めた名前が展開先の外を指さない |
| `xml` | XML を読み、文字と属性の値を戻す。入れ子が予算で止まり、文書型宣言の実体を戻さない |
| `step` | ISO 10303-21 を、フィーチャのコメントを読まない書き方と読む書き方で読み、文字列を戻す。入れ子が予算で止まる |
| `dxf`・`dwg`・`sxf`・`jww`・`pdf` | 読んで図面モデルに移す。`pdf` は、移した図面も 2 回で同じになることを確かめる（#506） |
| `saf`・`drawing` | SXF の属性ファイルと、図面モデルのバイナリを読む |
| `png` | シーンのバイナリを検査し、64×64 の PNG を書く。走査・合成・符号化を予算で止め、2 回の出力も一致することを確かめる |
| `svg` | シーンのバイナリを検査して SVG を書く。SVG 自体は読まず、2 回の出力も一致することを確かめる |
| `ifc` | IFC-SPF か ifcZIP を読み、曲線を必要時の getter に渡し、建物モデルと土木の領域モデルに移す |
| `express`・`ids`・`bcf` | EXPRESS のスキーマ・IDS・BCF を読む |
| `landxml` | 読んで土木の領域モデルに移す |
| `citygml`・`fgd`・`extdm` | 読んで地理の領域モデルに移す |
| `isg`・`par` | ジオイド高の格子（ISG）と、座標の補正量の格子（TKY2JGD・PatchJGD の形）を読む。`par` は、読めた格子で、決まった点の補間と JGD2011 への変換（`to_jgd2011`）まで通し、2 回の値をビットで比べる |
| `las`・`e57`・`ply`・`xyz` | 読んで点群の領域モデルに移す。LAZ は展開を止めているので、ヘッダーで断る（#510） |
| `delivery` | 電子納品の成果品のアーカイブを読み、照合する |
| `jpeg`・`boring`・`xlsx`・`csv` | 工事写真・ボーリング交換用データ・Excel の表・CSV を読む |
| `open` | API の `open` で形式を判定して開き、図面・建物・土木・地理・点群の op で読む。図面はシーンにし、図面モデルのバイナリと DXF に書いて読み直す。線形からは図（`civil_drawing`）を作ってシーンにする。LAS は範囲でも読む。開けない入力は、名指せる XYZ・拡張 DM と、固定の SXF の図面の属性ファイル（SAF、`open` の `saf`）と、写真・表・ボーリング交換用データ・成果品の op に渡す。P2Z・SFZ の中の SAF は、アーカイブの項目として結ぶ |
| `font` | シーンの文字のフォント（TrueType・OpenType）として渡し、固定の図面をシーンにする |
| `profile` | プロファイルとして渡し、固定の図面の照合（`check`）・線形の図（`civil_drawing`）・点群と設計面の差（`deviation`）を呼ぶ。線形の図はシーンにする |
| `review` | レビューの文書として渡し、固定の図面の版へ移し（`review_carry`）、照合の指摘を取り込む（`review_adopt`） |
| `review_scene` | レビューの JSON と、有限でない座標・不正な引数・ID・参照も含む Rust の値から、別のシーンを作る。シーンのバイト・出所・診断・使用量の再現、低い予算と中断、渡したフォントの字形を確かめる |
| `json` | 色の表として渡して固定の図面をシーンにし、要求として呼ぶ。配列なら、先頭の 16 の要素を順に要求として呼ぶ |

API を通す 5 つの target（`open`・`font`・`profile`・`review`・`json`）は、`fuzz/src/lib.rs` の部品で、`zumen` の `Session` を呼びます。

- どの要求の予算も、テストキットの API の呼び出しの fuzz の上限（`fuzz_call_limits`）にします。`fuzz_limits` より、要素・幾何の分割・ほかの繰り返しの上限が小さく、1 つの入力で多くの op を呼んでも、ASan と計装を入れた build で時間切れにならないようにします。`json` の target が受け取った要求も、`budget` を替え、時計で止める `time_limit_ms` を除きます。
- 2 回呼んで、応答の JSON と、取り出したバイナリの結果のバイト列を呼んだ順に並べたものが、同じになることを確かめます（`survives_calls`）。
- 応答ごとに、JSON として読め、成功したときだけ `result` を持ち、失敗した応答は理由の診断を持つことを確かめます。`blobs` の結果は、どれも取り出せ、記録した大きさと同じで、シーンの blob は `zumen` のリーダーで読めることを確かめます。
- 文書の中身に依らない入力（図面・照合のプロファイル・色の表・線形・設計面・点群・SXF の図面）は、適合テストの組の合成の入力を写した、`fuzz/src/lib.rs` の定数にします。図面（DXF）だけは、写したものに図形と文字を足しました。

`review_scene` は Rust のシーンの入口を直接呼びます。固定の空間・用紙・ビューに、有効な赤線・変更雲・注記・写真・指摘の場所を毎回合成し、入力で座標・寸法・起点・ID・参照を変えます。JSON で表せない値も渡し、空のフォントを省略した結果と明示した結果を比べます。入力をフォントとして読めたときは、注記を `H` の 1 文字だけに絞り、`Work` だけを 2 の 26 乗にします。1 文字の輪郭の事前予約（2 の 24 乗）を通して字形を作るためで、メモリと幾何の分割の上限は上げません。既存のレビューの JSON とフォントの合成の種は、`cargo xtask fuzz-seeds` がこの target にも配ります。

## 名前の付け方

target の名前は、`xtask/src/fuzz.rs` の検査が求める名前にします。crate が `[package.metadata.zumen]` の `formats` で名乗る形式、`schema/boundary.toml` の `[[detection]]` と `[[modules]]` の形式、L0 の `zip`・`xml`・`step` です。どれかに target がないと、`cargo xtask codegen --check` が落ちます。形式を足したら、`fuzz/fuzz_targets/<名前>.rs` を作り、`fuzz/Cargo.toml` の `[[bin]]` に足してください。

検査が求めない読み取りにも、target を置けます。名前は、読むものの短い英語にします（EXPRESS のスキーマの `express`、補正量の格子の `par`、API を通す `open`・`font`・`profile`・`review`・`json`）。

## 動かし方

cargo-fuzz は nightly の Rust を使います。Linux か macOS で動かします。Windows の MSVC では、libFuzzer が使う計測の記号がリンクで見つからず、作れません。CI と同じバージョンは、`.github/workflows/fuzz.yml` の `NIGHTLY` と `CARGO_FUZZ_VERSION` から読みます。

```bash
NIGHTLY=$(sed -n 's/^  NIGHTLY: //p' .github/workflows/fuzz.yml)
CARGO_FUZZ_VERSION=$(sed -n 's/^  CARGO_FUZZ_VERSION: //p' .github/workflows/fuzz.yml)
```

```bash
rustup toolchain install "$NIGHTLY" --profile minimal
```

```bash
cargo install cargo-fuzz --version "$CARGO_FUZZ_VERSION" --locked
```

```bash
cargo xtask fuzz-seeds
```

```bash
cp Cargo.lock fuzz/Cargo.lock
```

```bash
cargo "+$NIGHTLY" fuzz run -O --debug-assertions zip
```

- `cargo xtask fuzz-seeds` は、どの target にも `fuzz/corpus/<target>/` に種を書きます。種にするのは、次の 6 つです。受け取った図面と、国土地理院のデータは置きません（AGENTS.md、[座標系の扱い](../docs/formats/crs.md)）。
  - 公開サンプル（`samples/`）
  - 適合テストの組の合成の入力と、`call` で渡す要求（1 つずつと、組ごとに並べた配列）。`call_text`・`call_hex` で渡す要求のバイト列（読めない要求と、BOM を付けた要求）も、1 つずつ種にします
  - L0 の攻撃の形（ZIP 爆弾・膨らむ deflate・アーカイブの入れ子・パスの走査・XML の外部実体と深い入れ子・ISO 10303-21 の深い入れ子）
  - EXPRESS の攻撃の形（集まりの型の深い入れ子・定義された型と上位の型の長い鎖。#668）
  - 合成の格子（ISG・TKY2JGD・PatchJGD の形。補正量の格子は、格子点を 3 次メッシュの間隔に置くものと、その 5 倍の間隔に置くもの。[座標系の扱い](../docs/formats/crs.md)）
  - 線と列の参照を持つ合成シーン（ZMSC、SVG を書く target 用）
- `cp Cargo.lock fuzz/Cargo.lock` で、fuzz の crate の依存を、ワークスペースと同じバージョンから解きます。`fuzz/Cargo.lock` はリポジトリに入れません。
- `cargo "+$NIGHTLY" fuzz list` で、target の一覧を出せます。
- 見つけた入力は `fuzz/artifacts/` に出ます。直したら、その入力を最小にして、合成のテストに移します（非公開で扱う範囲は、修正したバージョンを公開したあと）。`corpus` と `artifacts` はリポジトリに入れません。
- 見つけた入力は種か種を変えたもので、表示を求めるライセンス（CC BY・MIT・公共データ利用規約）の公開サンプルから来ることがあります。入力を報告に添えるときは、最小にした入力にし、元の公開サンプルの出所とライセンス（`samples/ledger.toml`）を添えます。元が分からなければ、種を作ったコミットに固定した URL（`https://github.com/zumen-jp/zumen/blob/<コミット>/samples/ledger.toml`）で、台帳の全体を指します。サンプルを外した後も、指す先から表示が消えないようにするためです。種を作ったコミットは、暗号にした artifact の中の `NOTICE.txt` と、log の checkout に出ます。
  - 毎晩の実行なら、その夜の main のコミットです。
  - PR の実行なら、PR と main を合わせた一時のコミットです。このコミットは、後でどの ref からも指されなくなり、残るとは限らないので、件名の「Merge <PR の head> into <main のコミット>」の 2 つのコミットの台帳を、並べて指します。

## CI

`.github/workflows/fuzz.yml` が、毎晩すべての target を 1 つ 180 秒ずつ、4 つずつ並べて流します。見つけた入力と詳細（誤りの文・ログ・入力の名前とハッシュ）は、公開のログ・注釈（`::error::`）・summary・artifact・キャッシュに出しません（[#647](https://github.com/zumen-jp/zumen/issues/647)、[入力と詳細の公開範囲](#初回リリース後の記録先)）。公開の所に出るのは、target と失敗の種類だけです。初回リリースの前も同じにし、タグの push を頼んでから push までの扱い（下の「初回リリース後の記録先」）でも、CI の側を切り替えずに済むようにします。

- 前の夜までに育てた種を actions/cache で引き継ぎます。キャッシュのキーに公開サンプルの台帳（`samples/ledger.toml`）のハッシュを入れ、台帳が変わったら引き継ぎません。キャッシュは、フォークからの PR の実行でも、ワークフローを書き換えれば戻せます。そのため、流す手順か縮める手順で通らなかった target の種は、まるごと除いてから残します。種を流し始めたときに落ちた入力は種の中にあり、その後ろの種は流していないので、落ちるかが分からないからです。次の夜は、その target を `cargo xtask fuzz-seeds` の種から育て直します。流す手順か縮める手順が取り消された実行（時間切れ・concurrency）は、確かめていない種が混じるので、キャッシュを残しません。前の夜までのキャッシュに残る種は、この手順では消せません。非公開で扱う範囲の失敗では、下の「前の種のキャッシュを消す」で消します。
- 残す前に、target ごとに、通る辺を変えずに種を縮めます（libFuzzer の `-merge=1`）。libFuzzer は起動からの時間で止めますが、起動時に種をすべて流し終えるまでは止まりません。縮めないと、種が増えるほど新しい入力を試す時間が減り、種を流すだけで決まった時間を超える target も出ます。縮める前と後の種の数も、summary と log に書きます。流す手順で通らなかった target は、縮めません。こうした target と、縮められなかった target の種は、縮めて黙って外すことはせず、下のとおりキャッシュからまるごと除きます。
- target ごとの結果の表を、実行の summary と log に書きます。表には、結果（通過か、失敗と種類）・試した入力・通った辺・もっとも遅い入力（1 秒から）・使ったメモリ・流した後の種の数を出します。
- パニック、30 秒を超える入力、3 GB を超えるメモリを見つけたら失敗します。種を縮めるときに見つけたときと、1 つの target を縮めるのに 20 分を超えたときも、縮めずに失敗します。その target の種は、キャッシュに残しません。注釈（`::error::`）には、通らなかった target と失敗の種類（`crash`・`timeout`・`oom`・`leak`。入力を残さずに落ちたときは「入力なし」）だけを書きます。libFuzzer のログ（誤りの文と、入力のバイト列が出る）は、公開の log に出しません。
- 見つけた入力と、1 秒以上かかった入力のうち target ごとにそれまでの最長を超えたものと、通らなかった target（縮める手順を含む）のログを、1 つにまとめて暗号にし、artifact の `fuzz-private`（`fuzz-private.tar.gz.age`）に 14 日残します。公開サンプルの出所とライセンス（`samples/README.md`・`samples/ledger.toml`・`licenses/`）と、種を作ったコミットと実行の ID（`NOTICE.txt`）を添えます。平文は artifact に置きません。暗号にできなければ、何も置かずに落ちます。開き方は、下の「暗号にした入力を開く」にあります。
- 公開サンプルを台帳から外すと、台帳のハッシュが変わるので、外したサンプルとそれを変えた入力を含む前の種は戻りません。前の種のキャッシュを早く消す手順は、[`samples/README.md`](../samples/README.md) の「外し方」にあります。
- crate・種の元（`samples/`・`bindings/conformance/cases/`）・fuzz の target・このワークフローを変えた PR では、1 つ 20 秒ずつ流します。Markdown（`*.md`）だけの変更では流しません。種や実装に使う Markdown を足すときは、パスの除外条件の後ろにそのパスを足し、実行の対象に戻します。
- fuzz の crate はワークスペースの外にあるので、PR の fuzz で組み立ても確かめます。台帳が同じなら main の育てた種も戻すので、20 秒のうち新しい入力を試す時間が減ります。種を流すのに 20 秒より長くかかる target は、その分長くかかります。
- 落ちたときの扱いは、下の「落ちたとき」にあります。

## 落ちたとき

fuzz の job は、main の必須の検査ではありません。CI を軽く保つためです。PR で流れたら、結果も通ってからマージします。見つけた入力のある失敗は、直すまで、通ったとしません。流し直しや、新しいコミットの実行が通っても、手元で流して落ちなくても、同じです。直したら、その入力を最小にして合成のテストに移し、必須の検査で確かめます。非公開で扱う範囲（初回リリース後のものと、タグの push を頼んでから push までに対象として扱うもの）は、修正したバージョンを公開したあとに移します（下の「初回リリース後の記録先」）。入力のない一時の失敗（runner が取れないなど）は、流し直します。

通らなかった失敗は、下の「失敗を分ける」で、関係がある・関係がない・確かめられないの 3 つに分けます。PR の変更と関係のない失敗では、マージを止めません。

### 配ったパッケージに入るコード

次の基準を、初回リリース後、タグを打つ前の一覧、push を頼んでから push までの判定に使います。タグを打つコミットでは、そのコミットから作るパッケージを対象にします。

- 配ったパッケージは、crates.io・npm・PyPI・NuGet に出したものと、`release.yml` が GitHub の Release に置く配布物です。GitHub がどの Release にも添えるソースコードの圧縮は含めない。crates.io の crate では、既定で使わない機能のコードも入る。配る crate が使う依存のコードも入る。
- 失敗が対象かは、入力を渡した入口と、落ちた所で決める。配るパッケージの入口は、crates.io に出す crate の公開の関数と、各言語のパッケージと CLI が呼ぶ op です。ほかの入口（0.2.0 では `zumen-pdf` の API と、fuzz の `pdf` の target）を、配らない入口と呼ぶ。
  - 配るパッケージの入口に入力を渡して起きる失敗は、対象にする。
  - 配らない入口で見つけた落ちる失敗は、落ちた所が配ったパッケージに入るコードにあれば、対象にする。
    - 失敗は、fuzz の失敗の種類（libFuzzer が残す入力の名前の `crash`・`timeout`・`oom`・`leak`）で分ける。落ちる失敗は、種類が `crash` のものです。パニック・スタックのあふれ・メモリの誤りなど、プロセスが落ちるものが当たる。大きすぎる確保で止まったものも、この種類で分ける。
    - fuzz の外で見つけた失敗の種類は、同じ入力をその入口の fuzz の target に流して決める。決まらなければ、`crash` とする。
  - 落ちた所は、次のように決める。
    - パニックは、パニックの文が示す所とする。
    - スタックのあふれは、あふれたスタックで繰り返している関数とする。繰り返している関数のどれかが配ったパッケージに入るコードにあれば、落ちた所はそこにあるとする。繰り返している関数がなければ、ほかの落ち方と同じにする。
    - ほかの落ち方は、落ちたときに動いていた関数とする。
    - 決めた所か関数が、標準ライブラリ・C の実行時ライブラリ・サニタイザーと libFuzzer の関数・`libfuzzer-sys` の中なら、それらの外の最初の呼び出し元とする。ただし、標準ライブラリの関数が、配ったパッケージに入る型の実装（値を捨てる・比べるなど）を使って動いていたときは、その型のコードにあるとする。入れ子の値を捨てるときのスタックのあふれや、全順序でない比べ方で並べ替えが止まるパニックなどが当たる。
    - 手元で再現しなくても、ログなどで落ちた所が分かれば、これで決める。落ちた所が分からなければ、対象にする。
  - 配らない入口で見つけたほかの失敗は、対象にしない。落ちた所が配らないコードにある落ちる失敗と、種類が `timeout`・`oom`・`leak` の失敗（時間切れ・メモリの使い過ぎ・メモリの解放し忘れ）です。時間やメモリを使った所が配ったパッケージに入るコードにあっても、同じとする。ただし、同じ入力を配るパッケージの入口（その入口の fuzz の target）に流して失敗すれば、対象にする。

対象外でも、出所と再配布を認めるライセンスを示せない入力や詳細は公開しません。

### 初回リリース後の記録先

初回リリース後は、公開した最新のバージョン（最新の `v*` のタグで配ったパッケージに入るコード。[配ったパッケージに入るコード](#配ったパッケージに入るコード)）でも同じ入力で失敗する（落ちる・終わらない・メモリを使いすぎる。失敗の種類と誤りの文は問わない）不具合を、見つけたときによらず、[Security タブの非公開の窓口](https://github.com/zumen-jp/zumen/security/advisories/new) で報告します。担当者（その不具合を扱うエージェントか利用者）は、次のように記録します。初回リリースは、このリポジトリで最初に `v*` のタグを push した時点です。見つけ方（fuzz・テスト・監査・外部の実装との照合）によらず、最新のバージョンで確かめるまでは対象として扱います。確かめるには、見つけたときと同じ処理（入力を渡した入口と、その先の変換と、設定と予算）を最新の `v*` のタグのコードで流し、下の「見つけた入力を流す」と同じ条件で、失敗しない（落ちず、時間切れにもメモリの使い過ぎにもならない）かを見ます。fuzz で見つけたものは、見つけたときのコミットの target のファイル（`fuzz/fuzz_targets/<target>.rs`）・`fuzz/src/`・testkit（`crates/zumen-sdk/src/testkit.rs`）を、タグのコードに当てて組み立てて流します。予算は、見つけたときのコミットで `fuzz_limits()` と `fuzz_call_limits()` が返す値にそろえます。`depth` と `input_bytes` は testkit になく、`crates/zumen-base/src/budget.rs` の既定値から来るので、それも見つけたときの値にそろえます。fuzz 以外で見つけたものは、入力を渡した入口から落ちた所までの呼び出しを、タグのコードで同じ設定と予算で行います。あわせて、当てる前のタグのコードで組み立てたすべての target にも、同じ条件で入力を流し、配るパッケージの入口の target のどれかで失敗すれば対象とします。対象かは、入力を渡した入口と落ちた所で決めます。配らない入口（0.2.0 では `zumen-pdf` の API と `pdf` の target）で見つけた失敗の扱いを含め、決め方は [配ったパッケージに入るコード](#配ったパッケージに入るコード) のとおりです。タグを打つコミットで確かめるときと、下のタグの前の一覧でも、同じく決めます。公開の所に書く入力（最小にしたものなど）は、その入力でも確かめます。最小にしたら、見つけたときと同じ失敗か（失敗の種類・落ちた関数・誤りの文）を見て、その入力をタグでも流します。失敗の種類・誤りの文・落ちた関数が見つけたときと違っても、失敗すれば対象です。確かめたあとに新しい `v*` のタグが出たら、入力を公開の所に書く前に確かめ直します。時間切れ・メモリの使い過ぎ・手元で再現しない入力は、下の「失敗を分ける」と同じ理由で確かめられないとします。同じ処理をタグのコードで流せないもの（新しく足した形式や入口のように、当てて組み立てられないもの、予算をそろえられないもの、タグが要求を `call.op-unsupported`・`call.field-unsupported`・`call.version-unsupported` などの要求の誤りとして断るもの）と、外部からの報告で入口・設定・予算が分からないもののように、見つけたときの処理が分からないものも、確かめられないとします。確かめられない失敗は、配らない入口で見つけたもの（配ったパッケージの範囲のとおり）を除き、PR で直すものも対象のまま扱い、公開の issue と非公開のアドバイザリを作ります。`v*` のタグの push を頼んでから push までに、タグを打つコミットで失敗しないと確かめるときも、ここまでと同じ方法で行います。ここまでの確かめ方の「最新のバージョン」と「タグ」を、下のリリースの issue の最新の記録にある、タグを打つコミットと読み替えます。頼んでいるリリースの issue がいくつもあれば、それぞれのタグを打つコミットのすべてで確かめます。確かめられないものと、確かめられない失敗の扱いも同じです。タグを打つコミットを替えたら、公開の所に書く前に、替えたコミットで確かめ直します。初回リリース後に push を頼んでいる間は、最新のバージョンとタグを打つコミットの両方で確かめます。最新のバージョンでその入力が失敗しないと確かめたもの（PR が入れて同じ PR で直すもの、main にだけある不具合。下の、`v*` のタグの push を頼んでから push までに対象として扱うものを除く）は、この節の前後のとおり公開で扱い、回帰テストも修正の PR に入れます。ただし、出所と再配布を認めるライセンスを示せない入力（外部からの報告の入力、受け取った図面、ライセンスのはっきりしない公開のファイルなど）は、公開で扱うときも入力と詳細を貼らず、公開の issue には対象と失敗の種類だけを書きます。回帰テストは、規則を確かめる最小の入力をテストの中で作ります。アドバイザリの扱いと報告者への連絡（このリポジトリの外への送信）は、担当者が利用者に示し、利用者が決めます。初回リリースの前に、push を頼んでいない間に外部から報告が来たときも同じです。

- 公開の issue に書くのは、対象の target と失敗の種類（パニック、時間切れ、メモリの使い過ぎなど）だけです。親 issue や PR からは、その issue を参照します。
- 非公開のアドバイザリに公開の issue の番号と実行の ID を対応させ、入力、出所とライセンス、誤りの文、ログ、比較結果を記録します。最小にできなかった理由や artifact 内の名前もここに書きます。同じ失敗が再び出たときは、非公開の記録で照合し、その記録に新しい実行の ID を足します。
- PR の題・本文・ブランチの名前、レビューのコメント、コミットの説明、コードのコメントにも、入力と詳細を書きません。題とブランチの名前は、あとで消せません。
- 入力と詳細が公開の所（issue・PR・コメント・コミットなど）に入ってしまったら、秘密と同じく、すぐ利用者に伝え、非公開の記録にないものを写してから、そこを伏せて編集の履歴からも消します（AGENTS.md の「消さない」）。題・ブランチの名前・push したコミットに入ったものは、GitHub に消してもらうかを利用者に決めてもらいます。PR で足した種（`cargo xtask fuzz-seeds` が書く種。公開サンプル・適合テストの組など）が最新のバージョンでも失敗するとき（確かめられないときを含む）も、入力が公開の所に入ったものとして扱い、その種の元を PR から外します。
- 直せずに利用者の承認を求める場合は、非公開の記録を利用者と照合し、実行の ID・target・誤りを特定してから、その PR について会話で認めてもらいます。PR には、ほかの承認と同じく、認めた日・head・範囲・利用者の言葉を書きます。範囲は、公開の issue の番号と非公開の記録の場所で書きます。利用者の言葉に詳細が入っていたら、PR ではそこだけを伏せて伏せた所を示し、全文を非公開の記録に書きます。非公開の記録には、その承認へのリンクと、認めた実行・誤り・比較結果を残します。別の失敗を含めるときは、あらためて認めてもらいます。
- 修正の PR は公開で作り、CI と互いの確かめを通します。修正の差分は、修正したバージョンより先に公開されます。担当者は、入力で落ちなくなったことを手元で確かめ、非公開の記録に書きます。確かめる側も、非公開の記録を読んで入力を手元で流します。確かめる側は読むだけにし、入力と詳細（流した結果を含む）は結果に書かず、結果とは別に返します。作った側（修正の PR では担当者）は、それを手を加えずに非公開の記録に貼ります。結果は[開発の進め方](../docs/work.md) のとおり全文をレビューのコメントに貼り、非公開の記録の場所は答えに書きます。ほかの PR を確かめる側が対象の入力を見つけたときも、同じく扱います。
- 修正の PR では公開の issue を閉じません。マージしたら、公開の issue の開始条件を「修正したバージョンを公開したあと」にし、「待ち: 利用者」を付けます。修正したバージョンを公開したら、ラベルを外し、入力から作る合成のテストと公開できる詳細を出し、公開の issue から修正したバージョンと修正内容を案内してから閉じます。アドバイザリを公開するかは、利用者が決めます。push の頼みを取り下げて対象でなくなったものは、下の「取り下げたあと」のとおりにします。
- `v*` のタグの push を利用者に頼むときは、初回に限らず、タグを打つコミットで直っていない失敗（そのコミットのあとに直したものを含む。配ったパッケージの範囲で対象になるものに限る）のうち、入力か詳細を公開の所に置いたものを、置いた所（issue、PR の本文と承認の記録、main と開いた PR の合成のテストと種の元、#647 の前の実行のログと artifact）とともに一覧で示し、タグの前に直すか、扱いを利用者に決めてもらいます。push を頼んでから push までは、タグを打つコミットで失敗する入力と詳細を、初回リリースの前でも非公開で扱う範囲として扱います（失敗しないと確かめるまで、公開の所に書きません。確かめ方は、この節の初めの段落のとおりです）。push を頼んだことは、下の「リリースの issue」のとおりに記録し、ほかのエージェントは、作業を選ぶ前にそれを見ます（`docs/work.md` の「選び方」）。頼みを取り下げたら、この扱いは終わり、下の「取り下げたあと」のとおりにします。push を頼むエージェントは、push の直前に一覧の作り直しを頼むよう利用者に伝え、利用者は push の直前にエージェントに一覧を作り直させ、エージェントは作り直した一覧を示し直します。一覧は会話か非公開のアドバイザリで示し、公開の所には対象と失敗の種類と公開の issue の番号までを書きます。直さずにタグを打つという判断の記録も、上の承認と同じく、範囲を公開の issue の番号と非公開の記録の場所で書き、利用者の言葉の詳細の所は伏せます。直さずにタグを打つと決めた失敗は、そのときから非公開で扱う範囲として扱い、入力と詳細（PR の本文と承認の記録の、利用者の言葉を含む）を、公開の issue の番号と一緒に非公開のアドバイザリに写してから、上のとおりに伏せます。これをタグの push の前に終えます（実行のログと artifact を消すかは、戻せないので利用者が決めます）。main の合成のテストと種の元に入った入力は伏せられないので、利用者に伝え、直しを含むコミットにタグを打つかを決めてもらいます。タグのあとは、こうした失敗を、新しい最新のバージョンでその入力が失敗しないと確かめるまで非公開で扱う範囲として扱います。一覧に入らなかったもの（一覧を示したあとに置いたものを含む）が公開の所に見つかったら、上のとおりに写してから伏せます。
- **リリースの issue。** `v*` のタグの push を利用者に頼むエージェントは、頼む前に、出すバージョンのリリースの issue を作り、ラベル「リリース」を付けます。初回は、新しく作らずに #317 を使います。題には、出すタグの名前（`v0.3.0` など）を入れます（#317 の題は変えず、タグの名前は記録に書きます）。タグの push は利用者を待つものなので、「待ち: 利用者」も付けます。頼んだとき・タグを打つコミットを替えたとき・push したとき・頼みを取り下げたときに、その issue にコメントで記録を書きます。記録は、担当者が新しいコメントとして足します。GitHub が返す投稿者の数値 ID を、利用者とエージェントが使う共通のアカウント（#317 の作成者）の ID と照合します。記録のコメントは、1 行目を「push の頼み: 頼んだ」「push の頼み: コミットを替えた」「push の頼み: push した」「push の頼み: 取り下げた」のどれかにし、頼んだときとコミットを替えたときは、タグの名前とタグを打つコミットの完全な SHA を書きます。一覧と詳細は書きません。ほかのエージェントは、ラベル「リリース」の開いた issue とそのコメントの全ページを調べ、各 issue の担当者の最新の記録を見て、「頼んだ」か「コミットを替えた」の issue が 1 つでもあれば、push を頼んでいる間とします（下のコマンド）。記録のない issue は、頼んでいる間に数えません。作業を選んだあとに頼みが始まることがあるので、見つけた入力か詳細を公開の所に書く前にも、同じく見ます。push して公開を終えたときと、そのバージョンを出さないと決めたときに、issue を閉じます（#317 は、その完了の条件で閉じます）。頼んでいる間に出さないと決めたら、先に「push の頼み: 取り下げた」を書き、下の「取り下げたあと」を終えてから閉じます。
- **取り下げたあと。** push の頼みを取り下げたら、取り下げたことをリリースの issue に書いたエージェントが、閉じていない非公開のアドバイザリのすべてを見直します。すべてを見るのは、頼む前からあるものと、ほかの頼みのために前の取り下げで残したものも見落とさないためです。失敗の担当者は、push の頼みを理由に非公開で扱うとき、そのリリースの issue の番号を非公開の記録に残します。記録を作成・追記した直後と、修正の PR のマージ後に公開の issue を待ちにした直後に、当初のリリースの issue（閉じたものを含む）の最新の記録と、現在のすべての頼みと公開した最新のバージョンを確かめ直します。取り下げた側の見直しよりあとに記録や待ちを足した場合は、失敗の担当者が下の手順を引き受けます。すでに写した記録と済んだ手順を確かめて、残りを進めます。タグの前の一覧だけで対象だったもの（初回リリースの前のものと、公開した最新のバージョンでは失敗しないと確かめたもの）は、対象でなくなるので、この節の前後のとおり公開で扱います。写す直前にもリリースの issue を見て、取り下げた issue で頼み直したときを含め、どこかで push を頼んでいれば、そのタグを打つコミットでも失敗しないと確かめたものだけを、対象でなくなったものとします。直さずにタグを打つという判断は、取り下げで効かなくなり、次に頼むときに決め直します。対象でなくなったものは、次のようにします。
  - 非公開のアドバイザリにだけある入力と詳細を、下の「issue にする」のとおり公開の issue に写します（落ちた target か手順・誤りの文・実行の ID と、最小にして元の公開サンプルの出所とライセンスを添えた入力）。写す入力は、出所と再配布を認めるライセンスを示せるもの（公開サンプルと合成の入力から来たもの）に限ります。写す前に、同じ失敗の公開の issue がほかにないかを確かめ、あればそちらにまとめます。取り下げを書いてから写すまでに、ほかのエージェントが毎晩の失敗を公開の issue にすることがあるためです。写し終えたアドバイザリは、閉じます。
  - 出所と再配布を認めるライセンスを示せない入力（外部からの報告の入力、受け取った図面（`ZUMEN_SAMPLES`）、ライセンスのはっきりしない公開のファイルなど）で見つけた失敗は、入力と詳細を写しません（上の、公開で扱うときと同じです）。公開の issue には対象と失敗の種類だけを残し、回帰テストは、入力を写さずに、規則を確かめる最小の入力をテストの中で作ります。そのアドバイザリを閉じるか、公開するか、報告者に公開の許しを求めるかは、取り下げを書いたエージェントが利用者に示し、利用者が決めます（報告者への連絡は、このリポジトリの外への送信です）。
  - 修正の PR のマージで開始条件を「修正したバージョンを公開したあと」にし、「待ち: 利用者」を付けた issue は、開始条件を戻してラベルを外し、入力から作る合成のテスト（入力を写さないものは、規則を確かめる最小の入力から作るテスト）を公開の PR で足してから閉じます。別の理由で利用者を待つ issue は、その開始条件とラベルを残します。

`gh` と `jq` でリリースの issue と担当者の記録を全件取得し、各 issue の最新の記録を表示します。最初の 1 行は下の 4 種類のいずれかに一致する必要があります。「頼んだ」「コミットを替えた」の記録は、次の 2 行を「タグ: v…」「コミット: 完全な SHA」にします。タグ名がその issue のリリースと合い、有効な Git のタグ名であること、SHA がこのリポジトリの対象コミットを指すことも確かめます。取得が途中で失敗した場合や記録を確かめられない場合は、入力と詳細を非公開のままにします。

```bash
set -o pipefail
repo=repos/zumen-jp/zumen
release_actor=$(gh api "$repo/issues/317" --jq '.user.id | if type == "number" then . else error("担当者を確認できない") end') || exit 1
issues=$(gh api --method GET --paginate "$repo/issues" -f state=open -f labels=リリース -F per_page=100 \
  --jq '.[] | select(.pull_request == null) | .number') || exit 1
for number in $issues; do
  echo "#$number"
  gh api --paginate --slurp "$repo/issues/$number/comments?per_page=100" | jq -r --argjson actor "$release_actor" '
    add | map(select(.user.id == $actor) | select(.body | startswith("push の頼み:"))) | max_by(.id) |
    if . == null then "記録なし"
    else (.body | gsub("\r\n"; "\n") | split("\n")) as $lines |
      if $lines[0] == "push の頼み: 頼んだ" or $lines[0] == "push の頼み: コミットを替えた" then
        if (($lines[1] // "") | test("^タグ: v[^[:space:]]+$")) and (($lines[2] // "") | test("^コミット: [0-9a-f]{40}$"))
        then $lines[:3] | join("\n") else error("タグまたはコミットを確認できない") end
      elif $lines[0] == "push の頼み: push した" or $lines[0] == "push の頼み: 取り下げた" then $lines[0]
      else error("頼みの状態を確認できない") end
    end' || exit 1
done
```

取り下げ後の見直しで、非公開の記録にあるリリースの issue がすでに閉じていたら、その番号のコメントも同じ方法で取得して照合します。

### 見つけた入力を流す

見つけた入力は、落ちた実行の暗号にした artifact `fuzz-private` の中の、落ちた target のフォルダー（`artifacts/<target>/`）にある `crash-*`・`timeout-*`・`oom-*`・`leak-*` です。artifact には、通った実行でも、1 秒以上かかった入力（`slow-unit-*`）が入ります。通らなかった target の libFuzzer のログは `logs/fuzz/<target>.log`、縮める手順のログは `logs/fuzz-merge/<target>.log` です。開き方は、下の「暗号にした入力を開く」にあります。PR の実行は、PR のブランチの名前で引けます。

```bash
gh run list --workflow fuzz.yml --branch <PR のブランチ> --limit 5
```

開いた中身は、リポジトリの外の、自分だけが読めるフォルダーに置きます。中身（入力・誤りの文・ログ・入力の名前とハッシュ）は、非公開で扱う範囲なら、非公開のアドバイザリにだけ書きます（上の「初回リリース後の記録先」）。

#### 暗号にした入力を開く

artifact は、`fuzz/recipients.txt` の公開鍵で [age](https://github.com/FiloSottile/age) の形に暗号にしてあります。開くには、age と、どれかの公開鍵に対応する秘密鍵が要ります。秘密鍵は利用者が持つ機械にだけあり、リポジトリにも secrets にも置きません。

秘密鍵のない機械のエージェントは、開けないので、次のようにします。

1. 公開の所に書けることだけで進めます。毎晩の失敗と、PR と関係のない失敗の issue には、落ちた target か手順と失敗の種類を書きます。秘密鍵のない側が実行の ID を書くのは、初回リリースの前で、`v*` のタグの push を頼んでいないときに限ります。その期間に、入力によらない組み立てやツールの失敗だけと公開の手順やログで確かめ、その失敗を issue にする場合は、手順・誤りの文・実行の ID を公開の issue に書きます。失敗に入力があれば、出所と再配布を認めるライセンスを確かめられたときだけ実行の ID を書きます。入力の有無が分からない間は対象と失敗の種類だけを公開します。同じ実行の別の失敗が非公開のときも、その実行の ID を公開しません。
2. 開くことと、それを要る作業（下の「失敗を分ける」の 3・4、入力を最小にする、issue か非公開の記録に入力と誤りの文を書く）を、利用者に頼みます。利用者の手元にしかないものを用意することなので、開くことを頼む issue に「待ち: 利用者」を付けます（AGENTS.md の「人を待つもの」）。PR の fuzz で入力のある失敗が出たら、分けるまでマージしません。PR には、このラベルを付けず、本文でその issue を指して、開くのを待っていることを書きます。PR の側で人を待つもの（分けられずに利用者に認めてもらう失敗など）が出たときは、AGENTS.md の「人を待つ PR」の手順で扱います。
3. 利用者か、秘密鍵のある機械のエージェントが開いたら、その人が続けます。入力のある失敗が非公開で扱う範囲か、その入力の出所や再配布の許しを示せないときは、詳細を非公開のアドバイザリに書き、公開の issue には対象と失敗の種類だけを書きます。それ以外は、下の「issue にする」に従います。開いて続けられるようになったら、issue のラベルを外します。

```bash
gh run download <実行の ID> --name fuzz-private --dir <置き場所>
```

```bash
age -d -i <秘密鍵のファイル> <置き場所>/fuzz-private.tar.gz.age | tar -xzf - -C <置き場所>
```

取り出すと、`<置き場所>/artifacts/<target>/crash-…` のように並びます。`fuzz/recipients.txt` の受け取り手（公開鍵）を足す・替える・外すのは、秘密鍵の持ち主を決めることなので、利用者が決めます（AGENTS.md の「人を待つもの」の鍵）。外しても、前の実行の artifact は、外した鍵で開けるまま 14 日残ります。

#### 前の種のキャッシュを消す

非公開で扱う範囲の失敗を見つけたら、担当者は、前の夜までに残した種のキャッシュを消します。前の夜までのキャッシュには、見つけた入力と、まだ流していない種が残ることがあり、フォークの PR から戻せるからです。流れている fuzz の実行が終わってから、[`samples/README.md`](../samples/README.md) の「外し方」と同じコマンドで消し、`gh cache list --key fuzz-corpus-` で何も出ないことを確かめます。種は、次の夜から `cargo xtask fuzz-seeds` の種で育て直します。消したことは、非公開の記録に書きます。

PR の実行は、PR の head と main を合わせた一時のコミットで流れます。そのコミットは、log の checkout と、暗号にした artifact の中の `NOTICE.txt` に出ます。手元の target は、次のコミットで作ります。

- PR の target: そのコミットか、そのコミットの main を取り込んだ PR の head
- main の target: そのコミットの main か、それより新しい main

入力は、CI と同じ条件（`-timeout=30 -rss_limit_mb=3072`）で流します。上の「動かし方」と同じく、Linux・macOS か WSL で動かします。最小にするときは、`cargo fuzz tmin` を使います。手元で流すのは、調べる・比べる・最小にするためで、落ちなくても、通ったとはしません。

```bash
cargo "+$NIGHTLY" fuzz run -O --debug-assertions <target> <置き場所>/artifacts/<target>/<入力> -- -timeout=30 -rss_limit_mb=3072
```

```bash
cargo "+$NIGHTLY" fuzz tmin -O --debug-assertions <target> <置き場所>/artifacts/<target>/<入力> -- -timeout=30 -rss_limit_mb=3072
```

### 失敗を分ける

次の順に見ます。誤りは、種類と、パニックならその関数と文で比べます。行の番号は、PR の変更でずれるので比べません。

1. PR で足した種（`cargo xtask fuzz-seeds` が書く種）そのものが落ちるなら、関係があります。マージすると、その後の実行が、その種で落ち続けるからです。種のファイルの名前は、中身の SHA-256 です。空の `fuzz/corpus` で、PR の側と main の側のそれぞれで `cargo xtask fuzz-seeds` を流し、見つけた入力の SHA-256 の名前の種が、PR の側にだけあるかを見ます。macOS では、`sha256sum` の代わりに `shasum -a 256` を使います。
2. 時間切れとメモリの使い過ぎは、確かめられないとします。時間切れは機械の速さで、メモリの使い過ぎは OS とメモリの割り当て方で変わるので、main の target と比べても決まりません。メモリは、それまでに流した入力で積もった分も数えるので、入力を 1 つだけ流しても再現しないこともあります。
3. ほかの、見つけた入力のある失敗は、その入力を手元で PR の target と main の target に流します。どちらの target でも落ちなければ、確かめられないとします。main の target が、PR の実行と同じ誤りで落ちれば、関係がありません。ほかは、関係があります。
4. 入力のない失敗（組み立てやツールの失敗）は、main の実行と比べます。同じ手順が同じ誤り（落ちた target と誤りの文）で落ちれば、関係がありません。PR の実行の log に、main の実行の log にない誤りがあれば、関係があります。target を流す手順と縮める手順の誤りの文は、公開の log になく、暗号にした artifact のログにあります（上の「暗号にした入力を開く」）。比べる main の実行は、PR の実行が合わせた main のコミットか、それより新しいものにします。main の最新の毎晩の実行がそれより古いときだけ、手で流します。

```bash
sha256sum <置き場所>/artifacts/<target>/<入力>
```

```bash
gh run list --workflow fuzz.yml --branch main --limit 5
```

main の fuzz を手で流すときと流し直すときは、走っている実行がないことを確かめ、毎晩の実行（日本時間 4:00 から）の前後を避けます。手で流した実行と毎晩の実行は同じ組（concurrency）で、後から始まったほうが、前のほうを取り消すからです。

```bash
gh run list --workflow fuzz.yml --branch main --status in_progress
```

```bash
gh workflow run fuzz.yml --ref main -f seconds=20
```

分けたあとは、次のようにします。

- 関係がある失敗は、直してからマージします。
- 関係のない失敗では、マージを止めません。下の「issue にする」のとおり、issue にします。
- 確かめられない失敗は、直してからマージします。直せないときは、その PR でマージの条件を緩めることになるので、人を待つ PR の手順で扱います（AGENTS.md の「並行して進める」）。PR に「待ち: 利用者」を付けます。非公開で扱う範囲の入力と詳細は上の「初回リリース後の記録先」に従い、利用者に PR の番号・head・失敗した実行の ID と、分けた結果（手元でどちらの target が落ちたか）を示して、会話で認めてもらいます。認める範囲は、その失敗（実行の ID・target・誤り）です。認めた日・head・範囲・言葉を PR に書き（非公開で扱う失敗について承認の範囲を書く方法は、上の「初回リリース後の記録先」のとおりです）、認めた会話のエージェントか利用者がマージします。あとの実行で、範囲の外の確かめられない失敗が出たら、認め直してもらいます。この失敗も、下の「issue にする」のとおり、issue にします。

### issue にする

関係のない失敗と、利用者に認めてもらってマージする失敗は、次のように issue にします。非公開で扱う範囲の失敗は、PR で直すときも issue にします（上の「初回リリース後の記録先」）。

- マージの前に issue にし、PR の本文にその issue を書きます。同じ失敗の issue があれば、それを使います。落ちた target と誤りの文で同じ失敗かを確かめ、実行の ID を足します。失敗に入力があり、非公開で扱う範囲か、その入力の出所や再配布の許しを示せないときは、非公開のアドバイザリで照合し、そこに追記します。入力の有無を確認できない間は対象と失敗の種類だけを公開します。同じ実行の別の失敗が非公開の場合も、実行の ID を公開しません。
- 入力のある失敗が非公開で扱う範囲か、その入力の出所や再配布の許しを示せないときは、公開の issue には対象と失敗の種類だけを書きます。入力・誤りの文・実行の ID などの詳細は非公開にします（上の「初回リリース後の記録先」、[入力と詳細の公開範囲](#初回リリース後の記録先)）。入力によらない組み立てやツールの失敗だけと確かめた実行は、下の「issue にする」に従い、公開の issue に手順・誤りの文・実行の ID を書きます。入力を公開できる失敗でも、落ちた target か手順、誤りの文、公開できる実行の ID を書きます。見つけた入力があれば、最小にし、元の公開サンプルの出所とライセンスを添えて貼ります（上の「動かし方」）。artifact は 14 日で消えるので、直すときに再現できるようにするためです。手元で再現せず、最小にできない入力は、貼らずに、artifact の中の名前と、最小にできなかったわけを書きます。
- issue は、いちばん前の開いた段階の issue の子にし、開いた子 issue のいちばん上に並べます。早めに直すためです。並べた理由は、親の issue のコメントに、この節を指して書きます。
- main の組み立てかツールが落ちている間は、PR の fuzz は何も確かめないので、パニックを足す変更も止まりません。早めに直します。

### 毎晩の実行

毎晩の実行で見つけた失敗も、同じく issue にして早めに直します。fuzz は入力を乱数で作るので、ある夜に落ちても、次の夜は通ることがあります。初回リリース後と、`v*` のタグの push を頼んでから push までのほか、失敗の入力について出所や再配布の許しを示せないときも、実行の ID と issue の対応を非公開のアドバイザリで調べます。入力によらない失敗だけと確かめた実行など、公開できる実行の ID は公開の issue で照合します。エージェントは、作業を選ぶ前に、main の毎晩の fuzz の終わった実行を引き、結論が `success` でない実行に、その実行に対応する issue がなければ、issue にします（`docs/work.md` の「選び方」）。入力のない一時の失敗（runner が取れない、ほかの実行に取り消された、など）は、流し直して通れば、issue にしません。毎晩の実行は 1 日 1 回なので、新しいほうから 14 回分見れば、artifact が残る 14 日の分はすべて入ります。main で手で流した実行が通らなかったときは、流した側が、同じく issue にします。

```bash
gh run list --workflow fuzz.yml --branch main --event schedule --status completed --limit 14
```

次の検索は、実行の ID を公開している場合に使います。実行の ID が非公開なら、上の「初回リリース後の記録先」のとおり、非公開のアドバイザリで照合します。

```bash
gh issue list --state all --search "<実行の ID>"
```

```bash
gh run rerun <実行の ID>
```

## ライセンス

libfuzzer-sys は LLVM の libFuzzer を同梱し、そのライセンスは NCSA です。fuzz のツールにだけ使い、配る成果物には入りません。`deny.toml` の許可リストに理由を書いてあります。
