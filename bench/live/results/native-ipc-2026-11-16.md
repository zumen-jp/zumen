# 常駐する AcadLive と Node.js の往復（2026-11-16）

`zumen live --stdio` と実際の Node.js 接続で、移動と 64 要素ブロックの差分反映を測りました。中央値は 1 万・100 万要素で 120.5〜132.1 µs、100 万要素の文書を持つ子プロセスの最大ワーキングセットは約 407 MiB でした。目標の 1 ms を超えた試行もあり、全条件の達成にはしていません。

## 対象と手順

- 実行入口と Node.js 接続: [`3fe7ad65`](https://github.com/zumen-jp/zumen/commit/3fe7ad65195cbf0e106d7fe27e01fec4fc5eb216)。測定器は [`native-ipc.mjs`](../native-ipc.mjs)。
- Windows x64、AMD Ryzen 5 3600XT、Rust 1.99.1 MSVC、ワークスペースの release ビルド、Node.js 24.22.2。
- 1 万・100 万本の LINE を格子状に置く合成 DXF。単位は mm、一意のハンドルを持ちます。1・4 スレッドを指定して開きます。
- 各構成で 100 回の慣らし後、1,000 回ずつ、行の ID とハッシュの取得、1 要素の移動、取り消しを直列に行います。対象の行は固定の整数列で図面全体から選びます。
- 移動・取り消しの時間には、要求の生成、パイプの往復、コアの処理、応答の検査、Node.js 側の表示列への塊のコピーと受領確認の記録を含めます。GPU・Electron の描画は含めません。
- `target` は行の ID とハッシュを取得する操作です。空間索引で範囲を選ぶ操作は、この測定には含めません。
- 初期表示は、入力の生成と子の起動の要求を計測前に行い、`open` の呼び出しから Node.js の初期列へのコピーまでを 1 回測ります。
- コアの予算は既定値のままです。Node.js の通信期限だけ 120 秒にします。計測前に明示した GC を流し、計測中の GC は実行環境に任せます。同じ端末のほかの作業は隔離していません。

```sh
cargo build -p zumen-cli --release --locked
node --expose-gc bench/live/native-ipc.mjs target/release/zumen 10000 1000 1
node --expose-gc bench/live/native-ipc.mjs target/release/zumen 1000000 1000 1
node --expose-gc bench/live/native-ipc.mjs target/release/zumen 10000 1000 4
node --expose-gc bench/live/native-ipc.mjs target/release/zumen 1000000 1000 4
```

Windows の実行ファイルは `zumen.exe` です。`ZUMEN_BENCH_COMMIT` にビルド元のコミットを指定すると、JSON の `nativeCommit` に記録します。メモリのピークは Windows の `PeakWorkingSet64`、Linux では `VmHWM` を読みます。ほかの OS では未取得を表す `null` にします。

## 初期表示とメモリ

メモリの単位は MiB（1,048,576 バイト）です。子のピークは読み込み・編集・保存を含みます。Node.js 側は測定器の親で、入力の生成、表示列、直接比較のために保持する初期パケット、保存の応答も含みます。親子全体の同時ピークは測っていません。

| 要素数 | スレッド数 | 初期表示 ms | 子のピーク MiB | 親のピーク MiB |
| ---: | ---: | ---: | ---: | ---: |
| 10,000 | 1 | 25.2 | 10.0 | 70.6 |
| 1,000,000 | 1 | 1,456.7 | 407.3 | 239.3 |
| 10,000 | 4 | 21.4 | 10.4 | 70.9 |
| 1,000,000 | 4 | 1,107.1 | 407.4 | 245.1 |

100 万要素の入力は 46,493,241 バイト、初期の表示パケットは 44,375,224 バイトです。初期表示の従来実装との同条件比較は、この測定ではしていません。5 分の 1 以下という条件は未検証のままです。

## 等価の確認と残件

慣らしを含む全移動をそれぞれ取り消した後、全体保存を合成入力の全バイトと直接照合しました。受信側の全 13 列も、初期パケットの全バイトと直接照合しました。4 構成すべてで一致しています。記録用の SHA-256 も出し、同じ規模の 1・4 スレッドで保存・表示の値が一致しました。

この測定器は、大規模図面の変更後の保存を従来の逐次 `apply` と比較したり、保存前の保持モデル全体・ID・診断を再読と照合したりはしません。その等価検査は[コアの検証](core-2026-11-16.md)と、実行入口の[合成 DXF・公開 DWG の検査](../../../bindings/cli/live.md#検査)を続けて広げます。

今回の中央値と p99 は、1 万と 100 万要素で同じ桁でした。全回 1 ms 以内という条件、空間索引による選択、混在図面・他形式、製品全体のメモリ、描画順と表示定義、Electron の描画までを含む性能は残件です。試作 `Document` の過去の 48〜62 µs と、今回の常駐する `AcadLive` の値は別の測定です。
