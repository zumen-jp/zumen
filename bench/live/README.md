# 文書エンジンの検証と測定

[文書エンジン](../../docs/live.md)のコアを検証する `core-live` と、DXF・DWG の試作を検証する `live` を置きます。図面を開いたまま持つ実装を、従来実装の逐次 `apply`・保持モデル・保存バイト列と照合し、時間とメモリを測ります。作業は [#878](https://github.com/zumen-jp/zumen/issues/878) で追います。

コアのワークスペースには入れていません（形式に依らない表・版・トランザクション・取り消し・ページ配列・空間索引・変更フラグは `crates/zumen-live` に切り出し、1 オブジェクトごとの読み書き規則は `crates/zumen-acad` で共有しています）。依存は、このリポジトリの `zumen`・`zumen-acad`・`zumen-base`・`zumen-drawing`・`zumen-jww`・`zumen-live`・`zumen-scene`・`zumen-sdk`・`zumen-sxf` と、`libm` です。`Cargo.lock` は、ワークスペースの `Cargo.lock` から同じバージョンを引き継いでいます。CI はこのフォルダーのコードを組み立てないので、下の結果は、書いた日付に手元で流したものです。

## コアの検証と測定

`core-live` は `AcadLive`・`JwwLive`・`SxfLive` の公開入口を呼びます。対象の拡張子は DXF・DWG・JWW・SFC・P21 です。既存の `live` コマンドは、下に記した試作を動かします。

```sh
cargo build --release --locked --manifest-path bench/live/Cargo.toml --bin core-live --target-dir target/bench-live-core
target/bench-live-core/release/core-live compare target/bench-editor/sfc-10k.sfc --threads 1
target/bench-live-core/release/core-live compare target/bench-editor/sfc-10k.sfc --threads 4
target/bench-live-core/release/core-live measure target/bench-editor/sfc-10k.sfc --threads 4 --runs 7
target/bench-live-core/release/core-live open target/bench-editor/sfc-10k.sfc --threads 4
```

生成先はコアのワークスペースと分けます。異なるワークスペースで機能の組が変わると、同じ名前の ABI のライブラリを上書きし、別の組み立ての doctest と競合するためです。Windows では実行ファイルに `.exe` が付きます。入力には、[bench/editor](../editor/README.md) で作った図面や公開サンプルを使います。

- `compare` は、最初の空間か用紙にある最後の線・点・円・折れ線を 2 回動かします。変更結果と診断を逐次 `apply` と比較し、保存バイト列、保存前の保持モデル全体・ID・ハッシュ・診断を比較します。保存後の従来実装の再読とも照合し、2 回の取り消しとやり直しの状態・保存を確かめます。モデルの出所の範囲も比較に含め、不一致は `FAIL` と終了コード 1 で返します。
- `measure` は、開いて表示のバッファーを持つまで、1 件の確定、選択、取り消しの中央値・最小・最大をマイクロ秒で出します。初回の編集も集計に含みます。選択は上記の要素を囲む範囲か、円の中心・点・折れ線の最初の頂点を含む範囲です。
- 初期表示の比較先は、従来実装の読み取り・モデル変換・`zumen-scene` の構築を同じ予算で通した時間です。コアの表示のバッファーは曲線や文字を要素の値で持ち、従来のシーンは近似と字形を作るため、両者が行う仕事の違いを結果に添えます。
- `open` は読み込み後に入力のバイト列を手放し、PID と生存行数を出して、標準入力の改行まで文書を保持します。OS のメモリ測定には新しいプロセスでこの操作を使い、`compare` の検証用モデルや保存の写しを混ぜません。

各操作の予算は `Cx` で共有します。展開・確保量の既定値は測定用に 16 GiB とし、`--decoded-mib` で変更できます。ほかの単位はコアの既定値です。これは累計の確保予算であり、常駐メモリ 500 MiB の目標とは別です。停止したときは理由・診断・各単位の使用量を出します。入力に起因する異常終了や資源の超過の記録は [fuzz の公開範囲](../../fuzz/README.md#初回リリース後の記録先)に従います。

`compare` の `--evidence-dir` は、入力名のフォルダーに、初期状態・各移動後・取り消し後・やり直し後の記録を置きます。`.bin` は保存バイト列、`.ids` は全要素の ID とハッシュ、`.diagnostics` は保持モデル取得時の診断全項目、`.budget` は同じ取得で使った各予算単位です。既存の同名の記録は上書きするため、環境ごとに記録先を分けます。

```sh
node bench/live/synthetic.mjs target/bench-live-inputs 10000 1000000
target/bench-live-core/release/core-live compare target/bench-live-inputs/lines-1000000.dxf --threads 1 --evidence-dir target/bench-live-native-1
target/bench-live-core/release/core-live compare target/bench-live-inputs/lines-1000000.dxf --threads 4 --evidence-dir target/bench-live-native-4
cargo build --release --locked --manifest-path bench/live/Cargo.toml --bin core-live --target wasm32-wasip1 --target-dir target/bench-live-core
node bench/live/core-wasi.mjs target/bench-live-core/wasm32-wasip1/release/core-live.wasm target/bench-live-inputs target/bench-live-wasm lines-1000000.dxf --threads 1
node bench/live/compare-evidence.mjs target/bench-live-native-1 target/bench-live-native-4 target/bench-live-wasm
```

`compare-evidence.mjs` は全ファイルを区切って読み、バイト列を直接比べます。WASI の比較はコアの文書エンジンが対象で、`Session` の `wasm32-unknown-unknown` 適合テストを代替しません。`synthetic.mjs` の格子状の LINE は `$INSUNITS` を持たず、単位未指定の診断も比較します。

Windows のメモリは、PowerShell 7 で次のように測ります。入力の写しを解放して文書だけを持つ時点のワーキングセット、専用メモリと、構築中も含むワーキングセットの最大値を分けて出します。時間には、プロセス起動・ファイル読み取り・40 ms 間隔の確認が含まれます。性能の時間比較には `measure` の値を使います。

```powershell
pwsh -File bench/live/memory.ps1 -Executable target/bench-live-core/release/core-live.exe -InputPath target/bench-live-inputs/lines-1000000.dxf -Threads 4
```

この入口の比較は 2 回の移動の経路です。全種類の操作の検証は単体テストと fuzz でも続けます。初回の結果と未達は [2026-11-16 の記録](results/core-2026-11-16.md)、公開サンプル・5 形式×4 規模・1 万／10 万／100 万要素（LINE・混在・ブロック挿入）の検証と達成結果は [2026-11-20 の記録](results/core-2026-11-20.md) にあります。

## 常駐子プロセスの測定

`native-ipc.mjs` は実際の `zumen live --stdio` と Node.js の接続を使い、行の ID とハッシュの取得、移動と表示差分、取り消しを往復します。1 万・100 万本の LINE を生成し、受信側の列へ 64 要素ブロックを反映します。最後に、保存の全バイトと表示の全列が初期状態と同じであることを直接照合します。

```sh
cargo build -p zumen-cli --release --locked
node --expose-gc bench/live/native-ipc.mjs target/release/zumen 1000000 1000 4
```

引数は実行ファイル、要素数、試行数、開くときのスレッド数です。Windows では `zumen.exe` を使います。要素数の代わりに入力のファイルを渡すと、JWW・SFC・P21・DWG もその図面で測ります。描く順の行を混ぜた順に試し、移動を受けた行を 1,000 行まで対象にします。取り消し後の保存は、開いた直後の保存と照合します。入力と同じバイト列かどうかは `savedEqualsInput` に出します。4 スレッドの 5 形式を含む最新の結果は [2026-11-20 の記録](results/core-2026-11-20.md#常駐子プロセス-ipc-の往復) にあります。過去の測定として [2026-11-18 の記録](results/native-ipc-formats-2026-11-18.md) と [2026-11-16 の結果](results/native-ipc-2026-11-16.md) も残しています。

## 範囲

以下は既存の試作 `live` の範囲・手順・過去の測定です。コアの `core-live` の範囲は上に記したとおりです。

扱うものは、次のとおりです。

- 入力は ASCII の DXF と、DWG（R2000・R2004・R2007・R2010〜R2018）です。DXF の行の終わりは LF と CR LF のどちらも読み、Shift_JIS（`$DWGCODEPAGE` が `ANSI_932`、DWG の R2004 以前も同じ）の非 ASCII 文字も読み書きします。R2007 の DWG は今の実装と同じく読み取りのみで、変更は両方とも断ります。
- 要素は、モデル空間の LINE・CIRCLE・ARC・LWPOLYLINE（DWG の 2D の POLYLINE で折れ線になるものを含みます）・TEXT・INSERT です。DXF では複数の ENTITIES セクションがある図面も扱います。INSERT は、続く ATTRIB と SEQEND を付けて、1 つの要素として持ちます。要素になる条件と ID（`space/0/h2D9` など）は、今の実装と同じにしています。
- ブロックの定義は、開くときに 1 回読みます。名前・基点・中身の図形と、属性の定義（ATTDEF）を持ちます。
- 変更は、要素を動かす・除く・属性を変える・足すの 4 種類です。今の実装の `apply` の `transform`・`remove`・`restyle`・`add` に当たります。属性を変える変更は、画層・色・線種・線種の尺度・線の太さを変えます。足す変更は、線・円・円弧・折れ線・文字と、記号（ブロックの挿入。ATTDEF の既定値から ATTRIB と SEQEND を付けるものと、格子に並べるものを含みます）を、モデル空間に足します。
- 1 回の変更は、種類の違う変更をいくつでも並べられて、すべて受け付けるか、すべて受け付けないかのどちらかになります。
- ほかの操作は、取り消し・やり直し・全体の保存・範囲で選ぶことです。加えて、64 要素の塊ごとに汚れた印を持つ表示のバッファーと WebGPU での実測（`live gpu`）、動かす場所（同一プロセス・別プロセス IPC・単一スレッド wasm・共有メモリ並列 wasm）の測定（`live place`）を持ちます。
- 開くときは、ファイルやレコード列を区間に分けて、複数のスレッドで読みます。

扱わないものは、次のとおりです。

- 寸法・ハッチング・MTEXT・点など、ほかの種類の図形と、ペーパー空間の図形。ペーパー空間にある 6 種類の図形は、数だけを数えます。
- 要素を置き換える変更（`replace`）と、画層・線種・文字スタイル・寸法スタイルなどの表の変更。
- 変更の入力で属性（ATTRIB）の値を個別に指定して記号を足す変更。
- バイナリ DXF と、R14 以前の DWG。バイナリ DXF は、開くときに断ります。4 GiB 以上のファイルも、位置を 32 bit で持つので断ります。
- 予算・中断・変更ごとの診断・文書のハッシュ・文書が古くなっていないかの確かめ・JSON のメッセージ（要素と表のハッシュ、および開いたときの診断は、検査のときに保持状態から組み立てて今の実装と照合します）。
- ハンドルのない図形を指す変更。図形は持ちますが、ID がないので指せません。
- 後ろに足す保存、変更の記録をファイルに足すこと、版。

当初の試作（コミット `dd186812` 時点）では、表のレコード 1 つで決まらない画層・線種の名前、レコードの並びだけで決まらない ATTRIB と SEQEND の付き方、ATTDEF を持つ記号の追加、Shift_JIS の非 ASCII 文字、複数の ENTITIES セクションの 5 つを範囲の外（`Outside`）として断っていました。コミット `72407064` でこれらをすべて差分で書き戻せるようにしたため、今は範囲の外として断る変更はありません（[書き戻しに要るもの](#書き戻しに要るもの)）。

## 持ち方

- DXF では、元のファイルのバイト列を 16 KiB のページごとに LZ4 で圧縮して持ち続けます（`zumen-live` の `SourceBytes`）。レコード（グループ・コード 0 のタグから、次の 0 の前まで）の先頭の位置を覚え、要るページだけを展開して読みます。
- DWG では、全オブジェクトの `AcadDb`（`Vec<Object>`）は常駐させず、`DwgFile`（オブジェクト位置表と、R2000 ではファイルのバイト列、R2004 以降では展開済みの `AcDb:AcDbObjects` セクション）と、表・クラス・ヘッダー・モデル空間の所有者鎖だけを軽く索引化した `DwgSingle`（`crates/zumen-acad/src/dwg/single.rs`）を持ち続けます。変えたレコードの新しいビット列と、足したレコード・除いたレコードの集合だけを差分で持ちます。
- 要素は、列ごとの配列で持ちます。行（ハンドル・レコードの番号・種類・画層・色）と、種類ごとの形の表、頂点・文字・記号の属性の置き場に分けます。伸びる列・表示のバッファー・空間の索引は、固定長のページに分けた配列（`zumen-live` の `Paged`）で持ち、開いた直後に足しても既存の要素を写し直しません。行の番号は、32 bit の整数です。
- 除いた要素の行は、場所を残して、生きていない印を付けます。足した要素の行は、終わりに足します。行の番号とレコードの番号は、変更で変わりません。
- INSERT の行は、定義の番号・置く点・尺度・回転・格子と、付いた属性の範囲を持ちます。ATTRIB と SEQEND の付く先は、開くときに今の実装と同じ規則（所有者と、レコードの並び）で決め、並びがそろわない図面で足す・除く変更をしたときは影響する範囲だけを決め直します。
- DXF では、変えたレコードと足したレコードだけをタグの列として別に持ち、変えていないレコードは保存のときに元のバイト列を展開して写します。DWG では、変えたレコード（モデル空間の `BLOCK_RECORD` の図形リストやヘッダーを含みます）と足したレコードのビット列だけを `DwgSingle` で符号化し、R2000 は元のファイルのバイト列へ部分書き換えし、R2004〜R2018 は未変更レコードのビット列をそのまま流用してコンテナーを作り直します。
- 表示のバッファー、要素を囲む箱、ハンドルから行を引く表、範囲の索引を持ち続け、変更のたびに、変えた行の分だけを直します。表示のバッファーは、線分・円弧・文字・記号の挿入を、要素ごとの値のまま詰めて並べたもので、列ごとに 64 要素（`zumen-live` の `DIRTY_BLOCK`・`DirtyColumn`）の塊単位で変更フラグのビット集合を持ちます。GPU や別プロセス・wasm へ渡すときは、汚れた 64 要素ブロックの区間だけを転送します。除いた行は、表示のバッファーの場所を残して持ち主を外し、箱を空にして、索引から外します。範囲の索引は、段ごとにセルの大きさが 2 倍になる格子（`zumen-live` の `SpatialGrid`）です。
- INSERT の表示は、定義の番号と置き方（置く点・尺度・回転・格子）を持つ 1 つの挿入と、表示する属性の文字です。定義の中身は、開くときに 1 回だけ、別の表示のバッファーにします。定義の中身を挿入ごとに置くことは、描く側の仕事として、この試作では行いません。INSERT の箱は、置く点・属性を置く点と、定義の中身の箱を格子の四隅に写したものを囲みます。
- 開くときに 1 回読んで、持ち続けるものがあります。画層・線種・文字スタイル・寸法スタイル・ブロックの定義の表（`zumen-acad` の `SingleCatalog` と共有し、図形が指すだけの画層・線種の現れた順も持ちます）、ほかのオブジェクトからの参照の逆引き、ハンドルの最大、ヘッダーの変数（`$HANDSEED`・`$EXTMIN`・`$EXTMAX`）、版（`$ACADVER`）、文字コード、モデル空間の持ち主、ENTITIES セクションの終わりの位置です。
- 変更は、文書を変える前にすべて決めてから当てます。当てた操作（タグの置き換え・追加・削除と、行を足す・除くこと）を記録し、取り消しは、記録にある前の値を戻します。逆の変換は当てません。
- ハンドルは値で引く配列（飛び飛びのときは、ハンドルの順に並べた列の二分探索）で引きます。

## 今の実装と共有する規則

要素になる条件、変更の後のレコードの値、タグやビット列の差し替え方、除く要素への参照の外し方と所有する拡張ディクショナリの削除（#881）は、DXF（コミット `ba16aeec`・`72407064`）と DWG の両方で `crates/zumen-acad` の共通関数にまとめ、今の実装と試作の両方から呼ぶ形にしました。ページ配列・元のバイト列のページ圧縮・空間索引・64 要素ブロックの変更フラグは `crates/zumen-live` に切り出しています。変換の計算は `zumen-drawing` の `transform` をそのまま呼びます。今の実装の列は、特に書かない限り `crates/zumen-acad/src/` からの位置です。

## 流し方

リポジトリのルートで流します。図面は、[bench/editor](../editor/README.md) の `prepare.mjs` が作る `target/bench-editor/dxf-*.dxf`・`dwg-*.dwg` と、公開サンプルを使います。受け取った図面は使いません。

```bash
cargo build --release --locked --manifest-path bench/live/Cargo.toml --target-dir target
```

- `compare` は、文書エンジンと今の実装に同じ変更を流して比べます（[照らし方](#照らし方)）。違いがなければ 0、あれば 1、引数や入力を読めなければ 2 で終わります。`--steps` は変更の数、`--seed` は乱数の種（指定しなければ 1）、`--threads` は開くときのスレッドの数（指定しなければ論理 CPU の数）です。`--hashes` を付けると、今の実装の要素のハッシュを変更のたびに取り直して、変更が指していない要素のハッシュが変わっていないかを見ます。`--show` を付けると、違いの前後のバイト列を出します。図面の中身が出るので、公開できる入力だけで使います。
- `measure` は、文書エンジンの時間を測ります。`--current` を付けると、今の実装の同じ操作も、同じプロセスで測ります。`--runs` は、開くこと・保存・今の実装の操作を繰り返す回数（指定しなければ 7 回）です。範囲で選ぶ小さい範囲は、bench/editor の図面では決まった範囲を使い、ほかの図面では `--region` で渡すか、要素の 1 つの周りを選びます。
- `gpu` は、開発用ポート（24100〜24199）で一時的なローカルサーバーを立て、ヘッドレスの Edge または Chrome の WebGPU で初回転送・視点移動描画・変更時の 64 要素ブロック差分転送と描画・全体再転送の比較を測ります。
- `place` は、同一プロセス（`open_path` と `fs::read + open_slice`）、別プロセス（`live worker` との標準入出力パイプ）、単一スレッドの wasm Worker（`postMessage`）、共有メモリの並列 wasm Worker（`SharedArrayBuffer` ＋ `atomics`）の 4 構成で、開く時間と各操作の往復時間を測ります。
- `grow` は DXF のモデル空間の要素をずらしながら写して増やし、`grid` は DXF または DWG の土台に 5 種類の図形を格子状に足して指定件数の合成図面を作ります。
- `cases` は、書き方を変えた図形を足した DXF の入力を作ります（[書き方を変えた図面](#書き方を変えた図面)）。`--variant` は、図面の作りの変種です。
- `open` は、開いたまま `--hold` のミリ秒だけ待ちます。プロセスのメモリを、外から測るために使います。`--current` を付けると、今の実装で開いて `scene` を 1 回作ってから待ちます。
- `--budget` は、今の実装の要求に付ける予算の JSON です。100 万要素の DWG で今の実装（`--current`）を測るときだけ上限を外す JSON を渡し、ほかは付けずに流しました。
- `grow` と `cases` が作るファイルは、測ることと照らすことのための入力です。写した図形の拡張ディクショナリやリアクターは元の図形と同じものを指し、`cases` はわざと読めない値も書くので、ほかのアプリケーションに渡す図面にはなりません。

## 照らし方

`compare` は、入力ごとに次を行います。

1. 両方で開き、今の実装の `entities` が返す要素の ID と、文書エンジンが持つ要素の ID を比べる。文書エンジンだけが持つ要素は、違いに数える。今の実装だけが持つ要素（この試作が扱わない種類と、ペーパー空間の要素）は、種類ごとの数を出す。
2. ファイルを 1・2・3・7・16 個の区間に分けて開いた結果が、ふつうに開いた結果と同じことを確かめる。
3. 種を決めた乱数で変更を作り、両方に 1 つずつ当てる。変更の作り方は、下に書く。
4. 1 つ当てるごとに、受け付けるかどうかが両方で同じことと、文書エンジンが保存したバイト列が、今の実装が書き戻したバイト列と同じことを確かめる。足す変更では、今の実装が返した新しい要素の ID と、文書エンジンが振ったハンドルが同じことも確かめる。
5. 受け付けた変更ごとに、取り消して保存したバイト列が変更の前と同じことと、やり直して保存したバイト列が変更の後と同じことを確かめる。
6. 決まった間隔（変更の数の 16 分の 1 ごと）で、文書エンジンが持つ列・表示のバッファー・箱が、保存したバイト列から開き直したものと同じこと、範囲で選ぶ結果が総当たりや開き直した文書と同じこと、さらに保存・開き直しをせずに保持状態から組み立てた要素の ID・種類・画層・ハッシュ・箱、表示のバッファーの値、画層・線種の表、範囲で選ぶ結果、開いたときの診断が、今の実装（`Today`）の出力と直接一致することを確かめる。表示のバッファーは、生きている行の値を比べ、あわせて、並びまで同じかどうかを数える。
7. 最後に、すべて取り消したバイト列が始まりと同じことと、変えたレコードと除いた行が残っていないこと、すべてやり直したバイト列が今と同じことを確かめる。

文書エンジンだけが受け付けた変更と、文書エンジンだけが断った変更は、違いです（コミット `dd186812` 時点では試作の範囲の外の 5 分類を別に数えていましたが、コミット `72407064` ですべて差分で扱うようにしたため、今は範囲の外として断る変更はありません）。

変更の数は、指定しなければ、要素の数から 80〜4,000 回の間で決めます。変更は、次の割合で作ります。

| 変更 | 割合 | 1 回に指す数 | 混ぜるもの |
| --- | ---: | --- | --- |
| 動かす | 52% | 1 件が 78%、2〜8 件が 15%、9〜100 件が 7% | ない ID、同じ要素を 2 度。変換は、平行移動・回転・拡大と縮小・鏡映・相似・縦横で違う拡大・せん断・恒等・逆のない変換 |
| 足す | 16% | 1 件が 78%、2〜6 件が 22% | 表にない名前、綴りの違う名前、ない定義、受け付けない値（半径が 0 以下の円、頂点が 1 つの折れ線など） |
| 属性を変える | 14% | 1 件が 75%、2〜8 件が 25% | ない ID、同じ要素を 2 度、表にない名前 |
| 除く | 12% | 1 件が 72%、2〜5 件が 23%、6 件以上が 5% | ない ID、同じ要素を 2 度 |
| 種類を混ぜる | 6% | 2〜6 個の変更 | すでに指した要素を、別の種類の変更でもう 1 度指す |

指せる要素がなくなれば、足す変更だけを作ります。ASCII でない文字を足す変更は、終わりの 5% の回だけで作ります。

今の実装と比べているのは、要素の ID の集まりと、受け付けるかどうかと、保存したバイト列と、足した要素の ID に加えて、保存・開き直しをせずに保持している要素の ID・種類・画層・`v2:...` のハッシュ・囲む箱、表示のバッファーの値（今の実装の形との照合）、画層・線種の表（ID・名前・ハッシュ）、範囲で選ぶ結果、開いたときの診断です（コミット `72407064` で追加。下の `dd186812` 時点の表は追加前の記録です）。

### 書き方を変えた図面

合成の図面は `apply` の `add` が書いた図形で、公開サンプルは 6 種類の要素が少ないので、書き方の幅が足りません。`cases` は、土台の図面の ENTITIES セクションの終わりに、6 種類の図形を、乱数で書き方を変えながら足します。変えるのは、次のものです。

- 実数の書式（小数の桁、指数、前後の空白、正の符号、先頭の 0 を省いた小数、小数点のない値、`-0.0`）、整数の桁寄せ、ハンドルの大文字と小文字。
- 座標の大きさ（0、負の値、桁の多い値、とても大きい値と小さい値）。
- 省けるタグの有無と値（持ち主・サブクラスマーカー・線種・色・RGB の色・透明度・線の太さ・線種の尺度・表示しない印・厚さ・押し出しの向き・Z の値）。
- CIRCLE と ARC の、0 と負の半径、0〜360 度の外の角。
- LWPOLYLINE の、0 個と 1 個の頂点、頂点の数と合わない 90、閉じる印と線種の生成、一定の幅、頂点ごとの幅、膨らみ、頂点の ID、高さ。
- TEXT の、高さ（0 と負の値を含む）、回転、幅の係数（0 と負の値を含む）、傾き、文字スタイル、反転、位置合わせと第 2 の点、`%%d` などの書き方を含む中身。
- INSERT の、定義の名前（下に書く定義と、ない定義）、尺度（0 と負の値を含む）、回転、列と行の数（0 と負の値を含む）と間隔、属性が続く印（続かないのに書くもの、0 を書くものを含む）、続く ATTRIB の数（0〜3 個）、SEQEND の有無。
- ATTRIB の、所有者の有無、画層、色、高さ、中身、回転、幅の係数、傾き、文字スタイル、反転、位置合わせと第 2 の点、タグ、表示しない印などのフラグ。
- XDATA（文字・制御・整数・実数・距離・倍率・点・変位・向きなど。Y と Z の値が続かない点を含む）。
- 読めない値（数でない文字、空の値、範囲を超える数など）と、ペーパー空間の印。

図形のほかに、次のものも足します。

- 表のレコード。画層は、大文字と小文字の違う 2 つの綴りを同じ名前で持つものを含みます。線種と文字スタイルも 1 つずつ足します。図形は、表にない画層も指します。
- ブロックの定義と BLOCK_RECORD。基点のある定義、属性の定義を持つ定義、空の定義、ほかの定義を中に置く定義、同じ名前の定義が 2 つあるもの、小文字の名前で BLOCK_RECORD のないものです。
- 足した図形を指すオブジェクト。DICTIONARY の項目、リアクターの組（`{ACAD_REACTORS`）の中の参照、組の外の所有者と参照です。図形の先頭にも、前の図形を指す組を書きます。除く変更で、参照の外し方を確かめるためです。

`--variant` で、図面の作りを変えます。

| 変種 | 図面の作り |
| --- | --- |
| `plain` | ATTRIB と SEQEND の付き方がそろった図面 |
| `loose` | 付き方のそろわない図面。所有者がほかを指す ATTRIB、印のない INSERT に続く ATTRIB、親のない ATTRIB と SEQEND を混ぜます |
| `no-seed` | `$HANDSEED` のない図面 |
| `low-seed` | `$HANDSEED` が、ハンドルの最大より小さい図面 |
| `two-sections` | ENTITIES セクションが 2 つある図面 |
| `no-tables` | TABLES セクションのない図面 |
| `empty` | ENTITIES セクションが空の図面。図形は足さず、定義と表のレコードだけを足します |

- `--hashes` は、公開サンプルと、書き方を変えた図面と、INSERT を増やした図面で付けました。変更が指していない要素のハッシュが変わったのは、延べ 457 件で、すべて `no-tables` の変種の 1 個です（[分かったこと](#分かったこと)）。保存したバイト列の違いではありません。

## 書き戻しに要るもの

[採らない条件](../../docs/live.md#進め方)は、書き戻しに図面の全体の解釈が要ることです。変更の種類ごとに、そのレコードのタグのほかに何を使ったかを書きます。

| 変更 | そのレコードのタグのほかに使ったもの |
| --- | --- |
| 動かす | INSERT では、付いた ATTRIB のレコード。文字コード。図面の範囲（`$EXTMIN`・`$EXTMAX`） |
| 属性を変える | 画層と線種の名前の表。版（RGB の色と線の太さを書けるか） |
| 除く | ほかのオブジェクトからの参照の逆引き。ハンドルの最大。ATTRIB と SEQEND の付き方がそろっていること |
| 足す | 次のハンドル（ハンドルの最大と `$HANDSEED`）。画層・線種・文字スタイルの名前の表。ブロックの定義。ENTITIES セクションの終わりの位置。モデル空間の持ち主。版と文字コード。図面の範囲 |

- この範囲では、どの変更も、図面の全体を解釈し直さずに書き戻せました。使ったものは、開くときに 1 回読んで、変更のたびに、変えた分だけを直します。
- 動かす変更と属性を変える変更は、そのレコード（INSERT では、付いた ATTRIB も）のタグを直すだけです。ほかのレコードは変えません。
- 除く変更は、除く要素を指すオブジェクトから、参照を外します。今の実装は、除く要素ごとに、すべてのオブジェクトのタグを見て外します。この試作は、開くときに逆引き（指されるハンドルと、指しているレコードの組）を 1 回作り、指しているレコードだけを直します。外すのは、今の実装と同じく、102 の組の中のハンドルと、DICTIONARY の項目です。組の外の所有者や参照は、残します。除いた要素が所有する拡張ディクショナリのオブジェクトは、今の実装（#881）と同じく一緒に除きます（コミット `ba16aeec` で反映）。
- 足す変更は、ほかのオブジェクトを指す参照を、組の中に書きません。所有者（モデル空間）は組の外です。逆引きは、開くときに作ったものを、変更で直さずに使い続けられました。
- 足す要素のハンドルは、ハンドルの最大の次と `$HANDSEED` の大きいほうから、足す順に振ります。ハンドルの最大は、開くときに 1 回数え、足す・除く変更で直します。最大のハンドルを持つ行を除いたときは、次に大きいハンドルを、ハンドルから行を引く表を下へたどって探します。
- 属性の続く INSERT を除く変更は、今の実装も受け付けないので、付いた ATTRIB と SEQEND を除く規則は要りませんでした。

当初に範囲の外としていた 5 つの分類も、コミット `72407064` で図面の全体を作り直さずに差分で書き戻せました。

- 付き方: 並びだけで決まらない図面で足す・除く変更をしたときは、ATTRIB と SEQEND の付く先が変わりうる前後の範囲だけを決め直します。
- 名前: 表のレコード 1 つで決まらない画層・線種の名前（表にない名前、重複、大文字と小文字の違い）も、開くときに作った表と図形が指す名前の記録を使って、今の実装と同じ綴りに決めます。
- 定義: ATTDEF を持つ定義の記号を足すときは、保持している ATTDEF から既定の ATTRIB と SEQEND を組んで足します。同じ名前の定義が複数ある図面でも、今の実装と同じ選び方を共有します。
- 文字コード: Shift_JIS（`ANSI_932`）の変換を `zumen-acad` と共有し、非 ASCII 文字を含む図形と属性も差分で読み書きします。
- セクション: ENTITIES セクションが複数ある図面でも、今の実装が足すセクションの終わりの位置を持って同じ場所に書きます。
- DWG でも同じ方針が成り立ちました。全オブジェクトの `AcadDb` を常駐させず、開くときに表・クラス・ヘッダー・モデル空間の `BLOCK_RECORD` の所有者鎖だけを `DwgSingle` に索引化しておけば、変更時は対象レコード（足す・除く変更ではモデル空間の `BLOCK_RECORD` のハンドルリストとヘッダーの `HANDSEED` も）のビット列だけを符号化し直せば足りました。保存時は、R2000 ではオブジェクト位置表と変更分だけを元のバイト列へ部分書き換えし、R2004〜R2018 では未変更レコードのビット列をそのまま流用してコンテナーを作り直します。

## 決まった判断

2026-11-15 に、利用者の判断で次が決まりました。

- 文書エンジンを採用して本実装に進むこと。
- 形式に依らない基盤を `crates/zumen-live` に置き、形式別の差分読み書きは各 L1 crate 側に置くこと。
- 差分で更新する表示のバッファーは、開き直した直後とのスロット順のバイト列一致は求めず、描く結果（要素の値と描画順）が一致すること、かつ同じ入力・操作列なら環境間で同じになることを契約とすること（従来の `scene` のバイナリと `render` の画像は従来どおりバイト列一致）。
- 全体を書く保存は今の実装とのバイト列一致を必須としたうえで、後ろに足す保存を設ける場合は、全体を書く保存とバイト列が違ってよく、読み直した図面モデル・ID・ハッシュ・診断が一致すること（かつ同じ入力・操作列なら環境間で同じバイト列になること）を契約とすること。

## 分かったこと

- 取り消しは、タグやビット列と行の前の値を戻すので、DXF でも DWG でも、保存したバイト列が変更の前と同じになりました。足す・除く変更でも同じです。今の実装で逆の変換を当てて戻すときの、丸めの違い（[`apply` で直すときの性質](../../docs/editor.md#apply-で直すときの性質)）は起きません。
- 足す・除く変更のあとは、差分で直した表示のバッファーが、開き直して作ったものと、並びが変わります。除いた行は場所を残し、足した行は終わりに足すためです。開き直すと、除いた行の場所が詰まり、足した行はレコードの順に並びます。動かす変更と属性を変える変更だけなら、並びまで同じです。
- 今の実装の要素のハッシュは、そのレコードの外に依ることがあります。今の実装は、画層の ID を、表のレコードの順と、表にない画層が図形に現れた順で振り、要素のハッシュに画層の ID を入れます（`crates/zumen-acad/src/drawing/style.rs` と `crates/zumen-drawing/src/hash.rs`）。TABLES セクションのない図面で、ある画層を最初に指す図形を除くと、後ろの画層の ID がずれて、指していない要素のハッシュが変わります。直接照合（`src/inspect.rs`）では、生きている画層・線種の ID を今の実装と同じ順で振り直して一致を確かめました。文書エンジンが常駐で要素のハッシュを差分で保つなら、こうした、そのレコードの外に依る値をどう扱うかを決める必要があります。
- 今の実装の除く変更は、除く要素ごとに、すべてのオブジェクトを見ます。逆引きや所有者数とモデル空間のハンドル鎖を持ち続ければ、指しているレコードだけで済みました。
- `$HANDSEED` のない図面では、ハンドルの最大の次から振るので、最大のハンドルを持つ要素を除いたあとに足すと、除いた要素と同じハンドルになります。今の実装も同じです。取り消しの記録には、同じハンドルの、除いた行と足した行が並びます。ハンドルから行を引く表は、生きている行だけを引きます。
- 最大のハンドルを持つ行を除くと、次に大きいハンドルを探し直します。ハンドルから行を引く表を、大きいほうから下へたどるので、除いた行のハンドルが下へ続いていると、その数だけ進みます。表を配列で持つ図面では、行のないハンドルも通ります。下の 124〜1,999 件を除いたあとで測ると、0.7〜6.0 マイクロ秒でした。取り消しは、控えた値を戻すので、探しません。
- 今の実装は、変更のたびに `$HANDSEED` と図面の範囲を確かめて直します。文書エンジンでは、ヘッダーの変数を開くときに 1 回読み、変更で値が変わるときだけ、ヘッダーのレコードを直します。
- 分けて読んだ結果を入力の順に集めれば、開いた結果は、区間の数にもスレッドの数にも依りませんでした。
- 今の実装と同じバイト列を書くには、DXF では数の書式やタグの順、DWG ではビット列の符号化順やハンドル鎖まで同じにする必要がありました。DXF（`drawing/single.rs`）と DWG（`dwg/single.rs`）の両方で 1 オブジェクトごとの読み書き規則を `crates/zumen-acad` の共通関数に切り出し、今の実装と試作の両方から呼ぶ形にできたので、規則を 2 か所に写して持つ必要はなくなりました。
- 変えたレコードと足したレコードを別に持ち、除いた行も場所を残すので、変更の多い文書では、メモリが増えます。測った場合では、変えたレコードと取り消しの記録が、DXF で 10〜38 MiB、DWG で 32〜61 MiB でした（[測った値](#測った値)）。
- 開いた直後に足す最初の 1 回が図面の大きさに比例していた問題（100 万要素で 19.6 ms）は、伸びる配列を固定長のページに分けることで解消しました（100 万要素で中央値 63〜74 マイクロ秒）。
- 元のファイルのバイト列をそのまま持つと、INSERT が 100 万要素ある DXF では元のファイルだけで 468 MiB になりましたが、16 KiB のページごとに LZ4 で圧縮して持ち、行と表示のバッファーを詰めることで、プロセスのワーキングセットを 483 MiB、開く時間を 795 ms に抑えられました。DWG でも `AcadDb` を常駐させないことで、100 万要素のワーキングセットが 339〜351 MiB（今の実装のピークは 1,173〜1,192 MiB）に収まりました。
- 表示のバッファーを 64 要素の塊ごとの汚れた印で管理すると、100 万要素（GPU バッファー 48.8〜99.2 MiB）でも 1 件移動の GPU 転送は 2,048〜2,304 B（1 回）で済み、WebGPU でのレンダーパス実行は 0.77〜2.19 ms、描画完了待ちを含めて 2.8〜3.4 ms でした。
- 動かす場所では、同一プロセスで `open_path` と `fs::read + open_slice` の差が小さく、`unsafe` を伴うメモリマップは不要でした。別プロセスのパイプ IPC でも 64 要素ブロックの差分転送なら 1 件移動の往復は中央値 48〜62 マイクロ秒（99% 118〜143 マイクロ秒）で、wasm Worker（単一スレッド・共有メモリ）でも中央値 99〜128 マイクロ秒でした。ただし共有メモリ並列 wasm で DWG を 12 スレッドで開くときは、レコードごとの一時確保が標準アロケーター（`dlmalloc`）の大域ロックで競合して遅くなるため、DXF のようにスレッドごとの作業領域を使い回す設計が要ります。

## 確かめていないこと

- コアの lint（添字・`unwrap`・`panic` などを禁じる）には、`bench/live` 側はまだ合わせていません（切り出した `crates/zumen-live` と共有した `crates/zumen-acad` 側はコアの lint を通しています）。`bench/live` 全体として入力でパニックしないことは、まだ確かめていません（fuzz を流していません）。
- 公開サンプルにある 6 種類の要素は少なく、ほかのアプリケーションが書いた図面での幅は狭いままです。
- 寸法・ハッチング・実際の文字の字形を入れた表示のバッファーと GPU 描画（この試作の WebGPU 測定では、INSERT は定義の線分展開で描き、文字は外接枠の線分で描きました）。
- 要素を置き換える変更（`replace`）、表の変更、変更の入力で属性値を指定して記号を足す変更、残りの図形の種類、ペーパー空間の要素、DWG の後ろに足す保存。
- 変更ごとの診断・予算・中断を入れたときの時間と、共有メモリ wasm で DWG の作業領域を使い回したときの並列オープン時間。
- 測ったときに、同じ端末でほかの仕事が動いていなかったことは、確かめていません。マイクロ秒の値は、端末の様子で変わります。
