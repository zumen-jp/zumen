# 文書エンジンの試作

[文書エンジン](../../docs/live.md)を、DXF で縦に 1 本通した試作です。図面を開いたままメモリに置き、要素を動かす変更・取り消し・やり直し・全体の保存・範囲で選ぶことを、変えた要素の分だけの手間で行います。今の実装（要求のたびに図面の全体を作り直す、今のコアの動かし方）に同じ変更を 1 つずつ当てて、保存したバイト列を比べ、同じ操作の時間とメモリを測ります。作業は [#878](https://github.com/zumen-jp/zumen/issues/878) で追います。

コアのワークスペースには入れていません。`crates/` と公開の API には、何も足していません。依存は、このリポジトリの `zumen`・`zumen-acad`・`zumen-drawing` と、`libm` です。`Cargo.lock` は、ワークスペースの `Cargo.lock` から同じバージョンを引き継いでいます。CI はこのフォルダーのコードを組み立てないので、下の結果は、書いた日付に手元で流したものです。

## 範囲

扱うものは、次のとおりです。

- 入力は ASCII の DXF です。行の終わりは、LF と CR LF のどちらも読みます。
- 要素は、ENTITIES セクションの、モデル空間の LINE・CIRCLE・ARC・LWPOLYLINE・TEXT です。要素になる条件と ID（`space/0/h2D9` など）は、今の実装と同じにしています。
- 操作は、要素を動かす変更（`apply` の `transform` に当たります）・取り消し・やり直し・全体の保存・範囲で選ぶことです。1 回の変更は 1 件から何件でも指せて、すべて受け付けるか、すべて受け付けないかのどちらかになります。
- 開くときは、ファイルを区間に分けて、複数のスレッドで読みます。

扱わないものは、次のとおりです。

- ブロック参照（INSERT）・寸法・ハッチング・MTEXT・点など、ほかの種類の図形と、ペーパー空間の図形。ペーパー空間にある 5 種類の図形は、数だけを数えます。
- 要素を足す・除く・属性を変える変更（`add`・`remove`・`restyle`）。
- DWG と、バイナリ DXF。バイナリ DXF は、開くときに断ります。4 GiB 以上のファイルも、位置を 32 bit で持つので断ります。
- 診断・予算・中断・要素と文書のハッシュ・文書が古くなっていないかの確かめ・JSON のメッセージ。
- Shift_JIS（`$DWGCODEPAGE` が `ANSI_932`）の図面にある、ASCII でない文字を持つ図形。数だけを数えます。
- ハンドルのない図形を指す変更。図形は持ちますが、ID がないので指せません。
- `$HANDSEED` が、いちばん大きいハンドルより大きくない文書の変更。今の実装は変更のたびに `$HANDSEED` を直しますが、この試作は直さず、その文書の変更を受け付けません。
- 後ろに足す保存、変更の記録をファイルに足すこと、版。
- wasm での組み立てと測定。

## 持ち方

- 元のファイルのバイト列を、そのまま持ち続けます。レコード（グループ・コード 0 のタグから、次の 0 の前まで）の先頭の位置を覚えます。
- 要素は、列ごとの配列で持ちます。行（ハンドル・レコードの番号・種類・画層・色）と、種類ごとの形の表、頂点と文字の置き場に分けます。行の番号は、32 bit の整数です。
- 変えたレコードだけを、タグの列として別に持ちます。変えていないレコードは、保存のときに元のバイト列を写します。
- 表示のバッファー、要素を囲む箱、ハンドルから行を引く表、範囲の索引を持ち続け、変更のたびに、変えた行の分だけを直します。表示のバッファーは、線分・円弧・文字を、要素ごとの値のまま並べたものです。範囲の索引は、段ごとにセルの大きさが 2 倍になる格子です。
- 変更は、文書を変える前にすべて決めてから当てます。当てたタグの操作（置き換え・追加・削除）を記録し、取り消しは、記録にある前の値を戻します。逆の変換は当てません。
- ハッシュの表は使いません。画層の名前は順序のある表、ハンドルは値で引く配列（飛び飛びのときは、ハンドルの順に並べた列の二分探索）で引きます。

## 今の実装と同じにした規則

要素になる条件、動かした後の値、タグの差し替え方は、今の実装のコードと同じ規則を、この試作の中に書いています。変換の計算は `zumen-drawing` の `transform`、値の型は `zumen-acad` の型を、そのまま呼びます。今の実装の列は、`crates/zumen-acad/src/` からの位置です。

| 試作 | 今の実装 | 規則 |
| --- | --- | --- |
| `src/scan.rs`・`src/value.rs` | `dxf.rs`・`dxf/objects.rs` | 行とタグの切り方、値の型と書式 |
| `src/lift.rs` | `drawing.rs`・`drawing/geometry.rs`・`drawing/style.rs` | 図形が要素になる条件と、形の読み方 |
| `src/edit.rs` | `drawing/apply/replace.rs`・`drawing/apply/transform.rs`・`dxf/write_back.rs` | 動かした後のレコードの値、タグの差し替え方、図面の範囲（`$EXTMIN`・`$EXTMAX`）の広げ方 |
| `src/save.rs` | `dxf.rs` | 書き出し |

規則が 2 か所にあるので、今の実装の規則を変えると、この試作は合わなくなります。そのときは `compare` が違いを出します。

## 流し方

リポジトリのルートで流します。図面は、[bench/editor](../editor/README.md) の `prepare.mjs` が作る `target/bench-editor/dxf-*.dxf` と、公開サンプルを使います。受け取った図面は使いません。

```bash
cargo build --release --locked --manifest-path bench/live/Cargo.toml --target-dir target
mkdir -p target/bench-live
target/release/live compare target/bench-editor/dxf-1k.dxf samples/dxf/text_alignments.dxf
target/release/live measure target/bench-editor/dxf-100k.dxf --current
target/release/live grow target/bench-editor/dxf-100k.dxf target/bench-live/dxf-1m.dxf 10
target/release/live cases samples/dxf/text_alignments.dxf target/bench-live/cases.dxf 400 --seed 1
target/release/live open target/bench-live/dxf-1m.dxf --hold 3000
```

- `compare` は、文書エンジンと今の実装に同じ変更を流して比べます（[照らし方](#照らし方)）。違いがなければ 0、あれば 1、引数や入力を読めなければ 2 で終わります。`--steps` は変更の数、`--seed` は乱数の種（指定しなければ 1）、`--threads` は開くときのスレッドの数（指定しなければ論理 CPU の数）です。`--show` を付けると、違いの前後のバイト列を出します。図面の中身が出るので、公開できる入力だけで使います。
- `measure` は、文書エンジンの時間を測ります。`--current` を付けると、今の実装の同じ操作も、同じプロセスで測ります。`--runs` は、開くこと・保存・今の実装の操作を繰り返す回数（指定しなければ 7 回）です。範囲で選ぶ小さい範囲は、bench/editor の図面では決まった範囲を使い、ほかの図面では `--region` で渡します。
- `grow` は、モデル空間の要素を、ずらしながら写して増やします。上の例は、10 万要素の図面を 10 枚並べて、100 万要素にします。
- `cases` は、書き方を変えた図形を足した入力を作ります（[書き方を変えた図面](#書き方を変えた図面)）。
- `open` は、開いたまま `--hold` のミリ秒だけ待ちます。プロセスのメモリを、外から測るために使います。`--current` を付けると、今の実装で開いて `scene` を 1 回作ってから待ちます。
- `--budget` は、今の実装の要求に付ける予算の JSON です。下の結果は、付けずに流しました。
- `grow` と `cases` が作るファイルは、測ることと照らすことのための入力です。写した図形の拡張ディクショナリやリアクターは元の図形と同じものを指し、`cases` はわざと読めない値も書くので、ほかのアプリケーションに渡す図面にはなりません。

## 照らし方

`compare` は、入力ごとに次を行います。

1. 両方で開き、今の実装の `entities` が返す要素の ID と、文書エンジンが持つ要素の ID を比べる。文書エンジンだけが持つ要素は、違いに数える。今の実装だけが持つ要素（この試作が扱わない種類と、ペーパー空間の要素）は、種類ごとの数を出す。
2. ファイルを 1・2・3・7・16 個の区間に分けて開いた結果が、ふつうに開いた結果と同じことを確かめる。
3. 種を決めた乱数で変更を作り、両方に 1 つずつ当てる。変換は、平行移動・回転・拡大と縮小・鏡映・相似・縦横で違う拡大・せん断・恒等・逆のない変換から選び、1 回に 1〜100 件を動かす。ない ID を指す変更と、同じ要素を 2 度指す変更も混ぜる。
4. 1 つ当てるごとに、受け付けるかどうかが両方で同じことと、文書エンジンが保存したバイト列が、今の実装が書き戻したバイト列と同じことを確かめる。
5. 受け付けた変更ごとに、取り消して保存したバイト列が変更の前と同じことと、やり直して保存したバイト列が変更の後と同じことを確かめる。
6. 決まった間隔で、文書エンジンが持つ列・表示のバッファー・箱が、保存したバイト列から開き直したものと同じことと、範囲で選ぶ結果が総当たりと同じことを確かめる。最後に、すべて取り消したバイト列が始まりと同じことと、すべてやり直したバイト列が今と同じことを確かめる。

変更の数は、指定しなければ、要素の数から 80〜4,000 回の間で決めます。

今の実装と比べているのは、要素の ID の集まりと、受け付けるかどうかと、保存したバイト列です。バイト列が同じなので、読み直した図面モデル・ID・ハッシュ・診断も同じになります。文書エンジンが中に持つ形・表示のバッファー・範囲で選ぶ結果は、文書エンジンどうし（開き直したものや総当たり）で比べていて、今の実装のシーンや `entities` の結果とは照らしていません。

### 書き方を変えた図面

合成の図面は `apply` の `add` が書いた図形で、公開サンプルは 5 種類の要素が少ないので、書き方の幅が足りません。`cases` は、土台の図面の ENTITIES セクションの終わりに、5 種類の図形を、乱数で書き方を変えながら足します。変えるのは、次のものです。

- 実数の書式（小数の桁、指数、前後の空白、正の符号、先頭の 0 を省いた小数、小数点のない値、`-0.0`）、整数の桁寄せ、ハンドルの大文字と小文字。
- 座標の大きさ（0、負の値、桁の多い値、とても大きい値と小さい値）。
- 省けるタグの有無と値（持ち主・サブクラスマーカー・線種・色・RGB の色・透明度・線の太さ・線種の尺度・表示しない印・厚さ・押し出しの向き・Z の値）。
- CIRCLE と ARC の、0 と負の半径、0〜360 度の外の角。
- LWPOLYLINE の、0 個と 1 個の頂点、頂点の数と合わない 90、閉じる印と線種の生成、一定の幅、頂点ごとの幅、膨らみ、頂点の ID、高さ。
- TEXT の、高さ（0 と負の値を含む）、回転、幅の係数（0 と負の値を含む）、傾き、文字スタイル、反転、位置合わせと第 2 の点、`%%d` などの書き方を含む中身。
- XDATA（文字・制御・整数・実数・距離・倍率・点・変位・向きなど。Y と Z の値が続かない点を含む）。
- 読めない値（数でない文字、空の値、範囲を超える数など）と、ペーパー空間の印。

## 照らした結果

2026-11-13 に、コミット `d3e26650` にこの試作を足したものを、ネイティブのリリースのビルドで流しました。Windows 11・AMD Ryzen 5 3600XT（12 論理 CPU）です。main をコミット `f3aaaa51` まで取り込んだあとに、同じ入力と同じ種で流し直して、下の表と同じ数になりました。

| 入力 | ファイル | 流した回数 | 変更 | 両方が受け付けてバイト列が同じ | 両方が受け付けない | 違い |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 合成の図面（1,002 要素。種 1〜3） | 1 | 3 | 11,976 | 10,049 | 1,927 | 0 |
| 合成の図面（10,002 要素。種 1・2） | 1 | 2 | 798 | 688 | 110 | 0 |
| 合成の図面（100,002 要素。種 1） | 1 | 1 | 80 | 67 | 13 | 0 |
| 合成の図面（1,000,020 要素。種 1） | 1 | 1 | 8 | 8 | 0 | 0 |
| 公開サンプル（5 種類の要素を持つ 6 個。種 1〜3） | 6 | 18 | 72,000 | 60,858 | 11,142 | 0 |
| 書き方を変えた図面 | 16 | 16 | 58,268 | 39,837 | 18,431 | 0 |
| 合わせて | 26 | 41 | 143,130 | 111,507 | 31,623 | 0 |

- 今の実装だけが受け付けた変更と、文書エンジンだけが受け付けた変更は、ありませんでした。
- 要素の多い図面ほど、今の実装の 1 回の変更に時間がかかるので、流した変更が少なくなっています。100 万要素の図面は、8 回だけです。
- 公開サンプル（`samples/` の ASCII の DXF 18 個）のうち、5 種類の要素を持つのは 6 個で、要素は合わせて 76 件（ARC 12・CIRCLE 35・LINE 10・LWPOLYLINE 3・TEXT 16）です。残りの 12 個は、比べる要素がありません。公開サンプルで確かめられる幅は狭いので、合成の図面と、書き方を変えた図面で補っています。
- 書き方を変えた図面は、公開サンプル 4 個と 1,002 要素の合成の図面を土台に、種を変えて 16 個作りました。足した図形は、土台ごとに 400〜1,500 個です。16 個のすべてで、今の実装がモデル空間に持つ 5 種類の要素と、文書エンジンが持つ要素が、同じ ID で一致しました。文書エンジンが要素にしない図形（押し出しの向きが既定でないもの、Z の値が 0 でないもの、半径が 0 以下のもの、読めない値を持つものなど）は、今の実装でも要素になりません。
- 両方が受け付けない変更は、ない ID、同じ要素を 2 度指すもの、相似でない変換で種類を保てないもの、逆のない変換と、今の実装が動かさない書き方の図形を指すものです。動かさない書き方には、頂点の ID が頂点の数とそろわない LWPOLYLINE、幅の係数が 0 以下の TEXT、Y の値が続かない XDATA の点などがあります。
- 文書エンジンの中の確かめは、取り消しとやり直しのバイト列が 111,507 回、開き直した文書との一致が 730 回、範囲で選ぶ結果が 17,520 回で、違いはありませんでした。表示のバッファーは、730 回のすべてで、開き直して作ったものと並びまで同じでした。
- 区間の数を変えて開いた結果は、すべての入力で同じでした。

## 測った値

照らした結果と同じ日付・端末で、コミット `d3e26650` にこの試作を足したものの値です。合成の図面は bench/editor の 1,002・10,002・100,002 要素の DXF で、100 万要素は `grow` で作りました。時間は中央値です。開くこと・保存・今の実装の操作は 7 回（100 万要素は 3 回）、変更は 2,000 回（100 件の変更は 200 回）測りました。

### 開く

単位はミリ秒です。

| 要素の数 | 1,002 | 10,002 | 100,002 | 1,000,020 |
| --- | ---: | ---: | ---: | ---: |
| ファイルの大きさ（MiB） | 0.3 | 1.6 | 14.7 | 148.7 |
| 文書エンジン: 表示のバッファーまで（1 スレッド） | 0.83 | 6.45 | 66.1 | 649 |
| 文書エンジン: 表示のバッファーまで（12 スレッド） | 0.88 | 3.32 | 23.2 | 203 |
| 文書エンジン: 範囲の索引まで（1 スレッド） | 0.88 | 6.96 | 71.3 | 709 |
| 文書エンジン: 範囲の索引まで（12 スレッド） | 0.94 | 3.82 | 28.7 | 256 |
| 今の実装: `open` と `scene` | 5.91 | 56.4 | 568 | 6,396 |

- 100 万要素を 12 スレッドで開く 203 ms の内訳は、読んで列にする 97 ms、区間をまとめる 47 ms、表示のバッファー 59 ms です。分けて流しているのは、読んで列にするところだけです。
- 文書エンジンの表示のバッファーと、今の実装のシーンは、同じものではありません。表示のバッファーは、線分・円弧・文字を要素ごとの値のまま並べたもので、曲線を折れ線にすること、字形、線種の破線、線の太さ、描く順を持ちません。今の実装は、診断・予算・ブロック・寸法なども扱います。この表の比は、採る条件の目安であり、同じ仕事どうしの比ではありません。

| 1 件を 90 度回す | 4.0 | 5.1 | 5.5 | 6.0 |
| 100 件を 1 回で動かす | 332 | 367 | 414 | 406 |

| 取り消す（100 件の変更） | 78 | 115 | 135 | 140 |
| やり直す（1 件の変更） | 0.8 | 1.3 | 1.6 | 1.5 |

- 1 件を動かす変更の 99% の値は 16〜33 マイクロ秒、2,000 回のうちの最大は 0.08〜2.07 ms でした。2.07 ms は、10,002 要素の図面で 1 回だけ出た値で、原因は調べていません。
- 変更の時間には、タグを直すこと、その行の列・表示のバッファー・箱・索引を直すこと、取り消しの記録を含みます。ハッシュ・診断・JSON の読み書きは含みません。
- 範囲で選ぶ時間は、当たる件数に比例します。返すのは行の番号です。縦横 1/10 の範囲と図面の全体は、変更のあとに測りました。動かした要素が外に出ているので、全体でも、当たる件数は要素の数より少なくなります。
- 変更のあと（6,200 回の変更で、のべ 26,000 要素）に、変えたレコードのタグと取り消しの記録が使うメモリは、8〜20 MiB でした。

| 取り消し（前のバイト列を開き直して `scene`） | 6.39 | 60.4 | 546 | 6,395 |

- [bench/editor で測った値](../../docs/live.md#測ったこと)と比べると、1,002 要素と 100,002 要素では 1 割以内で合い、10,002 要素では 1〜2 割大きい値でした。この試作は場合と要求を自分で作るので、測り方は bench/editor と同じではありません。
- 今の実装の `entities` は、種類・レイヤ・ハッシュ・形を JSON で返します。範囲に当たる要素の決め方も、文書エンジンの箱（文字は置く点だけ、円弧と膨らみのある辺は広め）と違い、当たる件数が 1 件ずれることがあります。

### メモリ

プロセスのワーキングセットを、外から約 20 ms ごとに読んだ値です。単位は MiB で、「いちばん大きい値／開いたまま待っている間の中央値」です。文書エンジンは 12 スレッドで開き、今の実装は、開いて `scene` を 1 回作って捨てたあとに待っています。

| 要素の数 | 1,002 | 10,002 | 100,002 | 1,000,020 |
| --- | ---: | ---: | ---: | ---: |
| 文書エンジン | 7.6／7.6 | 12.0／12.0 | 45.9／45.2 | 380／372 |
| 今の実装 | 11.3／9.7 | 34.5／20.4 | 249／119 | 2,299／1,100 |

- 文書エンジンが数えた内訳は、100,002 要素で、列・表示のバッファー・索引が 21.5 MiB、元のファイルが 14.7 MiB です。1,000,020 要素では、214.5 MiB と 148.7 MiB です。
- 1 スレッドで開いても、ほぼ同じ値でした（100,002 要素で 44.5／43.6、1,000,020 要素で 378／371）。
- 1,000,020 要素の文書エンジンは、プライベートのメモリでは 413 MiB でした。

## 採る条件に照らして

[進め方](../../docs/live.md#進め方)の 3 つの条件を、この試作の範囲（DXF の 5 種類の要素と、動かす変更）で見ます。

- 確定・選択・取り消しの時間は、1 万要素と 100 万要素で同じ桁でした。1 件を動かす変更が 4.2 と 5.9 マイクロ秒、取り消しが 1.4 と 2.1 マイクロ秒、小さい範囲で選ぶのが 0.16 と 0.19 マイクロ秒です。
- 開いて表示のバッファーを作るまでの時間は、10 万要素で今の実装の 8.6 分の 1（1 スレッド）と 24 分の 1（12 スレッド）、100 万要素で 9.9 分の 1 と 31 分の 1 でした。上に書いたとおり、同じ仕事どうしの比ではありません。
- 全体を書く保存のバイト列は、公開サンプル・合成の図面・書き方を変えた図面で流した変更のすべてで、今の実装と同じでした。
- [目標の値](../../docs/live.md#目標の値)のうち、100 万要素を開いて表示のバッファーを作るまで（0.65 秒と 0.20 秒）、確定・選択・取り消し（1 ms 以内）、メモリ（10 万要素で 46 MiB、100 万要素で 380 MiB）は、この範囲では届いています。10 万要素のメモリは、目標の 50 MiB に近い値です。
- 採らない条件（書き戻しに図面の全体の解釈が要る）には、この範囲では当たりませんでした。書き戻しに使ったのは、そのレコードのタグ、置かれた空間、文字コード、ヘッダーの変数（`$EXTMIN`・`$EXTMAX`・`$HANDSEED`）、ハンドルが重なっていないことです。ヘッダーの変数とハンドルは、開くときに 1 回読みます。

ブロック参照、要素を足す・除く・属性を変える変更、DWG は、まだ試していません。採るかどうかは、それらを通してから決めます。

## 分かったこと

- 取り消しは、タグの前の値を戻すので、保存したバイト列が変更の前と同じになりました。今の実装で逆の変換を当てて戻すときの、丸めの違い（[`apply` で直すときの性質](../../docs/editor.md#apply-で直すときの性質)）は起きません。
- 動かす変更では、差分で直した表示のバッファーが、開き直して作ったものと、並びまで同じになりました。要素の数が変わらず、同じ場所に書き直すためです。表示のバッファーを決定性の契約の対象から外すかどうか（[採る前に利用者に確かめること](../../docs/live.md#採る前に利用者に確かめること)）は、要素を足す・除く変更を入れるときに要る判断です。
- 分けて読んだ結果を入力の順に集めれば、開いた結果は、区間の数にもスレッドの数にも依りませんでした。
- 今の実装と同じバイト列を書くには、今の実装の規則を、数の書式まで同じにする必要がありました。規則を写して 2 か所に持つ形は、続けられません。採るときは、1 つのオブジェクトのタグを受け取って直す 1 つの実装にまとめ、今の実装と文書エンジンの両方から呼ぶ形がよいと見ています。
- 今の実装は、変更のたびに `$HANDSEED` を確かめて直します。文書エンジンでは、開くときに 1 回確かめれば足りますが、直す必要のある文書の扱いを決める必要があります。
- 変えたレコードをタグの列で持つので、変えた要素の多い文書では、メモリが増えます。

## 確かめていないこと

- コアの lint（添字・`unwrap`・`panic` などを禁じる）には、合わせていません。テストでないコードに、添字で読む所が 30 か所あります。`unsafe`・`unwrap`・`expect`・`panic!` はありません。入力でパニックしないことは、確かめていません（fuzz を流していません）。
- 公開サンプルにある 5 種類の要素は 76 件で、ほかのアプリケーションが書いた図面での幅は狭いままです。
- 文書エンジンが中に持つ形・表示のバッファー・範囲で選ぶ結果を、今の実装のシーンや `entities` の結果と照らすこと。
- 診断・予算・中断・ハッシュを入れたときの時間と、wasm での結果と時間。
- 測ったときに、同じ端末でほかの仕事が動いていなかったことは、確かめていません。マイクロ秒の値は、端末の様子で変わります。
