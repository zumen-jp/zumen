# 形式の権利の台帳

[台帳](ledger.toml)には、仕様の入手先・権利の根拠・読み書きを確かめた範囲を記録します。実装の置き場所は形式ごとの `place`（コア・外部プラグイン・実装しない）で示します。コアに置けるのは `rights` が `public` の形式に限ります。

## 形式を足す

1. 実装を始める前に、`ledger.toml` に形式の項目を足す。公式の仕様があれば、先に `[specs]` に足す。
2. 仕様の版・入手先・権利の根拠は、公式の文書で確かめ、確かめた日を書く。入手に条件への同意が要れば、その条件が AI での利用を禁じるかも書く（下の「仕様」）。仕様の本文は写さない。
3. 権利が `public` でない形式は、`place` を `core` にしない。
4. 実装する crate の `Cargo.toml` で形式を名乗る。権利が `public` でない形式の既知の crate は、`deny.toml` の `[bans].deny` に例外・版の制限なく加える。
5. 新しい形式・版・読み書きの向きには、外部実装との照合、再配布できる公開サンプルの読み取り、fuzz、予算・ID の契約テストをそろえる。外部実装や適切なサンプルがないときは、調べた先を形式の文書に残す。読み書き別に[台帳と形式の文書の段と範囲](#確かめた度合い)を一緒に更新する。
6. `cargo xtask codegen` で一覧を作り直し、台帳と生成した文書を一緒にコミットする。

## 仕様（`[specs.<ID>]`）

ID は英小文字・数字・`_` にし、版を含めます（`sxf_3_1` など）。診断の `cite`（[診断のカタログ](../catalog/README.md)）は、この ID で仕様を指します。形式の項の `specs` から指さない仕様も置けます。ISO 10303-21 のように、いくつかの形式の土台になっていても、形式の権利の判断に使っていない規格は、入手の条件と、エージェントが本文を読むか（[資料を読む条件](#資料を読む条件)）を記録するために置きます。

| キー | 要るか | 中身 |
| --- | --- | --- |
| `title` | 要る | 仕様の名前 |
| `publisher` | 要る | 仕様を出している者 |
| `version` | | 版と日付 |
| `access` | 要る | `public`（誰でも無償で入手できる）・`members`（会員などにだけ配る）・`paid`（買う） |
| `url` | 要る | 入手先 |
| `checked` | 要る | 確かめた日。文字列の `YYYY-MM-DD` にする |
| `note` | | 補足 |

入手に同意の操作（購入・登録・会員・NDA・同意のボタンなど）が要る仕様は、`note` に、同意の操作が要ることと、その条件が AI での利用を禁じるかを書きます。`paid`・`members` のほか、無償でも登録や手続きで受け取るものが当たります。確かめていなければ、そう書きます。誰でも見られるページやファイルの注記が AI での利用を禁じるときも、その中身を `note` に書きます。注記は、ページの本文だけでなく、折りたたまれた部分（`<details>` など）とページの下まで読みます。仕様は、持ち主か、持ち主がその版の公開を許した配布者から入手し、`url` にもその入手先を書きます。エージェントが何を読めるかは、[資料を読む条件](#資料を読む条件)にあります。

## 形式（`[formats.<キー>]`）

キーは英小文字と数字だけにします（`sxf`・`stbridge` など）。API の列挙の値（[API のスキーマ](../schema/README.md)）にも、診断の code の範囲にも、そのまま使えるようにするためです。

| キー | 要るか | 中身 |
| --- | --- | --- |
| `name` | 要る | 形式の名前 |
| `family` | 要る | L1 の系統（[コアの設計](../docs/architecture.md)）。同じ系統の形式は、1 つのファイルモデルを共有する |
| `domains` | 要る | L2 の領域: `drawing`・`building`・`civil`・`geo`・`pointcloud`・`delivery`・`review` |
| `specs` | 要る | 仕様の ID の並び。公式の仕様がなければ空にする |
| `rights` | 要る | 下の 3 つの値 |
| `rights-note` | 要る | 権利の根拠の要約 |
| `evidence` | | 仕様のほかに、権利の根拠にした文書（`title`・`url`・`checked`・`note`） |
| `place` | 要る | `core`（このリポジトリのコア）・`plugin`（外部のリポジトリのプラグイン）・`none`（実装しない） |
| `repository` | `plugin` なら要る | プラグインのリポジトリ |
| `basis` | `none` でなければ要る | 実装の根拠: `spec`（仕様）・`inferred`（推定）・`reference`（参照した実装） |
| `references` | `reference` なら要る | 参照した実装（`name`・`license`・`url`）。GPL などの実装のソースは読まない |
| `verify` | | 照合に使う候補の、外部の実装と基準になるソフト。段の根拠にはしない。照らしたら、[確かめた度合い](#確かめた度合い)の `implementations`・`software` にバージョンと一緒に書く |
| `samples` | | サンプルの出どころ。[公開サンプルの条件](../samples/README.md) の条件に合う公開サンプルは `samples/` に置ける。置いたら、[公開サンプルの台帳](../samples/ledger.toml)に書く。受け取った図面は Git に入れない |
| `known-crates` | | crates.io にある、この形式を読み書きする crate。権利が `public` でない形式のものは、`deny.toml` で禁じる |
| `legacy-decisions` | | 旧版のリポジトリにある記録の番号の配列。`["0008"]` のように 4 桁の文字列にする |
| `issues` | | 関わる issue（`zumen-jp/zumen-legacy#140` の形） |
| `docs` | 確かめた度合いがあれば要る | 形式の文書のパスの配列。リポジトリの根から `docs/formats/` 内の実在する Markdown を指す |
| `notes` | | そのほかの補足 |
| `read`・`write` | `core` で実装した向きには要る | 読み・書きの[確かめた度合い](#確かめた度合い)。実装していない向きと、`core` でない形式には書かない |

## 確かめた度合い

コアの実装を、読みと書きに分けて、どこまで確かめたかを `[formats.<キー>.read]`・`[formats.<キー>.write]` に書きます（[開発の進め方](../docs/work.md)）。API の `capabilities` には出しません。

| 段 | 読む向き | 書く向き |
| --- | --- | --- |
| `synthetic` | 仕様と、テストの中で作ったファイルだけで確かめた。公開サンプルや受け取った図面を読んでも、値を照らしていなければこの段にする。根拠は要らない | 書いたファイルを、自前の読み取りだけで確かめた。根拠は要らない |
| `external` | 自前で作っていないファイル（公開サンプル・受け取った図面・外部の実装が書いたもの）を読み、外部の実装が読んだ値か、ファイルに添えられた値と照らした。`implementations` か `attached-values` が要る | 書いたファイルを外部の実装が読み、読んだ値が書いた値と合った。`implementations` が要る |
| `application` | その形式の基準になるソフト（作るソフトか、受け取る側のソフト）で開いた結果と照らした。`software` が要る | 書いたファイルを、基準になるソフトで開いて確かめた。`software` が要る |

段は一部の規則で得た根拠も含めてもっとも強い方法で決め、その範囲を `scope` と形式の文書に示します。入力の出どころは検査で確かめないので、読みの `scope` に書きます。公開サンプルや受け取った図面を読んだだけなら、その旨を書き `synthetic` とします。zumen やテストが作った入力は外部実装で照らしても、読みの `external` に数えません。`verify` に載るだけの候補や、コアの読み取りに使う依存の crate も根拠に数えません。

| キー | 要るか | 中身 |
| --- | --- | --- |
| `level` | 要る | `synthetic`・`external`・`application` |
| `scope` | 要る | 現在の検証範囲と方法、未検証の所、段を上げる issue。範囲が変わったら該当箇所を書き換える |
| `checked` | 要る | 確かめた日。文字列の `YYYY-MM-DD` にする |
| `public-samples` | | 読みだけ。読んだ公開サンプル。`samples/` の中の道筋（`samples/dwg/` のように `/` で終われば、そのフォルダー）は、[公開サンプルの台帳](../samples/ledger.toml)にあるもの。Git にない公開サンプルは URL で書く |
| `received` | | 読みだけ。読んだ受け取った図面の種類と件数（`kind`・`count`）。ファイル名・顧客の名前・中身は書かない |
| `attached-values` | | 読みだけ。読んだ公開サンプルか受け取った図面に添えられていて、読んだ値と照らした値（作ったソフトが添えた一覧など）。`public-samples` か `received` が要る |
| `implementations` | | 読みでは、自前で作っていないファイルを読み、読んだ値を照らした外部の実装（`name`・`version`）。書きでは、書いたファイルを読み、読んだ値が書いた値と合った実装。コアが読むのに使う依存の crate は数えない |
| `software` | | 開いて確かめた、その形式の基準になるソフト（`name`・`version`） |

形式の文書の「確かめた度合い」には、次の形の表を置きます。その文書を `docs` に持つ形式を、段がある向きごとに台帳と同じ段で並べます。表の後に検証範囲と限界を示し、`synthetic` にとどまる規則を明記します。件数・ツールのバージョン・手順の明細は、根拠を置いた台帳や個別の検証節にリンクします。

```markdown
## 確かめた度合い

| 形式 | 向き | 段 |
| --- | --- | --- |
| `ifc` | 読み | `synthetic` |
| `ifc` | 書き | `external` |
```

## 権利

| 値 | 意味 | 置ける所 |
| --- | --- | --- |
| `public` | 実装を公開するのに、第三者の許諾が要らない。持ち主が仕様を公開して実装を制限していないもの、または持ち主の仕様がなく、公開された資料と推定で読むもの | `core`・`plugin`・`none` |
| `permission` | 持ち主が、仕様の入手か実装の公開に、契約・会員・許諾を求めている | `plugin`・`none` |
| `unknown` | 持ち主か、その条件を確かめられていない | `plugin`・`none` |

## 資料を読む条件

仕様・ページ・資料をエージェントが読めるかは、利用者が同意の操作をした条件で決めます。公開の資料を読むことは利用者が読むことと同じに扱い、利用者が同意の操作をした条件はエージェントが読んでも利用者を縛るので分けて扱います（#669・#677）。

- 公開の資料は、そのまま読む。公開の資料とは、その資料の持ち主（著作権者）か、持ち主がその版の公開を許した配布者が、ログインも同意の操作もなしに誰でも見られるようにしているページとファイル（出版物の一部を見せるプレビューを含む）をいう。中の注記（AI での利用を禁じるものや、アクセス・使用で同意したとするもの）と、許諾の種類（CC の NC・ND など）では止めない。読むためにページを開き、ファイルを取得することは、写すことに数えない。
- ISO の出版物（規格と、その一部。OBP のプレビューを含む。規格の一部として配るファイルも、ECLA が当たるかを確かめていないので、用心のために含める）は、同意の操作なしに見られるものも読まない。ECLA（End Customer Licence Agreement）は、出版物の一部へのアクセスでも同意したとする。同意したと見られると、7(b) で AI で読むことが禁じられ、6(b) で形式の実装と公開が縛られうる。ISO のサイトのページ（販売のページ・書誌など）は、出版物ではないので読む。ほかの持ち主が自分で公開する同じ内容（buildingSMART の IFC など）は、その持ち主の資料として読む。ほかの持ち主の出版物に同じ形の条件が見つかっても、利用者が ISO と同じく扱うと決めるまでは、上の決まりのとおり読み、台帳の `note` に書いて利用者に知らせる。
- 購入・登録・会員・NDA・同意のボタンなど、同意の操作をして手に入れた資料は、その条件に従う。条件が AI での利用を禁じていれば読まない。確かめていなければ、確かめるまで読まない。条件の文はエージェントが読んでまとめてよいが、読むと決めるのは利用者にする（[利用者に頼むこと](../docs/work.md#利用者に頼むこと)）。同意の操作は、エージェントが利用者の代わりにしない。
- 持ち主が許さずに上げたと分かる写しは開かない。持ち主の条件が写すことを許していないウェブ・アーカイブの写しも、これに当たる。著作権を侵害して上げられたものと知りながらダウンロードすることは、軽微なものなどを除き、私的使用のための複製の例外に入らない（著作権法 30 条 1 項 4 号）。疑わしければ、持ち主の所から入手する。
- 自動の取得を拒むページは、利用者のブラウザー（ブラウザーの拡張）で開いてよい。ログイン・CAPTCHA・支払いは越えない。利用者がログインしているサイトでは、ログインしないと見られない所も開けてしまうので、ログインした状態でしか見られないものは開かない。
- 学習済みの知識は使ってよい。外部の実装のソースは、寛容なライセンスのものだけを読み、GPL の実装のソースは読まない（[依存と照合ツール](../CONTRIBUTING.md#依存と照合ツール)。書くコードに混ざるのを防ぐ決まりで、同意した条件によらない）。本文を読めない仕様は、学習済みの知識・公開の資料・寛容なライセンスの実装と、テストで確かめた結果で実装し、台帳の実装の根拠（`basis`）は上の「形式」のとおりに書く。
- 仕様の本文・表・図は写さない。節の番号・名前・値などの事実は書いてよい。写す・配る・作り変える・写しを残すときは、そのときにその版の許諾を確かめる。NC・ND の読みで採否が決まるものは[利用者に頼む](../docs/work.md#利用者に頼むこと)。写しを残すとは、使い続けるために置いておくこと（リポジトリ・共有のフォルダー・手元の資料の置き場など）をいう。読むためにツールが作る一時の写し（取得した出力の保存・一時フォルダー・clone など）は、使い続けなければ入らない。

## 検査

crate は、実装する形式を `Cargo.toml` の `[package.metadata.zumen]` の `formats` で名乗ります。

```toml
[package.metadata.zumen]
formats = ["dxf", "dwg"]
```

`cargo xtask codegen` と `cargo xtask codegen --check` は、次を検査します。

- 要る項目・値の語・キー・空欄・重複、仕様の参照、HTTP または HTTPS の入手先、実在する日付。
- `core` の権利が `public` であること、`plugin` のリポジトリ、実装の根拠に必要な仕様や参照した実装。
- 参照先の形式の文書があること。旧版の記録は番号の形、issue は `所有者/リポジトリ#番号` の形を確かめる。
- 確かめた度合いの段が向きと根拠の種類に合うこと、`public-samples` が公開サンプルの台帳にあること、確かめた度合いを持つ形式の文書に節があること。節の表が台帳と過不足なく合い、形の崩れた行がないこと（段を持たない形式の文書も、節があれば照らす）。
- `cargo metadata --format-version 1 --all-features --locked` に含まれる全パッケージの名乗り。台帳にない形式、`public` の `core` でない形式、確かめた度合いのない形式、不正な名乗りを拒む。通常・build・dev・間接の依存を含み、環境で絞らない。
- 権利が `public` でない形式の既知の crate に、例外・版の制限のない禁止があること。`"stb-parser"` または `{ crate = "stb-parser", reason = "理由" }` の形を使う。古い `name` の形も読めるが、`wrappers` による例外や、複数の版だけを禁じる指定では代わりにならない。既知の crate が Cargo の依存に現れた場合も拒む。

`codegen` は [形式と権利の一覧](../docs/formats/README.md)を生成します。`--check` はファイルを書き換えず、不足や古い生成物を検出します。CI の「書式・lint・生成物」でも同じ条件を検査し、依存のライセンスと禁止は cargo-deny でも検査します。

外部の URL の到達、権利の根拠の正しさ、参照した実装のライセンスは、この検査で再確認しません。形式を名乗らず、既知の crate にも載っていない実装も自動では見つかりません。これらは台帳を変更する際の資料確認とレビューで確かめます。
