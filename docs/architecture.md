# コアの設計

## モデルと依存

読み書き・変換・解析は Rust に実装します。各言語のバインディングは同じコアを呼び、形式の判定もコアのデータから生成します。

| 層 | 扱うもの | ほかの層との関係 |
| --- | --- | --- |
| L0 | 字句、ビット列、コンテナー | 形式の意味に依存しない部品を共有する |
| L1 | 系統ごとのファイルモデルとコーデック | 同じ系統の符号化はモデルを共有し、未知のレコードも元のバイト範囲と結び付ける |
| L2 | 図面・建物・土木・地理・点群などの領域モデル | L1 の型に依存しない。系統と領域をつなぐ処理が双方の型を扱う |
| L3 | シーン、描画、解析などの派生データ | 領域モデルから作り直せる。元の要素とレコードまで出所をたどれるようにする |

各層の crate は [リポジトリの地図](../AGENTS.md#リポジトリの地図) にあります。

## 書き出しの経路

| 場面 | 経路 |
| --- | --- |
| 低水準の編集 | L1 のトランザクションで、レコードと生の値を直接書き換える |
| 同じ形式の編集 | L2 の変更セット → `apply` → L1 の触れたレコードだけを書き換える |
| バージョンの変更、同じ系統の別の符号化 | L1 の系統の中で書き分ける |
| 別の形式への変換 | L1(A) → `lift` → L2 → `lower` → L1(B) → B のコーデック |
| 新規作成・作図 | L2 → `lower` → L1(B) → B のコーデック |

- どの経路でも、L1 への書き込みはトランザクションで行う。
- 書き出す前に、忠実度の見積もり（dry-run）を返せるようにする。

同じ符号化・版・文字コードへの編集では、変更と、それに伴って更新する参照や件数だけを書き戻します。未知のレコードを含むほかの部分は元のバイトを保ちます。出力先で表せない値は、出所・種類・件数・忠実度を診断で返します。

DXF の編集では、[DXF の書き戻し](formats/dxf.md) と [図面モデルの対応表](formats/drawing2d-mapping.md) で、残す値と診断を確認します。API の操作と期待する結果は [適合テストの `apply`](../bindings/conformance/cases/apply.json) と [`convert`](../bindings/conformance/cases/convert.json) にあります。外部の実装との照合は [検証キット](../xtask/verify/README.md) に従います。

## 幾何と許容差

領域モデルには曲線の定義を残します。表示・位相の計算や、出力形式で曲線を表せない場合に折れ線にし、作った点を `segments` の予算で数えます。別の形式への近似では弦の誤差を忠実度とともに記録します。用紙・実寸・プロジェクト・地図の座標と許容差を区別し、長さと面積は可能な限り元の形から求めます。2D の位相は許容差より細かな整数の格子で求め、使った間隔を記録します。

## 決定性

同じ版・入力・設定・予算なら、書き出すバイト列、領域モデル、シーン、診断の順と停止位置までネイティブと wasm で一致させます。コアが描く画像も含みます。各端末の表示、外からの中断、環境の資源が先に尽きた場合は区別します。版をまたいで保証するのは ID です。

- IEEE 754 で結果が決まる演算を使い、精度が環境に依存する関数は `libm` を通す。出力の NaN は同じビット列にそろえる。32 bit の x86 は SSE2 を使い、wasm の relaxed SIMD は使わない。
- 位置・長さ・個数は `u64` で扱い、あふれを検査する。ハッシュ表の反復順や番地に頼らず、比較は全順序にする。同順位は ID か元の位置で決める。
- 並列の結果は入力順に集め、浮動小数の総和も分割によらず同じ順で計算する。時計・乱数・環境変数・ロケール・OS のフォントやファイルを結果に使う場合、値は呼び出し側から受け取る。
- 依存にも同じ条件を適用する。[適合テスト](../bindings/conformance/README.md) は、各環境から同じ入力を処理したハッシュをコミット済みの一覧と比べる。形式の正しさは仕様から求めた期待値と、独立した実装の出力で確かめる。

## 予算と中断

呼び出しの文脈に予算、診断の収集先と中断の合図を持たせ、入れ子の読み取りでも予算を共有します。確保前に残りの入力と予算を確かめ、バイト・レコード・要素・深さ・分割数・繰り返しを作業量で数えます。並列でも入力順に予算を使います。停止位置を診断に残し、読み取りで部分結果を返すのは明示して求められた場合だけです。書き出しはすべての変更を確かめてから反映し、失敗時には何も書きません。中断や trap の後の wasm インスタンスの扱いは [JavaScript のバインディング](../bindings/js/README.md) にあります。

## 設計を変更するとき

API と ID の契約は [スキーマ](../schema/README.md)、診断は [カタログ](../catalog/README.md)、形式ごとの規則は [形式の文書](formats/README.md)、権利と検証の根拠は [形式台帳](../formats/README.md) を更新します。作業手順は [開発の進め方](work.md) にあります。変更する規則とテストを同じ PR で更新し、選択肢と理由は PR に、未実装の約束は issue に残します。

過去の PR・issue・ソースのコメントにある決定番号は、[移行前の記録](https://github.com/zumen-jp/zumen/tree/86192aa34daad415a33dc07f92969aef9a3a1c5e/docs/decisions) から引けます。
