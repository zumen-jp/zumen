# 表記の基準

文書・診断の文・CLI のヘルプ・コードのコメントの表記と用語を決めます。考え方と選んだ理由は [決定 0021](decisions/0021-notation-and-terms.md) にあります。

機械で確かめられる規則は `prh.yml`（揺れの辞書）と `.textlintrc.yml` に置き、CI の「表記の検査」で確かめます。手元では次のように確かめます（Node.js 22 以降）。

```bash
npm ci
npm run lint:text
```

Markdown の誤りの多くは、`npm run fix:text` で直せます。

## 文体

- 利用者と貢献者が読む文書（README・CONTRIBUTING・SECURITY・`docs/` の案内）は「です・ます」で書く。
- 規則と記録（AGENTS.md・決定の記録・コードのコメント・台帳の説明）は常体で書く。
- 診断の文（`catalog/ja.toml`）は「です・ます」の過去形で書く（例: 上限を超えたので、止めました。）。
- 1 つのファイルの中で文体を混ぜない。手順の箇条書きは常体でもよい。

## 文字

### カタカナ語の長音

- 英語の -er・-or・-ar などに当たる語末には「ー」を付ける。
  - 例: ブラウザー・サーバー・フォルダー・ヘッダー・コンパイラー・コンテナー・バッファー・ポインター・パラメーター・ユーザー
- 英語の -y の語末（-ry・-ty・-gy・-xy）には付けない。
  - 例: メモリ・ライブラリ・リポジトリ・ディレクトリ・バイナリ・セキュリティ・プロキシ
- 内閣告示「外来語の表記」の原則と、2008 年からの Microsoft の表記に合わせる。利用者が毎日見る Windows の画面と同じ書き方になる。
- 要領・基準が定める用語は、原典に合わせる。
  - 例: レイヤ（CAD製図基準・SXF・Jw_cad の用語）

### 漢字とかな

「公用文作成の考え方」（文化審議会、2022 年）に沿って、次の語はかなで書きます。

- 形式名詞: こと・とき・もの・ため・ほう・とおり・うえ
- 補助動詞: 〜していく・〜してくる・〜してください・〜していただく
- 副詞と接続詞: すでに・さらに・まだ・すべて・ただし・なお・または・および・ならびに
- そのほか: できる（動詞）・よい・ほか・など・ごと・まで

次の語は漢字で書きます。どちらも、今の文書に多い書き方に合わせました。

- 場所を表す「所」（止まる所・使える所）。形式名詞の「ところ」とは別
- 分かる・分かれる
- 出来形・出来高（建設の用語）

### 英数字と記号

- 英数字は半角で書く。全角の英数字と半角カナは使わない。図面に記録された文字を引くときは除く。
- 半角の英数字と全角の文字の間に、半角の空白を入れる。句読点と括弧の前後には入れない。
- インラインのコードの前後にも、空白を入れる。
- 句読点は「、」と「。」、括弧は全角の（）と「」を使う。
- コロンは半角にし、後ろに空白を入れる（例: 状態: 提案）。
- 範囲の波線は「〜」（U+301C）を使う。`～`（U+FF5E）は、CP932 との変換で取り違えやすいので使わない。
- 並べるときは「・」を使う。
- 日付は 2026-10-24 の形で書く。

### 固有名詞

- 製品・基準・団体の名前は、空白・長音・大文字と小文字も含めて原典どおりに書く。
  - 例: Jw_cad・CAD製図基準・GitHub・Node.js・WebAssembly・macOS・AutoCAD・.NET
- 空白の規則より原典を優先する。「CAD製図基準」の CAD と製図の間には、空白を入れない。

## 用語

### 読み手が知っている言葉を使う

読み手は 3 つに分かれます。設計・施工・維持管理の実務者、ソフトウェアの開発者、導入を決める人（情報システム部門・法務・決裁者）です。語は、次の順で選びます（[決定 0257](decisions/0257-established-terms-over-coined-words.md)）。

1. 要領・基準・製品が定める語を使う。CAD製図基準と SXF の語（成果品・出来形・レイヤ・表題欄・発注者）、AutoCAD の日本語版の語（画層・文字スタイル・寸法スタイル・フィット点・挿入単位）、Excel の語（結合セル）。
2. 開発で定着したカタカナ語と英語を使う。API・ラッパー・バインディング・フィールド・ヘッダー・バージョン・テストなどを、和語に言い換えない（下の「書き方を決めた語」）。
3. どちらでもない語は、ふつうの日本語で書く（診断・予算・台帳・出所など）。
4. 一般の語に、この文書群だけの意味を持たせない。決めた意味で使う語は、下の「意味を決めた語」に載せる。

- 「意味を決めた語」を、利用者向けの文（README・サイト・診断の文・CLI のヘルプ）で初めて使う所では、「予算（処理量の上限）」のように言い換えを括弧で添える。
- 要領・基準は、名前と版の年月で呼ぶ。版の年月は、原典の書き方（和暦など）に合わせる。

### 検査の結果の言い方

- ツールが自動で行う検査は「チェック」と呼び、「照査」とは呼ばない。照査は照査技術者が責任を持って行うもので、ツールが代わるものではない。
- 結果に「合格」「適合」「保証」を使わない。「指摘なし」「確認できなかった項目」のように、何を確かめたかが分かる言い方にする。

## 辞書と規則を直す

- 揺れを見つけたら、`prh.yml` に規則と `specs`（直す前と後の例）を書き、この文書も直す。prh は、読み込むときに `specs` を確かめる。
- 前後で意味が決まる語（`境界`・`版`・`欄`・`見出し` など）は、取り違えのない言い方だけを規則にする。規則に掛からない所は、上の表で選ぶ。
- Markdown の辞書の指摘は、`npm run fix:text` で直せる。ソースコードと設定は、文字列リテラルやテストのデータを書き換えないよう、指摘を見て手で直す。
- Markdown は `.textlintrc.yml` のすべての規則で確かめる。ソースコード（`.rs`）・TOML・YAML は、揺れの辞書だけで確かめる。
- 英語の語の規則は、後ろに和文が続くときだけに当てる。識別子や列挙の値を和文の中に書くときは、コードとして書く（`native`）。
- 固有名詞や原典の題名が規則に合わないときは、`.textlint-allow.yml` に理由と一緒に足す（例: 測地成果2024、基準面補正パラメータ）。
- その場だけ外したいときは、Markdown なら `<!-- textlint-disable 規則の名前 -->` と `<!-- textlint-enable -->` で囲む。
