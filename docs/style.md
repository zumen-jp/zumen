# 表記の基準

文書・診断・CLI のヘルプ・コードのコメントに使います。語を探すには `rg -n -F '画層' docs/style.md prh.yml` のように検索します。変更した Markdown は[変更に応じた検査](../CONTRIBUTING.md#変更に応じた検査)で確かめます。

## 文体

- README・CONTRIBUTING・SECURITY・`docs/` の案内は敬体、AGENTS.md・コードのコメント・台帳などの規則と記録は常体で書く。
- 診断は敬体の過去形にする（「上限を超えたので、止めました。」）。
- ファイル内で文体をそろえる。手順の箇条書きは常体でもよい。

## 文字

### カタカナ語の長音

内閣告示「外来語の表記」と 2008 年からの Microsoft の表記に従い、英語の -er・-or・-ar などの語末は「ブラウザー」、-y の語末は「メモリ」「ライブラリ」のように書きます。製品名の「SXF ブラウザ」や CAD製図基準の「レイヤ」は原典に合わせます。

### 漢字とかな

「公用文作成の考え方」（文化審議会、2022 年）に沿い、形式名詞（こと・とき・もの・ため・ほう・とおり・うえ・ところ）と補助動詞（〜していく・〜してくる・〜してください・〜していただく）はかなで書きます。「すでに・さらに・まだ・すべて・ただし・なお・または・および・ならびに」「できる・よい・ほか・など・ごと・まで」も同じです。場所を指す「所」、「分かる・分かれる」、建設用語の「出来形・出来高」は漢字を使います。

### 英数字と記号

- 英数字は半角、カナは全角。英数字と和文の間、インラインコードの前後に半角の空白を入れる。句読点・括弧の前後は詰める。
- 句読点は「、」「。」、括弧は全角の（）と「」、列挙は「・」、コロンは半角で後ろに空白を置く。範囲は「〜」（U+301C）、日付は 2026-10-24 の形にする。
- 図面から引いた文字は原文を保つ。

### 固有名詞

製品・基準・団体の名前は、空白・長音・大文字小文字も原典に合わせます（Jw_cad・CAD製図基準・Node.js など）。要領・基準には名前と版の年月を記し、和暦などの表記も原典に従います。

## 用語

### 読み手が知っている言葉を使う

設計・施工・維持管理の実務者、開発者、導入を決める人に通じる語を選びます。要領・基準・製品の用語、開発で定着した用語、ふつうの日本語の順に使います。一般の語には独自の意味を持たせません。意味を決めて使う語は下の表に置き、利用者向けの README・サイト・診断・CLI ヘルプでは初出に「予算（処理量の上限）」のような言い換えを添えます。

### 検査の結果の言い方

自動検査は「チェック」と呼びます。「照査」は照査技術者が責任を持って行う業務です。結果は「指摘なし」「確認できなかった項目」のように確かめた範囲を示します。「合格」「適合」「保証」は結果の判定に使いません。

### 意味を決めた語

| 語 | 意味 |
| --- | --- |
| コア | 形式を読み書きし、解析する Rust の 1 つの実装 |
| API | 各言語からコアを呼ぶ、数個の関数と、スキーマで定めたメッセージ。C ABI と wasm の関数を含む |
| バインディング | 各言語から API を呼ぶための層 |
| ラッパー | バインディングのうち、手で書く薄い層 |
| Tier | 言語ごとの対応の約束。Tier 1 のように書く |
| 実行の形態 | API の出し方。ネイティブ・wasm・プロセスの外・HTTP。識別子は `engine` |
| 文書エンジン | 開いた図面をメモリに持ち続け、変更を差分で当てる、コアの中の実装（[設計](live.md)）。要求のたびに図面の全体を作る「今の実装」と並べて作る。実行の形態の `engine` や「子プロセスのエンジン」とは別 |
| 予算 | 処理量の上限。利用者向けの文では「上限」と書く |
| 診断 | code・場所・値で返す、警告とエラーの知らせ |
| 忠実度 | 変換で意味を保てたかの段 |
| 台帳 | 診断の code・形式の権利・公開サンプルを決める表（`catalog/codes.toml`・`formats/ledger.toml`・`samples/ledger.toml`） |
| 出所 | 表示した要素から、ファイルのレコードまでたどる情報 |
| ミラーのリポジトリ | 配る仕組みのために中身を写したリポジトリ |
| 正（日本語を正とする） | 訳の元になり、食い違ったときに優先する文（正文・正本） |
| 確かめた度合い | 形式ごとに、読み書きをどこまで確かめたかの段（検証の段階）。`synthetic`・`external`・`application` |
| 外部の実装 | 結果を照らすのに使う、ほかの人が作った実装（テストのオラクル）。成果物に入れない。外部のプラグインとは別。旧版の参照実装（TypeScript のリーダー）と、台帳の `references`（参照した実装）とも別 |
| 検証キット | 実際のソフトで開くファイルと、作るコマンド・開く手順・期待する結果の組 |

### 書き方を決めた語

一意に置き換えられる語は[表記の辞書](../prh.yml)で引けます。次の語は前後の意味で選びます。

| 文脈 | 書き方 |
| --- | --- |
| API とファイルの構造 | 各言語から呼ぶのは「API」、ハッチング・切り抜き・8 バイトの境目は「境界」。ファイル・レコード・HTTP は「ヘッダー」、表・文書は「見出し」。値を入れる「フィールド」と、表題欄・空欄・縦断図の欄を区別する |
| バージョン | ソフトウェア・形式・スキーマ・API・モデルには「バージョン」を使う。要領・基準・仕様書の「版」、zumen-legacy を指す「旧版」はそのまま |
| タグ・フラグ・マーカー | 共用体や JWW のクラス・オブジェクトは「タグ」、値やビットに立てるものは「フラグ」。データの始まり・終わり（JPEG、SXF のフィーチャのコメントの開き、線形の終わり）や点の印は「マーカー」。バイト順は「バイト順マーク」、バイナリ DXF の先頭は「センチネル」 |
| セクションと区切り | ファイルのまとまりは「セクション」。CSV の区切り文字、値・文字列・書式の区切り、建物や基盤地図情報の DEM の区画はそれぞれの名で呼ぶ。JPEG は「セグメント」 |
| DWG | 大きさ・データ・CRC の組は「オブジェクトのレコード」、`AcDb:AcDbObjects` 全体は「オブジェクトのセクション」。セクションマップ、ハンドル・文字列のストリームと書く。基盤地図情報や地図の空間には「地図」を使う |
| DXF・AutoCAD | 100 は「サブクラスマーカー」、その範囲は「サブクラス」。MLINE の 74・75 は「パラメーター」、MLINESTYLE は「マルチラインスタイル」。折れ線の頂点の bulge（42）は「膨らみ」 |
| CAD と図面モデル | AutoCAD の LAYER は「画層」、図面モデル・CAD製図基準・SXF・Jw_cad は「レイヤ」。文字スタイル・寸法スタイル・フィット点・挿入単位は製品の語を使う。スプラインは「ノット」、八分木は「ノード」、構造は「節点」 |
| データと人 | 型付きのビュー・JSON を包むビュー、形式を読むリーダー、人の読み手。データは「キー」、署名は「鍵」。建物モデルのコンポーネント、ベクトル・行列の成分。プラグインの登録先は「レジストリ」 |
| 操作と識別子 | 名詞は「追加・削除」、動詞は「足す・除く」も使える。本文はネイティブ・パニック・モジュール・コミット・[ワークフロー](https://docs.github.com/ja/actions/get-started/understand-github-actions)、crate・issue・PR・wasm（WebAssembly）。識別子・コマンド・lint 名・パスはコードで原文を保つ |
| ソフトウェアと実務 | 言語の「バインディング」と Excel の「結合セル」。ソフトウェアの「サンプル・テスト」と地盤の「土質試料・試料採取・標準貫入試験」。確保量は「メモリの最大」。ライセンスの文では「貢献（Contribution）」 |
| 線形 | 道路・鉄道の中心線（alignment）。linear は「線形の寸法」「線形のスプライン」と名詞を添える |
| PDF | ソフトマスク（ISO 32000-2 の 11.6.5 節）、空白文字（7.2.3 節）、字形（glyph）。`%` から行末までは「コメント」（7.2.4 節）、図面の引出線などと、文書やサイトの著作権・利用の条件の注記（notice）は「注記」。表示・印刷を切り替える OCG（optional content group、8.11 節）は図面モデルのレイヤにし、その組み合わせでの表示は OCMD（optional content membership dictionary、8.11.2.2 節）で扱う |
| 公開サンプル | 誰でも入手できる公開ファイル。受領図面は含めず、リポジトリに入れる場合は[ライセンスと大きさの条件](../samples/README.md#入れてよいもの)に従う |

## 辞書と規則を直す

- 一意に決まる表記は `prh.yml` に規則と `specs`（修正前後の例）を書く。文脈で選ぶ語はこの文書に使い分けを残し、確実に判別できる場合だけ辞書にも加える。prh は読み込み時に `specs` を検査する。
- Markdown は[文法と表記の規則](../.textlintrc.yml)で検査し、`npm run fix:text` で修正できる。Rust・TOML・YAML は[辞書だけで検査](../.textlintrc.code.yml)し、文字列やテストデータを確認して手で直す。英語の語の規則は後ろに和文が続く場合に当てる。
- 固有名詞・原典の題名の例外は[許す語の一覧](../.textlint-allow.yml)に理由を添える。Markdown の一部分だけ規則を外すときは `<!-- textlint-disable 規則の名前 -->` と `<!-- textlint-enable -->` で囲む。
