# 旧版の赤入れをレビュー文書に移す

旧版の `zumen-markup` バージョン 1 の JSON、その JSON が指す図面、対象とビューの対応表を用意します。コマンドは手元で図面の SHA-256 を旧版の記録と比較し、一致した図面の `v2:` ハッシュを新しい文書の対象に記録します。[旧版の書式](https://github.com/zumen-jp/zumen-legacy/blob/7c1c400e9791bd60f4a5bba355ca90362ad607c2/docs/markup.md)・[現行の書式](decisions/0218-review-document-and-ops.md)

受け取った図面と旧版の JSON は、リポジトリの外のフォルダー（例: `../review-work/`）に置いてください。対応表と移した文書も同じフォルダーに置きます。

## 対応表を作る

元の図面を現行の `open`・`drawing` で開き、用紙と空間の ID を確認します。旧版の `view` ごとに同じ範囲を表す現行の用紙か空間を選び、次のように `mapping.toml` に書きます。この例の ID と数は、実際の図面で確かめた値に置き換えます。コマンドは図面を開かないので、ID が図面にあるかを確かめません。

```toml
target = "plan"
default_view = "sheet/0"

[views]
"二階平面図" = "sheet/h12"
Model = { view = "space/0", scale = 0.001, offset = [35000, 120000] }

[topic_ids]
"指摘-1" = "00000000-0000-4000-8000-000000000001"
```

- `target` は新しい文書内でその図面に付ける ID です。
- `views` は、元の `view` の値を現行の用紙・空間に結びます。元の項目が `view` を省略している場合だけ `default_view` を使います。
- 現行の点は「旧版の点 × `scale` + `offset`」です。`scale` には正の数、`offset` には現行の座標の 2 つの数を書きます。ID だけを書けるのは、JWW の図面の用紙（`sheet/` で始まる ID）だけです。この場合だけ、旧版と現行の座標系が同じと確かめています。ほかの形式とビューで ID だけを書くと、コマンドは止まります。座標が同じと確かめたときは `scale = 1`・`offset = [0, 0]` と書きます。
- `topic_ids` は省略できます。旧版の `finding` の ID が UUID ならその ID を使い、ほかは図面の SHA-256 と項目の ID から UUID を決めます。同じ旧版の文書からは、何度移しても同じ UUID になります。外部の BCF の Guid に合わせるときなどは、旧版の項目の ID ごとに UUID を書くと、それを優先します。旧版にない ID を書くと、コマンドは止まります。2D の場所には元の項目の ID が残ります。
- 同じ図面に対する別の旧版の文書で、同じ項目の ID を使っていると、指摘の UUID が重なります。それらの文書をまとめるときは、`topic_ids` で別の UUID を指定します。

### 縮尺と移動を決める

旧版と現行で、同じ図形の 2 点（線の端点など）の座標を読みます。旧版の座標は、旧版で同じ図面を開いて読みます。現行の座標は、`entities` の `from` にその用紙か空間の ID を指定して読みます。旧版の 2 点を `(x1, y1)`・`(x2, y2)`、現行の 2 点を `(X1, Y1)`・`(X2, Y2)` とすると、`scale` は 2 点の距離の比（現行 ÷ 旧版）、`offset` は `[X1 - scale * x1, Y1 - scale * y1]` です。離れた 3 点目でも、写した点が現行の点と合うことを確かめます。

旧版は DXF・DWG のモデル空間を mm に直し、原点から遠い図面では原点を 1 m 単位で寄せていました。現行の空間は図面の単位のままです。たとえば単位が m の図面では `scale` が 0.001 になり、`offset` は旧版が寄せた原点（図面の単位）になります。レイアウトでは、旧版が足していた余白と印刷の原点の差が `offset` に出ます。

## 移行して確かめる

ソースを取得したリポジトリのルートで実行します。入力と出力には、リポジトリの外のパスを指定します。出力先には新しいファイル名を指定します。

```sh
cargo xtask migrate-markup ../review-work/markup.json ../review-work/drawing.dxf ../review-work/mapping.toml ../review-work/review.json
```

図形の件数、指摘の件数、現行のフィールドに直接移せなかった値の件数と元の JSON Pointer が標準エラーに出ます。コマンドは変換結果を `Review::read` で読み直して ID と参照を検査し、成功した文書を保存します。ハッシュの不一致・対応の不足・不正な座標・対応表の誤りの場合は、示された位置や対応表の項目を確認してもう一度実行します。

| 旧版の項目 | 新しい文書で確かめる値 |
| --- | --- |
| `redline`・`cloud` | `markups` の ID・対象・ビュー・写した点の順・文字 |
| `text` | `markups` の写した最初の点と文字列 |
| `photo` | `markups` の写した最初の点と `text` に入る写真の参照。参照先を開く操作は利用側で行います |
| `finding` | `topics` の UUID・状態・作者・日時・題と、2D の場所の ID・写したピン。本文があれば題に使い、省略時は元の項目の ID を使います |

指摘の多角形は、写した頂点の最小・最大で囲む `extent` と、元の頂点を持つ `legacy.points` になります。`scale` と `offset` で写した点の元の値は、図形の `legacy.points`、メモ・写真・指摘の `legacy.position` に残ります。図形と指摘が混在した場合は `/items` を報告し、両方を含めた元の描画順を `legacy_item_order` に旧版の項目の ID で残します。元のビュー名は `legacy.view` でも確認できます。

コマンドが報告した各フィールドの元の値は、対応する文書・対象・図形・指摘の `legacy.` で始まるキーにあります。たとえば `/items/0/entities` は、その項目の `legacy.entities` です。旧版の要素 ID・引き継ぎの記録・線幅・矢印・撮影方向などの固有の値は、用途に応じてこの報告から照合できます。線幅・文字の高さなど用紙の mm の大きさは、写さずに元の値で残ります。

図面の SHA-256 は対象の `legacy.sha256` でも確認できます。`sfc`・`p21`・`sfz`・`p2z` は現行の形式名 `sxf` に合わせ、元の形式名を `legacy.format` に保ちます。ツールの 1 回の入力上限は図面 256 MiB、旧版の JSON 8 MiB、対応表 1 MiB、項目 16,384 件です。対応表に指定する対象とビューの ID は UTF-8 の 1〜1024 バイトです。[決定 0282](decisions/0282-legacy-markup-review-identity.md)
