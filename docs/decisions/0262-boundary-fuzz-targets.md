## 背景

#501 の fuzz の target は、登録した形式と L0 の読み取りと、領域モデルへの移しまでを流す（[0258](0258-fuzz-seeds-and-runs.md)）。利用者が境界に渡したバイト列が通る次の所は、どの target も通らない（#517）。

- 形式の判定、P2Z・SFZ と属性ファイルを結ぶ所、LAS を範囲で読む所
- 領域モデルから応答のメッセージを作る所と、図（線形の図とシーン）を作る所
- 形式でない入力（シーンの文字のフォント・プロファイル・レビューの文書・要求の JSON と色の表）

`xtask/src/fuzz.rs` の検査は、どの target も、テストキットの fuzz の関数（`survives`・`survives_lift`・`survives_with`）を呼ぶことを求める（[0017](0017-format-rights-ledger-and-plugin-sdk.md)）。どの関数も、テストキットが作った文脈（`Cx`）の予算で読み取りを 2 回呼び、結果を比べる。境界では、予算を要求の `budget` で渡し、応答はバイト列で返るので、どの関数にも当たらない。`zumen-sdk` は `zumen-abi` から使われるので、テストキットはセッションを持てない。

0258 は、種を、公開サンプル・適合テストの組の `push` で入れる合成の入力・L0 の攻撃の形・合成の格子の 4 つとする。要求の形は、どの種にもない。

境界を通す target を流すと、適合テストの組の種の 1 つ（升の多い格子の配置を持つ 699 バイトの DXF）で、シーンを作る呼び出しが重くなった。

- 配置をたどる walk（[0159](0159-drawing-walk-placements.md)）は、返す要素を集めて返し、返す要素ごとに `work` を 1 と数える。fuzz の上限（`work` が 2^24）で止まるまでに、1 回の呼び出しが 9 秒ほど掛かり、3 GB ほどのメモリを使った。
- 返す要素を `elements` でも数えると（下の walk の予算）、ネイティブの build では 1 回 1 秒ほどになった。ASan と計装を入れた CI の fuzz の build では、30 秒（fuzz の時間切れ）を超えた。
- 返す要素のない定義の格子も、升ごとに `work` を数えてたどり、上限まで升を回った。

## 選択肢

### target の分け方

1. `open` の target 1 つで、形式でない入力も、図を作る op も呼ぶ。
2. `open` の target に、形式でない入力ごとの target（`font`・`profile`・`review`・`json`）を足す。図を作る op は、`open` と `profile` から呼ぶ。
3. 形式でない入力は、境界を通さず、crate の関数（`Font::parse`・`resolve`・`Review::read`・`zumen_json::parse`）を直に呼ぶ target にする。

### `xtask/src/fuzz.rs` の検査

1. テストキットに、境界の呼び出しを試す関数 `survives_calls` を足す。関数は、テストキットの上限を渡して呼び出しの並びを 2 回作らせ、応答のバイト列の並びを比べる。境界の target も、この関数を呼ぶ。
2. 境界の target を、検査の例外にする。target の名前の一覧を検査に置く。

### 境界の呼び出しの予算

1. テストキットの fuzz の上限（`fuzz_limits`）を、そのまま要求の `budget` に書く。
2. テストキットに、境界の呼び出しの上限（`fuzz_call_limits`）を足す。`fuzz_limits` から、要素・幾何の分割・ほかの繰り返し（`elements`・`segments`・`work`）の上限を小さくしたものにする。
3. 配置をたどる walk の升ごとの費用（配置の道筋・切り抜きの複製と ID の文字列）を下げる（#563）。
4. fuzz の workflow の `-timeout` を上げる。

### 配置をたどる walk の予算

1. 0159 のまま、返す要素を `work` だけで数える。
2. 返す要素を `elements` でも数える。返す要素のない定義（描く順がどの要素も指さない定義）の格子は、升をたどらない。描く順のうち要素の外を指す添字は、空間ごとに一度だけ除き、1 つごとに `work` を 1 と数える。

### 種

1. 0258 の 4 つのままにする。`json` の target は、要求の形を、変異だけで見つける。
2. 適合テストの組の `call` の要求を、1 つずつと、組ごとに並べた配列で、種に足す。`call_text`・`call_hex` で渡す要求のバイト列（読めない要求と、BOM を付けた要求）も、1 つずつ足す。
3. `json` の target にだけ、別の種を書く。

## 決定

target の分け方は選択肢 2、検査は選択肢 1、境界の呼び出しの予算は選択肢 2、walk の予算は選択肢 2、種は選択肢 2 にする。

- 選択肢 2 の分け方では、fuzz が変えるバイト列は、どの target でも、試す読み取りに直に渡る。ほかの入力は、適合テストの組の合成の入力を写した固定の入力にする。選択肢 1 では、1 つのバイト列を文書とフォントとプロファイルに分けることになり、変異の多くが、試す所に届かない。target ごとに、毎晩の時間と、結果の表の行（通った辺と種の数）を持てる。選択肢 3 は、要求を読む所と、応答と図を作る所を通らない。
- 検査を選択肢 1 にすると、どの target も同じ検査を通り、例外の一覧を持たずに済む。予算は、関数が渡す上限から要求の `budget` に書くので、テストキットの上限と食い違わない。関数は呼び出しを閉包で受け、応答をバイト列で比べるので、`zumen-sdk` は `zumen-abi` に依らない。選択肢 2 は、例外の target が、上限と 2 回の比べ方を各自で持つことになる。
- 境界の呼び出しの予算を選択肢 2 にすると、境界の target は、1 つの入力で多くの op を呼んでも、どの呼び出しも小さい作業量で止まる。形式ごとの target は `fuzz_limits` のままなので、読み取りを試す深さは変わらない。境界の target が試すのは、判定から応答を作るまでの道で、大きい図面を読み切ることではない。予算で止まる道は、上限が小さいほど多く通る。選択肢 1 は、上の種で時間切れになる。選択肢 3 は升ごとの費用を下げるが、ほかの op の繰り返しの重さは残り、時間切れにならないことを保てない。#563 で、既定の予算でのメモリと合わせて進める。選択肢 4 は workflow を変え、止まらない繰り返しを見つける力が落ちる。
- walk の予算を選択肢 2 にすると、集める要素の数が `elements` の上限で止まり、集めたメモリが上限に比例する。返す要素は、どの領域モデルでも、要素として `elements` で数えるものである（[0010](0010-budget-by-work.md)）。要素のない定義の格子は、どの升でも何も返さないので、たどらなくても、返す要素・ID・診断は変わらない。図面モデルのバイナリは描く順の添字を確かめずに読むので、描く順が要素の外だけを指す定義も、要素のない定義とする。要素の外を指す添字を升ごと・ビューごとに見直すと、`work` を数えずに、升の数と添字の数の積だけ回る。空間ごとに一度だけ除いて数えれば、繰り返しは回数で数えられ、作業量は添字の数と升の数の和になる。選択肢 1 は、`work` の上限まで要素を集め、上限で止まる前にメモリを使い果たす。
- 種を選択肢 2 にすると、`json` の target が、どの op の要求からも始められる。配列の種は、`open` から読む op までの並びを試す。要求は、適合テストの組の合成の入力なので、0258 の権利の考え（受け取った図面を種にしない、表示を求める公開サンプルは出所を添える）に何も足さない。選択肢 3 は、どの target にも同じ種を書く今の仕組みを分けるのに、得るものがない。

境界を通す target は、次のことを確かめる。

- どの要求の予算も、テストキットの境界の呼び出しの上限（`fuzz_call_limits`）にする。受け取った要求（`json` の target）も、`budget` を替え、時計で止める `time_limit_ms` を除く。止まる所が実行ごとに変わり、2 回で比べられないためである。
- 2 回呼んで、応答の JSON と取り出したバイナリの結果のバイト列を呼んだ順に並べたものが、同じになる（`survives_calls`）。
- 応答が JSON として読め、成功したときだけ `result` を持ち、失敗した応答は理由の診断を持つ。`blobs` の結果は、どれも取り出せ、記録した大きさと同じで、シーンの blob は `zumen` のリーダーで読める。

target ごとの中身と、固定の入力は、`fuzz/README.md` と `fuzz/src/lib.rs` にある。

## 影響

- 境界を通す 5 つの target が、毎晩と PR の fuzz で流れる。target の一覧は `cargo fuzz list` から取るので、workflow は変えない。PR の実行は、target が 5 つ増えた分、長くなる。
- 境界を通す target は、1 つの入力で多くの op を呼ぶので、入力ごとの時間が、ほかの target より長い。1 回の呼び出しは境界の呼び出しの上限で止まるが、呼び出しの数だけ掛かる。`open` の target は、書き直した文書（図面モデルのバイナリと DXF）をシーンにせず、シーンにする空間と用紙の数にも上限を置く。
- テストキットの関数が 2 つ（`survives_calls`・`fuzz_call_limits`）増える。足すだけなので、ほかの関数とプラグインに影響しない（[0015](0015-add-only-boundary-and-version-floors.md)）。
- 配置をたどる walk は、返す要素を `elements` でも数える。升の多い格子の配置は、`work` より先に `elements` の上限で止まることがある。返す要素・ID・診断は、上限で止まらない図面では変わらず、適合テストの応答も変わらない。描く順のうち要素の外を指す添字（図面モデルのバイナリで作れる）は、その数だけ `work` を多く使う。0159 の予算の項と影響の節の上限を、この記録で改める。既定の予算（`elements` が 1 億）では、止まるまでのメモリがまだ大きく、#563 で直す。
- 種は、適合テストの組の要求の分だけ増える。どの target にも同じ種を書くので、ほかの target の起動の時間も、その分だけ延びる。0258 の決定の、種の 2 つ目（適合テストの組の `push` で入れる合成の入力）を、この記録で改める。
