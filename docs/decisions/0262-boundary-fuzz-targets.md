# 0262: 境界を通す fuzz の target を足し、テストキットの呼び出しの関数で確かめ、適合テストの組の要求も種にする

| 項目 | 内容 |
| --- | --- |
| 日付 | 2026-11-05 |
| 状態 | 採用 |

## 背景

#501 の fuzz の target は、登録した形式と L0 の読み取りと、領域モデルへの移しまでを流す（[0258](0258-fuzz-seeds-and-runs.md)）。利用者が境界に渡したバイト列が通る次の所は、どの target も通らない（#517）。

- 形式の判定、P2Z・SFZ と属性ファイルを結ぶ所、LAS を範囲で読む所
- 領域モデルから応答のメッセージを作る所と、図（線形の図とシーン）を作る所
- 形式でない入力（シーンの文字のフォント・プロファイル・レビューの文書・要求の JSON と色の表）

`xtask/src/fuzz.rs` の検査は、どの target も、テストキットの fuzz の関数（`survives`・`survives_lift`・`survives_with`）を呼ぶことを求める（[0017](0017-format-rights-ledger-and-plugin-sdk.md)）。どの関数も、テストキットが作った文脈（`Cx`）の予算で読み取りを 2 回呼び、結果を比べる。境界では、予算を要求の `budget` で渡し、応答はバイト列で返るので、どの関数にも当たらない。`zumen-sdk` は `zumen-abi` から使われるので、テストキットはセッションを持てない。

0258 は、種を、公開サンプル・適合テストの組の `push` で入れる合成の入力・L0 の攻撃の形・合成の格子の 4 つとする。要求の形は、どの種にもない。

## 選択肢

### target の分け方

1. `open` の target 1 つで、形式でない入力も、図を作る op も呼ぶ。
2. `open` の target に、形式でない入力ごとの target（`font`・`profile`・`review`・`json`）を足す。図を作る op は、`open` と `profile` から呼ぶ。
3. 形式でない入力は、境界を通さず、crate の関数（`Font::parse`・`resolve`・`Review::read`・`zumen_json::parse`）を直に呼ぶ target にする。

### `xtask/src/fuzz.rs` の検査

1. テストキットに、境界の呼び出しを試す関数 `survives_calls` を足す。関数は、fuzz の上限（`fuzz_limits`）を渡して呼び出しの並びを 2 回作らせ、応答のバイト列の並びを比べる。境界の target も、この関数を呼ぶ。
2. 境界の target を、検査の例外にする。target の名前の一覧を検査に置く。

### 種

1. 0258 の 4 つのままにする。`json` の target は、要求の形を、変異だけで見つける。
2. 適合テストの組の `call` の要求を、1 つずつと、組ごとに並べた配列で、種に足す。
3. `json` の target にだけ、別の種を書く。

## 決定

target の分け方は選択肢 2、検査は選択肢 1、種は選択肢 2 にする。

- 選択肢 2 の分け方では、fuzz が変えるバイト列は、どの target でも、試す読み取りに直に渡る。ほかの入力は、適合テストの組の合成の入力を写した固定の入力にする。選択肢 1 では、1 つのバイト列を文書とフォントとプロファイルに分けることになり、変異の多くが、試す所に届かない。target ごとに、毎晩の時間と、結果の表の行（通った辺と種の数）を持てる。選択肢 3 は、要求を読む所と、応答と図を作る所を通らない。
- 検査を選択肢 1 にすると、どの target も同じ検査を通り、例外の一覧を持たずに済む。予算は、関数が渡す fuzz の上限から要求の `budget` に書くので、テストキットの上限と食い違わない。関数は呼び出しを閉包で受け、応答をバイト列で比べるので、`zumen-sdk` は `zumen-abi` に依らない。選択肢 2 は、例外の target が、上限と 2 回の比べ方を各自で持つことになる。
- 種を選択肢 2 にすると、`json` の target が、どの op の要求からも始められる。配列の種は、`open` から読む op までの並びを試す。要求は、適合テストの組の合成の入力なので、0258 の権利の考え（受け取った図面を種にしない、表示を求める公開サンプルは出所を添える）に何も足さない。選択肢 3 は、どの target にも同じ種を書く今の仕組みを分けるのに、得るものがない。

境界を通す target は、次のことを確かめる。

- どの要求の予算も、テストキットの fuzz の上限にする。受け取った要求（`json` の target）も、`budget` を替え、時計で止める `time_limit_ms` を除く。止まる所が実行ごとに変わり、2 回で比べられないためである。
- 2 回呼んで、応答の JSON と取り出したバイナリの結果のバイト列を呼んだ順に並べたものが、同じになる（`survives_calls`）。
- 応答が JSON として読め、成功したときだけ `result` を持ち、失敗した応答は理由の診断を持つ。`blobs` の結果は、どれも取り出せ、記録した大きさと同じで、シーンの blob は `zumen` のリーダーで読める。

target ごとの中身と、固定の入力は、`fuzz/README.md` と `fuzz/src/lib.rs` にある。

## 影響

- 境界を通す 5 つの target が、毎晩と PR の fuzz で流れる。target の一覧は `cargo fuzz list` から取るので、workflow は変えない。PR の実行は、target が 5 つ増えた分、長くなる。
- 境界を通す target は、1 つの入力で多くの op を呼ぶので、入力ごとの時間が、ほかの target より長い。1 回の呼び出しは fuzz の上限で止まるが、呼び出しの数だけ掛かる。`open` の target は、書き直した文書（図面モデルのバイナリと DXF）をシーンにせず、シーンにする空間と用紙の数にも上限を置く。
- テストキットの関数が 1 つ増える。足すだけなので、ほかの関数とプラグインに影響しない（[0015](0015-add-only-boundary-and-version-floors.md)）。
- 種は、適合テストの組の要求の分だけ増える。どの target にも同じ種を書くので、ほかの target の起動の時間も、その分だけ延びる。0258 の決定の、種の 2 つ目（適合テストの組の `push` で入れる合成の入力）を、この記録で改める。
