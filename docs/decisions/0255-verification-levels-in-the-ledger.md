# 0255: 形式の確かめた度合いは、もっとも強い方法の段と範囲を台帳と形式の文書に置き、API の capabilities には出さない

| 項目 | 内容 |
| --- | --- |
| 日付 | 2026-11-03 |
| 状態 | 採用 |

## 背景

[決定 0254](0254-parallel-agents-and-cross-review.md) で、形式ごとに、読みと書きを確かめた度合いを `synthetic`・`external`・`application` の段で示すと決めた。台帳のフィールドと検査は別の PR で足すとした（#502）。次の 3 つは決めていない。

- **段が何を表すか。** 1 つの形式の中でも、規則ごとに確かめ方が違う。DXF・DWG の書きは、引出線を書き戻したファイルだけを AutoCAD 2027 で開いた（#345）。点・寸法・表を書き戻したファイルは開いていない（#342・#314）。
- **API に出すか。** `capabilities` は、コアのバージョンと、使える op・形式を返す（[決定 0015](0015-add-only-boundary-and-version-floors.md)）。形式は、図面の 4 つ、土木・地理と点群の 8 つ、入れたプラグインの形式を、`read`・`write` の真偽で返す。wasm のモジュールは、持つ形式だけを返す（[決定 0221](0221-wasm-modules.md)）。IFC・BCF・IDS・電子納品の管理ファイル・工事写真・ボーリング交換用データ・表などは、この一覧に載らない。応答は、適合テスト（`bindings/conformance/cases/capabilities.json`）のハッシュに入る。確かめた度合いは、#503・#504・#505 の確かめる作業で、コアのコードを変えずに上がる。
- **`verify` を分けるか。** 台帳の `verify` は、照合に使うソフトの一覧で、外部の実装（ezdxf・IfcOpenShell など）と、その形式の基準になるソフト（Jw_cad・SXF ブラウザなど）が混ざっている。決定 0254 は、`verify` に載っていることでは段を決めないとした。

## 選択肢

段が何を表すか。

1. 確かめた方法のうち、もっとも強いもの。範囲を一緒に書く。
2. 形式の規則のすべてに言える、もっとも弱いもの。
3. 規則か要素の種類ごとに段を持つ。

API に出すか。

1. 台帳（`formats/ledger.toml`）に置き、生成する一覧（`docs/formats/README.md`）と形式の文書に出す。`capabilities` には出さない。
2. 1 に加えて、`capabilities` の形式に、読みと書きの段のフィールドを足す。台帳から生成した表をコアに入れる。
3. 1 に加えて、形式の文書の URL を `capabilities` で返す。

`verify` をどうするか。

1. 照合に使う候補の一覧のまま残し、段の根拠にしない。
2. 外部の実装と、基準になるソフトの 2 つのキーに分ける。

## 決定

段・API・`verify` のどれも、選択肢 1 を採る。

- **段は、もっとも強い方法。** 段は、根拠のうちもっとも強い種類で決める。基準になるソフトで開いていれば `application`。自前で作っていないファイル（公開サンプル・受け取った図面・外部の実装が書いたもの）を読み、外部の実装が読んだ値か、そのファイルに添えられた値と照らしていれば `external`。どれもなければ `synthetic`。公開サンプルと受け取った図面は、読んだだけでは段を上げず、読んだことを範囲に書く。テストの中で自前で作ったファイル（zumen かテストのコードが書いたもの）を外部の実装にも読ませて照らしたことは、読みでは `external` に数えない（決定 0254 の表）。書きの根拠は、書いたファイルを外部の実装が読み、読んだ値が書いた値と合ったことと、ソフトで開いたことだけにする。読んだファイルの出どころは検査で確かめられないので、範囲に書く。その方法で確かめたのが一部の規則だけでも、その段にし、範囲を一緒に書く。生成する一覧と形式の文書にも、そう書く。
  - もっとも弱い段（選択肢 2）では、ほとんどの形式が `synthetic` になり、AutoCAD で開いたことのような、実際に確かめたことが見えない。
  - 規則ごとの段（選択肢 3）は、形式の文書が規則ごとに書く。台帳で同じことを持つと、2 か所を合わせ続けることになる。決定 0254 が許すバージョンごとの段は、要るときに台帳のフィールドを足す。
- **台帳。** 形式ごとに `[formats.<キー>.read]`・`[formats.<キー>.write]` を置き、段・確かめた範囲・確かめた日と、根拠（公開サンプル・受け取った図面の種類と件数・ファイルに添えられた値・外部の実装とソフトのバージョン）を書く。書き方は `formats/README.md` にある。
- **検査。** `cargo xtask codegen` は、次を拒む。
  - 向きと根拠に合わない段、`core` でない形式の段、公開サンプルの台帳にない `samples/` の道筋。
  - 実装を名乗る crate（`[package.metadata.zumen]`）の形式で、読みにも書きにも段がないもの。
  - 段を持つ形式の文書に「確かめた度合い」の節がないもの。節の表が台帳と違うか、形の崩れた行があるもの。

  `zumen-abi` のテストは、`capabilities` の `read`・`write` と、台帳の段のある向きを照らす。
- **capabilities には出さない。** 理由は次のとおり。
  - 段は、確かめる作業で、コアと別に上がる。API に出すと、段を上げるたびに `capabilities` の応答と適合テストのハッシュが変わる。確かめる作業が、API の契約の変更と絡む。
  - `capabilities` の形式は、半分ほどの形式しか載せない。出しても、残りの形式の段を返せない。
  - 段だけでは範囲が分からない。アプリケーションが段で振る舞いを変えると、一部しか確かめていない `application` を、全部を確かめたものとして扱う。
  - API は、1.0 から足すだけになる（決定 0015）。今の段の意味でフィールドを足すと、段や範囲の表し方を後で変えにくい。
- **`verify` は分けない。** `verify` は照合に使う候補の一覧のままにし、段の根拠にしない。照らした外部の実装とソフトは、`read`・`write` の `implementations`・`software` にバージョンと一緒に書く。同じツールでも、外部の実装として照らすか、基準になるソフトとして開くかは、確かめ方で決まる。候補の段階で分けると、確かめたときの分け方と食い違う。
- **見直すとき。** アプリケーションが、確かめた度合いを API から引いて利用者に示す必要が出たら、API の選択肢 2 を新しい記録で決める。そのときは、範囲を返す形と、段を上げたときに適合テストのハッシュの一覧を作り直す手順も決める。

## 影響

- 利用者とエージェントは、確かめた度合いを、生成する一覧と形式の文書で見る。
- 形式を足すときと、確かめた度合いを上げるときは、台帳の段と形式の文書の節を同じ PR で直す。
- 段が上がっても、API の応答と適合テストのハッシュは変わらない。
