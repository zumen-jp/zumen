# 0253: 複数のエージェントが並行して進め、互いに確かめ、人を待つのは人にしかできないことに限る

| 項目 | 内容 |
| --- | --- |
| 日付 | 2026-11-03 |
| 状態 | 採用 |

## 背景

作業は、[決定 0174](0174-plan-in-issues.md) の選び方で、主にエージェントが進めている。2026-10-24 からの 10 日で、形式は約 25、境界の op は 31、決定の記録は 252 件になった。利用者は、複数のエージェントを同時に動かし、互いに確かめさせて、広げる速さを保つことを選んだ。人の判断は、できるだけ待たない。

この進め方で、次の問題が出た。

- **待ちがたまり、確かめていない形式が増えた。** 選び方は、待ちのラベルのない最初の葉を選ぶ。待ちに当たると飛ばして次の形式へ進むので、待ちの issue が 27 件（試料 13・判断 9・検証環境 5）たまった。J-LandXML・LAS・CityGML などは、実物のファイルを読まずにマージした。#412 は、使える公開サンプルを見つけたあとも、待ちのラベルのために取り込まれなかった。
- **自前の試験だけでは、誤りが見つからなかった。** 組み直した R2004・R2010・R2018 の DWG は、2026-11-02 に AutoCAD 2027 で開くまで、どれも図面ファイルとして無効と判定されていた（#345）。自前の往復の試験は通っていた。書く側と同じ読みで作った試験は、仕様の読み違いを見つけない。
- **確かめた度合いが、読む人に分からない。** `docs/formats` の文書は、実物で確かめた規則と、仕様だけから書いた規則を分けていない。
- **別の目が入っていない。** PR の多くは、開いてから数分でマージした。PR を通さずに main に入れたコミットが 88 件あった。決定の記録はマージで採用になるので、別の目を通らずに採用になっていた。
- **「待ち: 判断」の一部は、エージェントが決められた。** 9 件のうち 3 件は、公開の API の形や、変換で書く形式のような設計の選択だった。
- **誰が着手したかが分からない。** エージェントは同じ GitHub のアカウントで動くので、ラベルと本文だけでは、着手した者を見分けられない。「作業中」なのに本文が未着手のままの issue もある。
- **並行してマージすると、main が壊れうる。** 必須の検査は、最新の main を取り込むことを求めていない。それぞれの PR の CI は古い main の上で通るので、決定の番号・診断の code・生成物のずれが、main に入ってから見つかる。
- **決定の記録が、実装の細部の記録になった。** 0023〜0104 の 82 件はすべて AutoCAD の系統で、その多くは欄の符号化の細部だった。大事な判断が埋もれる。
- **形式や用途ごとの op が増えた。** `ids_check`・`bcf_read`・`photo`・`sheet`・`boring`・`delivery_check` のように、領域の op で表せたかもしれないものが、境界に足されている。
- **受け取ったファイルを読む所の守りが、形式の数に追いついていない。** fuzz の対象は 4 つの形式だけで、CI でも流していない。浮動小数の足し算で数える繰り返しが止まらない誤り（#486）は、マージの後に見つかった。

## 選択肢

1. 段階に関門を置き、前の段階を確かめるまで次の形式に進まない。確かめた順に進むが、同時に動けるエージェントの数を生かせず、利用者の選んだ速さと合わない。
2. 今のまま進める。速いが、待ちと確かめていない形式がたまり続け、誤りは実際のソフトで開くまで見つからない。
3. 広げるのは続ける。人を待つのは人にしかできないことに限り、ほかの判断はエージェントが決める。人の確認の代わりに、別のエージェントの確認と、外部の実装・公開サンプルとの照合を入れる。確かめた度合いを形式ごとに示し、確かめる作業を広げる作業と並べて進める。

## 決定

選択肢 3 を選ぶ。決定 0174 のうち、待ちのラベルの意味、待ちに当たったときの扱い、着手の名乗り方と古い着手の引き継ぎを、この決定で変える。決定 0171 のうち、ライセンスがはっきりしない公開サンプルの扱いも変える。木・優先順・依存の仕組みは変えない。

### 人を待つもの

人を待つのは、次のことだけにする。

- 権利者への問い合わせ、契約・規約への同意（同意の要る道具を入れることを含む）、費用のかかること（規格の書籍の購入など）。
- 権利の判断。台帳の `rights` を `unknown`・`permission` から `public` に変えること、NC・ND や利用規約の読みで採否が決まるもの。
- アカウント・署名の鍵・secrets、パッケージの名前の確保と公開（`v*` のタグの push・GitHub の Release・レジストリへの公開）。
- GitHub の設定の変更。設定は、GitHub の画面か API でだけ変えるもので、ルールセット・ブランチの保護・Actions の権限・secrets と変数・環境・Webhook・アプリ・公開の範囲を指す。
- workflow の変更のうち、`permissions` を広げる・secrets を使う・権限つきで動く発火の条件（`pull_request_target`・`workflow_run` など）を足す・公開の手順（`release.yml`）を変えるもの。ほかのリポジトリのファイル（workflow の普通の変更、`deny.toml`・`rust-toolchain.toml` など）は、PR で変えて互いに確かめる。
- このリポジトリの外への書き込みと送信。ほかのリポジトリへの issue・PR・コメント、メール、外部のサービスへのファイルの送信。上流への報告は、文案を issue に書いて利用者に頼む。
- 利用者の手元にしかないものを用意すること。受け取った図面を `ZUMEN_SAMPLES` に置く、ライセンスの要るソフトを使えるようにする、アプリの利用を許す。
- この一覧、下の「互いに確かめる」、`AGENTS.md` の「範囲と権利」「図面と秘密」「守る約束」を緩める変更。

ほかの判断（設計・優先順・仕様の読み方・`AGENTS.md` の規則の範囲での依存の選択など）は、エージェントが選択肢と理由を書いて決める。`site/` の変更はマージで公開されるが、パッケージの公開に当たらないので、PR で互いに確かめて進める。

### ラベル

- **「待ち: 利用者」。** 人を待つものに付ける。利用者は、このラベルで、自分を待つものを一覧する。今の「待ち: 判断」を、この名前に変える。利用者の判断のほか、利用者の行い（問い合わせ・費用・公開・設定など）を待つものも含めるためである。
- **「待ち: 試料」「待ち: 検証環境」。** 試料と検証環境を待つものに付ける。エージェントが待ちを減らす対象にする。利用者の手元のものが要るなら、「待ち: 利用者」も付ける。
- ラベルの種類と説明は、決定の記録で決めてから変える。

### 待ちに当たったら

飛ばす前に、待ちを減らす。待ちを減らす作業も、着手と同じく名乗る。

- **試料。** 決定 0171 の条件に合う公開サンプルを探す。[決定 0019](0019-coordinate-systems-and-gsi-data.md) と台帳で入れないとしたもの（国土地理院のデータなど）は除く。外部の実装で読めるなら、その実装と照らす。
- **検証環境。** 確認の束を作り、issue に置く。束に入れるのは、試験で作るファイルか `samples/` のファイルと、それを作るコマンド・開く手順・期待する結果だけにする。受け取った図面と、そこから作ったファイル・名前・画面の写しは、公開の issue に置かない。利用者の手元のソフトは、そのセッションで利用者がアプリの利用を許したときだけ、束のファイルを開くのに使う。
- **判断。** 人を待つものに当たらなければ、エージェントが決める。決定の記録にする判断は、その PR に選択肢と理由を書き、マージの後にラベルを外す。記録にしない判断は、issue のコメントに選択肢と理由を書いてから外す。
- **試みた記録。** 試みた日と、探した所・結果を issue に書く。それより後に新しい手がかりがなければ、次からは飛ばしてよい。

### 着手の名乗り

- 着手するときは、issue のコメントで名乗る（ブランチ・worktree・時刻）。名乗ったあとに読み直し、いちばん早い名乗りだけが進める。後の側は、名乗りを取り下げて別の issue を選ぶ。
- 名乗りが通ったら、ラベル「作業中」を付け、本文の「着手・引き継ぎ」を書く。
- 名乗りから 24 時間、PR・ブランチ・名乗りの更新がなければ、引き継ぐと名乗って引き継げる。
- 同じ issue か、同じ crate・同じ形式の文書を主に変える開いた PR があれば、着手しない。一覧・台帳・生成物（決定の一覧・`catalog/`・スキーマの版・適合試験のハッシュの一覧・`Cargo.lock`）が重なるのは構わず、マージの前に解く。

### 互いに確かめる

- PR は、作った側と別の確かめる側が確かめてからマージする。確かめる側は、作った側の会話を引き継がないエージェント（新しいセッションか、会話を渡さないサブエージェント）か、人にする。
- 依頼には、PR の番号と確かめる観点だけを渡し、作った側の見立ては渡さない。確かめる側は読むだけにし、自分で直さない。
- 観点は、差分と issue の完了の条件、`AGENTS.md` の「範囲と権利」「図面と秘密」「守る約束」（決定性・黙って捨てない・ID の契約・信用しない入力・境界の互換）、仕様の節、試験、依存のライセンス、表記とする。決定の記録なら、選択肢が実際にあるか、採用済みの決定と食い違わないかも見る。
- 結果は、確かめた head の commit と確かめる側の種類を添え、手を加えずに全文を PR のレビューのコメントに貼る。
- 作った側は、指摘のすべてに答える（直すか、直さない理由を書く）。権利・秘密・境界の互換・ID・採用済みの決定との食い違いの指摘を直さずにマージするなら、別の確かめる側にも見せる。
- 直したあとの差分も、確かめる側に見せる。
- 新しい形式の権利を `public` とする PR は、確かめる側を 2 つにし、別々に確かめる。
- CI の通過は、この確認の代わりにしない。

### マージ

- main へは、PR を通さずに push しない。利用者は 2026-11-03 に、ルールセットの管理者の迂回を残すと決めたので、この規則は手順で守る。
- マージの前に、最新の `origin/main` を取り込み、生成物を作り直し、CI を通し直す。
- 指摘に答え、直したあとの差分の確認が済み、CI が通ったら、squash merge してブランチを消す。

### 形式を足すときの完了の条件

形式・版・向き（読む・書く）を足す issue は、次をそろえて閉じる。ほかの変更は、変えた所の試験を足し、確かめた度合いの節を直す。

- 外部の実装があれば、その実装と結果を照らす試験。外部の実装は、Cargo の依存（dev を含む）にせず、ソースもバイナリもリポジトリに入れず、別に入れたプログラムとして呼ぶ（[決定 0011](0011-bindings-through-ffi.md) の道具の表）。入っていない環境では試験を飛ばし、指定したときと毎晩の CI で流す。照らして食い違ったら、仕様と、出力・診断を比べて調べる。外部の実装のソースは、寛容なライセンスのものだけを読む。
- 決定 0171 の条件に合う公開サンプルがあれば、`samples/` に足して読む試験。なければ、探した所を形式の文書に書く。
- fuzz の対象と、テストキットの予算・ID の契約試験（[決定 0010](0010-budget-by-work.md)・[0017](0017-format-rights-ledger-and-plugin-sdk.md)）。
- 形式の文書の、確かめた度合いの節。

### 確かめた度合い

形式ごとに、読みと書きを分けて、次の 3 つの段で示す。版ごとに分けてよい。段の名前は、台帳の今の語（`basis` の `spec`、キーの `samples`・`verify`）と重ならず、保証と取られない語にした。

| 段 | 読む向き | 書く向き |
| --- | --- | --- |
| `synthetic` | 仕様と、試験の中で作ったファイルだけで確かめた | 書いたファイルを、自前の読み取りだけで確かめた |
| `external` | 公開サンプル・受け取った図面・外部の実装との照合で確かめた | 書いたファイルを、外部の実装が誤りなく読めた |
| `application` | その形式の基準になるソフト（作るソフトか、受け取る側のソフト）で開いた結果と照らした | 書いたファイルを、基準になるソフトで開いて確かめた |

- 受け取った図面で確かめたことは、件数と種類だけを書き、ファイル名・顧客の名前・中身を書かない。
- 段は、実際に確かめたことで決める。台帳の `verify` に載っていることでは決めない。
- `synthetic` の段の規則は、読む人に確かめ済みと取られないように書く。台帳の欄と検査は、別の PR で足す。

### 確かめる作業を並べて進める

- 確かめていない形式を確かめる issue を、段階ごとに作り、段階の子の上のほうに置く。広げる作業を止めず、待ちのない確かめる作業が先に選ばれるようにする。
- 不確実性の大きい試作（3D の形状と開口のブーリアンなど）は、試料の条件をゆるめてでも先に進める。日本のソフトの試料は、確かめた度合いを上げるときに使う。

### 公開サンプルの扱い

[決定 0171](0171-public-samples-in-git.md) は、ライセンスがはっきりしない公開サンプルを、足さずに利用者に尋ねるとした。これを、足さずに理由を issue に書くことに変える。どうしても足したいときは、権利者への問い合わせとして利用者に頼む。

### 境界の整理

- 1.0 より前は、[決定 0015](0015-add-only-boundary-and-version-floors.md) のとおり、境界を整理するために壊してよい。壊す判断は決定の記録にし、壊す PR は、タイトルの種別に `!` を付け（`feat(abi)!: …`）、本文に移り方を書く。リリースノートは、PR のタイトルから作る。
- ID の規則は、この例外に入らない。
- 形式や用途ごとの op を足す前に、領域の op（`drawing`・`building`・`civil`・`geo`・`pointcloud` など）で表せないかを確かめる。

### 決定の記録にするもの

決定の記録は、実際に選択肢があり、境界・ID・層とモデル・依存・権利・形式をまたぐ振る舞い・作業の進め方のどれかに関わる判断に限る。形式ごとの欄や符号化の細部は、`docs/formats` に書く。

## 影響

- ラベル「待ち: 判断」を「待ち: 利用者」に名前を変え、説明を直す。今の issue を見直し、エージェントが決められるものからラベルを外す。「待ち: 試料」「待ち: 検証環境」のうち、利用者の手元のものを待つものに「待ち: 利用者」を足す。
- `AGENTS.md`・`docs/work.md`・`docs/decisions/README.md`・`docs/style.md` の用語集・`CONTRIBUTING.md`・issue と PR のひな形を、この決定に合わせる。
- 確かめる作業の issue（#501〜#505）と、旧版を置き換える issue（#506・#507）を、段階の子に足す。
- 1 つの変更にかかる手間は増えるが、同時に動くエージェントが受け持つ。人が見るのは、「待ち: 利用者」の issue だけになる。
- マージの前に最新の main を取り込むので、並行する PR は順にマージされる。ルールセットで最新の main を求めれば仕組みで守れるが、設定の変更なので利用者が決める。
- 決定 0174 の待ちと着手の扱い、決定 0171 のライセンスがはっきりしない公開サンプルの扱いを、この決定で変える。それぞれの記録から、この決定にリンクする。
