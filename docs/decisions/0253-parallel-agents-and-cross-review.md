# 0253: 複数のエージェントが並行して進め、互いに確かめ、人を待つのは人にしかできないことに限る

| 項目 | 内容 |
| --- | --- |
| 日付 | 2026-11-03 |
| 状態 | 採用 |

## 背景

作業は、[決定 0174](0174-plan-in-issues.md) の選び方で、主にエージェントが進めている。2026-10-24 からの 10 日で、形式は約 25、境界の op は 31、決定の記録は 252 件になった。利用者は、複数のエージェントを同時に動かし、互いに確かめさせて、広げる速さを保つことを選んだ。人の判断は、できるだけ待たない。

この進め方で、次の問題が出た。

- **待ちがたまり、確かめていない形式が増えた。** 選び方は、待ちのラベルのない最初の葉を選ぶ。待ちに当たると飛ばして次の形式へ進むので、待ちの issue が 27 件（試料 13・判断 9・検証環境 5）たまった。J-LandXML・LAS・CityGML などは、実物のファイルを読まずにマージした。
- **自前の試験だけでは、誤りが見つからなかった。** 組み直した R2004・R2010・R2018 の DWG は、2026-11-02 に AutoCAD 2027 で開くまで、どれも図面ファイルとして無効と判定されていた（#345）。自前の往復の試験は通っていた。書く側と同じ読みで作った試験は、仕様の読み違いを見つけない。
- **確かめた度合いが、読む人に分からない。** `docs/formats` の文書は、実物で確かめた規則と、仕様だけから書いた規則を分けていない。
- **別の目が入っていない。** PR の多くは、開いてから数分でマージした。PR を通さずに main に入れた変更もあった。決定の記録はマージで採用になるので、別の目を通らずに採用になっていた。
- **「待ち: 判断」の多くは、エージェントが決められた。** 公開の API の形や、変換で書く形式のような設計の選択も、利用者の判断として待っていた。
- **決定の記録が、実装の細部の記録になった。** 0023〜0104 の 82 件は、AutoCAD の系統の欄の符号化などの細部で、大事な判断が埋もれる。
- **受け取ったファイルを読む所の守りが、形式の数に追いついていない。** fuzz の対象は 4 つの形式だけで、CI でも流していない。浮動小数の足し算で数える繰り返しが止まらない誤り（#486）は、マージの後に見つかった。

## 選択肢

1. 段階に関門を置き、前の段階を確かめるまで次の形式に進まない。確かめた順に進むが、同時に動けるエージェントの数を生かせず、利用者の選んだ速さと合わない。
2. 今のまま進める。速いが、待ちと確かめていない形式がたまり続け、誤りは実際のソフトで開くまで見つからない。
3. 広げるのは続ける。人を待つのは人にしかできないことに限り、ほかの判断はエージェントが決める。人の確認の代わりに、別のエージェントの確認と、外部の実装・公開の試料との照合を入れる。確かめた度合いを形式ごとに示し、確かめる作業を広げる作業と並べて進める。

## 決定

選択肢 3 を選ぶ。決定 0174 のうち、待ちのラベルの意味と、待ちに当たったときの扱いを、この決定で変える。木・優先順・作業中の扱いは変えない。

### 人を待つもの

人を待つのは、次のことだけにする。

- 権利者への問い合わせ、契約・規約への同意、費用のかかること（規格の書籍の購入など）。
- アカウント・署名の鍵・secrets、パッケージの名前の確保と公開（リリースのタグ）。
- リポジトリと GitHub の設定の変更。
- 利用者の手元にしかないもの（受け取った図面、利用者のライセンスで動くソフト）を使う確認。

ラベル「待ち: 判断」は、このうち利用者の判断が要るものだけに付ける。設計・優先順・仕様の読み方・依存の選択（`AGENTS.md` の規則の範囲）は、エージェントが選択肢と理由を書いて決め、下の「互いに確かめる」を受けて進める。あとで変えるなら、新しい決定の記録を足す。

### 待ちに当たったら

飛ばす前に、待ちを減らす。

- **試料。** 再配布できる公開の試料を探す（[決定 0171](0171-public-samples-in-git.md)）。外部の実装で読めるなら、その実装と照らす。見つからなければ、探した所と結果を issue に書く。
- **検証環境。** 開くファイル・手順・期待する結果をそろえた確認の束を作り、issue に置く。利用者の手元のソフトは、利用者がアプリの利用を許せば、エージェントが画面の操作で使う。
- **判断。** 上の「人を待つもの」に当たらなければ、エージェントが決めて、ラベルを外す。

### 互いに確かめる

- PR は、作ったエージェントと別のエージェントが確かめてからマージする。確かめる側は、作った側の会話を引き継がない（新しいセッションか、会話を渡さないサブエージェント）。
- 確かめる側は、差分と issue の完了の条件を照らし、仕様の節・試験・予算・診断・決定性・権利・表記を見る。決定の記録なら、選択肢が実際にあるか、採用済みの決定と食い違わないかも見る。
- 確かめた点と結果は、PR のレビューのコメントに書く。指摘は、作った側が直すか、直さない理由を書く。
- CI の通過は、この確認の代わりにしない。
- main へは、PR を通さずに push しない。

### 形式を足すときの完了の条件

形式を読む・書く issue は、次をそろえて閉じる。

- 外部の実装（成果物に入れず、試験で別のプログラムとして動かすもの）があれば、その実装と結果を照らす試験。毎晩の CI で流してもよい。GPL の実装のソースは読まない。
- 再配布できる公開の試料があれば、`samples/` に足して読む試験。なければ、探した所を形式の文書に書く。
- fuzz の対象と、テストキットの予算・ID の契約試験（決定 0010・0017）。
- 形式の文書の、確かめた度合いの節。

### 確かめた度合い

形式ごとに、読みと書きを分けて、次の 3 つの段で示す。

| 段 | 意味 |
| --- | --- |
| `spec` | 仕様と、試験の中で作ったファイルだけで確かめた |
| `samples` | 公開の試料か、外部の実装との照合で確かめた |
| `verified` | その形式の基準になるソフト（作るソフトか、受け取る側のソフト）で開いて確かめた。書くなら、書いたファイルも開いた |

段は、形式の文書に書く。台帳の欄と、その検査は別の PR で足す。`spec` の段の規則は、読む人に検証済みと取られないように書く。

### 確かめる作業を並べて進める

- 確かめていない形式を確かめる issue を、段階ごとに作り、段階の子の上のほうに置く。広げる作業を止めず、待ちのない確かめる作業が先に選ばれるようにする。
- 不確実性の大きい試作（3D の形状と開口のブーリアンなど）は、試料の条件をゆるめてでも先に進める。日本のソフトの試料は、確かめた度合いを上げるときに使う。

### 境界の整理

1.0 より前は、[決定 0015](0015-add-only-boundary-and-version-floors.md) のとおり、境界を整理するために壊してよい。壊したことは、リリースノートに書く。形式や用途ごとの op を足す前に、領域の op で表せないかを確かめる。

### 決定の記録にするもの

決定の記録は、実際に選択肢があり、境界・ID・層とモデル・依存・権利・形式をまたぐ振る舞い・作業の進め方のどれかに関わる判断に限る。形式ごとの欄や符号化の細部は、`docs/formats` に書く。

## 影響

- 「待ち: 判断」の issue を見直し、エージェントが決められるものからラベルを外す。
- `AGENTS.md`・`docs/work.md`・`docs/decisions/README.md`・`CONTRIBUTING.md`・issue と PR のひな形を、この決定に合わせる。
- 確かめる作業の issue（全コーデックの fuzz、確かめた度合いの台帳の欄、外部の実装との照合、公開の試料）を、段階の子に足す。
- 1 つの変更にかかる手間は増えるが、同時に動くエージェントが受け持つ。人が見るのは、「人を待つもの」の issue だけになる。
- 決定 0174 の待ちの扱いを、この決定で置き換える。
