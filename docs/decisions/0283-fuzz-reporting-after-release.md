# 0283: 初回リリース後に見つけた入力と詳細は、修正したバージョンを公開するまで非公開にする

| 項目 | 内容 |
| --- | --- |
| 日付 | 2026-11-07 |
| 状態 | 採用 |

## 背景

[0261](0261-fuzz-outside-required-checks.md) は、fuzz が見つけた失敗を issue にして早めに直す。初回リリース後に同じ手順で入力や実行の詳細を貼ると、影響を受けるバージョンを利用者が使っている間に、その入力が公開される。入力で起きる不具合は、fuzz のほか、テスト・監査・外部の実装との照合・外部からの報告でも見つかる。

## 選択肢

1. 公開の issue に対象と失敗の種類を記録し、入力と詳細は非公開のセキュリティアドバイザリで扱う。
2. 修正したバージョンを公開するまで、対象と失敗の種類も含めて非公開のセキュリティアドバイザリで扱う。

## 決定

選択肢 1 にする。利用者は 2026-11-07 に「公開 issue に対象と失敗の種類を記録し、入力と詳細は修正版の公開まで非公開にする」と決めた。利用者は理由を挙げていない。#557 の提案では、未修正の問題があることを利用者が公開の計画から知ることができ、`SECURITY.md` の非公開の報告とも両立することを、選択肢 1 の理由に挙げた。

エージェントが次を補った。補ったことは、この記録を書く PR で利用者に認めてもらう。

1. **初回リリース。** このリポジトリで最初に `v*` のタグを push した時点（[#317](https://github.com/zumen-jp/zumen/issues/317)）とする。
2. **対象。** [`SECURITY.md`](../../SECURITY.md) の報告の対象のうち、入力で起きるもの（読み取りが終わらない、落ちる、メモリや CPU を使いすぎる入力）とする。見つけ方によらない。
3. **公開と非公開の分け方。** 報告者は [非公開の報告窓口](https://github.com/zumen-jp/zumen/security/advisories/new) を使う。担当者（その不具合を扱うエージェントか利用者）は、公開の issue には対象（fuzz なら target）と失敗の種類だけを書く。入力、誤りの文、ログ、実行の ID、調べた結果、同じ失敗かを見分ける情報は、非公開のアドバイザリに公開の issue の番号と一緒に記録する。入力を添えるときは [0258](0258-fuzz-seeds-and-runs.md) に従って出所とライセンスを示す。受け取った図面と秘密は添えない。PR の本文・レビューのコメント・コミットの説明と、Actions の実行の記録・ログ・artifact・キャッシュにも、入力と詳細を出さない。
4. **修正。** 修正の PR は公開で作り、CI と互いの確かめを今の条件で通す。非公開にするのは、入力と詳細と、入力から作る回帰テストである。担当者は、入力で落ちなくなったことを手元で確かめ、非公開の記録に書く。入力から合成のテストを作って足すのは、修正したバージョンを公開したあとにする。
5. **承認の記録。** 確かめられない失敗を利用者に認めてもらうときも、認めた日・head・範囲・利用者の言葉を PR に書く（[0254](0254-parallel-agents-and-cross-review.md)）。範囲は、公開の issue の番号と非公開の記録の場所で書く。実行の ID・誤り・比較の結果は、非公開の記録に書く。利用者の言葉に詳細が入っていたら、そこだけを伏せる。
6. **修正したバージョンを公開したあと。** 担当者は、公開できる詳細と合成のテストを出し、公開の issue から、修正したバージョンと修正内容を案内する。アドバイザリを公開するか（CVE を求めるかを含む）は、利用者が決める。
7. **初回リリースの前にすること。** 公開の CI が入力と詳細を出さないようにする切り替え（[#647](https://github.com/zumen-jp/zumen/issues/647)）を終える。間に合わなければ、公開の fuzz の実行を止めてからリリースする。入力を貼ったまま開いている issue（たとえば #510）は、リリースの前に直すか、扱いを利用者に決めてもらう。

## 影響

- 0261 の補ったことの記録先と時期を、初回リリース後はこの決定に合わせる。1（直したら入力を合成のテストに移す）は、上の 4 の時期に行う。3（承認の記録）の範囲は、上の 5 のとおりに書く。4（issue に誤りの文と実行の ID を書く）と 5（実行の ID で毎晩の失敗と issue を対応させる）は、公開の issue でなく非公開の記録で行う。PR との関係の判定、マージの条件、利用者が認める失敗の範囲は、0261 に従う。
- 0254 の「結果に書かないもの」に、初回リリース後の、修正したバージョンを公開していない入力と詳細が加わる。確かめた結果をレビューのコメントに貼るときは、そこだけを伏せ、伏せた所と理由を書く。
- 初回リリース前にリポジトリの fuzz が見つけた入力の扱いは、0258・0261 に従う。外部からの脆弱性の報告窓口は、初回リリース前から非公開である。
