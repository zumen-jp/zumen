# 0283: 初回リリース後は、入力と詳細を、修正したバージョンを公開するまで非公開にする

| 項目 | 内容 |
| --- | --- |
| 日付 | 2026-11-07 |
| 状態 | 採用 |

## 背景

[0261](0261-fuzz-outside-required-checks.md) は、fuzz が見つけた失敗を issue にして早めに直す。初回リリース後に同じ手順で入力や実行の詳細を貼ると、影響を受けるバージョンが使われている間に、その入力が公開される。入力で起きる不具合は、fuzz のほか、テスト・監査・外部の実装との照合・外部からの報告でも見つかる。

## 選択肢

1. 公開の issue に対象と失敗の種類だけを記録し、入力と詳細は非公開のセキュリティアドバイザリで扱う。修正したバージョンを出してから修正内容を公開する。
2. 修正したバージョンを公開するまで、対象と失敗の種類も含めて非公開のセキュリティアドバイザリで扱う。

## 決定

選択肢 1 にする。利用者は 2026-11-07 に「公開 issue に対象と失敗の種類を記録し、入力と詳細は修正版の公開まで非公開にする」と決めた。利用者は理由を挙げていない。#557 の提案は、公開の計画で残件を追え、`SECURITY.md` の非公開の報告とも両立することを、選択肢 1 の理由に挙げた。

エージェントが次を補った。補ったことも、利用者が会話で認めた（日付・head・言葉は PR #650 にある）。

1. **初回リリース。** このリポジトリで最初に `v*` のタグを push した時点（[#317](https://github.com/zumen-jp/zumen/issues/317)）とする。
2. **対象。** [`SECURITY.md`](../../SECURITY.md) の報告の対象のうち、入力で起きるもの（読み取りが終わらない、落ちる、メモリや CPU を使いすぎる入力。以下、失敗）で、公開した最新のバージョン（最新の `v*` のタグ）でも同じ入力で失敗するものとする。最新のバージョンでの失敗の種類・関数・誤りの文は、見つけたときと違ってもよい。見つけ方（fuzz・テスト・監査・外部の実装との照合・外部からの報告）と見つけたときによらず、初回リリースのあとに入力か詳細を公開の所に書くときに当たる。担当者は、最新のバージョンで確かめるまで対象として扱う。確かめるには、見つけたときと同じ処理（入力を渡した入口と、その先の変換と、設定と予算）を最新のバージョンで流す。fuzz なら、見つけたときのコミットの target のファイル・`fuzz/src/`・testkit を最新のバージョンのコードに当てて組み立て、予算は見つけたときの値（testkit にない既定値を含む）にそろえる。あわせて、当てる前の最新のバージョンのコードで組み立てたすべての fuzz の target にも同じ条件で流し、どれかで失敗すれば対象とする。公開の所に書く入力（最小にしたものなど）は、その入力でも確かめる。確かめたあとに新しい `v*` のタグが出たら、公開の所に書く前に確かめ直す。確かめられない失敗は、PR で直すものも対象のまま扱う。時間切れ・メモリの使い過ぎ・手元で再現しない入力と、同じ処理を最新のバージョンで流せないもの（新しく足した形式や入口のように組み立てられないもの、予算をそろえられないもの、最新のバージョンが要求の誤りとして断るもの）と、外部からの報告で入口・設定・予算が分からないもののように見つけたときの処理が分からないものは、確かめられない。初回リリースの前でも、7 で対象として扱うもの（`v*` のタグの push を頼んでから push までの、タグを打つコミットで失敗しないと確かめていない入力と、直さずにタグを打つと決めた失敗）は対象とする。以下の対象は、これを含む。最新のバージョンでその入力が失敗しないと確かめたもの（PR が入れて同じ PR で直すもの、main にだけある不具合。7 で対象として扱うものを除く）は、0258・0261 のとおりに公開で扱い、回帰テストも修正の PR に入れる。
3. **公開と非公開の分け方。** 報告者は [非公開の報告窓口](https://github.com/zumen-jp/zumen/security/advisories/new) を使う。担当者（その不具合を扱うエージェントか利用者）は、公開の issue には対象（fuzz なら target）と失敗の種類だけを書く。入力、誤りの文、ログ、実行の ID、調べた結果、同じ失敗かを見分ける情報は、非公開のアドバイザリに公開の issue の番号と一緒に記録する。入力を添えるときは [0258](0258-fuzz-seeds-and-runs.md) に従って出所とライセンスを示す。受け取った図面と秘密は添えない。PR の題・本文・ブランチの名前・レビューのコメント・コミットの説明・コードのコメントと、Actions の実行の記録・ログ・artifact・キャッシュにも、入力と詳細を出さない。入力と詳細が公開の所に入ったら、秘密と同じく、すぐ利用者に伝え、非公開の記録にないものを写してから、そこを伏せて編集の履歴からも消す（名乗りと確かめた結果のコメントも、その所だけを伏せる）。題・ブランチの名前・push したコミットに入ったものは、GitHub に消してもらうかを利用者に決めてもらう。PR で足した種（`cargo xtask fuzz-seeds` が書く種。公開サンプル・適合テストの組など）が最新のバージョンでも失敗するとき（確かめられないときを含む）も、入力が公開の所に入ったものとして扱い、その種の元を PR から外す。
4. **修正。** 修正の PR は公開で作り、CI と互いの確かめを今の条件で通す。[アドバイザリの一時的な非公開フォーク](https://docs.github.com/en/code-security/security-advisories/working-with-repository-security-advisories/collaborating-in-a-temporary-private-fork-to-resolve-a-repository-security-vulnerability)の PR では status checks が動かず、ブランチの保護の規則も当たらないためである。修正の差分は、修正したバージョンの公開より先に main に入って公開され、差分から原因が読めることがある。選択肢 1 の「修正したバージョンを出してから修正内容を公開する」のうち、差分はこの例外とする。非公開にするのは、入力と詳細と、入力から作る回帰テストである。担当者は、入力で落ちなくなったことを手元で確かめ、非公開の記録に書く。確かめる側も、非公開の記録を読んで入力を手元で流す。確かめる側は [0254](0254-parallel-agents-and-cross-review.md) のとおり読むだけにし、入力と詳細（流した結果を含む）は結果に書かず、結果とは別に返す。作った側（修正の PR では担当者）は、それを手を加えずに非公開の記録に貼る。結果は 0254 のとおり全文をレビューのコメントに貼り、非公開の記録の場所は答えに書く。ほかの PR を確かめる側が対象の入力を見つけたときも、同じく扱う。入力から合成のテストを作って足すのは、修正したバージョンを公開したあとにする。
5. **承認の記録。** 確かめられない失敗を利用者に認めてもらうときも、認めた日・head・範囲・利用者の言葉を PR に書く（[0254](0254-parallel-agents-and-cross-review.md)）。範囲は、公開の issue の番号と非公開の記録の場所で書く。実行の ID・誤り・比較の結果は、非公開の記録に書く。利用者の言葉に詳細が入っていたら、PR ではそこだけを伏せて伏せた所を示し、言葉の全文を非公開の記録に書く。
6. **修正したバージョンを公開したあと。** 修正の PR では公開の issue を閉じない。修正の PR をマージしたら、担当者は公開の issue の開始条件を「修正したバージョンを公開したあと」にし、「待ち: 利用者」を付ける（公開の時期は利用者が決める）。修正したバージョンを公開したら、担当者はラベルを外し、公開できる詳細と合成のテストを出し、公開の issue から修正したバージョンと修正内容を案内してから閉じる。アドバイザリを公開するか（CVE を求めるかを含む）は、利用者が決める。
7. **リリースの前にすること。** 公開の CI が入力と詳細を出さないようにする切り替え（[#647](https://github.com/zumen-jp/zumen/issues/647)）を、初回リリースの前に終える。これを初回リリース（#317）の開始条件に書く。#317 は公開の時期を利用者が決めるので、依存（blocked by）にはしない。初回に限らず、`v*` のタグの push を利用者に頼むときは、タグを打つコミットで直っていない失敗（そのコミットのあとに直したものを含む）のうち、入力か詳細を公開の所に置いたものを、置いた所（issue、PR の本文と承認の記録、main と開いた PR の合成のテストと種の元、#647 の前の実行のログと artifact）とともに一覧で示し、タグの前に直すか、扱いを利用者に決めてもらう。push を頼んでから push までは、タグを打つコミットで失敗する入力と詳細を、初回リリースの前でも対象として扱う（失敗しないと確かめるまで、公開の所に書かない）。push を頼んだエージェントは、頼んだことと、タグを打つコミットを、そのリリースの issue（初回は #317）にコメントで書く（一覧と詳細は書かない）。push したとき、頼みを取り下げたとき、コミットを替えたときも書く。ほかのエージェントは、作業を選ぶ前にそれを見る。頼みを取り下げたら、この扱いは終わる。push を頼むエージェントは、push の直前に一覧の作り直しを頼むよう利用者に伝え、利用者は push の直前にエージェントに一覧を作り直させ、エージェントは作り直した一覧を示し直す。一覧は会話か非公開のアドバイザリで示し、公開の所には対象と失敗の種類と公開の issue の番号までを書く。直さずにタグを打つという判断の記録も、5 と同じく、範囲を公開の issue の番号と非公開の記録の場所で書き、利用者の言葉の詳細の所は伏せる。直さずにタグを打つと決めた失敗は、そのときから対象として扱い、入力と詳細（PR の本文と承認の記録の、利用者の言葉を含む）を、公開の issue の番号と一緒に非公開のアドバイザリに写してから、上の 3 のとおりに伏せる。これをタグの push の前に終える（実行のログと artifact を消すかは、戻せないので利用者が決める）。main の合成のテストと種の元に入った入力は伏せられないので、エージェントは利用者に伝え、直しを含むコミットにタグを打つかを利用者に決めてもらう。タグのあとは、こうした失敗を、新しい最新のバージョンでその入力が失敗しないと確かめるまで対象として扱う。一覧に入らなかったもの（一覧を示したあとに置いたものを含む）が公開の所に見つかったら、上の 3 のとおりに写してから伏せる。

## 影響

- 対象（上の 2。7 で対象として扱うものを含む）では、0261 の補ったことの記録先と時期と、0261 の影響の、リリースするまでは見つけた入力を公開の issue に貼ることを、この決定に合わせる。1（直したら入力を合成のテストに移す）は、上の 4 の時期に行う。3（承認の記録）の範囲は、上の 5 のとおりに書く。4 で issue にする失敗に、PR で直すものも含めて対象が加わる（上の 2）。4（issue に誤りの文と実行の ID を書く）と 5（実行の ID で毎晩の失敗と issue を対応させる）は、公開の issue でなく非公開の記録で行う。1 の時期と 4 の範囲のほかの、PR との関係の判定、マージの条件、利用者が認める失敗の範囲は、0261 に従う。
- 0254 の「結果に書かないもの」と、issue・PR・コメント（名乗りと確かめた結果を含む）・本文・題・ブランチの名前・コミットを伏せる場合（秘密や受け取った図面の情報が入ったとき）に、対象の、修正したバージョンを公開していない入力と詳細が加わる（上の 3。伏せる前に、非公開の記録にないものを写す）。確かめた結果に入ってしまったときは、レビューのコメントに貼るときにそこだけを伏せ、伏せた所と理由を書き、伏せたものは作った側が非公開の記録に貼る。確かめる側は、入力と詳細を結果とは別に返し、作った側がそれを非公開の記録に貼る（上の 4）。0254 の、次の `v*` のタグの前に利用者に一覧で示すもの（新しく出す crate の名前）に、タグを打つコミットで直っていない失敗のうち入力か詳細を公開の所に置いたものが、置いた所とともに加わる。この一覧は、push の直前に作り直して示し直す（上の 7）。0254 の承認の記録では、対象の確かめられない失敗の範囲を、公開の issue の番号と非公開の記録の場所で書き、利用者の言葉のうち詳細の所だけを PR で伏せ、全文を非公開の記録に置く（上の 5）。
- 初回リリースの前に公開の所に書いた入力と詳細と、最新のバージョンでその入力が失敗しないと確かめたものの扱いは、上の 7 で対象として扱うものを除き、0258・0261 に従う。外部からの脆弱性の報告窓口は、初回リリース前から非公開である。
