# 0283: 初回リリース後に見つけた入力と詳細は、修正したバージョンを公開するまで非公開にする

| 項目 | 内容 |
| --- | --- |
| 日付 | 2026-11-07 |
| 状態 | 採用 |

## 背景

[0261](0261-fuzz-outside-required-checks.md) は、fuzz が見つけた失敗を issue にして早めに直す。初回リリース後に同じ手順で入力や実行の詳細を貼ると、影響を受けるバージョンが使われている間に、その入力が公開される。入力で起きる不具合は、fuzz のほか、テスト・監査・外部の実装との照合・外部からの報告でも見つかる。

## 選択肢

1. 公開の issue に対象と失敗の種類だけを記録し、入力と詳細は非公開のセキュリティアドバイザリで扱う。修正したバージョンを出してから修正内容を公開する。
2. 修正したバージョンを公開するまで、対象と失敗の種類も含めて非公開のセキュリティアドバイザリで扱う。

## 決定

選択肢 1 にする。利用者は 2026-11-07 に「公開 issue に対象と失敗の種類を記録し、入力と詳細は修正版の公開まで非公開にする」と決めた。利用者は理由を挙げていない。#557 の提案は、公開の計画で残件を追え、`SECURITY.md` の非公開の報告とも両立することを、選択肢 1 の理由に挙げた。

エージェントが次を補った。補ったことも、利用者が会話で認めた（日付・head・言葉は PR #650 にある）。

1. **初回リリース。** このリポジトリで最初に `v*` のタグを push した時点（[#317](https://github.com/zumen-jp/zumen/issues/317)）とする。
2. **対象。** [`SECURITY.md`](../../SECURITY.md) の報告の対象のうち、入力で起きるもの（読み取りが終わらない、落ちる、メモリや CPU を使いすぎる入力。以下、失敗）で、公開した最新のバージョン（最新の `v*` のタグ）でも同じ入力で失敗するものとする。最新のバージョンでの失敗の種類・関数・誤りの文は、見つけたときと違ってもよい。見つけ方（fuzz・テスト・監査・外部の実装との照合・外部からの報告）によらない。担当者は、最新のバージョンで確かめるまで対象として扱う。確かめられない失敗（時間切れ・メモリの使い過ぎ・手元で再現しない入力など）は、PR で直すものも対象のまま扱う。最新のバージョンでその入力が失敗しないと確かめたもの（PR が入れて同じ PR で直すもの、main にだけあるもの）は、0258・0261 のとおりに公開で扱い、回帰テストも修正の PR に入れる。
3. **公開と非公開の分け方。** 報告者は [非公開の報告窓口](https://github.com/zumen-jp/zumen/security/advisories/new) を使う。担当者（その不具合を扱うエージェントか利用者）は、公開の issue には対象（fuzz なら target）と失敗の種類だけを書く。入力、誤りの文、ログ、実行の ID、調べた結果、同じ失敗かを見分ける情報は、非公開のアドバイザリに公開の issue の番号と一緒に記録する。入力を添えるときは [0258](0258-fuzz-seeds-and-runs.md) に従って出所とライセンスを示す。受け取った図面と秘密は添えない。PR の題・本文・ブランチの名前・レビューのコメント・コミットの説明・コードのコメントと、Actions の実行の記録・ログ・artifact・キャッシュにも、入力と詳細を出さない。入力と詳細が公開の所に入ったら、秘密と同じく、すぐ利用者に伝え、そこを伏せて編集の履歴からも消す（名乗りと確かめた結果のコメントも、その所だけを伏せる）。題・ブランチの名前・push したコミットに入ったものは、GitHub に消してもらうかを利用者に決めてもらう。PR で足した種（`cargo xtask fuzz-seeds` が書く種。公開サンプル・適合テストの組など）が最新のバージョンでも失敗するときも、入力が公開の所に入ったものとして扱い、その種の元を PR から外す。
4. **修正。** 修正の PR は公開で作り、CI と互いの確かめを今の条件で通す。[アドバイザリの一時的な非公開フォーク](https://docs.github.com/en/code-security/security-advisories/working-with-repository-security-advisories/collaborating-in-a-temporary-private-fork-to-resolve-a-repository-security-vulnerability)の PR では status checks が動かず、ブランチの保護の規則も当たらないためである。修正の差分は、修正したバージョンの公開より先に main に入って公開され、差分から原因が読めることがある。選択肢 1 の「修正したバージョンを出してから修正内容を公開する」のうち、差分はこの例外とする。非公開にするのは、入力と詳細と、入力から作る回帰テストである。担当者は、入力で落ちなくなったことを手元で確かめ、非公開の記録に書く。確かめる側も、非公開の記録を読んで入力を手元で流し、結果を非公開の記録に書く。レビューのコメントには、非公開の記録で確かめたことと、その記録の場所だけを書く。入力から合成のテストを作って足すのは、修正したバージョンを公開したあとにする。
5. **承認の記録。** 確かめられない失敗を利用者に認めてもらうときも、認めた日・head・範囲・利用者の言葉を PR に書く（[0254](0254-parallel-agents-and-cross-review.md)）。範囲は、公開の issue の番号と非公開の記録の場所で書く。実行の ID・誤り・比較の結果は、非公開の記録に書く。利用者の言葉に詳細が入っていたら、PR ではそこだけを伏せて伏せた所を示し、言葉の全文を非公開の記録に書く。
6. **修正したバージョンを公開したあと。** 修正の PR では公開の issue を閉じない。修正の PR をマージしたら、担当者は公開の issue の開始条件を「修正したバージョンを公開したあと」にし、「待ち: 利用者」を付ける（公開の時期は利用者が決める）。修正したバージョンを公開したら、担当者はラベルを外し、公開できる詳細と合成のテストを出し、公開の issue から修正したバージョンと修正内容を案内してから閉じる。アドバイザリを公開するか（CVE を求めるかを含む）は、利用者が決める。
7. **リリースの前にすること。** 公開の CI が入力と詳細を出さないようにする切り替え（[#647](https://github.com/zumen-jp/zumen/issues/647)）を、初回リリースの前に終える。これを初回リリース（#317）の開始条件に書く。#317 は公開の時期を利用者が決めるので、依存（blocked by）にはしない。初回に限らず、`v*` のタグの push を利用者に頼むときは、タグを打つコミットで直っていない失敗の入力を貼った issue（そのコミットのあとに直して閉じたものを含む）を示し、タグの前に直すか、扱いを利用者に決めてもらう。タグのあとは、新しい最新のバージョンでその入力が失敗しないと確かめるまで対象として扱い、上の 3 の、公開の所に入ったときのとおりに伏せる。

## 影響

- 初回リリース後の対象（上の 2）では、0261 の補ったことの記録先と時期をこの決定に合わせる。1（直したら入力を合成のテストに移す）は、上の 4 の時期に行う。3（承認の記録）の範囲は、上の 5 のとおりに書く。4（issue に誤りの文と実行の ID を書く）と 5（実行の ID で毎晩の失敗と issue を対応させる）は、公開の issue でなく非公開の記録で行う。1 の時期のほかの、PR との関係の判定、マージの条件、利用者が認める失敗の範囲は、0261 に従う。
- 0254 の「結果に書かないもの」と、issue・PR・コメント（名乗りと確かめた結果を含む）・本文・題・ブランチの名前・コミットを伏せる場合（秘密や受け取った図面の情報が入ったとき）に、初回リリース後の対象の、修正したバージョンを公開していない入力と詳細が加わる（上の 3）。確かめた結果をレビューのコメントに貼るときは、そこだけを伏せ、伏せた所と理由を書く。0254 の、次の `v*` のタグの前に利用者に一覧で示すもの（新しく出す crate の名前）に、タグを打つコミットで直っていない失敗の入力を貼った issue が加わる（上の 7）。0254 の承認の記録では、利用者の言葉のうち詳細の所だけを PR で伏せ、全文を非公開の記録に置く（上の 5）。
- 初回リリース前に見つけた入力（上の 7 で対象として扱い直すものを除く）と、最新のバージョンでその入力が失敗しないと確かめたものの扱いは、0258・0261 に従う。外部からの脆弱性の報告窓口は、初回リリース前から非公開である。
