# 0021: 表記と用語の基準を決め、textlint と prh で確かめる

| 項目 | 内容 |
| --- | --- |
| 日付 | 2026-10-24 |
| 状態 | 採用 |

## 背景

- [0005](0005-japanese-first.md) で日本語を正にした。AGENTS.md は「分かりやすく簡潔な日本語で書く」と決めているが、表記の規則はない。文書は、人もエージェントも書く。
- 2026-10-24 の時点で、次の揺れがあった。
  - 長音では、「サーバー・ヘッダー・フォルダー・パラメーター」には付け、`ブラウザ`・`コンテナ`・`バッファ`・`ポインタ`・`デコーダ`・`コンパイラ` には付けていなかった。README の 1 行目にも `ブラウザ・サーバー` と並んでいた
  - コロンでは、和文の後のコロンが、半角で 44 か所、全角（`：`）で 7 か所あった
  - 英語とカタカナでは、`native` と「ネイティブ」、`panic` と「パニック」、`module` と「モジュール」が混ざっていた
  - 漢字とかなでは、「分かりやすい」と `わかりやすく`、「ほかの」と `他の`、「よい」と `良い` が混ざっていた
- 読み手は 3 つに分かれる。
  - 設計・施工・維持管理の実務者。要領・基準の言葉で読む（CAD製図基準の「レイヤ」など）
  - ソフトウェアの開発者。IT で通じる言葉で読む
  - 導入を決める人（情報システム部門・法務・決裁者）
- この文書群は、和語への言い換え（境界・結合・包みなど）が多い。導入を決める人には読みやすいが、開発者には「コア・API・バインディング・ラッパー」のほうが速く通じる。旧版の言語の方針には、「規格名・一般的な技術用語は、無理に訳して意味を変えません」とあった（[旧版の docs/language-policy.md](https://github.com/zumen-jp/zumen-legacy/blob/main/docs/language-policy.md)）。

## 選択肢

1. **規則を文書にだけ書く。** 手間は少ないが、揺れを防ぐのは人とエージェントの注意だけになる。
2. **既存のスタイルガイドをそのまま使う**（JTF 日本語標準スタイルガイドなど）。全角と半角の間に空白を入れない、コロンを全角にする、など今の書き方と逆の規則が多く、ほとんどの文書を直すことになる。
3. **今の書き方を基準として書き起こし、textlint と prh で確かめる。** 決まっていない所は、内閣告示「外来語の表記」と、文化審議会の「公用文作成の考え方」（2022 年）に寄せる。

## 決定

3 を選ぶ。

- **置き場所。** 規則と用語集は [docs/style.md](../style.md) に置く。機械で確かめる部分は、`prh.yml`（揺れの辞書）・`.textlint-allow.yml`（誤りとしない語）・`.textlintrc.yml`・`.textlintrc.code.yml` に置く。語を足すときは、これらを PR で直す。この記録には方針だけを書く。

### 表記

- **長音。** 英語の -er・-or・-ar などに当たる語末には「ー」を付ける（ブラウザー・サーバー・コンパイラー）。-y の語末には付けない（メモリ・ライブラリ・リポジトリ）。内閣告示の原則と、2008 年からの Microsoft の表記に合わせる。利用者が毎日見る Windows の画面と同じ書き方になる。
- **基準と製品の名前。** 要領・基準が定める用語（CAD製図基準の「レイヤ」）と固有名詞・原典の題名は、空白・長音・送り仮名・大文字と小文字も含めて原典どおりに書く。空白の規則より原典を優先する（測地成果2024、基準面補正パラメータなど）。
- **漢字とかな。** 形式名詞・補助動詞・副詞・接続詞は、かなで書く。場所を表す「所」と「分かる」は漢字で書く。どちらも、今の文書に多いほうに合わせた。
- **英語とカタカナ。** 同じ語を混ぜない。どちらで書くかは用語集で決める（ネイティブ・パニック・モジュールはカタカナ、crate・issue・wasm は英語）。識別子と列挙の値は、コードとして書く（`native`）。
- **空白と記号。** 半角の英数字と全角の文字の間に、半角の空白を入れる。コロンは半角にし、後ろに空白を入れる。範囲は「〜」（U+301C）で書く。どれも、今の文書に多い書き方。

### 用語

- **読み手が知っている言葉を使う。** 和語に言い換えた語は用語集に載せる。利用者向けの文（README・サイト・診断の文・CLI のヘルプ）で初めて使う所では、「境界（API）」のように一般の言い方を括弧で添える。
- **実務者向けの言葉は、要領・基準から取る。**
- **道具の検査の結果を「照査」と呼ばない。** 照査は、照査技術者が責任を持って行うもの。道具の結果には「チェック」を使う。「合格」「適合」「保証」の代わりに、「指摘なし」「確認できなかった項目」と書く。
- 文書全体の言い換え（境界を API にする、など）は、この記録では決めない。用語集で対応を示すにとどめる。

### 検査

- **道具。** textlint 15 と次の規則を、npm の devDependencies に版を固定して入れ、`package-lock.json` で依存を固定する。どれも寛容なライセンス（MIT など）で、成果物には入らない。
  - preset-ja-spacing（今の書き方に合わせて設定する）
  - preset-ja-technical-writing（文の長さ・読点の数・漢字の連続・助詞の重なり・弱い表現・半角のカンマの数は外す）
  - 形式名詞・副詞・補助動詞をかなにする 3 つの規則
  - prh（揺れの辞書）
- **対象。** Markdown はすべての規則で、ソースコード（`.rs`）・TOML・YAML は揺れの辞書だけで確かめる。コードの行を文として読むと、ほかの規則は誤りが多い。英語の語の規則は、後ろに和文が続くときだけに当て、識別子に当たらないようにする。
- **外す規則。** 文の長さなどは、揺れではなく、今の文書の書き直しも大きいので外す。半角のカンマの数は、数の桁区切りも数えてしまうので外す。
- **CI。** CI に「表記の検査」の job を足し、`npm ci --ignore-scripts` と `npm run lint:text` を走らせる。Node.js は [docs/support.md](../support.md) の下限（22）にそろえる。

### 決定の記録の直し

- 表記の基準に合わせる直しは、意味を変えないので、採用した記録にも行う。[README](README.md) の「決めたあとは内容を書き換えません」に、この例外を書き足す。

## 影響

- 揺れを直した。Markdown の約 80 か所と、コメント・説明・設定の約 25 か所。
  - スキーマ（`schema/messages.json`・`schema/boundary.toml`）と台帳（`catalog/codes.toml`）の説明を直し、生成したファイル（`messages.rs`・`codes.rs`・`zumen.h`）を作り直した。変わったのはコメントだけ。
- 文書・コメント・カタログ・スキーマの説明を変える PR は、`npm run lint:text` を手元で通す。AGENTS.md と CONTRIBUTING.md の手順に足す。
- 新しい言葉が出てきたら、用語集と辞書に足す。誤りと判定される固有名詞は、理由と一緒に `.textlint-allow.yml` に足す。
