# 0285: タグの push の頼みはバージョンごとのリリースの issue に書き、タグを打つコミットは最新のバージョンと同じ方法で確かめ、取り下げたら公開の扱いに戻す

| --- | --- |

| 状態 | 採用 |

## 背景

[0283](0283-fuzz-reporting-after-release.md) の補ったこと 7 は、`v*` のタグの push を利用者に頼んでから push までは、タグを打つコミットで失敗する入力と詳細を、初回リリースの前でも 0283 の対象として扱うとした。push を頼んだエージェントは、頼んだこととタグを打つコミットを、そのリリースの issue（初回は #317）に書き、ほかのエージェントは作業を選ぶ前にそれを見る。PR #650 の 8 回目の確かめは、次の 3 つが決まっていないことを挙げた。どれも、入力が漏れる道ではない。

- 2 回目からのリリースで、そのリリースの issue を誰が作り、ほかのエージェントがどう見つけるか。
- タグを打つコミットで、入力が失敗しないと確かめる方法。0283 の補ったこと 2 は、公開した最新のバージョンで確かめる方法だけを書いている。
- push の頼みを取り下げたあとの扱い。頼んでいる間に非公開の記録だけに残した失敗は、照合が非公開の記録に頼ったままになる。修正の PR のマージで「待ち: 利用者」にした issue（0283 の補ったこと 6）は、出すバージョンがないまま待つ。

タグを打つコミットでの確かめ方と、取り下げたあとの扱いは、初回の push の頼み（#317）から要る。

## 選択肢

### リリースの issue

1. push を頼むエージェントが、頼む前に、バージョンごとのリリースの issue を作り、新しいラベルで見つけられるようにする。
2. 1 つの issue に、すべてのバージョンの頼みを書く。コメントが積もり、どのバージョンの記録かを取り違えやすい。

### タグを打つコミットで確かめる方法

1. 0283 の補ったこと 2 の、最新のバージョンで確かめる方法を、そのままタグを打つコミットに当てる。
2. 見つけた target に、タグを打つコミットで入力を流すだけにする。予算の既定や入口が変わっていると、失敗しないと読み違えうる。2 つの確かめ方が分かれると、文書の間で食い違いやすい。

### 頼みを取り下げたあと

1. 0283 の補ったこと 7 だけで対象だったものを、[0258](0258-fuzz-seeds-and-runs.md)・[0261](0261-fuzz-outside-required-checks.md) の公開の扱いに戻す。
2. 取り下げても、修正したバージョンの公開まで非公開のままにする。出すバージョンがないので待つ先がなく、非公開の記録が残り続ける。

## 決定

3 つとも選択肢 1 にする。利用者は 2026-11-09 に、方針を示されたあと、会話で「この判断で記録して」と答えた（方針と言葉は [#661 のコメント](https://github.com/zumen-jp/zumen/issues/661#issuecomment-6736370532) にある）。選択肢 2 を採らない理由は、それぞれの選択肢に書いたとおりである。方針の細部は、エージェントが下の各項で補った。補ったことも、利用者が会話で認めてから採用する（認めた日・head・言葉は PR #665 に書く）。

### 1. リリースの issue

- `v*` のタグの push を利用者に頼むエージェントは、頼む前に、出すバージョンのリリースの issue を作り、ラベル「リリース」を付ける。初回は、新しく作らずに #317 を使う。
- 頼んだとき・タグを打つコミットを替えたとき・push したとき・頼みを取り下げたときに、その issue にコメントで記録を書く。0283 の補ったこと 7 のとおり、一覧と詳細は書かない。
- ほかのエージェントは、作業を選ぶ前に、ラベル「リリース」の開いた issue の最新の記録で、頼んでいる間かを見る。
- ラベル「リリース」を足す。説明は「v* のタグの、バージョンごとのリリースの issue。開いたものの最新の記録で、push を頼んでいる間かを見る（決定 0285）」とする。このラベルは、リリースの issue だけに付ける。

エージェントが次を補った。

- 題に、出すタグの名前（`v0.3.0` など）を入れる。どのバージョンの記録かを、題で見分けるためである。#317 の題は変えず、タグの名前は記録に書く。
- タグの push は利用者を待つもの（`AGENTS.md` の「並行して進める」）なので、「待ち: 利用者」も付ける。
- 記録のコメントは、1 行目を「push の頼み: 頼んだ」「push の頼み: コミットを替えた」「push の頼み: push した」「push の頼み: 取り下げた」のどれかにする。頼んだときとコミットを替えたときは、タグの名前とタグを打つコミットを書く。#317 のように記録でないコメントもある issue で、最新の記録を取り違えないためである。
- 最新の記録が「頼んだ」か「コミットを替えた」の issue が 1 つでもあれば、頼んでいる間とする。記録のない issue は、頼んでいる間に数えない。
- 見つけた入力か詳細を公開の所に書く前にも、同じく見る。作業を選んだあとに、頼みが始まることがあるためである。
- push して公開を終えたときと、そのバージョンを出さないと決めたときに、issue を閉じる。#317 は、その完了の条件で閉じる。開いた issue だけを見れば足りるようにするためである。頼んでいる間に出さないと決めたら、先に「push の頼み: 取り下げた」を書き、下の 3 の扱いを終えてから閉じる。閉じた issue は見ないので、取り下げを書かずに閉じると、3 の扱いを始める者がいなくなるためである。

### 2. タグを打つコミットで確かめる方法

- 0283 の補ったこと 2 の、公開した最新のバージョンで確かめる方法を、そのままタグを打つコミットに当てる。見つけたときと同じ処理（入力を渡した入口と、その先の変換と、設定と予算）を、タグを打つコミットのコードで流す。fuzz なら、見つけたときのコミットの target のファイル・`fuzz/src/`・testkit をタグを打つコミットのコードに当てて組み立て、予算は見つけたときの値（testkit にない既定値を含む）にそろえる。あわせて、当てる前のタグを打つコミットのコードで組み立てたすべての fuzz の target にも同じ条件で流し、どれかで失敗すれば、失敗するとする。公開の所に書く入力（最小にしたものなど）は、その入力でも確かめる。
- 確かめられないものも、0283 の補ったこと 2 と同じにする。時間切れ・メモリの使い過ぎ・手元で再現しない入力と、同じ処理をタグを打つコミットで流せないもの（当てて組み立てられないもの、予算をそろえられないもの、タグを打つコミットが要求の誤りとして断るもの）と、見つけたときの処理が分からないものである。確かめられない失敗は、対象のまま扱う。
- タグを打つコミットを替えたら、公開の所に書く前に、替えたコミットで確かめ直す。

エージェントが次を補った。

- タグを打つコミットは、リリースの issue の最新の記録にあるものとする。頼んでいるリリースの issue がいくつもあれば、それぞれの最新の記録にあるタグを打つコミットのすべてで確かめる。
- 初回リリース後に push を頼んでいる間は、公開した最新のバージョンとタグを打つコミットの両方で、失敗しないと確かめたものだけを公開で扱う。0283 の対象は、どちらかで確かめていないものの全体だからである。

### 3. 頼みを取り下げたあと

- 取り下げで対象でなくなったもの、つまり 0283 の補ったこと 7 だけで対象だったもの（初回リリースの前のものと、公開した最新のバージョンでは失敗しないと確かめたもの）は、0258・0261 の公開の扱いに戻す。戻すものは、次のようにする。
  - 非公開の記録だけにあった入力と詳細は、公開の issue に写す。
  - 修正の PR のマージで「待ち: 利用者」にした issue（0283 の補ったこと 6）は、ラベルを外し、0258・0261 のとおり入力と回帰テストを公開で足してから閉じる（入力を写さないものは、下の補ったことのとおり）。
- 直さずにタグを打つという判断（0283 の補ったこと 7）は、取り下げで効かなくなり、次に頼むときに決め直す。

エージェントが次を補った。

- 戻すのは、取り下げたことをリリースの issue に書いたエージェントとする。書いたあとに、閉じていない非公開のアドバイザリのすべてを見直す。すべてを見るのは、頼む前からあるものと、ほかの頼みのために前の取り下げで残したものも見落とさないためである。書いたあとに見直すのは、頼んでいる間に足された記録を取りこぼさないためである。
- 写す直前にも、リリースの issue を見る。取り下げた issue で頼み直したときを含め、どこかで push を頼んでいれば、そのタグを打つコミットでも失敗しないと確かめたものだけが、対象でなくなる。
- 公開の issue に写すのは、0261 の補ったこと 4 が issue に求めるもの（落ちた target か手順・誤りの文・実行の ID）と、0258 のとおり最小にして元の公開サンプルの出所とライセンスを添えた入力である。写す入力は、0258 で出所とライセンスを示せるもの（公開サンプルと合成の入力から来たもの）に限る。実行の ID を写すので、照合は公開の issue でできるようになる。写す前に、同じ失敗の公開の issue がほかにないかを確かめ、あれば 0261 の補ったこと 4 のとおりそちらにまとめる。取り下げを書いてから写すまでに、ほかのエージェントが毎晩の失敗を公開の issue にすることがあるためである。写し終えたアドバイザリは、閉じる。
- 外部からの報告と、受け取った図面（`ZUMEN_SAMPLES`）を読んで見つけた失敗は、入力と詳細を写さない。権利の分からない第三者のファイルと、受け取った図面の中身を公開しないためである（`AGENTS.md` の「図面と秘密」、0258）。公開の issue には対象と失敗の種類だけを残し、回帰テストは、入力を写さずに、規則を確かめる最小の入力をテストの中で作る。そのアドバイザリを閉じるか、公開するか、報告者に公開の許しを求めるか（このリポジトリの外への送信）は、取り下げを書いたエージェントが利用者に示し、利用者が決める。
- 0283 の補ったこと 6 で「修正したバージョンを公開したあと」にした開始条件も、戻す。

## 影響

- 0283 の補ったこと 7 の「そのリリースの issue」と「ほかのエージェントは、作業を選ぶ前にそれを見る」は、上の 1 のとおりに行う。push を頼んでから push までに「タグを打つコミットで失敗しない」と確かめるのは、上の 2 の方法で行う。「頼みを取り下げたら、この扱いは終わる」のあとは、上の 3 のとおりにする。取り下げで対象でなくなったものには、0283 の、修正したバージョンの公開まで非公開で扱うことは当たらない。
- ラベル「リリース」は、この決定のマージのすぐ後に、マージした側が作り、#317 に付ける。ラベルの種類と説明は、決定の記録で決めてから変える（[0254](0254-parallel-agents-and-cross-review.md)）。
- `AGENTS.md`・`docs/work.md`・`fuzz/README.md` を、この決定に合わせる。
- 上の 2 と 3 は、初回の push の頼みから効く。
