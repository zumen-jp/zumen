# 0271: wasm の入力の所有権を渡し、最初の入力のコピーを 1 回にする

| 項目 | 内容 |
| --- | --- |
| 日付 | 2026-11-06 |
| 状態 | 採用 |

## 背景

`Session.push` は、ホストの入力を `zm_alloc` の領域へ写し、`zm_push` がセッションの `Vec` へもう一度写していた。入力の長さの約 2 倍を wasm のメモリに確保し、解放しても `WebAssembly.Memory` の大きさは戻らない。300 MiB の入力を 1 回渡すだけで、読み取りを始める前に約 602 MiB になる（#533）。

`zm_push` は呼び出しの間だけバイト列を借りる契約で、同じ名前への追記も受ける（[決定 0012](0012-boundary-functions-and-messages.md)）。この関数の意味は変えない。

## 選択肢

1. **ラッパーで小分けにして `zm_push` を呼ぶ。** 一時の領域は小さくなるが、セッションの `Vec` を伸ばす再確保は残る。コピーは 2 回のままで、呼び出しも増える。
2. **セッションの領域を先に確保し、ホストに書かせてから確定する。** 名前と長さの予約・書き込み・確定・中止の状態が増え、途中のセッション操作と、未確定の入力の扱いを定める必要がある。
3. **ホストが確保した領域の所有権を渡す関数を足す。** 既存の `zm_alloc` を使い、最初の入力ならセッションの領域としてそのまま保持できる。失敗時にどちらが解放するかを明示する必要がある。

## 決定

3 を選ぶ。`schema/boundary.toml` に wasm 専用の `zm_push_owned` を足し、関数の定義と定数を生成する。

- 名前と追記の規則、状態コードは `zm_push` と同じにする。名前は呼び出しの間だけ借りる。
- データは、同じモジュールの `zm_alloc(data_len)` が返した、まだ渡しても解放してもいない領域に限る。長さ 0 は NULL で渡す。任意のホストのポインターや、別のアロケーターの領域は渡せない。
- 有効な領域は、成功・無効な引数・使用中・パニック済みのどの状態を返しても引き取る。呼んだ後は、ホストは領域を読まず、`zm_dealloc` でも返さない。関数を呼ぶ前に JS のコピーが失敗した場合だけ、ラッパーが返す。
- 入力名とセッションを検査する前に、領域を所有する `Vec` に戻す。名前やセッションが無効ならその場で解放する。新しい名前と空の入力では `Vec` を移して保持し、すでにバイト列がある名前では後ろへ写してから渡された領域を解放する。
- wasm の trap では、戻った状態と同じ解放を期待しない。[決定 0259](0259-javascript-on-node-servers.md) に従ってインスタンスを使えなくし、後片付けでも wasm に戻らない。
- JS の `Session.push` は、関数があれば使い、なければ既存の `zm_push` を使う。旧 ABI 1 のモジュールも引き続き読み込める。ホストの入力は引き渡した後も使える。入力や名前が同じ wasm のメモリを指す場合だけ、確保による `memory.grow` より前にホストへ写す。
- wasm を wazero で動かす Go の `Session.Push`・`PushBytes` も、新しい関数があれば同じ契約で使う。旧モジュールでは `zm_push` に戻り、trap・中断では従来どおりインスタンスを閉じる（[決定 0226](0226-go-wrapper.md)）。
- C・C++・Python・.NET は既存の `zm_push` を保つ。ネイティブではホストのバイト列を直接渡せるため、wasm の一時の領域に当たるコピーはない。Python の文字列・bytearray などを `bytes` にする変換は別に残る。プロセスの外への転送も従来のままにする。
- ABI 1、メッセージのスキーマ、ID の規則を変えない。関数だけの追加で、op・フィールド・列挙の値は増えない（[決定 0015](0015-add-only-boundary-and-version-floors.md)）。既存の `zm_push` と公開ラッパーのメソッドの意味も変えない。

## 確かめ方と影響

Rust で領域がそのまま保持されること、空の入力、借りた入力と所有権を渡す入力の混在した追記、無効な名前・セッション・使用中・パニック済みの状態を確かめる。JS では実際の wasm で、新旧の関数の経路、追記、渡した後のホストの書き換え、失敗を繰り返したときの解放、`memory.grow`、trap の後片付けを確かめる。Go も新旧の関数の経路、追記、ホストの書き換え、失敗時の解放、メモリの削減と中断を確かめる。既存の適合テストで応答とハッシュを照合する。

`bindings/js/test/input.mjs` は、同じ release wasm の exports から新しい関数だけを隠した経路を旧経路として比べる。各測定を別の Node.js で行い、新しいセッションへ 1 回 `push` した前後の `memory.buffer.byteLength` を測る。CI は 32 MiB の入力で削減を確かめる。手元の Windows・Node.js 24.22.2 では、300 MiB の入力で次の値になった（2026-11-06）。

| 経路 | 渡す前 | 渡した後 | 増加 |
| --- | --- | --- | --- |
| `zm_push` | 1,441,792 バイト | 630,718,464 バイト | 629,276,672 バイト |
| `zm_push_owned` | 1,441,792 バイト | 316,080,128 バイト | 314,638,336 バイト |

これは wasm のメモリの測定で、ホストの入力と文書の解析は含まない。最初の入力の wasm へのコピーは 1 回になるが、追記にはコピーと再確保が残り、文書を開く際のメモリは別に必要になる。新しい依存は足さない。

PR の既存の読み取り専用の wasm の job で、JS と Go の入力の契約・削減を確かめる。Go は下限の 1.26 で適合テストも流し、毎晩の 1.26・1.27 の検査も保つ。
