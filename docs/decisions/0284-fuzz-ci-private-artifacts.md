# 0284: fuzz の CI は、見つけた入力とログを暗号にして残し、通らなかった target の種をキャッシュに残さない

| 項目 | 内容 |
| --- | --- |
| 日付 | 2026-11-09 |
| 状態 | 採用 |

## 背景

[0283](0283-fuzz-reporting-after-release.md) は、初回リリース後の失敗の入力と詳細を、Actions の実行の記録・ログ・artifact・キャッシュにも出さないとし、その切り替え（#647）を初回リリースの前に終えるとした。公開のリポジトリでは、Actions の log・注釈・summary・artifact は誰でも読める。キャッシュは、フォークからの PR の実行でも、ワークフローを書き換えれば戻せる。

[0258](0258-fuzz-seeds-and-runs.md) までの CI は、通らなかった target の libFuzzer のログの末尾（誤りの文と、入力のバイト列が出る）を log に出し、見つけた入力を平文の artifact に置いていた。流す手順で通らなかった target の種は、見つけた入力の元を残すため縮めずにキャッシュに残し、縮められなかった target も縮める前の種を残していた。種を流し始めたときに落ちた入力は種の中にあり、その後ろの種は流していないので、落ちるかが分からない。

## 選択肢

### 入力と詳細を置く所

1. 公開の所には置かない。見つけた入力・遅い入力・通らなかった target のログを、リポジトリに置く公開鍵で暗号にして artifact に置く。復号の秘密鍵は利用者が持ち、リポジトリにも secrets にも置かない。
2. artifact を置かない。見つけた入力は、担当者が手元で流し直して作る。
3. 非公開のリポジトリか非公開の保存先に送る。

### キャッシュ

1. 通らなかった target と縮められなかった target の種を、キャッシュに残す前にまるごと除く。
2. 見つけた入力と同じ中身の種（名前が SHA-1 か SHA-256 のもの）だけを除く。
3. PR の実行ではキャッシュを戻さない。

### 当てる時期

1. 初回リリースの前から、いつも当てる。
2. 最初の `v*` のタグのあとから当てる。

## 決定

入力と詳細は選択肢 1、キャッシュは選択肢 1、時期は選択肢 1 にする。

- 公開の log・注釈・summary には、target と失敗の種類（`crash`・`timeout`・`oom`・`leak`、入力を残さずに落ちたときは「入力なし」）と、種の数などの集計だけを書く。libFuzzer のログは出さない。
- 見つけた入力・遅い入力・通らなかった target（縮める手順を含む）のログを、公開サンプルの出所とライセンス・種を作ったコミット・実行の ID と 1 つにまとめ、`fuzz/recipients.txt` の公開鍵で age の形に暗号にして、artifact に置く。平文は置かない。暗号にできなければ、何も置かずに job を失敗させる。受け取り手（公開鍵）を足す・替える・外すのは、秘密鍵の持ち主を決めることなので、利用者が決める。
- 毎晩と手で流す実行は、流す手順で通らなかった target と縮められなかった target の種を、キャッシュに残す前にまるごと除き、除いた target を log に書く（黙って外さない）。次の夜は、その target を `cargo xtask fuzz-seeds` の種から育て直す。流す手順か縮める手順が取り消された実行（時間切れ・concurrency）は、確かめていない種が混じるので、キャッシュを残さない。前の夜までのキャッシュに残る種は、0283 の対象の失敗を見つけた担当者が `gh cache delete` で消す。
- 秘密鍵のない機械のエージェントは、公開の所に書けることだけで進め、開くことを利用者に頼む（開くことを頼む issue に「待ち: 利用者」）。手順は `fuzz/README.md` にある。

理由は次のとおりである。

- 入力の選択肢 2 は、fuzz が乱数で入力を作るので、見つけた入力を流し直して作れるとは限らない。選択肢 3 は、新しいリポジトリ・保存先・secrets か、ワークフローの権限を広げることが要り、利用者の設定を待つ。選択肢 1 は、権限・secrets・発火の条件を変えずにできる。
- キャッシュの選択肢 3 は、フォークの PR が書き換えたワークフローで動くので、取り出す道を塞がない。選択肢 2 は、落ちた入力の後ろの、流していない種を残す。前の夜までのキャッシュをワークフローから消すには `actions: write` が要り、権限を広げることになるので、担当者が消す。
- 時期の選択肢 2 は、0283 の 7（#647 を初回リリースの前に終え、タグの push を頼んでから push までも対象として扱う）と合わない。
- 利用者は 2026-11-09 に会話で、受け取り手を「SSH の公開鍵を使う」「この PC の id_ed25519 だけ」と選んだ（PR #662）。

## 影響

- 0258 の「見つけた入力を artifact に残すときは、出所とライセンスと `NOTICE.txt` を添える」は、それらを暗号の中に添える形に改める。0258 の「流す手順で通らなかった target は縮めない」「縮める前の種を残す」は、この実行の中では縮めずに置き、キャッシュには残さない形に改める。
- [0261](0261-fuzz-outside-required-checks.md) の分け方 3・4（入力を手元で流す、誤りの文を比べる）と、初回リリースの前に入力と誤りの文を issue に貼ること、0283 の対象でないものを公開で扱うことは、暗号を開ける人が行う。秘密鍵のない機械のエージェントは、これらを利用者に頼むので、入力のある失敗が出た PR は、関係のない失敗でも、開くまでマージできないことがある。受け取り手を足すかは、利用者が決める。
- 通らなかった target は、次の夜に種を育て直すので、その target の fuzz が浅くなる。
- この記録の前の実行の log と artifact には、平文の入力と詳細が残る。扱いは 0283 の 7 のとおりにする。
