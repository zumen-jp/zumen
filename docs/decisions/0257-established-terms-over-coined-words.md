# 0257: 和語への言い換えをやめ、開発と実務で定着した語で書く

| 項目 | 内容 |
| --- | --- |
| 日付 | 2026-11-03 |
| 状態 | 採用 |

## 背景

<!-- textlint-disable prh -->

- [0005](0005-japanese-first.md) で日本語を正とし、[0021](0021-notation-and-terms.md) で表記の基準と用語集を決めた。0021 は、和語に言い換えた語（境界・結合・包みなど）を用語集に載せたが、文書全体の言い換えは決めなかった。
- その後、実装が進み、和語の言い換えは文書・コメント・カタログ・スキーマの説明に広がった。2026-11-03 の時点で、次のような語を使っていた（括弧の中は、一般の言い方）。
  - 言語への API: 境界（API）・包み（ラッパー）・結合（バインディング）・階層（Tier）・実行の形（形態）・鏡のリポジトリ（ミラー）
  - データの構造: 欄（フィールド）・印（フラグ・マーカー）・目印（タグ）・見出し（ヘッダー）・区画と区切り（セクション）・地図（マップ）・流れ（ストリーム）・入れ物（コンテナー）・書庫（アーカイブ）・見方（ビュー）・読み手と読み取り器（リーダー）・鍵（キー）・成分（コンポーネント）・窓口（レジストリ）
  - 版（バージョン）・大版と小版（メジャーバージョンとマイナーバージョン）
  - 開発: 試料（サンプル）・試験（テスト）・道具（ツール）・台本（スクリプト）・確認の束（検証キット）・寄稿（貢献）・試用画面（プレイグラウンド）
  - AutoCAD の語: 文字の体裁（文字スタイル）・当てはめる点（フィット点）・節点（ノット）・下敷き（アンダーレイ）・反応子（リアクター）・挿す単位（挿入単位）
- 言い換えは、次の点で読み手を迷わせた。
  - 開発者は、ラッパー・バインディング・フィールド・ヘッダー・バージョンで考える。和語を一度、頭の中で訳し戻すことになる。
  - 実務者も、CAD の画面の言葉（文字スタイル・寸法スタイル・フィット点）で考える。
  - 同じ和語が、ほかの意味でも使われる。境界は、API のほかに、ハッチングの境界と 8 バイトの境界にも使っていた。地図は、DWG のマップのほかに、基盤地図情報と地図の空間にも使う。節点は構造の節点と、試料は土質の試料と、試験は標準貫入試験と紛れる。
  - 同じ物を、文書によって和語とカタカナ語で呼んでいた（試料と公開サンプル）。
  - エージェントは、周りの文書の語を写して書くので、言い換えた語から、さらに新しい言い換えが生まれた。
- 利用者は、日本語を中心にする方針は保ったまま、カタカナ語のほうが一般的な語はカタカナ語で書くよう求めた（2026-11-03、「包みという語はラッパーのほうが親しまれているだろう」）。

<!-- textlint-enable -->

## 選択肢

1. **今の言い換えを保ち、用語集で対応を示す。** 直す手間はないが、迷わせる点は残る。
2. **利用者向けの文（README・サイト・診断の文）だけを直す。** 文書とコメントで語が分かれ、エージェントが古い語を写して広げる。
3. **語を選ぶ基準を決め、文書・コメント・カタログ・スキーマの説明を一度に直し、揺れの辞書で確かめる。**

## 決定

3 を選ぶ。0021 の「用語」のうち、言い換えた語の扱いを、この記録で改める。表記の規則（長音・漢字とかな・空白と記号）は変えない。

### 語の選び方

上から順に当てる。

1. **要領・基準・製品が定める語を使う。** CAD製図基準と SXF の語（レイヤ・表題欄・既定義シンボル・点マーカー）、AutoCAD の日本語版の語（画層・文字スタイル・寸法スタイル・フィット点・挿入単位・アンダーレイ）、Excel の語（結合セル）。
2. **開発で定着したカタカナ語と英語を使う。** API・ラッパー・バインディング・フィールド・フラグ・ヘッダー・セクション・ストリーム・コンテナー・アーカイブ・バージョン・テスト・サンプル・ツールは、和語に言い換えない。
3. **どちらでもない語は、ふつうの日本語で書く。** 一般の日本語で通じる語（診断・予算・台帳・出所・忠実度・符号化・要素・図形）は、そのまま使う。
4. **一般の語に、この文書群だけの意味を持たせない。** `形`・`印`・`欄`・`流れ`・`地図` のような語を、特別な意味で使わない。

### 変えないもの

- 識別子・JSON のキー・診断の code・列挙の値（[0015](0015-add-only-boundary-and-version-floors.md)）。`zumen-abi`・`engine`・`edition` などは、そのまま。
- 図面と納品のデータに記録される文字と、適合テストの入力。土木の図のレイヤの名前 `欄`、電子納品の要素の名前 `版` などは、データなので変えない。
- CI の job の名前のうち、main のルールセットが必須のチェックとして名前で指すもの（`試験（Linux x64）` などと `wasm32 で適合試験`）。名前を変えると、チェックが届かず、PR をマージできなくなる。ルールセットと一緒に改めるまで、そのままにする。
- 0021 の本文。言い換えた語そのものを論じているので、この記録へのリンクだけを足す。ほかの決定の記録は、[README](README.md) の 1 つ目の例外（表記の基準に合わせる直し）として直す。

### 確かめ方

- 改めた語のうち、意味が 1 つに決まる言い方を、`prh.yml` に誤りとして足す。前後で意味が決まる語（`境界`・`版`・`印`・`欄`・`見出し` など）は、取り違えのない言い方だけを規則にする。
- 用語集（[docs/style.md](../style.md)）の「言い換えた語」の表をやめる。書き方は「書き方を決めた語」の表に、決めた意味は「意味を決めた語」の表にまとめる。

## 影響

- 文書・コメント・カタログの文・スキーマの説明と、そこから生成したファイル、テストの文字列を直した（約 700 のファイル、約 1 万行）。コードの動きと、適合テストのハッシュは変わらない。
  - 診断の日本語の文が変わる。診断の code と値は変わらない。
  - 文字列が長くなった所で、rustfmt の整形が変わった。
- 開いている PR は、main を取り込むと、`npm run lint:text` が古い語を指摘する。Markdown・ソースコード・設定は、`npm run fix:text` で直せる。前後で意味が決まる語は、この記録の表で選ぶ。
- GitHub のラベル `結合`・`待ち: 試料` は、`バインディング`・`待ち: サンプル` に改める。文書は新しい名前で書く。
- 新しい語は、この基準で選び、用語集と辞書に足す。
