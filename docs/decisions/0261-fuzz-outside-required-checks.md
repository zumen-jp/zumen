# 0261: fuzz の job を main の必須の検査にせず、PR と関係のない失敗ではマージを止めずに早めに直す

| 項目 | 内容 |
| --- | --- |
| 日付 | 2026-11-04 |
| 状態 | 採用 |

## 背景

[0258](0258-fuzz-seeds-and-runs.md) で、crate などを変えた PR でも fuzz を流す。ただ、fuzz の job は main の必須の検査ではない。main の必須の検査は CI の 8 つの job で、fuzz の crate はワークスペースの外にあるので、どれも fuzz の target を組み立てない。fuzz の結果を見ずにマージすれば、fuzz の組み立てを壊す変更や、パニックを足す変更も入る（#545）。

必須の検査にするかは、ルールセットを変えるので、利用者が決める（[0254](0254-parallel-agents-and-cross-review.md)）。fuzz は、PR の変更と関係のない、前からある誤りも見つける。その失敗の扱いもマージの条件に関わるので、利用者が決める。

## 選択肢

### fuzz の job

1. main の必須の検査にする。workflow は `paths` で PR を選ぶので、どの PR でも動かし、変えたファイルを見て中を飛ばす形に直す。
2. 必須の検査にしない。マージの手順で、PR で流れた fuzz の結果も見る。

### PR の変更と関係のない失敗

1. 直すまで、マージを止める。
2. issue にし、利用者に確かめてからマージする。
3. マージを止めず、issue にして早めに直す。

## 決定

fuzz の job は選択肢 2、PR の変更と関係のない失敗は選択肢 3 にする。利用者が 2026-11-04 に会話で決めた（言葉は #545 にある）。CI を軽く保ちたいこと、関係のない失敗は無視してよいが早めに直すことが理由である。

- PR で fuzz が流れたら、その結果も通ってからマージする。
- PR の変更と関係のない失敗は、同じ入力が main でも落ちるものとする。マージを止めないが、見つけた入力を最小にして issue にし、早めに直す。issue に貼るときは、0258 のとおり、元の公開サンプルの出所とライセンスを添える。
- 毎晩の実行で見つけた失敗も、同じく issue にして早めに直す。

## 影響

- main の必須の検査は CI の 8 つの job のままで、CI を軽く保てる。
- fuzz の組み立てを壊す変更とパニックを足す変更は、必須の検査では止まらない。マージの手順で、fuzz の結果を見て止める。
- 関係のない失敗が直るまで、ほかの PR の実行でも、同じ失敗が出ることがある。その issue を指して、マージしてよい。
- 必須の検査にするかと、関係のない失敗の扱いを変えるには、利用者が決め直す（0254）。
