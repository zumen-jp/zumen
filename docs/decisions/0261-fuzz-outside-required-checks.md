# 0261: fuzz の job を main の必須の検査にせず、PR の変更と関係のない失敗ではマージを止めずに早めに直す

| 項目 | 内容 |
| --- | --- |
| 日付 | 2026-11-04 |
| 状態 | 採用 |

## 背景

[0258](0258-fuzz-seeds-and-runs.md) で、crate などを変えた PR でも fuzz を流す。ただ、fuzz の job は main の必須の検査ではない。main の必須の検査は、CI の 9 つの job のうち「サイト」を除く 8 つで、fuzz の crate はワークスペースの外にあるので、どれも fuzz の target を組み立てない。fuzz の結果を見ずにマージすれば、fuzz の組み立てを壊す変更や、パニックを足す変更も入る（#545）。

必須の検査にするかは、ルールセットを変えるので、利用者が決める（[0254](0254-parallel-agents-and-cross-review.md)）。fuzz は、PR の変更と関係のない、前からある誤りも見つける。その失敗の扱いもマージの条件に関わるので、利用者が決める。

## 選択肢

### fuzz の job

1. main の必須の検査にする。workflow は `paths` で PR を選ぶので、どの PR でも動かし、変えたファイルを見て中を飛ばす形に直す。
2. 必須の検査にしない。

### PR の変更と関係のない失敗

1. 直すまで、マージを止める。
2. 利用者に確かめてからマージする。
3. マージを止めず、早めに直す。

## 決定

利用者が 2026-11-04 に会話で、次のように決めた（言葉は #545 のコメントにある）。

- fuzz の job は、選択肢 2 にする。main の必須の検査にしない。理由は、CI を軽く保ちたいことである。
- PR の変更と関係のない失敗は、選択肢 3 にする。無視してよいが、早めに直す。

関係のない失敗について、利用者は理由を挙げていない。エージェントは、次の理由で、選択肢 3 が選択肢 1・2 より合うと考える。

- 選択肢 1 では、main に前からある失敗で PR が止まる。止めても main は安全にならず、直すまで、fuzz が流れる PR がすべて止まる。
- 選択肢 2 では、失敗のたびに利用者を待つ。

この判断をマージの手順にするため、エージェントが次を補った（#545 の範囲、[0174](0174-plan-in-issues.md)・0258 から）。補ったことも、利用者が会話で認めた（日付・head・言葉は PR #554 にある）。

1. PR で fuzz が流れたら、その結果も通ってからマージする。見つけた入力のある失敗は、直すまで、通ったとしない。流し直しや、新しいコミットの実行が通っても、手元で流して落ちなくても、同じである。直したら、その入力を最小にして合成のテストに移し、必須の検査で確かめる。入力のない一時の失敗（runner が取れないなど）は、流し直してよい。
2. 通らなかった失敗は、次の順に見て、関係がある・関係がない・確かめられないの 3 つに分ける。見つけた入力は CI と同じ条件で流し、比べる main は、PR の実行が合わせた main のコミットか、それより新しいものにする。誤りは、種類と、パニックならその関数と文で比べる。行の番号は、PR の変更でずれるので比べない。
   1. PR で足した種（`cargo xtask fuzz-seeds` が書く種）そのものが落ちるなら、関係がある。マージすると、その後の実行が、その種で落ち続けるからである。
   2. 時間切れとメモリの使い過ぎは、確かめられないとする。機械と OS で結果が変わるので、main の target と比べても決まらない。
   3. ほかの、見つけた入力のある失敗は、その入力を手元で PR の target と main の target に流す。どちらの target でも落ちなければ、確かめられないとする。main の target が、PR の実行と同じ誤りで落ちれば、関係がない。ほかは、関係がある。
   4. 入力のない失敗（組み立てやツールの失敗）は、main の実行と比べる。同じ手順が同じ誤り（落ちた target と誤りの文）で落ちれば、関係がない。PR の実行に、main の実行にない誤りがあれば、関係がある。
3. 分けたあとは、次のようにする。
   - 関係がある失敗は、直してからマージする。
   - 関係のない失敗では、マージを止めない。
   - 確かめられない失敗は、直してからマージする。直せないときは、その PR でマージの条件を緩めることになるので、AGENTS.md の「人を待つもの」の「『開発の手順』の PR・push・マージの条件を緩める変更」として、「人を待つ PR」の手順で扱う。PR に「待ち: 利用者」を付け、PR の番号・head・失敗した実行の ID と、分けた結果（手元でどちらの target が落ちたか）を示して、会話で認めてもらう。認める範囲は、その失敗（実行の ID・target・誤り）とする。認めた日・head・範囲・言葉を PR に書き、認めた会話のエージェントか利用者がマージする。あとの実行で、範囲の外の確かめられない失敗が出たら、認め直してもらう。
4. 関係のない失敗と、利用者に認めてもらってマージする失敗は、マージの前に issue にし、PR の本文にその issue を書く。同じ失敗の issue があれば、それを使い、実行の ID をコメントに足す。issue には、落ちた target か手順、誤りの文、実行の ID を書く。見つけた入力があれば、0258 のとおり最小にし、元の公開サンプルの出所とライセンスを添えて貼る。artifact は 14 日で消えるので、直すときに再現できるようにするためである。手元で再現せず、最小にできない入力は、貼らずに、artifact の中の名前と、最小にできなかったわけを書く。issue は、いちばん前の開いた段階の issue の子にし、開いた子 issue のいちばん上に並べる。並べた理由は、0174 のとおり、親の issue のコメントに、この決定を指して書く。
5. 毎晩の実行で見つけた失敗も、同じく issue にして早めに直す。fuzz は入力を乱数で作るので、ある夜に落ちても、次の夜は通ることがある。エージェントは、作業を選ぶ前に、main の毎晩の fuzz の終わった実行のうち、結論が `success` でなく、その実行の ID を書いた issue がないものを探し、あれば issue にする（`docs/work.md` の「選び方」）。入力のない一時の失敗（runner が取れない、ほかの実行に取り消された、など）は、流し直して通れば、issue にしない。main で手で流した実行が通らなかったときは、流した側が、同じく issue にする。

分け方と確かめ方は、`fuzz/README.md` の「落ちたとき」にある。

## 影響

- main の必須の検査は今の 8 つのままで、CI を軽く保てる。
- fuzz の組み立てを壊す変更とパニックを足す変更は、必須の検査では止まらない。マージの手順で、fuzz の結果を見て止める。PR のひな形の「確かめたこと」にも、fuzz の項目を足す。
- 関係のない失敗が直るまで、ほかの PR の実行でも、同じ失敗が出ることがある。その issue を PR の本文に書いて、マージしてよい。
- main の組み立てかツールが落ちている間は、PR の fuzz は何も確かめないので、パニックを足す変更も止まらない。入力のない失敗を関係のない失敗に入れた代わりに起きることで、早めに直す。
- 時間切れとメモリの使い過ぎと、手元で再現しない入力は、関係がないとは確かめない。main に前からある失敗でも、直るまで、当たった PR は直すか、利用者に認めてもらう。この種類では、選択肢 1・2 に近い扱いになる。機械で結果が変わる失敗を、確かめずに関係のない失敗としないためである。
- 見つけた入力は、リリースするまでは、公開の issue に貼る（貼るときの条件は 0258 にある）。`SECURITY.md` は、落ちる入力を公開の issue に書かないよう求めるので、リリースしたあとの扱いは #557 で決める。
- 必須の検査にするか、関係のない失敗の扱い、補ったことを変えるには、利用者が決め直す（0254）。
