# 0241: 電子納品の成果品は、名前の集まりか ZIP で受け、delivery_check の op でプロファイルと照らす

| 項目 | 内容 |
| --- | --- |
| 日付 | 2026-11-02 |
| 状態 | 採用 |

## 背景

段階 4（[#305](https://github.com/zumen-jp/zumen/issues/305)）では、電子納品の成果品を読み、要領に沿ってチェックする。成果品は、フォルダー・管理ファイル（`INDEX_C.XML`・`DRAWING.XML`・`PHOTO.XML` など）・図面・写真の集まりである。いまの `check`（[決定 0173](0173-profile-checks.md)）は、開いた図面モデルの文書 1 つだけを相手にする（#382）。

決めることは、次のとおり。

- 入力の形と、境界の op。
- 成果品の L1・L2（[決定 0008](0008-model-layers-and-codecs.md)）と、crate の置き場所。
- 管理ファイルの DTD の扱い。
- 結果の返し方。
- 要領の版と発注機関の違いの表し方。

## 選択肢

境界の入口の選択肢は、次の 2 つ。

1. **新しい op `delivery_check` を足す。** 成果品の全体を 1 回の要求で受ける。
2. **`check` に、成果品を指す欄を足す。** 図面の照合と、成果品の照合の欄が 1 つの要求に混ざる。

DTD の扱いの選択肢は、次の 2 つ。

1. **DTD を処理せず、要領の表の規則をプロファイルの規則にする。** DTD は同梱しない。
2. **DTD を読んで検証する。** XML の L0 は DTD を処理しない（[決定 0010](0010-budget-by-work.md) の予算と、外部の実体を読まない方針）。DTD は要領の頁の転載・改変の禁止に触れるので、同梱もできない（`formats/ledger.toml` の `delivery`）。

## 決定

入口は選択肢 1、DTD は選択肢 1 にする。

### 入力

- 成果品は、`zm_push` で渡した入力の名前の集まりか、ZIP の入力 1 つで受ける。
  - 名前の集まりは、`/` で区切った相対の名前（[決定 0012](0012-boundary-functions-and-messages.md)）で、共通の起点（`root`。`納品/` など）の下にあるものとする。
  - ZIP は、`zumen-zip` の L0 で展開し、中の名前を同じ規則で使う。展開した量は予算（`decoded-bytes`）で数える。
- 名前の大文字と小文字は、元のまま持つ。要領は英大文字を求めるので、違えば指摘にする（下の照合）。

### op

- `delivery_check` を足す（小版を 1 つ上げる、[決定 0015](0015-add-only-boundary-and-version-floors.md)）。欄は、次のとおり。
  - `root` か `archive`: 成果品の起点の名前か、ZIP の入力の名前。どちらか 1 つ
  - `profiles`・`profile`: `check` と同じ。プロファイルの入力の列と、使うプロファイルの `id` と `edition`
  - `offset`・`limit`: 返す指摘の範囲（`check` と同じ）
- 成果品の中の図面（SXF・DXF など）は、この op では開かない。図面の照合は、利用者が図面ごとに `open` と `check` で行う。成果品のファイルの名前を `check` の `file_name` に渡せる。

### L1・L2 と crate

- 新しい crate `zumen-delivery`（台帳の領域 `delivery`）に置く。依存は `zumen-base`・`zumen-sdk`・`zumen-xml`・`zumen-zip` にする。
- L1 は、成果品の名前の木（フォルダーとファイル、大きさ、元の入力の名前）と、管理ファイルごとの XML の要素のグラフ（`zumen-xml`）にする。
- L2（成果品のモデル）は、管理ファイルの記録を、要素の元の名前と値の文字の組の木で持つ。要領の版ごとに要素の名前が違うので、型にしない。管理ファイルが指すファイルの名前は、成果品の中の名前に解いて持つ。解けない名前も、元の文字のまま持つ。
- 管理ファイルは、宣言の文字コード（ふつうは Shift_JIS）で読む（`zumen-xml`）。

### DTD とプロファイルの規則

- DTD は処理せず、同梱もしない。`<!DOCTYPE>` の名前（`INDE_C05.DTD` など）は、L1 に文字のまま持つ。
- 管理ファイルはどれも文書型宣言を持つので、XML の L0 の `xml.dtd.dropped`（[決定 0209](0209-xml-l0-without-dependency.md)）は、成果品の読み取りでは返さない。DTD で宣言する実体の参照（`xml.entity.unsupported`）は返す。
- 要領の表に書かれた規則（要る要素、文字の数、使う文字、値の一覧、フォルダーの構成、ファイルの名前）は、プロファイル（[決定 0138](0138-profiles-as-versioned-data.md)）の照合の種類と規則にする。規則ごとに、要領の版と節を出典に書く。表の値は、要領の頁を写さず、照合に要る値だけを語彙にする。
- 照合の種類は、#384 で足す（フォルダーを含む名前、要るファイルの有無、管理ファイルと実際のファイルの突き合わせ、適用要領基準とプロファイルの一致、使う文字、DTD の名前と版）。古いコアは、知らない種類を飛ばす（[決定 0179](0179-profile-check-details.md)）。

### 結果

- `check` と同じ形にする。照合に使ったプロファイルの鎖、規則ごとの指摘の数と照合できなかった数、指摘の列、続きの位置。
- 指摘の場所は、成果品の中のファイルの名前と、管理ファイルの要素（バイトの範囲）にする。
- 指摘の code は、照合の種類ごとに `profile.<種類>.invalid`、照合できなかったものは `profile.<種類>.unsupported`（重要度 `info`）にする。結果は「指摘なし」「確認できなかった項目」と言い、適合とは言わない（`docs/style.md`）。
- 成果品を読めない（ZIP が壊れている、起点の下に名前がない）ときは、診断を返して何も照合しない。

### 版と発注機関

- 要領の版ごとに、プロファイルの版を足す。最初のプロファイルは、国土交通省の土木の要領（工事・設計業務）の最新の版にする。
- ほかの発注機関（都道府県など）と営繕の要領は、国土交通省のプロファイルを `extends` で引き、語彙と規則を足すか置き換える（[決定 0138](0138-profiles-as-versioned-data.md)）。

### wasm のモジュール

- 電子納品の crate と op は、まだ図面のモジュールに置く。モジュールを分けるときに、置き場所を見直す（[決定 0221](0221-wasm-modules.md)）。

## 影響

- #383 は、`zumen-delivery` の L1・L2 と、名前の集まりと ZIP からの読み取りを作る。境界の op（`delivery_check`）の骨組みも #383 で足し、照合の種類は #384 で足す。
- #384 の照合の種類は、この決定の一覧のとおり。
- #388 の写真の突き合わせは、同じ op とプロファイルに規則を足す。
