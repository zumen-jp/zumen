# 0288: エディターは `editor/` に置き、確定した操作ごとに apply してシーンを差し替え、取り消しは書き戻したファイルの版で持つ

| --- | --- |
| 日付 | 2026-11-10 |
| 状態 | 採用 |

## 背景

受け取った図面を、同じ形式のまま直して返すエディター（#692）を作る。書き出しの経路は[決定 0008](0008-model-layers-and-codecs.md#書き出しの経路) の「同じ形式の編集」で、`apply`（[決定 0139](0139-drawing-apply.md)）が触れたレコードだけを書き直す。作り始める前に、置き場所、変更を画面に見せる流れ、取り消しとやり直し、保存、1 回の操作に許す時間を決める（#693）。

使える部品と、その性質は次のとおり。

- `apply` は、文書のハッシュと要素のハッシュの前提条件を、一覧を当てる前の文書ですべて確かめ、1 つでも当てられなければ何も変えない。同じ要素を 1 つの一覧で 2 回指すと、一覧の全体を断る。成功すると、変更ごとの新しい ID とハッシュ、文書のハッシュ、書き戻したファイル（blob）を返し、セッションの文書を書き戻したものに替える。返す ID とハッシュは、書き戻したファイルを読み直したときと同じになる（0139）。
- `restyle`・`transform`・`remove`・`replace` は、要素のハッシュを必ず持つ。ハッシュは、`entities` か、前の `apply` の結果から得る。`entities` は、呼ぶたびに図面モデルへ変換し直す（[決定 0117](0117-entities-op.md)）。`scene` と `apply` も同じである。
- 表示部品の `setScene` は、レイヤの非表示・選択・hover・強調を消し、カメラを保つ（[決定 0274](0274-view2d-selection-and-state.md)）。操作の途中の形は、重ね描き（[決定 0276](0276-view2d-input-tools-and-measurement.md)）で描ける。
- wasm には時間の上限がない（[決定 0010](0010-budget-by-work.md)）。止めるには、予算か、Worker を終わらせる。
- `@zumen-jp/view2d`・`@zumen-jp/react` は公開していない（`private`）。プレイグラウンドは、このリポジトリの中から `file:` で使う。React のフック（`useDrawing`）の Worker は、開いて描くだけで、`apply` を呼ばない。

## 測ったこと

[bench/editor](../../bench/editor/README.md) で、公開サンプルの DWG・DXF（`samples/dwg/zumen-layout-r2018.dwg` と `zumen-layout-r2018_ascii.dxf`）と、適合テストの合成の JWW・SFC・P21 を土台にし、`apply` の `add` で要素を足した図面を作って測った。受け取った図面は使っていない。環境は Windows 11・AMD Ryzen 5 3600XT・Node.js 24.22 で、ネイティブは同じ機械のリリースのビルドである。

1 回の操作（1 件を動かす `apply` と、そのあとの `scene`）の時間は次のとおり。単位はミリ秒で、3〜5 回の中央値。wasm の値を書き、括弧の中はネイティブの値。

| 形式 | 1,000 要素 | 10,000 要素 | 大きな図面 |
| --- | ---: | ---: | ---: |
| DWG | 20（36） | 163（227） | 1,218（1,515）、6 万要素 |
| DXF | 14（22） | 125（206） | 2,891（1,823）、10 万要素 |
| JWW | 5（7） | 52（104） | 605（736）、10 万要素 |
| SFC | 13（17） | 126（187） | 1,910（2,039）、10 万要素 |
| P21 | 47（51） | 873（661） | 5,136（1,912）、3 万要素 |

- 時間は、変更の数より、図面の大きさで決まる。1 件を動かすのと 100 件を動かすのは、ほぼ同じ時間になる。`apply` は、図面モデルへの変換を 2 回と、ファイルの全体の書き出しを含む（0139）。1,000 要素から 1 万要素では、時間はおおむね要素の数に比例する。10 万要素では、wasm でそれより速く増え、DXF は 1 万要素の 23 倍かかる。
- P21 は、1 万要素から 3 万要素で、wasm の時間が 6 倍に増える。3 万要素では、ネイティブの 3 倍かかり、足すのに 8.9 秒、除くのに 7.7 秒かかる。
- `entities` は、呼ぶたびに図面モデルへ変換するので、10 万要素の図面では、1,000 件を読むだけで 77〜681 ms かかる。全件を 1 万件ずつ読むと、0.8〜4.7 秒かかる。
- 1 回の操作のあとの wasm のメモリは、10 万要素で 240〜417 MiB になる。ファイル（3.7〜15 MB）の 24〜68 倍である。
- 予算の作業量は、ネイティブと wasm で同じになった。1,000 要素の `open`・`scene`・`apply` と、1 万要素の `scene` について、4 つの単位の 80 の値を比べた。

## 選択肢

- **置き場所。** リポジトリのルートの `editor/`、`apps/editor/`、別のリポジトリを比べた。表示部品と React のフックは公開していないので、別のリポジトリは、それらを公開するまで作れない。`apps/` を作ると、ルートにあるプレイグラウンドとサイトと、並びが分かれる。
- **変更を画面に見せる流れ。**
  1. 確定した操作ごとに `apply` し、シーンを作り直す。操作の途中は重ね描きで見せる。
  2. 変更を重ね描きで見せて溜め、保存のときにまとめて `apply` する。
  3. JavaScript で図面のモデルを持って描き、保存のときに変更の一覧にする。

  2 は、当てられない変更が、保存のときまで分からない。1 つの一覧で同じ要素を 2 回指せず、足した要素の ID は `apply` まで決まらないので、直した要素や足した要素を続けて直せない。画面と保存するファイルが食い違いうる。3 は、コアと同じ解釈を JavaScript で作り直すことになり、どこでも同じ結果（[決定 0007](0007-single-rust-implementation.md)）と、描かないものを診断で返す約束を、画面で守れない。1 は、1 回の操作の時間が、図面の大きさに比例する。
- **取り消しとやり直し。**
  1. 操作ごとに、書き戻したファイルのバイト列を版として持ち、取り消すときは、その版を開き直す。
  2. 元のバイト列と操作の一覧を持ち、取り消すときは、元から当て直す。
  3. 操作ごとに逆の変更を作り、取り消すときに当てる。

  3 は、元のバイト列に戻らない。逆の行列で動かしても、浮動小数の丸めで元の座標に戻らない（0.1 に 5 を足して引くと 0.09999999999999964 になる）。除いた要素を足し直すと新しいハンドルが付き、`apply` で書けない値（拡張データなど）は戻せない。2 は、取り消すたびに、それまでの操作の数だけ `apply` を当て直す。1 は、同じバイト列から同じ ID とハッシュが返るので、操作の前の状態にそのまま戻る。メモリは、ファイルの大きさと版の数の積になる。
- **保存。** File System Access API で元のファイルに上書きする案と、ダウンロードだけにする案を比べた。File System Access API は、Chromium 系のブラウザーにしかない。ダウンロードはどのブラウザーでも使えるが、元の場所へ戻すのは利用者の手になる。

## 決定

置き場所は `editor/`、流れは 1、取り消しは 1 を採る。保存は、ブラウザーで使える方法に合わせて両方を使う。

### 置き場所

- リポジトリのルートの `editor/` に置く。npm のパッケージの名前は `zumen-drawing-editor` で、公開しない（`private`）。プレイグラウンドと同じく、Vite 8.3.5 と React 19.3.1 を使い、`@zumen-jp/react`・`@zumen-jp/view2d`・`@zumen-jp/zumen` を `file:` で使う。図面用の wasm は、ローカルの配布物に含める。
- CSS は `public` からそのまま写し、Lightning CSS（MPL-2.0）を通さない。組み込んだ依存のライセンスは、Vite で `licenses.md` に出す（[決定 0268](0268-distribute-wasm-modules.md)）。実行時の依存は、寛容なライセンスのものに限る。
- 画面の文は `editor/` に置く。診断の文は、プレイグラウンドと同じく、`describe` でカタログから引く。
- 編集の Worker は `editor/` に作る。`useDrawing` の Worker は開いて描くだけなので、使わない。Worker とのやり取りは、公開する部品の API にしない。
- AGENTS.md の地図に `editor/` を足す（作る PR で）。プレビューのポートは 24189 にする。
- PR ごとの CI の Chromium の検査に、エディターを組んで、開く・選ぶ・直す・取り消す・保存する操作と、通信を確かめる手順を足す。毎晩の CI では、Firefox と WebKit でも確かめる。テストの図面はテストの中で作り、通信は、ローカルの配布物を取得する GET だけを認める。

### 編集の流れ

- 1 つの Worker に 1 つのセッションを持ち、1 つの文書を開く。画面のスレッドは wasm を呼ばない。入力の上限は `useDrawing` と同じにする（ファイルは 64 MiB、予算の `input_bytes` は 64 MiB、`decoded_bytes` は 256 MiB）。
- 操作（移動・回転・拡大縮小・属性の変更・文字の変更・複写・削除・図形を足す）を確定したら、その操作の変更を 1 つの `apply` の一覧にまとめる。文書のハッシュ（`hash`）を必ず付け、要素は、`entities` か前の `apply` が返したハッシュで指す。1 つの要素に 2 つの変更が要る操作（動かしてレイヤを変えるなど）は、続けて 2 回 `apply` し、履歴では 1 つの操作にする。2 回目が断られたら、操作の前の版を開き直す。
- `apply` が成功したら、同じ起点で `scene` を呼び、`setScene` で差し替える。差し替えで消えるレイヤの非表示はレイヤの ID で戻し、選択は、変えた要素を `applied` の新しい ID に置き換えて戻す。`ids_shifted` が立ったら、変えた要素だけを選び直し、ほかの選択と、読んだハッシュを捨てる。
- 操作の途中（ドラッグ・図形を足すツール）は `apply` せず、重ね描きで見せる。確定から差し替えまでは重ね描きを残し、処理中であることを示す。
- 選んだ要素の値とハッシュは、選んだときに、起点（`place`）と選んだ範囲（`region`）で `entities` を呼んで読み、選んだ ID のものだけを使う。開いたときに全件を読まない。
- `apply` が断ったら、文書は変わらない。画面を操作の前に戻し、診断の種類・件数・場所を見せる。
- `apply` から差し替えまでは、次の操作を受けない。前提条件のハッシュは前の `apply` の結果で決まるので、操作を溜めない。
- 処理中は、止める操作を出す。wasm は時間で止められないので、利用者が止めたら Worker を終わらせ、新しい Worker で今の版を開き直す。

### 取り消しとやり直し

- 履歴は、版の並びで持つ。版 0 は、開いた元のファイルのバイト列にする。版 k は、k 回目の操作の最後の `apply` が返したファイルのバイト列にする。版ごとに、文書のハッシュと、操作の説明を持つ。
- 取り消しとやり直しは、その版のバイト列を開き直し、`scene` で差し替える。選択は消す。
- 取り消したあとに新しい操作をすると、今の版より後の版を捨てる。
- 版のバイト列は、画面のスレッドで持つ。Worker を作り直しても失わないためである。合計が 256 MiB か 100 版を超えたら、版 0 を残して、古い版から捨てる。捨てた版へは戻れないことを、画面に示す。

### 保存

- 保存するのは、今の版のバイト列そのものにする。画面のスレッドで書き換えない。
- `showSaveFilePicker` があるブラウザー（Chromium 系）では、File System Access API で、名前を付けて保存する。ほかのブラウザーでは、元のファイルの名前でダウンロードする。
- 元のファイルへの上書きは、`showOpenFilePicker` かドラッグで開いて、ファイルの handle を持つとき（Chromium 系）だけ選べるようにし、毎回確かめてから書く。書き込みは、閉じるまで元のファイルに反映されない（`FileSystemWritableFileStream`）。
- 保存の前に、`apply` が返した診断（形を変えて書いたもの・失った値）を、種類・件数・場所で見せる。
- 保存していない版があるときは、ページを閉じる前に知らせる。

### 外へ送らない・オフライン

- 図面は File API で読み、送る API（`fetch` の POST・`WebSocket`・`sendBeacon` など）を使わない。
- CSP は、プレイグラウンドの CSP（`default-src 'none'`・`script-src 'self' 'wasm-unsafe-eval'`・`connect-src 'self'` など）から始める。HTML の meta に書き、置き場所が HTTP のヘッダーを付けられるなら、同じものをヘッダーにも付ける。
- オフラインで開けるよう、Service Worker で、組んだファイル（HTML・JS・CSS・wasm）を同じ origin の GET だけで保存して返す。図面のバイト列は Service Worker を通らない。依存は足さない。作るのは公開のとき（#698）にする。

### 1 回の操作に許す時間

- wasm で、1 回の操作（`apply` と、そのあとの `scene`）を、1 万要素までの図面では 200 ms、10 万要素までの図面では 2 秒に収めることを目安にする。100 ms を超える操作では、処理中であることを示す。
- 測った結果では、1 万要素の DWG・DXF・JWW・SFC が目安に収まる。10 万要素の DXF と、P21 は収まらないので、コアの issue で速くする（#708・#709）。

### API に足りないもの

- #694 の範囲は、今の op（`open`・`drawing`・`tables`・`entities`・`scene`・`apply`・`describe`・`close`）で作れる。足す op はない。
- 足りないものは、コアの issue にした。DWG に足して `$HANDSEED` の長さが変わると断ること（#701）、JWW に API で線・円・円弧を足せないこと（#702）、図面モデルへの変換を呼び出しの間で使い回さないこと（#708）、P21 の `apply` が遅いこと（#709）。

## 影響

- #694〜#696 は、この流れで作る。#698 で、CSP をヘッダーに付け、Service Worker を作る。
- 大きな図面では、1 回の操作と取り消しに秒の単位がかかる。コアの issue が入るまで、10 万要素の DXF で約 3 秒、3 万要素の P21 で 5〜10 秒になる。
- 15 MB の DXF では、履歴は 256 MiB で 16 版ほどになる。それより前の操作は、版 0 に戻すことでしか取り消せない。
- 測りは `bench/editor` で作り直せる。コアを速くする PR は、同じ測りで前と比べる。
