# 0254: 複数のエージェントが並行して進め、互いに確かめ、人を待つのは人にしかできないことに限る

| 項目 | 内容 |
| --- | --- |
| 日付 | 2026-11-03 |
| 状態 | 採用 |

## 背景

作業は、[決定 0174](0174-plan-in-issues.md) の選び方で、主にエージェントが進めている。2026-10-24 からの 10 日で、形式は約 25、API の op は 31、決定の記録は 253 件になった。利用者は 2026-11-03 に、複数のエージェントを同時に動かし、互いに確かめさせて、広げる速さを保つことを選んだ。人の判断は、できるだけ待たない。

この進め方で、次の問題が出た。

- **待ちがたまり、確かめていない形式が増えた。** 選び方は、待ちのラベルのない最初の葉を選ぶ。待ちに当たると飛ばして次の形式へ進むので、待ちの issue が 27 件（サンプル 13・判断 9・検証環境 5）たまった。J-LandXML・LAS・CityGML などは、実物のファイルを読まずにマージした。#412 は、使える公開サンプルを見つけたあとも、待ちのラベルのために取り込まれなかった。
- **自前のテストだけでは、誤りが見つからなかった。** 組み直した R2004・R2010・R2018 の DWG は、2026-11-02 に AutoCAD 2027 で開くまで、どれも図面ファイルとして無効と判定されていた（#345）。自前の往復のテストは通っていた。書く側と同じ読みで作ったテストは、仕様の読み違いを見つけない。
- **確かめた度合いが、読む人に分からない。** `docs/formats` の文書は、実物で確かめた規則と、仕様だけから書いた規則を分けていない。
- **別の目が入っていない。** PR の多くは、開いてから数分でマージした。PR を通さずに main に入れたコミットが、最初のコミットを除いて 87 件あった。決定の記録はマージで採用になるので、別の目を通らずに採用になっていた。
- **「待ち: 判断」の一部は、エージェントが決められた。** 9 件のうち 3 件は、公開の API の形や、変換で書く形式のような設計の選択だった。
- **誰が着手したかが分からない。** エージェントは同じ GitHub のアカウントで動くので、ラベルと本文だけでは、着手した者を見分けられない。「作業中」なのに本文が未着手のままの issue もある。
- **並行してマージすると、main が壊れうる。** 必須の検査は、最新の main を取り込むことを求めていない。それぞれの PR の CI は古い main の上で通るので、決定の番号・診断の code・生成物のずれが、main に入ってから見つかる。決定の番号は、PR を開くまで押さえられない。この記録も、並行した PR と同じ番号を使い、後から付け替えた。
- **決定の記録が、実装の細部の記録になった。** 0023〜0104 の 82 件はすべて AutoCAD の系統で、その多くはフィールドの符号化の細部だった。大事な判断が埋もれる。
- **形式や用途ごとの op が増えた。** `ids_check`・`bcf_read`・`photo`・`sheet`・`boring`・`delivery_check` のように、領域の op で表せたかもしれないものが、API に足されている。
- **受け取ったファイルを読む所の守りが、形式の数に追いついていない。** fuzz の対象は 4 つの形式だけで、CI でも流していない。浮動小数の足し算で数える繰り返しが止まらない誤り（#486）は、マージの後に見つかった。

## 選択肢

1. 段階に関門を置き、前の段階を確かめるまで次の形式に進まない。確かめた順に進むが、同時に動けるエージェントの数を生かせず、利用者の選んだ速さと合わない。
2. 今のまま進める。速いが、待ちと確かめていない形式がたまり続け、誤りは実際のソフトで開くまで見つからない。
3. 広げるのは続ける。人を待つのは人にしかできないことに限り、ほかの判断はエージェントが決める。人の確認の代わりに、別のエージェントの確認と、外部の実装・公開サンプルとの照合を入れる。確かめた度合いを形式ごとに示し、確かめる作業を広げる作業と並べて進める。

## 決定

選択肢 3 を選ぶ。決定 0174 のうち、待ちのラベルの意味、待ちに当たったときの扱い、着手の名乗り方と古い着手の引き継ぎを、この決定で変える。決定 0171 のうち、ライセンスがはっきりしない公開サンプルの扱いも変える。決定 0015 の 1.0 より前の例外と、決定 0017 の形式を足す手順には、条件を足す。木・優先順・依存の仕組みは変えない。

### 人を待つもの

人を待つのは、次のことだけにする。

- 権利者への問い合わせ、契約・規約への同意（同意の要るツールを入れることを含む）、費用のかかること（規格の書籍の購入など）。
- 権利の判断。台帳の `rights` を `unknown`・`permission` から `public` に変えること、NC・ND や利用規約の読みで採否が決まるもの、持ち主が仕様を公開していない形式（推定や公開の実装で読む形式）と持ち主の分からない形式を、新しく `public` として足すこと。
- リポジトリのライセンス（[決定 0002](0002-dual-license.md)）を変えること。
- アカウント・署名の鍵・secrets、パッケージの名前の確保と公開（`v*` のタグの push・GitHub の Release・レジストリへの公開）。
- GitHub の設定の変更。設定は、リポジトリと組織の設定の画面か、その API で変えるもののすべてを指す。ルールセット・ブランチの保護・Actions の権限・secrets と変数・環境・Webhook・アプリ・公開の範囲・コラボレーターとチームの権限・deploy key・マージの設定（squash・自動マージ）・既定のブランチ、リポジトリの名前の変更・移管・アーカイブ・削除を含む。ラベル・issue・PR の操作は設定に入れず、ラベルは下の「ラベル」の節に従う。
- ワークフローの変更のうち、`permissions` を広げる・secrets を使う・権限つきで動く発火の条件（`pull_request_target`・`workflow_run` など）を足すもの。公開の手順（`release.yml`）のうち、出す先・認証（trusted publishing・`id-token`）・環境・発火の条件を変えるもの。公開の job（`id-token: write` か `contents: write` を持つ job）の手順を変えるもの。ただし、`CRATES` などの一覧に名前を足すだけの変更は除く。
- このリポジトリの外への書き込みと送信。ほかのリポジトリへの issue・PR・コメント、メール、外部のサービスへのファイルの送信。上流への報告は、文案を issue に書いて利用者に頼む。
- 利用者の手元にしかないものを用意すること。受け取った図面を `ZUMEN_SAMPLES` に置く、ライセンスの要るソフトを使えるようにする、アプリの利用を許す。
- 利用者が issue・PR・会話で決めたこと（日付と言葉の記録があるもの）を変えること。
- この決定の全体と `docs/work.md`、`AGENTS.md` の「並行して進める」「範囲と権利」「図面と秘密」「守る約束」と、「開発の手順」のうち PR・push・マージの条件を緩める変更。緩めるか迷うものも含める。

ほかの判断（設計・優先順・仕様の読み方・`AGENTS.md` の規則の範囲での依存の選択など）は、エージェントが選択肢と理由を書いて決める。リポジトリのファイルは、PR で変えて互いに確かめる。ワークフローの普通の変更、出す crate や wasm のモジュールを `release.yml` の一覧に足すだけの変更、`deny.toml`・`rust-toolchain.toml` の変更も、これに入る。ただし、上の最後の項に当たるもの（`deny.toml` で寛容でないライセンスを許す・`[bans]` の禁止を外すなど）は除く。新しく出す crate の名前は、次の `v*` のタグの前に、利用者に一覧で示す。`site/` の変更はマージで公開されるが、パッケージの公開に当たらないので、PR で互いに確かめて進める。issue・PR・コメントは消さず、閉じるか、新しいコメントで直す。秘密や受け取った図面の情報が入ったら、すぐ利用者に伝える。コメントは消すか、伏せたうえで編集の履歴から前のバージョンを消す。名乗りと確かめた結果のコメントは、消さずに、その所だけを伏せる。本文のように消せないものも、伏せたうえで、編集の履歴から前のバージョンを消す（エージェントが消せなければ、利用者に頼む）。消した所か伏せた所と理由は、秘密を書かずに新しいコメントに書く。push したコミット・ブランチの名前・題に入ったものは、force push や題の変更では GitHub から消えないので、GitHub に消してもらうかを利用者に決めてもらう。secrets は、利用者に替えてもらう。

人を待つものを含む PR は、次のように扱う。

- ラベル「待ち: 利用者」を付け、本文に、一覧のどの項に当たるかと、その中身を書く。ラベルは、マージか閉じるまで外さない。利用者が認めたかは、ラベルでなく PR の記録で見る。
- 利用者が認めたとするのは、エージェントが利用者に PR の番号・head・当たる項を示したあとの、その PR についての利用者の会話での言葉だけである。ワークフローの項に当たる PR は、下の push の前の承認で、その PR の全体の差分と当たる項のすべてを示したときに、それをその PR の承認とする。足りなければ、PR を開いたあとに、PR の番号・head・当たる項を示して認めてもらう。前からある一般の指示は、これに当たらない。エージェントと利用者は同じ GitHub のアカウントで動くので、ラベルが外れたことや GitHub のコメントも、利用者が認めたとはみなさない。
- 認めた日・head・範囲・利用者の言葉を、PR に書く。認めた head と比べて、PR の側で当たる項に関わる所（緩める変更の項なら、その項が守る範囲の文）を変えたら、強める向きの変更でも、変えた所を示して認め直してもらう。main の取り込みで入っただけの変更は除き、衝突を解くために PR の側で変えた所は含む。
- マージするのは、利用者が認めた会話のエージェントか、利用者だけにする。PR の記録だけを読んだエージェントは、マージせずに利用者に確かめる。
- ワークフローの項に当たる変更は、push の前に、差分と当たる項を利用者に示し、会話で認めてもらってから push する。GitHub は、PR を開いた時点で PR の側のワークフローを動かし、`on: push` のワークフローは push した時点で動かすためである。この承認では、PR を開く前なら、PR の番号と head の代わりに、ブランチの名前と push するコミットを示す。PR を開いたあとなら、PR の番号と push するコミットを示す。PR を開いたら、その承認を PR に書く。認める前に、そのブランチでワークフローを手で走らせない。

### ラベル

- **「待ち: 利用者」。** 人を待つものに付ける。利用者は、このラベルで、自分を待つ issue と PR を一覧する。今の「待ち: 判断」を、この名前に変える。利用者の判断のほか、利用者の行い（問い合わせ・費用・公開・設定など）を待つものも含めるためである。
- **「待ち: サンプル」「待ち: 検証環境」。** サンプルと検証環境を待つものに付ける。エージェントが待ちを減らす対象にする。利用者の手元のものが要るなら、「待ち: 利用者」も付ける。
- ラベルの種類と説明は、決定の記録で決めてから変える。

### 待ちに当たったら

飛ばす前に、待ちを減らす。待ちを減らす作業も、着手と同じく名乗る。

- **サンプル。** 決定 0171 の条件に合う公開サンプルを探す。[決定 0019](0019-coordinate-systems-and-gsi-data.md) と台帳で入れないとしたもの（国土地理院のデータなど）は除く。外部の実装で読めるなら、その実装と照らす。
- **検証環境。** 検証キットを作り、issue に置く。キットに入れるのは、テストで作るファイルか `samples/` のファイルと、それを作るコマンド・開く手順・期待する結果だけにする。受け取った図面と、そこから作ったファイル・名前・画面の写しは、公開の issue に置かない。利用者の手元のソフトは、そのセッションで利用者がアプリの利用を許したときだけ、キットのファイルを開くのに使う。
- **判断。** 作業の中で判断に当たったら、人を待つものに当たるかを見る。当たらなければ、エージェントが決めて進める。決定の記録にする判断は、その PR に選択肢と理由を書き、記録にしない判断は、issue のコメントに選択肢と理由を書く。当たれば、「待ち: 利用者」を付け、利用者に頼むことを開始条件に具体的に書く。人を待つものとほかの作業が混ざるなら、人を待つものを別の issue に分ける。
- **「待ち: 利用者」の見直し。** 選ぶ順で「待ち: 利用者」の issue に当たったら、開始条件とコメントを読む。人を待つものに当たらなければ、理由をコメントに書いてラベルを外し、選ぶ。利用者の判断の記録（日付と言葉）があれば、その判断に従う。利用者が何かを待つと決めたもの（要望が来るまで待つなど）は、待つものを開始条件に書き、利用者に頼むことが残っていなければ、ラベルを外す。判断を変えて先に進めたいなら、ラベルを付けて利用者に頼む。
- **試みた記録。** 試みた日と、探した所・結果を、issue のコメントに書く。次のどれかが出るまでは、次からは飛ばしてよい: その issue か親の issue への新しいコメント、関係する PR のマージ、台帳（`formats/ledger.toml`・`samples/ledger.toml`）の変更、前の試みから 14 日が過ぎること。

### 着手の名乗り

- 着手するときは、issue のコメントで名乗る。ブランチ・worktree のフォルダーの名前・時刻と、決定の記録を書くなら使う番号を書く。絶対パスは書かない。名乗ったあとに読み直し、いちばん早い名乗りだけが進める。後の側は、名乗りを取り下げて別の issue を選ぶ。
- 名乗りが通ったら、ラベル「作業中」を付け、本文の「着手・引き継ぎ」を書く。
- 名乗りから 24 時間、PR・ブランチ・名乗りの更新がなければ、引き継ぐと名乗って引き継げる。前の PR とブランチは消さない。「待ち: 利用者」の issue と PR は、24 時間では引き継がず、利用者に確かめてから引き継ぐ。
- 利用者が指定した issue に、ほかの名乗りがあれば、利用者に伝えて指示を待つ。24 時間の更新がない名乗りは、引き継いでよい。
- 同じ issue か、同じ crate・同じ形式の文書を主に変える開いた PR か名乗りがあれば、着手しない。一覧・台帳・生成物（決定の一覧・`catalog/`・スキーマのバージョン・適合テストのハッシュの一覧・`Cargo.lock`）が重なるのは構わず、マージの前に解く。
- 決定の番号は、開いた PR と、名乗りに書かれた番号を見て選ぶ。issue のない作業は、先に issue を作り、その issue で名乗る。番号だけを早く押さえたいときは、下書きの PR を開いてもよい。ぶつかったら、後にマージする側が付け替え、古い番号でその決定を指す開いた PR・issue と main のファイルを探して、直すか知らせる。
- 名乗りと、確かめた結果のコメントは、書き換えず、消さない。直すときは、新しいコメントで直す。秘密や受け取った図面の情報が入ったときだけは、消さずに、その所を伏せて、編集の履歴から前のバージョンを消す。そのときは、伏せた所と理由を、秘密を書かずに新しいコメントに書く。

### 互いに確かめる

- PR は、作った側と別の確かめる側が確かめてからマージする。確かめる側は、作った側の会話を引き継がないエージェント（新しいセッションか、会話を渡さないサブエージェント）か、人にする。
- 依頼には、PR の番号と確かめる観点だけを渡し、作った側の見立ては渡さない。2 回目からは、前の結果と作った側の答えを渡してよい。確かめる側は読むだけにし、自分で直さない。
- 観点は、差分と issue の完了の条件、`AGENTS.md` の「範囲と権利」「図面と秘密」「守る約束」（決定性・黙って捨てない・ID の契約・信用しない入力・API の互換）、仕様の節、テスト、依存のライセンス、表記とする。人を待つものに当たる所がないかと、当たるなら、PR にラベル・当たる項・その中身があるかも見る。利用者が認めた記録があれば、記録の範囲が当たる項のすべてを含むかと、認めた head のあとに当たる項に関わる変更がないかも見る。記録がまだないことは、指摘にしない。記録は、マージする側も確かめる。決定の記録なら、選択肢が実際にあるか、採用済みの決定と食い違わないかも見る。
- 依頼には、結果に書かないもの（受け取った図面のファイル名・顧客の名前・図面の中身・秘密の値・利用者の名前を含むパス）も書く。テストの出力は、件数・code・ハッシュに限って書いてもらう。
- 結果には、指摘ごとに重さ（重・中・軽微）を付けてもらう。結果は、確かめた head のコミットと確かめる側の種類を添え、手を加えずに全文を PR のレビューのコメントに貼る。書かないものが入っていたら、そこだけを伏せ、伏せた所と理由を書く。
- 作った側は、指摘のすべてに答える（直すか、直さない理由を書く）。権利・秘密・API の互換・ID・採用済みの決定との食い違いの指摘を直さずにマージするなら、別の確かめる側にも見せる。人を待つものに当たるという指摘は、作った側が当たらないと考えても、人を待つものとして扱い、利用者に示す。
- 直したあとの差分も、確かめる側に見せる。重と中の指摘がなくなったあとの軽微の直しと、生成物・ハッシュの一覧・一覧の中の位置だけを直す main の取り込みは、確かめ直さない。衝突を解くために、PR の側で番号・文・コードを変えた取り込みは、その差分（`git show --remerge-diff <取り込みの commit>`）を見せる。
- 確かめ直しは、直した差分と答えを主に見る。直した差分の外から出た新しい指摘のうち、重のものと、権利・秘密・人を待つものに関わるものは、その PR で直す。ほかは、追跡先の issue に回してよく、答えにその issue を書く。
- 新しい形式を `public` として足す PR は、確かめる側を 2 つにし、別々に確かめる。足せるのは、持ち主が仕様を公開し、実装を制限していないことを、公式の文書（仕様の文書か、台帳の `evidence` に書く文書）で示せる形式と、持ち主のいない慣用の形式（区切ったテキストなど）だけにする。ほかは、権利の判断として人を待つ。台帳にある形式のバージョン違い・別名は、新しい形式として扱わない。
- CI の通過は、この確認の代わりにしない。

### マージ

- main へは、PR を通さずに push しない。利用者は 2026-11-03 に、ルールセットの管理者の迂回を残すと決めたので、この規則は手順で守る。
- マージの前に、最新の `origin/main` を取り込み、生成物を作り直し、CI を通し直す。
- 指摘に答え、直したあとの差分の確認が済み、CI が通ったら、squash merge してブランチを消す。人を待つものを含む PR は、上の「人を待つもの」の条件で利用者が認めたことを PR に書いてから、利用者が認めた会話のエージェントか、利用者がマージする。

### 形式を足すときの完了の条件

形式・バージョン・向き（読む・書く）を足す issue は、次をそろえて閉じる。ほかの変更は、変えた所のテストを足し、確かめた度合いの節を直す。

- 外部の実装があれば、その実装と結果を照らすテスト。外部の実装のソースもバイナリも、リポジトリに入れない。別に入れたプログラムとして呼ぶ（[決定 0011](0011-bindings-through-ffi.md) のツールの表）か、寛容なライセンスの crate なら dev の依存にする（決定 0011 と `AGENTS.md` の依存の規則に従う）。プログラムとして呼ぶものは、入っていない環境ではテストを飛ばし、指定したときと毎晩の CI で流す。照らして食い違ったら、仕様と、出力・診断を比べて調べる。外部の実装のソースは、寛容なライセンスのものだけを読む。
- 決定 0171 の条件に合う公開サンプルがあれば、`samples/` に足して読むテスト。なければ、探した所を形式の文書に書く。
- fuzz の対象と、テストキットの予算・ID の契約テスト（[決定 0010](0010-budget-by-work.md)・[0017](0017-format-rights-ledger-and-plugin-sdk.md)）。
- 形式の文書の、確かめた度合いの節。

### 確かめた度合い

形式ごとに、読みと書きを分けて、次の 3 つの段で示す。バージョンごとに分けてよい。段の名前は、台帳の今の語（`basis` の `spec`、キーの `samples`・`verify`）と重ならず、保証と取られない語にした。

| 段 | 読む向き | 書く向き |
| --- | --- | --- |
| `synthetic` | 仕様と、テストの中で作ったファイルだけで確かめた | 書いたファイルを、自前の読み取りだけで確かめた |
| `external` | 自前で作っていないファイル（公開サンプル・受け取った図面・外部の実装が書いたもの）を読み、外部の実装が読んだ値か、ファイルに添えられた値と照らした | 書いたファイルを外部の実装が読み、読んだ値が書いた値と合った |
| `application` | その形式の基準になるソフト（作るソフトか、受け取る側のソフト）で開いた結果と照らした | 書いたファイルを、基準になるソフトで開いて確かめた |

- 受け取った図面で確かめたことは、件数と種類だけを書き、ファイル名・顧客の名前・中身を書かない。
- 段は、実際に確かめたことで決める。台帳の `verify` に載っていることでは決めない。
- `synthetic` の段の規則は、読む人に確かめ済みと取られないように書く。台帳のフィールドと検査は、別の PR で足す。

### 確かめる作業を並べて進める

- 確かめていない形式を確かめる issue を、段階ごとに作り、段階の子の上のほうに置く。広げる作業を止めず、待ちのない確かめる作業が先に選ばれるようにする。
- 不確実性の大きい試作（3D の形状と開口のブーリアンなど）は、開始条件のサンプル（日本のソフトの書き出し）を待たずに先に進める。日本のソフトのサンプルは、確かめた度合いを上げるときに使う。

### 公開サンプルの扱い

[決定 0171](0171-public-samples-in-git.md) は、ライセンスがはっきりしない公開サンプルを、足さずに利用者に尋ねるとした。これを、足さずに理由を issue に書くことに変える。どうしても足したいときは、権利者への問い合わせとして利用者に頼む。

### API の整理

- 1.0 より前は、[決定 0015](0015-add-only-boundary-and-version-floors.md) のとおり、API を整理するために壊してよい。壊す判断は決定の記録にし、`schema/README.md` の手順でマイナーバージョン（`schema-minor`）を上げて壊す。壊す PR は、PR とコミットの題の種別に `!` を付け（`feat(abi)!: …`）、PR の本文に移り方を書く。リリースノートは、PR のタイトルから作る。
- ID の規則は、この例外に入らない。
- 形式や用途ごとの op を足す前に、領域の op（`drawing`・`building`・`civil`・`geo`・`pointcloud` など）で表せないかを確かめる。

### 決定の記録にするもの

決定の記録は、実際に選択肢があり、API・ID・層とモデル・依存・権利・形式をまたぐ振る舞い・作業の進め方のどれかに関わる判断に限る。形式ごとのフィールドや符号化の細部は、`docs/formats` に書く。

## 影響

- ラベル「待ち: 判断」を「待ち: 利用者」に名前を変え、説明を直す。名前は、この決定のマージのすぐ後に変える。今の issue を見直し、エージェントが決められるものからラベルを外す。「待ち: サンプル」「待ち: 検証環境」のうち、利用者の手元のものを待つものに「待ち: 利用者」を足す。
- `AGENTS.md`・`docs/work.md`・`docs/decisions/README.md`・`docs/style.md` の用語集・`CONTRIBUTING.md`・issue と PR のひな形を、この決定に合わせる。
- 確かめる作業の issue（#501〜#505）を、段階の子に足す。
- 1 つの変更にかかる手間は増えるが、同時に動くエージェントが受け持つ。人が見るのは、「待ち: 利用者」の issue と PR だけになる。
- マージの前に最新の main を取り込むので、並行する PR は順にマージされる。ルールセットで最新の main を求めれば仕組みで守れるが、設定の変更なので利用者が決める（#527）。
- 公開の守りも、利用者が決める設定の変更で強められる。`release` の環境を `v*` のタグからだけ使えるようにして利用者の承認を付けることと、各レジストリの trusted publishing をこの環境に限ることである。今はリポジトリに環境がなく、job が参照する `release` の環境は、保護のないまま作られる。利用者に頼むことは、#527 にまとめた。
- 外部のプラグイン（決定 0017）のリポジトリへの書き込みも、このリポジトリの外への書き込みとして、人を待つ。
- 決定 0174 の待ちと着手の扱い、決定 0171 のライセンスがはっきりしない公開サンプルの扱いを、この決定で変える。決定 0015 の 1.0 より前の例外と、決定 0017 の形式を足す手順には、条件を足す。それぞれの記録から、この決定にリンクする。
