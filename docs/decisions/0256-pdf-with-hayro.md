## 背景

PDF は #1 の 2 章の対象で、台帳では `public`（ISO 32000-2:2020）である。旧版は、hayro-interpret でページを解釈し、線・文字・画像をシーンに読んだ（[旧版の決定 0020](https://github.com/zumen-jp/zumen-legacy/blob/main/docs/decisions/0020-pdf-drawings-in-rust.md)）。ブラウザーでは、PDF を別の wasm のモジュールにした（[旧版の決定 0030](https://github.com/zumen-jp/zumen-legacy/blob/main/docs/decisions/0030-pdf-in-a-webassembly-module-of-its-own.md)）。新しい層（[決定 0008](0008-model-layers-and-codecs.md)）で読むには、次のことを決める必要があった（#506）。

- ページの内容（内容のストリーム・フォント・CMap・色空間・フィルター）を、自前で解釈するか、依存に任せるか。依存にするなら、`AGENTS.md` の依存の規則（ライセンス・wasm で動くこと・[決定 0007](0007-single-rust-implementation.md) の決定性）を満たすか。
- ファイルモデル（L1）のレコードを、どう区切るか。
- 図面モデルの要素の ID（[決定 0156](0156-drawing-stable-ids-and-preconditions.md)）を、何から作るか。
- wasm のモジュール（[決定 0221](0221-wasm-modules.md)・[0253](0253-wasm-civil-and-pointcloud-modules.md)）のどれに入れるか。

## 選択肢

### ページの解釈

1. 自前で書く。依存は増えないが、内容のストリームの演算子のほかに、フォント（TrueType・CFF・Type 1・Type 3）・CMap・圧縮のフィルター・画像の符号化を読む必要があり、大きい。
2. hayro-interpret を使う（旧版と同じ）。Rust で書かれ、wasm で動き、描く先を `Device` の trait で受けるので、線・塗り・文字・画像をラスターにせずに受け取れる。
3. pdf.js など、ほかの言語の実装を使う。Rust の 1 つの実装（決定 0007）に反し、ネイティブと wasm で同じ結果を返せない。

### L1 の区切り

1. hayro-syntax が読んだオブジェクトを使う。hayro-syntax は、オブジェクトのバイト列の範囲を返さないので、書き戻しにも、診断の場所にも使えない。
2. 自前の走査で、ファイルの字句（7.2〜7.5 節）からオブジェクトの範囲を区切る。

### 要素の ID

1. ページの最初の内容のストリームのレコードと、hayro が描いた順から作る（決定 0156 のキーのない形式の規則）。
2. 要素を描いたオブジェクトのレコード（フォームと画像の XObject は、そのオブジェクト）と、その中の順から作る。同じフォームを何度も呼ぶと、同じレコードの要素が重なるので、呼んだ所でも見分ける必要がある。hayro の `Device` は、いまどのフォームを解釈しているかを渡さない。
3. 内容のストリームの中の、演算子のバイトの位置から作る。hayro は演算子の位置を渡さないので、自前で解釈しないと得られない。

### wasm のモジュール

1. 図面のモジュール（`drawing`）に入れる。
2. PDF だけの `pdf` のモジュールに分け、PDF を開くときだけ読む（旧版の決定 0030 と同じ）。

## 決定

ページの解釈は選択肢 2、L1 は選択肢 2、要素の ID は選択肢 1、wasm のモジュールは選択肢 2 を採る。

### 依存

- `hayro-interpret` を `=0.9.0` で固定し、既定の機能（埋め込みのないフォントの代わりと、定義済みの CMap を同梱する）で使う。PDF の crate（`zumen-pdf`）の機能 `drawing` だけが使い、L1 だけを使う利用者は外せる。
- 結果と ID を決める crate は、`Cargo.lock` の効かない利用者のところでも変わらないよう、どれも `=` で固定する: hayro-interpret 0.9.0・hayro-syntax 0.9.0（字句と展開）・hayro-font 0.5.0（フォント）・hayro-cmap 0.1.1（CMap）・kurbo 0.13.1（経路）・flate2 1.1.10・moxcms 0.8.1（ICC のプロファイルを読めるかで、色空間の系統が決まる）・skrifa 0.49.0 と read-fonts 0.46.0（フォントのプログラムを読み、`Widths` のない TrueType の送りを決める）。moxcms と read-fonts は、コードからは使わず、バージョンを固定するためだけの依存にする。skrifa は、フォントのプログラムの手間を数えるときに、hayro-font と同じ表を見るためにも使う。展開の zlib-rs は、RFC 1950・1951 で結果が決まるので固定しない。画像の展開（zune-jpeg・hayro-jbig2 など）は、画素を読まないので結果に入らない。flate2 は、壊れた Flate を見つけるために、hayro-syntax と同じ crate と backend（zlib-rs）で厳しく展開し直すのに使う（hayro-syntax は、展開できない所から後ろを黙って捨てる）。flate2 は MIT か Apache-2.0、zlib-rs は Zlib で、どちらも hayro-syntax がすでに使い、wasm で動き、決まった入力から決まった出力を返す。
- `=` で固定する代償: 公開する crate の依存を `=` で固定すると、利用者の依存の木で、同じ crate の新しい patch バージョンを求める依存とは、バージョンを決められなくなる。2026-11-03 には、よく使われる image 0.25.10 が moxcms を `^0.8.0` で求めるので合う。バージョンを上げるときに、この代償も見直す。
- ライセンス: 2026-11-03 に、依存の木（hayro-syntax・hayro-font・hayro-cmap・hayro-jbig2・hayro-jpeg2000・hayro-ccitt・hayro-postscript・skrifa・read-fonts・moxcms・kurbo・zune-jpeg・flate2・zlib-rs・brotli ほか）のライセンスを `cargo tree` で確かめた。どれも MIT・Apache-2.0・BSD-3-Clause・Zlib・Unicode-3.0 か、それらを選べるもので、`deny.toml` の一覧に入る。
- 同梱のデータ: crate のフィールド（Apache-2.0 か MIT）とは別のライセンスのデータを含む。cargo-deny はこれを見ない。
  - hayro-font 0.5.0 の代わりのフォント（Foxit のフォント、PDFium の BSD 形式のライセンス。`assets/LICENSE_FOXIT`）
  - hayro-cmap 0.1.1 の Adobe の CMap（BSD-3-Clause。`assets/LICENSE.txt`）
  - hayro-interpret 0.9.0 の ICC のプロファイル（CC0-1.0。`assets/README.md`）

  どれも寛容なライセンスだが、BSD の 2 つは、バイナリで配るときに著作権の表示を求める。wasm と CLI で配るとき（#518）に、第三者の表示（決定 0014 の cargo-about）にこれらの文が入るかを確かめる。
- wasm: `wasm32-unknown-unknown` で build と clippy が通る。hayro-interpret は、ファイルの外（ファイルシステム・時刻・環境変数）を読まない。
- 決定性: hayro の結果のうち、環境で値が変わりうるものは使わない。
  - 色: hayro は DeviceCMYK と ICC の色を moxcms で sRGB にする。浮動小数で色を管理する計算は、バージョンと環境で値が変わりうるので、hayro の色の値は使わず、色空間の系統と成分から自前の式で色にする。ただし、系統そのもの（ICC のプロファイルを読めるか）は moxcms のバージョンで変わりうるので、moxcms も固定する。hayro は系統を公開していないので、色空間の `Debug` の表記の頭で見分ける。バージョンを固定するのは、このためでもある。転送関数（`TR`・`TR2`）があると、hayro は moxcms と std の `powf` で関数を当てた色を DeviceRGB として渡し、系統が分からなくなる。そこで、解釈の前の走査で転送関数を見つけ、そのページの色はレイヤに従わせる。
  - 座標: hayro に渡す装置の空間を 1/1024 mm にする。2 の冪なので、mm に戻すときに丸めが入らない。
  - 角度と長さ: 自前のコードの三角関数と `hypot` は `libm` を使う。hayro の中には、std の数学関数を使う計算がある。たとえば hayro-syntax 0.9.0 は、小数の部分が 20 桁以上の数を、std の `powi` で読む。2026-11-04 に、ネイティブと wasm32 で値の最後の桁が違うことを確かめた。普通の図面では通らないが、外から止めていないので、残りとして持ち、#521 で上流に直してもらう。ほかの経路は、API につなぐとき（#518）に適合テストで確かめる。
  - 整数の大きさ: hayro-syntax 0.9.0 は、予測子の行の長さを確かめずに掛けて割り、オブジェクトのストリームの `N`・`First` と中の位置・ICCBased の `N`・CCITT の `Columns` を、環境の大きさの整数で読み、LZW と ASCII85 の入力の長さを、同じく環境の大きさの整数で掛ける。0 で割るとパニックし、2 の 32 乗からの値は 32 ビットの環境で読めず、2 の 29 乗バイトからの LZW の入力は読む位置が回る。hayro-syntax は、ファイルのどの位置の定義も、どこに書いたストリームも読み、表を作り直すときは、どこにある型が `ObjStm` の辞書も展開するので、`Pdf::new` の前に、辞書の中かを見ずに、ファイルとオブジェクトのストリームの中身のすべての名前の後ろの値を見て、こうした値を持つ文書は読まない（`pdf.document.unsupported`）。値の参照は、すべての定義の数を候補にし、どの値がどのストリームのものかを見ないので、多めに断る。LZW と ASCII85 は、入力の長さがファイルか展開した中身の長さの定数倍に収まり、2 の 28 乗バイトより短いものだけを読み、フィルターの値に参照があれば、フィルターの値として読めない所の名前も断る。オブジェクトのストリームは hayro-syntax と同じく展開して中の位置を確かめ、型が `ObjStm` の辞書は、確かめたストリームと型の値の字が同じで、辞書の始まりから型の値までにコメントも文字列の終わり（`)`）もないものだけを読む。暗号化した文書は、オブジェクトのストリームの中身を読む前に復号できず、読み込みの後に確かめると確かめ漏らすので、オブジェクトのストリームを使えば読まない。上流が中の位置を確かめるようになれば（#521）、読む。hayro-interpret の Type 0 の関数とメッシュは、展開した長さを 8 倍してビットで読むので、2 の 29 乗バイトからの長さを使うページは解釈しない。
  - 順序: 要素は hayro が描いた順に並べ、自前の表は `BTreeMap` だけにする。hayro は表に `FxHashMap` を使い、そのハッシュの値は 32 ビットと 64 ビットの環境で違いうる。読んだかぎりでは、引くことと、順に依らない処理（拡張グラフィックス状態の辞書の項目を当てるなど）にだけ使い、Type 3 の字形の名前は並べ替えてから番号を振っている。ただし、相互参照の表の項目を順に引く `objects` は、同じ位置の項目を表の順に並べる。自前のコードは `objects` を使わない。ページの木を読めない文書では、hayro-syntax 0.9.0 が `objects` の順にページを探すので、同じ位置を指す項目があると、どの定義をページにするかと、ページの順が環境で変わる（2026-11-04 に、ネイティブと wasm32 で違うことを確かめた）。探したかも、表を作り直したかも公開の API では分からないので、ファイルの写しの後ろに、どの表にも載らない番号の定義を足して読み、その番号を引けたら（hayro-syntax がファイルを走査した表に作り直した）、またはカタログの `Pages` が `Kids` を持つ辞書でなければ、1 度目の文書を放して、読めない位置の `startxref` を足し、ファイルを走査した表で読み直す。走査した表では、同じ位置の項目のうち読めるものは 1 つで、表を作り直さないので、順がハッシュによらない（読める木を持ち、作り直さない文書は読み直さない）。1 度目の文書は、作り直しても展開したオブジェクトのストリームを覚えたままにするので使わない。読み直すかは表とファイルだけで決まり、環境では変わらない。
- バージョンを上げるのは読み取りの変更として扱い、ID の一覧のテスト（`crates/zumen-pdf/tests/ids/pdf.txt`）・色のテスト・適合テストで確かめる。
- 予算（[決定 0010](0010-budget-by-work.md)）: hayro-interpret の解釈は、予算でも中断の合図でも止まらない。フォームが次の段のフォームを 2 回ずつ呼ぶと、解釈する数は段の数の冪で増え、数 KB のファイルでも終わらなくなる。そこで、ページを渡す前に、内容のストリームを hayro-syntax の同じリーダー（`TypedIter`）で走査し、hayro-interpret が解釈する手間を `Work` に、展開するバイト数を `DecodedBytes` に、たどりながら先に数える。
  - hayro-syntax は、相互参照の表の壊れた項目をはじめて引いたときに、表をファイルの全体から作り直し、同じ参照が別のオブジェクトを指すようになる。走査の途中で作り直すと、走査が数えたものと hayro-interpret が解釈するものが食い違う。そこで、走査の前に、カタログとページの辞書から参照でたどれるオブジェクト（`Pdf::new` の後で引かれうるものは、これだけ）を、書いた順にたどって番号ごとにオブジェクト・辞書・配列のすべてで引き（作り直すかは引く型で変わる）、作り直しを済ませて、読む手間を数える。たどれない項目は誰も引かないので、壊れていても作り直しを起こさない。順はファイルで決まるので、数える量は環境によらない（`objects` の順は環境で変わる）。作り直す手間そのもの（ファイルの全体を読む）は予算の外にあり、#521 で扱う。
  - `Work` は、簡単な演算子を 1 とし、hayro-interpret の中で重い演算子に、測った比で重みを付ける: フォームの呼び出し 50・`gs` と画像と `sh` 16・文字列の 1 バイト 8（切り抜きにする文字は 40 と、輪郭の経路の要素の 1 つに 3）・経路を塗るか線を描く演算子 6・`BDC` 4・メッシュの頂点かパッチの 1 つ 4・CID フォントの幅の 1 項目 2・関数を作るときに読む Type 0 の標本 8 個で 1・関数の数の配列の 1 項目で 1・Type 4 の手続き 4 バイトで 1。2026-11-03・2026-11-04 に、hayro-interpret 0.9.0 を release で build し、同じ演算子を何万回も並べたページを解釈して測った。重みを付けると、`Work` の 1 あたりの時間は、測った演算子で 0.05〜0.35 µs になり、多くは 0.1〜0.3 µs になる。関数を当てる手間・グラフィックス状態の写し・合成の字形をたどる数・TrueType の命令は多めに数えるので、これらの多いページでは、もっと短い。
  - hayro-interpret が演算子ごとに作り直して展開するもの（フォーム・ソフトマスクのグループ・転送関数・シェーディングの関数・直接書いた色空間の関数と表）は、使うたびに `DecodedBytes` に数える。hayro-interpret が作るものの大きさ（メッシュの三角形とパッチ・Type 0 の関数の標本・Type 4 の関数の手続き・切り抜きにする文字の輪郭・写すグラフィックス状態の破線と輪郭・CID フォントの幅の表）も、hayro-interpret 0.9.0 の型の大きさか測ったメモリを、配列を伸ばす間の写し（前と後の配列が同時にある）を含めて倍にして、メモリの代わりに `DecodedBytes` に数える。経路と字形の並びの配列は、ページの中で容量を持ったまま使い回すので、文書の中でいちばん長いものの、65,536 を超える要素だけを数える。同じオブジェクトの手間はページの中で覚えるが、覚えるのは、資源の辞書の項目が参照で指すオブジェクトと、それ自身の間接オブジェクトのストリームだけにする。hayro-syntax の `obj_id` は、直接書いた辞書と、直接書いたストリーム（7.3.8.1 節に反するが、hayro-syntax は読む）に、それを含む間接オブジェクトの番号を返すので、キーにすると、直接書いた別のものの手間を使ってしまう。ストリームは、その番号で引いたストリームと辞書のバイト列を比べて見分け、比べるために引くコンテナーは、番号ごとに 1 度だけ引く。図面モデルの要素も、フォームを呼ぶたびに作り直すので、小さいファイルから指数的に増える。要素ごとに、測ったメモリを多めにしたものと、形が持つ配列の大きさの倍（64 ビットの型の大きさで、環境によらず同じに数える）を、字形の Unicode は 1 バイトを 4 バイトとして、`DecodedBytes` に数える（既定の予算では、文書の中でおよそ 100 万の要素まで。数え方・超えたときの code・部分の結果は #559 で決める）。
  - 大きさで手間が増えるものは、大きさで数える。hayro-syntax は資源を引くたびにオブジェクトを読み直すので、資源を引く演算子ごとに、引いたオブジェクトの大きさ（4 バイトを 1）を `Work` に数える。キーを引くたびと配列の項目を読むたびに値の参照を解き、型が違っても読み飛ばして確かめるので、読み直すオブジェクトとページの辞書を使うたびに、値の参照の先を 3 段たどり、書いた回数を掛けて数える（どのキーを読むかは見ない）。資源の名前が別の型を指すときと、ストリームの `Length` の先も数え、`endstream` のないストリームは、読むたびにファイルを読み通すものと数える。hayro-interpret は線と文字を描くたびに破線の配列を写すので、破線の長さを、描く演算子ごとに数える。グラフィックス状態は、`q` の後で状態を変えるとき・フォームを呼ぶとき・Type 3 の字形ごとに写すので、写す破線と、切り抜きに貯めた文字の輪郭の長さも数える。切り抜きにする文字の輪郭の大きさはフォントのプログラムで決まり、数百バイトのフォントでも 1 字に数万の要素を持たせられるので、走査も hayro-font の同じ API で、フォントと符号ごとに 1 度だけ輪郭を作り、経路の要素の数で数える。hayro-font は輪郭を覚えずに字ごとに作り直し、作る時間はプログラムで決まる（TrueType の合成の字形は部品を 2,048 本までたどり、CFF と Type 1 は 1 字に 100 万の演算まで動く）。そこで、展開したプログラムから、輪郭を 1 度作る手間の上限を求め、作るたびに `Work` に数える。TrueType の命令を動かすフォント（`is_hint_reliant`）と VARC を描くフォントは、1 字の手間の上限が大きすぎて数えられないので、その文字を切り抜きにするページを解釈しない。命令を動かすフォントは、読むときにも `fpgm` と `prep` を動かすので、読む前に上限で数える（描画モードによらない。飛ぶ命令があれば、上限に数えない定義の読み飛ばしも、定義の命令を動かせる回数といちばん長い本体で数える）。色を RGB にするときに関数を当てる手間（Separation などの 256 色の表と、多成分の DeviceN の塗るたびの当て方と、転送関数の表）と、`BDC` の性質の辞書と OCMD の `OCGs` の読み直しも数える。装置は、色を演算子（文字は文字列）ごとに 1 度だけ RGB にして、走査の数え方と合わせる。
  - hayro-interpret は、関数と色空間と Type 4 の関数の手続きを深さの上限なしに再帰して作り、長い鎖や深い入れ子ではスタックを使い切ってプロセスが落ちる（パニックでないので捕まえられない）。hayro-font は、CID フォントの幅の範囲の CID を 1 つずつ表に入れ、数十バイトの指定から、範囲に比例した時間とメモリを使う。Type 0 の関数は、大きさが 2 の 24 乗を超えると、f32 で丸めた標本の位置が範囲の外を指してパニックし、格子のメッシュは、行の頂点の数が 0 だと、行を足し続けてメモリを使い切る。そこで、走査で、16 段より深い関数か色空間の入れ子か、64 段より深い手続きか、大きさが 2 の 24 乗を超える Type 0 の関数か、行の頂点の数が 0 の格子のメッシュを使うページと、幅の項目が 2 の 18 乗より多い CID フォントか、文字の範囲の値が 2 の 18 乗を超える単純なフォントを使うページは、解釈せずにシートだけを作り、`pdf.page.dropped` を返す。手続きは、`if`・`ifelse` を重ねて関数をつなぐ入れ子より深く書かれうるので、上限を多めにした。上流に上限を求めることは #521 で扱う。
  - 同じフォームを同じ文脈で呼ぶ所は 1 度だけ走査し、覚えた手間と診断を、呼んだ回数だけ足す。走査の手間は段の数に比例する。マーク付きの内容の入れ子は、hayro-interpret と同じくページの中で 1 つの重なりとして追い、入れ子が釣り合わないフォームは覚えない。そうしないと、見え方を hayro-interpret と違えて、描く内容を数えないことがある。
  - 走査は中断の合図を見る。解釈を始めた後は、hayro-interpret を途中で止められない。要素を描くときと、ページを解釈した後に合図を見て、中断を返す。中断してから止まるまでの時間は、長くても 1 ページの解釈の時間になる。解釈の時間は、測った演算子では数えた `Work` におよそ比例するが、測っていない入力の形では、もっとかかりうる。今の仮の既定値（`Work` 100 億）では、十数分から 1 時間ほどになりうる。既定値を実図面で測って決め直すときに、この時間も見る（#521）。
  - hayro-interpret がページごとにカタログを読み直す作業も、そのバイト数で数える。自前のコードは、さらにパス・字形の並び・画像ごとに `Work` を、要素ごとに `Elements` を使う。
  - 予算の外に残るのは、ストリームの展開そのもの（展開してから数える）・`Pdf::new` の中の読みとメモリ（ページの木の節とページの値。hayro-syntax 0.9.0 は、ページごとに資源の辞書の表を作って文書の間持つので、同じ大きな資源の辞書を多くのページが指すと、ページの数とキーの数の積で増え、100 KB ほどのファイルで 1 GiB を超える）・相互参照の表の作り直し・オブジェクトのストリームの展開・読み飛ばす空白とコメントと、読んだ値から読んだ長さが分からない定義（読み飛ばせても数として読めない並び・長い数・空白だけの 16 進の文字列など）を読む手間（hayro-syntax 0.9.0 が、展開したストリームも、読んだ長さも、項目の位置も返さないので数えられない。読む回数とファイルの大きさの積で増える）・フォントと ICC のプロファイルの読み（CID フォントと単純なフォントの幅の表だけは、項目の数か文字の範囲の値をフォントごとに先に制限し、表のメモリを文書の中で数える）・曲線の平坦化と、解釈の途中での中断。hayro-syntax 0.9.0 の展開は出力の大きさに上限を持たない。これは決定 0010 の「依存の中の作業は、入力の大きさで先に制限する」に合わないので、API から開けるようにする前（#518 の前）に、#521 で止め方を決める。

### ファイルモデル（L1）

- レコードは、ヘッダー・間接オブジェクト（`N G obj … endobj`）・相互参照表・トレーラー・`startxref`・コメント・読めないバイト列とする。オブジェクトのストリームと相互参照のストリームの中は分けず、1 つのオブジェクトにする。
- 書き戻しは、レコードのバイト列をそのまま並べ、読んだバイト列と同じものを返す。
- 図面モデルへの移しは、hayro-syntax が読んだ文書を使い、L1 のレコードは ID と診断の場所に使う。同じ番号のオブジェクトが何度も出るときは、最後のレコードを使う（増分の更新、7.5.6 節）。

### 要素の ID

- ページの要素の ID は、ページの最初の内容のストリームのレコードから、決定 0156 の規則で作る（`sheet/{ページ}/r{レコード}`、2 つ目から `/1`・`/2`…）。内容のストリームがなければ、ページのオブジェクトのレコードにする。フォームの XObject の中の要素も、呼んだページの順に入る。
- 選択肢 2・3 は、hayro が渡さない情報（解釈しているフォーム、演算子の位置）が要るので、hayro を使うかぎり作れない。選択肢 1 は、hayro の描く順と、字形の並びを分ける規則に結びつくので、バージョンを固定する。hayro のバージョンを上げたり、分ける規則を変えたりして、描く順や数が変わると、ID が変わる。その PR は、ID の一覧（`crates/zumen-pdf/tests/ids/pdf.txt`）の差と理由を書く。

### wasm のモジュール

PDF の読み取りだけを入れた wasm を、2026-11-03 に測った。測ったものは、`zumen-pdf`・`zumen-drawing`・`zumen-sdk`・`zumen-base` を path で使い、`Pdf::read` と `lift` を呼ぶ関数を 1 つだけ export した使い捨ての `cdylib` で、API の関数は入れない。`cargo build --release --target wasm32-unknown-unknown` の出力から名前のセクションを除き、brotli は Node.js の `zlib.brotliCompressSync` の既定の水準で縮めた。

| モジュール | バイト | brotli |
| --- | ---: | ---: |
| 図面（`drawing`、決定 0253） | 5,889,456 | 1,170,885 |
| PDF の読み取りだけ | 4,297,107 | 1,316,581 |

2 つは、API の関数を入れたかがそろっておらず、PDF の読み取りの数は図面モデルを含む。そのため、図面のモジュールに PDF を足して増える量は、この表の 2 つの和より小さい。それでも、増える量は図面のモジュールと同じ桁になると見込む（転送量で最大およそ 2 倍。共通の部分を 2 回数えた上限の見積もりで、足したモジュールを測った値ではない）。図面だけを開くアプリが、使わない PDF の分を読むことになるので、`pdf` のモジュールに分ける。すべてを入れたモジュールとネイティブ・CLI には、PDF を入れる。API につなぐこと（`open` の判定・モジュールの表・適合テスト）は #518 で行い、そのときに、実際のモジュールを測り直す。

## 影響

- 台帳の PDF の項目に、この決定と形式の文書（`docs/formats/pdf.md`）を書く。移しの規則と、移せないものの診断は、形式の文書に書く。
- `Cargo.lock` に、hayro とその依存の crate が加わる。どれも `zumen-pdf` の機能 `drawing` の下にある。
- hayro が描かないもの（隠した OCG と OCMD の中身、代わりのフォントで描けない文字列）と、`Device` に渡さないもの（XObject の OCG、一部のフォントの名前、縦書きの原点の移動、字形の幅を合わせる伸縮）は、移せないか近似する。字形ごとの位置は、大きな隙間で文字を分け、小さなずれを診断で返す。どれも診断で返し、#520 で追う。
- 外部の実装（pdf.js）との照合と公開サンプルは #519 で足す。
