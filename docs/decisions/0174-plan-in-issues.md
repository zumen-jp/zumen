# 0174: 計画の優先順と状態を、全体計画 #1 の下の issue の並び・ラベル・依存で持つ

| 項目 | 内容 |
| --- | --- |
| 日付 | 2026-10-30 |
| 状態 | 採用 |

## 背景

[決定 0020](0020-work-selection-and-handoff.md) は、優先順・開始条件・次の一手を `docs/work.md` の一覧に置き、issue の開閉と進行中の状態を写さないことにした。GitHub Projects とラベルに集める案は、専用の設定と更新が要るとして選ばなかった。

使ってみて、次の問題が出た。

- 一覧の「次の一手」の欄に、できたことの経過が積もった。#170 の行は、1 つの欄が数千字になった。経過はマージ済みの PR にあり、記録の規則（`docs/decisions/README.md`）も、経過を記録に書かないとしている。
- 一覧の 7 行は段階 1 と 2 の作業だけで、段階 0・3・4・5 の作業と、#1 の段階のチェック欄が別にあった。全体の計画が 1 か所で見えなかった。
- 一覧と issue の両方に開始条件を書き、片方だけが古くなった。
- 作業を進める PR が、どれも一覧を書き換えるので、同時に開いた PR が、一覧の同じ行でぶつかりやすかった。

GitHub は、いまは sub-issue（親と子の issue）と、issue の依存（blocked by）を持つ。どちらも、リポジトリの issue の権限だけで使える。GitHub Projects は、組織の Project の権限が別に要る。

## 選択肢

1. 今のまま、`docs/work.md` の一覧に優先順と次の一手を書く。
2. #1 を根にして、段階の issue と作業の issue を sub-issue の木にする。優先順は子 issue の並び、待っているものはラベルと依存で持つ。`docs/work.md` は、作業の選び方の手順だけにする。
3. GitHub Projects の表に、優先順と状態の欄を置く。

1 は、上の問題が残る。3 は、Project の権限と、表の欄の設定と更新が要る。木の並びとラベルで足りるうちは、要らない。

## 決定

選択肢 2 を選ぶ。

- **木。** [全体計画 #1](https://github.com/zumen-jp/zumen/issues/1) を根にし、段階 0〜5 の issue を子に置く。作業の issue は、段階の子に置く。大きな作業は、さらに子 issue に分ける。段階の issue には、ラベル「段階」を付ける。
- **優先順。** 子 issue の並びで表す。上ほど先に行う。段階の順に、段階の中は上から見る。
- **待っているもの。**
  - ほかの issue の成果物を待つものは、issue の依存（blocked by）で表す。
  - issue でないものを待つときは、ラベルで表す。「待ち: 試料」は試料の図面、「待ち: 判断」は利用者の判断、「待ち: 検証環境」は AutoCAD などで確かめる環境を待つ。待っているものを、issue の本文の開始条件に具体的に書く。
  - PR のマージを待つものは、開始条件に PR を書く。
- **作業中。** 着手した人が、ラベル「作業中」を付け、issue の本文の「着手・引き継ぎ」に、ブランチ・担当する範囲・PR を書く。中断するときは、引き継ぎを書いてラベルを外す。
- **選び方。** 木を上から深さ優先にたどり、閉じていない葉の issue のうち、待ちと作業中のラベルがなく、依存で止められていない最初のものを選ぶ。利用者が指定した作業は、この順より優先する。
- **次の一手と経過。** 次の一手は、その issue の本文に書く。できたことの経過は、PR に書き、issue の本文に積まない。
- **`docs/work.md`。** 確認先・選び方・着手・完了・引き継ぎの手順だけを書く。優先順と次の一手の一覧は置かない。
- **並びの変更。** 優先順を変えるときは、子 issue を並べ替え、その理由を親の issue にコメントで書く。新しい作業は、ひな形で issue を作り、段階の子に置く。
- 決定 0020 のうち、issue に範囲と完了の条件を置くこと、完了の根拠を main で確かめること、利用者の依頼を優先することは、変えない。

## 影響

- 作業を進める PR は、`docs/work.md` を書き換えない。PR がぶつかるのは、同じ issue の本文を同時に書き換えるときだけになる。
- 優先順の変更は、PR のレビューを通らなくなる。代わりに、親の issue のコメントに理由が残る。
- 状態は、ラベルと依存を見ればよい。ただし、人とエージェントが更新する仕組みであり、ロックではない。着手する前に、開いた PR と手元の worktree も確かめる。
- 作業の issue のひな形に、親の段階と、止めている issue の欄を足す。
- `AGENTS.md`・`CONTRIBUTING.md`・`README.md` の作業一覧への言及を、この手順に合わせる。
- 決定 0020 を、この決定で置き換える。
