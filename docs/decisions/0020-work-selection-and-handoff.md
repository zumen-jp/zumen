# 0020: 作業の入口と優先順をリポジトリに置き、範囲と完了条件を issue で追う

| 項目 | 内容 |
| --- | --- |
| 日付 | 2026-10-24 |
| 状態 | 0174 に置き換え |

## 背景

全体計画 #1 と子 issue、決定の記録、PR に作業の情報が分かれている。設計が済んでも試作が残る issue と、設計だけで閉じる issue がある。新しいエージェントが毎回、全履歴から次の作業を組み立てていた。

決定 0017 の台帳検査のように、設計の issue を閉じたあとに残る実装もある。完了済みの設計を繰り返さず、残る成果物を見つけられる入口が必要になった。

## 選択肢

1. 全体計画のチェック欄と issue の開閉から、毎回判断する。開始条件と優先順を読み取りに頼る。
2. GitHub Projects とラベルに優先順と状態を集める。専用の設定と更新が要り、作業の選び方は別に定める必要がある。
3. リポジトリに作業を選ぶ手順と順序を置き、詳細は issue、進行中の変更は PR、完了の根拠は main で確かめる。

## 決定

3 を選ぶ。

- `AGENTS.md` を入口にし、`docs/work.md` に確認先・選び方・優先順・開始条件・次の一手を書く。
- issue に目的・範囲・開始条件・完了条件・参照と引き継ぎを置く。新しい作業には issue のひな形を使う。
- 優先順は `docs/work.md` を正とし、issue の開閉・進行中の状態は写さない。着手前に GitHub と手元の変更を確かめる。
- 決定の内容は採用済みの記録を、実装の有無は main のコードと試験を根拠にする。どちらかだけで issue の完了を判断しない。
- 完了条件の一部を満たす PR も認める。完了と残件を PR に書き、同じ PR で作業一覧を更新する。残る実装には追跡先を用意する。
- 利用者の具体的な依頼を優先する。この一覧から、依頼されていない次の作業を自動で始めるわけではない。

## 影響

後に[決定 0174](0174-plan-in-issues.md) で、優先順と状態を #1 の下の issue の並び・ラベル・依存で持ち、`docs/work.md` を手順だけにすることにした。

- 新しいエージェントは、作業一覧から候補を選び、その issue と関連する決定・PR を読むことで着手できる。
- 優先順の変更を PR で確認できる。作業を進める側が一覧も更新し、別の棚卸しに頼らない。
- 人とエージェントが手順を守る仕組みであり、排他的なロックや状態の自動同期ではない。同時着手を避けるため、issue の着手記録、開いた PR、共有する作業場所を確認する。
- 既存の issue は、着手するときに足りない条件を補う。全体計画の長文を書き直す必要はない。
