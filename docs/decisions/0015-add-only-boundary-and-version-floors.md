# 0015: API は足すだけにし、4 つのバージョンを分け、古い環境への下限を表で約束する

| 項目 | 内容 |
| --- | --- |
| 日付 | 2026-10-24 |
| 状態 | 採用 |

## 背景

- 業務のマクロや社内ツールは、十年単位で使われる。一度書いた VBA やアドインが、コアを新しくしても動き続けることが求められる。
- Revit・AutoCAD・Excel は、複数のアドインを 1 つのプロセスに読み込む。違うバージョンの DLL を持ち込んだアドインどうしが、ぶつかる。
- ホストアプリに埋め込まれた言語のバージョンは、古いことがある（2026-10-24 に確かめた）。
  - Rhino 8 と、Revit 2025・2026 に付く Dynamo 3.x の既定の Python は 3.9。CPython 3.9 のサポートは、2025-10-31 に終わった。
  - Revit・AutoCAD は、2024 まで .NET Framework 4.8 を使う。2025・2026 は .NET 8 で出て、2026 年 8〜9 月の更新で .NET 10 に移った。2027 は .NET 10。Autodesk は、現行と過去 3 版をサポートする。
  - 業務システムには、Java 8 も残る。Oracle の延長サポートは、2030 年 12 月まで続く。
- [0012](0012-boundary-functions-and-messages.md) で、API を、数個の関数と、バージョン `v` のあるメッセージにした。[0011](0011-bindings-through-ffi.md) で、ネイティブで呼ぶ言語は、同じ C ABI のライブラリを共有するとした。
- ID は契約で、ID を変える変更には、先に決定の記録が要る（AGENTS.md）。

## 選択肢

### バージョンの付け方

1. **1 つの版番号だけにする。** API を壊したかどうかが、番号から分からない。
2. **パッケージのバージョンと、ABI・メッセージのスキーマ・ID の規則のバージョンを分ける。**

### API の変え方

1. **メジャーバージョンを上げて壊すことを許す**（semver のふつうの使い方）。メジャーバージョンのたびに、利用者のマクロやアドインを直すことになる。
2. **足すだけにする。** 意味を変えたいときは新しい名前で足し、古いものを残す。

### 下限

1. **各言語の新しいバージョンだけに対応する。** 業務の環境で使えない。
2. **古い環境に、期限なく対応する。** 保守が重くなり続ける。
3. **ホストアプリと言語のサポート期間に合わせて下限を決め、表にして公開し、上げる規則も決める。**

## 決定

バージョンの付け方は 2、変え方は 2、下限は 3 を選ぶ。

### 4 つのバージョン

| バージョン | 形 | 上げるとき | 確かめ方 |
| --- | --- | --- | --- |
| パッケージ | semver（`1.4.2` など）。コアの crate・全言語のパッケージ・カタログで同じ番号 | リリースごと | 各パッケージのバージョン |
| ABI | 整数（1 から） | 関数の引数か意味を変えるとき。上げないことを目指す | `zm_abi_version`、ライブラリのファイル名 |
| メッセージのスキーマ | メジャーバージョンとマイナーバージョン（`1.7` など） | マイナーバージョンは、op・フィールド・列挙の値を足すたび。メジャーバージョンは、壊すとき（上げないことを目指す） | 要求と応答の `v`（メジャーバージョン）、`capabilities`（マイナーバージョン） |
| ID の規則 | 形式ごとの整数 | ID を変えるとき。先に決定の記録を書く | `capabilities` |

バイナリの配置（[#6](https://github.com/zumen-jp/zumen/issues/6)）とプロファイル（[#9](https://github.com/zumen-jp/zumen/issues/9)）のバージョンは、それぞれの記録で決める。

### API は足すだけ

- **関数。** 足すだけにする。引数か意味を変えたいときは、新しい名前の関数を足す。
- **op とフィールド**
  - op と、要求・応答のフィールドは、足すだけにする。消さず、名前と意味を変えない。
  - 要求に足すフィールドは、書かなければ今までと同じ動きになるようにする。
  - 意味を変えたいときは、新しい op かフィールドを足し、古いものは「廃止」として残す。廃止したものも動かし続ける。
- **列挙の値。** 足すだけにする。生成したラッパーは、知らない値も受け取れる（[0012](0012-boundary-functions-and-messages.md)）。
- **古いものと新しいものの組み合わせ**
  - 古いラッパーと新しいコア: ラッパーは、知らないフィールドを無視し、知らない値を受け取るので、動き続ける。
  - 新しいラッパーと古いコア: 古いコアは、知らない op とフィールドを失敗にする（[0012](0012-boundary-functions-and-messages.md)）。ラッパーは、`capabilities` で確かめてから新しい op を使い、古いコアでは分かる失敗にする。
- **検査。** CI で、前のリリースのスキーマと比べ、消したものや変えたものがあれば失敗にする。
- **メジャーバージョン。** メッセージのスキーマのメジャーバージョンは、足すだけでは済まないときにだけ上げ、決定の記録を書く。上げたあとも、`v` を見て前のメジャーバージョンを受け付け続け、いつまで受け付けるかを記録に書く。
- **1.0 より前。** パッケージの 1.0 より前は、API もマイナーバージョンで壊すことがある。壊したことは、リリースノートに書く。この節の約束は、1.0 から守る。後に[決定 0254](0254-parallel-agents-and-cross-review.md) で、壊す判断を決定の記録にし、PR とコミットの題に `!` を付けて移り方を書くことにし、ID の規則をこの例外から外した。

### 同じプロセスに並べる

- ネイティブのライブラリのファイル名には、ABI のメジャーバージョンを入れる（`zumen_abi1.dll`・`libzumen_abi1.so`・`libzumen_abi1.dylib`）。ABI のメジャーバージョンが違うものは、同じプロセスに並べて読み込める。
- 同じメジャーバージョンのライブラリは、新しいものほど多くを受け付ける。古いものが先に読み込まれていたら、ラッパーが `capabilities` で確かめ、分かる失敗にする。
- .NET のアセンブリは、名前を `Zumen` のままにし、強い名前を付け、AssemblyVersion を ABI のメジャーバージョン（`1.0.0.0`）に固定する。
  - .NET Framework 4.8 のホストで、同じメジャーバージョンのものを 1 つとして扱い、バージョンごとのリダイレクトを要らなくするため。
  - ABI のメジャーバージョンを上げるときは、アセンブリの名前にもメジャーバージョンを入れ、並べて読み込めるようにする。
- アドインどうしのぶつかりは、ホストの仕組みでも避ける。Revit は 2026 から、アドインごとに読み込みの文脈を分けられる。分ける仕組みがないホストでは、アドインが Zumen を自分のアセンブリに取り込む（ILRepack など）ことを、文書で勧める。

### パッケージのバージョン

- コアの crate と全言語のパッケージは、同じリリースで、同じ版番号にする。カタログも同じにする（[0009](0009-diagnostics-and-catalog.md)）。
- メジャーバージョンを上げるのは、どれかのパッケージの公開の API を壊すときにする。API は足すだけなので、各言語のパッケージの API は壊れない。壊れうるのは、Rust の crate の API だけになる。
- Rust の crate の `rust-version` は、固定したツールチェーンのバージョン（今は 1.99）にする。

### 下限

- 下限は、言語の実行環境・OS・ホストアプリごとに決め、表にして [docs/support.md](../support.md) に置く。この記録は規則を決め、表はこの規則で直す。最初のバージョンは、この記録と同じ PR で置く。
- **決め方**
  - ホストアプリの中で使われる言語は、メーカーがサポートしているバージョンのホストアプリが使う、いちばん古い実行環境まで下げる。
  - 言語そのもののサポートが切れていても、それを使うホストアプリのサポートが続く間は、表に残す。
  - ホストアプリの外だけで使う実行環境（Node.js など）は、その実行環境のサポートが続いているバージョンに限る。
- **上げ方**
  - 下限を上げるのは、その環境を使うホストアプリと、その言語の、両方のサポートが切れてからにする。
  - 上げる 1 つ前のリリースの、リリースノートで知らせる。
  - 下限を上げるのはマイナーバージョンで行い、メジャーバージョンは上げない。古い環境の利用者は、前のリリースを使い続けられる。
- **確かめ方。** 表の下限の環境で、適合テスト（[0012](0012-boundary-functions-and-messages.md)）を流す。CI で流せない環境（32 bit の Excel など）は、Windows の実機（[0004](0004-repositories.md) の案の `verify`）で確かめる。確かめていない環境は、表にそう書く。

## 影響

- API を変える PR ごとに、前のリリースとの差を CI が確かめる。
- 廃止した op とフィールドが、残り続ける。古い形を新しい形に直す処理を、API の側に持つ。
- 下限の表を守るために、古い環境（.NET Framework 4.8、32 bit の Excel など）でテストを流し続ける。
- [#17](https://github.com/zumen-jp/zumen/issues/17) は、この記録と、表の最初のバージョンで完了する。
