# 0215: IFC から建物モデルへの変換は、意味を持つ実体の表で読み、材料と通り芯の軸を GlobalId のない要素にし、ほかの版は作らずに断る

| 日付 | 2026-10-31 |

## 背景

[決定 0207](0207-building-model-components.md) は、IFC2X3・IFC4・IFC4X3 から建物モデルを作り、形状表現を除く成分から足すと決めた（#409）。変換を `zumen-ifc` に置くにあたり、次の 4 つが決まっていなかった。

- 版ごとに属性の位置が違う実体を、どう読むか。
- GlobalId を持たない資源の実体（材料と通り芯の軸）を、要素にするか。
- ほかの版のファイルを渡されたときに、何を返すか。`Lift` は、止めたときだけ失敗する約束だった。
- どの要素も持たない中間の配置を、どう写すか。

## 選択肢

実体の読み方の選択肢は 2 つある。

1. EXPRESS のスキーマから、実体と属性の表を生成する。
2. 意味を持つ実体ごとに、版ごとの属性の位置を手で書いた表を置く。

選択肢 1 は、スキーマとそこから生成したコードをリポジトリに入れることになり、決定 0207 の守ることに反する。

ほかの版の扱いの選択肢も 2 つある。

1. 空の建物モデルを返して診断する。
2. 診断して `Error::Unsupported` を返し、`Lift` の約束に「作らない版」を足す。

選択肢 1 では、空のモデルと、要素のない正しいファイルの区別がつかない。

## 決定

- 変換は `zumen-ifc` の feature `building`（既定で入る）に置き、`IfcFile` と `IfcZipFile` に `Lift<Building>` を実装する。
- 実体は、手で書いた表で読む。
  - 表の 1 行は、元の名前・IFC4.3 でのクラスの名前・分け方・版ごとの定義された種類の位置を持つ。分け方は、プロジェクト・空間・要素・型・様式・グループ・格子の 7 つ。
  - `StandardCase`・`ElementedCase` の派生は元のクラスにまとめ、元の名前は `class.original` に残す。
  - IFC2X3 の `IfcRoof`・`IfcStair`・`IfcRamp` の ShapeType は、IFC4 の PredefinedType と同じ列挙なので、定義された種類として読む。
  - 表にない実体は L1 に残し、`ifc.entity.dropped` で種類ごとに数える。
- `IfcMaterial` と `IfcGridAxis` は、GlobalId を持たない要素にする。ID は `i` とインスタンスの番号で作り、`ifc.global-id.missing` は出さない。材料の層と通り芯は、これらの要素を指す。
- 版は `FILE_SCHEMA` の最初の名前で決める。
  - `IFC2X3` で始まる名前、`IFC4`、`IFC4X3` で始まる名前の 3 つを読む。
  - IFC4X1・IFC4X2 は正式の版でないので、ほかの版と同じく読まない。
  - ほかの版は、`ifc.version.unsupported` を出して `Error::Unsupported` を返す。`Lift` の約束に、領域モデルを作らない版のときも失敗することを足す。
- 配置は、`IfcLocalPlacement` の連鎖をたどって写す。
  - 親の配置を持つ要素に着くまで、どの要素も持たない中間の配置を、局所の変換に掛けて畳む。畳んだ配置の番号は、出所の `folded_placements` に内側から順に残す。
  - 同じ配置を複数の要素が持つときは、書いた順で初めの要素を、その配置の持ち主にする。
  - 軸は `IfcBuildAxes`・`IfcFirstProjAxis` の規則で正規直交にする。長さが 0 の向きと、Axis に平行な RefDirection は、軸を作れない配置にする。
- 関係の出所は、成分を付けた要素ごとに、関係の番号・GlobalId・列の中の位置を `Source.relations` に残す。
- 要素の親は 1 つにする。2 つ目の集約・入れ子・空間への包含は写さず、`ifc.parent.exists` を出す。入れ子の順は、IFC4 からの順のある列のときだけ持つ。
- プロパティは `IfcPropertySingleValue` だけを写す。ほかのプロパティと材料の定義（断面・構成）は、試料で使われ方を見てから足す。
- 値の型の名前は、表にある型だけ仕様の書き方（`IfcLengthMeasure`）に直し、表にない型は書いたまま持つ。表にない量の型（名前が `MEASURE` で終わる型）の値は、単位が解けないものとして診断する。

## 理由

- 手で書いた表なら、スキーマも生成したコードも入れずに済む。位置は各版の仕様の属性の節で確かめ、表の上に書いた。
- 材料と通り芯の軸は、GlobalId を持たないことが仕様の形である。そのため、なくて当然のものを診断しない。要素にすれば、材料の層と格子が、ほかの成分と同じく要素を指せる。
- 空の建物モデルを返すと、利用者は版が違うことに気づけない。

## 影響

- `zumen-sdk` の `Lift` の説明が変わる。図面モデルへの変換は、いままでどおり止めたときだけ失敗する。
- 表にない実体（設備の個別のクラスなど）は、試料で件数を見てから表に足す。足すと、その実体が要素になり、ID の付く要素が増える。
- 形状表現・表示の様式・階・区域・分類は、決定 0207 のとおり試料を得てから足す。
