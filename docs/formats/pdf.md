# PDF

PDF を、ファイルモデル（L1）として読み書きし、図面モデルに移す規則と、仕様が決めない所の扱いを記録します。実装は `crates/zumen-pdf` です。ページの内容は hayro-interpret 0.9.0 で解釈します。仕様の本文は写しません（`formats/ledger.toml`）。節の番号は ISO 32000-2:2020 のものです。

## 対象

- PDF 1.0〜2.0 の図面を読む。API にはまだつないでいない（`open` と wasm の `pdf` のモジュールは #518）。
- `zumen-pdf` は crates.io に出さず、どのパッケージにも入れない。配るのは、#521 など（hayro の中の展開・再帰・フォントの読みを予算で止めること）を直してからにする。
- 暗号は、空のパスワードで開けるものだけを読む（hayro-syntax が復号する）。
- 書き戻しは、読んだバイト列をそのまま書く（下の「書き戻し」）。

## 判定

- 先頭が `%PDF-` なら PDF とする（`Signature::Bytes`、7.5.2 節）。
- 読むときは、先頭の 1,024 バイトの中に `%PDF-` があればよい。前にあるバイト列は、読めないバイト列のレコードにする（推定。多くの読み取りが許す範囲に合わせた）。同じ行の `%PDF-` の前のバイト列（`xx%PDF-1.7` など）も、ヘッダーの前で切る。なければ `pdf.file.invalid` を返して読まない。

## レコードの区切り

- ファイルの字句（7.2〜7.3 節）をたどり、ヘッダー・コメント・間接オブジェクト（`N G obj … endobj`、7.3.10 節）・相互参照表（`xref`、7.5.4 節）・トレーラー（7.5.5 節）・`startxref` を、それぞれ 1 つのレコードにする。どれでもないバイト列は、続く分をまとめて読めないバイト列のレコードにする。
- ストリーム（7.3.8 節）は、外側の辞書の `/Length` が直接の整数で、その後ろに `endstream` があれば、その長さで飛ばす。間接参照の長さか、長さが合わなければ、次の `endstream` を探す。
- オブジェクトのストリームと相互参照のストリーム（7.5.7・7.5.8 節）の中は分けず、1 つの間接オブジェクトのレコードにする。
- 同じ番号のオブジェクトが何度も出るときは、図面モデルへの移しで、最後のレコードを使う（増分の更新、7.5.6 節）。

## 壊れた所

- `endobj` のないオブジェクトは、次のオブジェクトの前（後ろの空白を除く）か入力の終わりまでとし、`pdf.object.repaired` を返す。
- 相互参照とページの木を読めなければ `pdf.document.invalid` を、空のパスワードで開けない暗号なら `pdf.encryption.unsupported` を返し、図面モデルに移さない。どちらも、L1 としては読める。
- 内容のストリームを展開できないか、途中から読めないときは、`pdf.content.invalid` を返し、読めた所までを移す。場所は、そのストリームのレコードにする。次の場合を含む。
  - 内容のストリームの配列（7.7.3.3 節）の、展開できない項目と、ストリームでない項目。hayro-syntax は、それを飛ばしてつなぐ。
  - 壊れた Flate（7.4.4 節）。hayro-syntax は、zlib の形と、ヘッダーのない deflate の形の順に厳しく展開し、どちらも失敗すると、展開できた所までを返す。途中で切れた zlib の形は、厳しい展開でも、展開できた所までを返す。フィルターが Flate だけで予測子（7.4.4.4 節）のないストリームは、同じ crate（flate2）で、zlib の形・ヘッダーのない deflate の形・zlib のヘッダーを除いた deflate の形の順に厳しく展開し直す。どれでも deflate の終わりまで読めないか、長さが合わなければ、壊れているとみなす。Adler-32 が違うか、ないだけのものと、空のもの（生のデータが空白だけで、展開した長さが 0）は、壊れていないとみなす（中身はすべて読める）。予測子のあるものと、ほかのフィルターの壊れ方は、展開に失敗したときだけ見つかる（推定）。
  - 引数の足りない演算子と閉じない文字列。hayro-syntax は、そこから後ろを読まない。内容の後ろに終わりのマーカーの演算子を足し、そこまで読めるかで見る。
  - `BBox` のないフォームと、展開できないフォーム（8.10 節）、画素の数（`Width`・`Height`、8.9.5 節）のない画像。hayro-interpret は描かない。
- 入れ子が 50 段より深いフォームの中身は、hayro-interpret が解釈しないので移さず、`pdf.nesting.dropped` を返す。場所は、そのフォームのレコードにする。
- 資源にない XObject と、循環する参照で引けない XObject（自分を呼ぶフォームなど）は、hayro-interpret が描かないので移さず、`pdf.xobject.missing` を、ページと資源の名前ごとに 1 件返す。

## 上限

L1 は、入力のバイト数（`InputBytes`）とレコードの数（`Records`）を予算で数える。

### フィルターと復号

- ASCIIHex（7.4.2）または ASCII85（7.4.3）を 1 個、その後に Flate または LZW を 1 個並べた系列も、共通の 22 種類の入口で確保前に数える（#623）。先頭 Crypt は除き、フィルターとパラメーターの優先順位・短縮名・未知の名前・名前でない項目での終了は hayro-syntax 0.9.0 に合わせる。`F` が外部ファイルを指す文字列か辞書なら、hayro は `Filter` の配列を適用する前に失敗するため、埋め込まれたバイト列を数えない。外部ファイルは開かない。ASCII の長さだけを先に走査し、予算内なら中間出力を保持して、既存の圧縮の確認へ渡す。逐次リーダーにする案に比べ、Flate の再試行と LZW の長さの表を変えずに使え、不正な ASCII も中間出力の確保前に見分けられるため、この方法を採る。最終の出力は元のストリームから hayro が作る。
- ASCII の `DecodedBytes` は、上流の初期容量として Hex は入力長の半分を切り上げ、ASCII85 は入力長の 4/5 を切り捨てた量と群の 5 バイトを先に数える。終端の後の入力も含め、多めに数える。ASCII85 の出力が初期容量を超える場合は、部分の出力長と最小容量 8 の大きいほうを 4 倍して足し、伸長中の新旧の確保を含める。不正な入力でもそこまでの分を戻さない。成功時に確認自身が保持する中間出力は、その長さを別に足してから確保する。
- ASCII の `Work` は、`F` の確認に 1、上流の読みとして入力の 16 バイトごとに 1、長さの走査と中間出力を作る走査でそれぞれ入力の 16 バイトごとに 1、出力長と上記の伸長分の合計の 16 バイトごとに 1 を数える。2 回目の走査の作業量は、1 回目に終端まで実際に読んだ量を使い、中間出力の確保前にまとめて数える。走査中は空白だけでも 16 バイトごとに中断を見る。Hex の奇数の桁、終端の省略、ASCII85 の部分群の後の `z` と整数のあふれは、上流と同じ読み方にする。失敗した ASCII からは圧縮の確認へ進まない。圧縮の出力・予測子前の量・失敗と再展開は、単独 Flate/LZW と同じ方法で数える。後ろに別のフィルターが続く系列は、下の項のとおり前の段を数える。
- この系列では、ファイルに `Encrypt` の名前があれば復号する場合を見込む。辞書に続く `stream` と改行、直接の `Length` の後ろの `endstream` を元のファイルで確かめる。境界の空白・コメントが 64 バイト以内で確かめられないときや長さが違うときは、残りの範囲を上限にする。読み直す長さを調べるためには復号しない。復号を伴う ASCII の確認と hayro の展開の 2 回分は、1 回につき上限と 16 の大きいほうの 4 倍を、復号前に `DecodedBytes` と 16 バイトごとの `Work` に数える。RC4 の写しと AES のバッファーの伸長を含み、暗号化の印だけの文書では多めになる。
- `F` の直接の文字列は中身を作らず見分け、hayro がその文字列を読む分を先に数える。同じ辞書に別の参照があっても、参照を探すためには文字列を展開しない。非暗号でエスケープのないリテラルは元の列を借り、16 進文字列は半分の長さ、エスケープ・改行を含むリテラルは伸長分を見込む。辞書はキーの数と元の長さから、確認と hayro の 2 回分を数える。
- 参照の `F` は、ファイルと確認済みの ObjStm から参照先の番号を拾う（異なる番号ごとに 64 バイト）。参照をたどる対象はストリーム・辞書・配列である。ほかの型では、相互参照表が別番号の値を指していても hayro が修復できるよう、文字列の展開・復号を含む上限を先に数えてから、その番号をオブジェクトとして引く。
- 辞書の表は、参照先になりうる各辞書を表にせず読み、1 つの辞書のキーの数とエスケープした名前の長さから求めた最大値で見積もる。ObjStm の項目が前の辞書の途中を指す場合は、そのコンテナー全体の名前を上限にし、重なる範囲を読み直さない。ページごとに別のフォントを `F` と名付けたときも、文書全体のすべてのキーをページごとに重ねて数えない。相互参照表が別の定義に変わりうるため、走査後に到達した番号だけを引き直して結果を共有し、ページや資源の手間を見積もるために同じ表を何度も作らない。
- ObjStm の展開直後に、名前を探す手間を 16 バイトごとに 1 として先に数える。中の辞書を読む必要があれば、最初の辞書の位置から末尾までの手間も 4 バイトごとに 1 として先に数える。キーの中の `#xx` は長さを数え、判定に使わない長い名前のバッファーは作らない。名前を探す途中とキーをたどる途中も 1,024 バイトごとに中断を確かめる。
- hayro の API は参照先の元の範囲を返さないため、範囲が分からないときの走査の手間と、実際に外部ファイルの指定を読む前の確保は、ファイルと確認済みの ObjStm の最大長から多めに数える。`F` が別の用途の名前でも参照を記録するため、多くの名前がある文書や短い参照先では、直接書いた場合より早く止まることがある。

- 単独 LZW（7.4.4）も、ObjStm・内容・フォーム・描画資源・フォント・ICC の共通の入口で、全出力の確保前に数える（#616）。符号の辞書は長さだけを 4,096 項目の表（8 KiB）で持ち、確認の間は出力のバイト列を保持しない。`EarlyChange` とフィルターのパラメーターは hayro-syntax 0.9.0 と同じ順で読む。先頭 Crypt・短縮名・配列、9〜12 ビットの切り替わり・表の初期化・満杯を扱う。不正な符号で失敗するまでの量と、切れた入力の部分の出力も数える。予測子前の量を保ち、十分な予算なら元のストリームを hayro で展開する。
- LZW の `Work` は、入力の 16 バイトごとに 1 と、固定の表の初期化に 512、符号ごとに 1、出力と辞書に写す語の 16 バイトごとに 1、辞書への追加ごとに 1 を数える。`DecodedBytes` は出力のバイト数と、辞書に作る語の長さを数える。辞書の表は最初の 258 項目と、その後に足す項目を 1 つ 96 バイトで見積もる（64 ビットの `Option<Vec<u8>>` の 24 バイトの 4 倍。容量を倍にする表の、それまでの確保の合計を含む）。初めの 256 個の 1 バイトの語も数える。上流は表が満杯でも語を写した後で追加を断るので、その語も数える。環境によらず同じ量とし、符号ごとに中断を確かめる。再展開の見積もりにもこの量を使い、予測子などの失敗で戻さない。数え方を広げたため、低い予算では以前より早く止まる。
- 単独 RunLength（7.4.5）と、ASCIIHex・ASCII85 を 1 個前置した RunLength も、同じ 22 種類の入口で全出力の確保前に数える（#629）。名前・短縮名 `RL`・先頭 Crypt・未知の名前・配列の終了と、ASCII を前置した系列の `F` の外部ファイルの扱いは、上の Flate・LZW と同じく hayro-syntax 0.9.0 に合わせる。単独の RunLength は、単独 Flate・LZW と同じく `F` を見分けずに埋め込まれたバイト列を数えるので、`F` が外部ファイルを指すときは多めに数える。符号は hayro-syntax 0.9.0 と同じ順で読み、出力のバイト列を保持せず長さだけを数える。128 で終わる入力と、続くバイトが足りないリテラルで終わる入力は成功、くり返すバイトがない入力と 128 の前に終わる入力は失敗とし、どちらも失敗までの分を戻さない。
- RunLength の `DecodedBytes` は、上流が空の Vec に足していく出力の確保として、出力の長さ（最小容量 8）の 4 倍を数える。倍に伸ばす Vec の全確保の合計はこれ未満で、ASCII85 の伸長と同じ見積もりである。くり返しでは、上流がくり返しごとに作る同じ長さの一時の列も足す。`Work` は、上流の読みとして入力の 16 バイトごとに 1、符号ごとに 1 と、その符号で数える `DecodedBytes` の 16 バイトごとに 1 を数える。符号ごとに予算と中断を確かめ、上限を超える符号の前で止める。再展開の見積もりにもこの量を使い、失敗で戻さない。Flate・LZW の出力の容量と一時の確保も、下記の共通の規則で先に数える（#772）。
- 複数フィルターは、Flate・LZW・RunLength・ASCIIHex・ASCII85 の各段を、同じ 22 種類の入口で全出力の確保前に数える（#659・#769）。後ろの段が失敗しても縮めても、そこまでに確保する量は戻さない。次の段を調べる中間出力は、処理量・確保量を先に予約してから保持する。圧縮の段は、元の文脈で解いた `Predictor`・`Colors`・`BitsPerComponent`・`Columns`・`EarlyChange` を使った 1 段の合成ストリームを hayro で展開し、予測子を当てた後のバイト列を次に渡す。元のストリームの最終的な読み取りは、引き続き hayro が行う。
- 単独と系列の Flate・LZW は、出力量を数えた後、上流へ渡す前に出力の Vec の容量も予約する（#772）。Flate は、失敗した試行と寛容な展開の上限を含む出力量の 4 倍と 256 バイトを足し、寛容な展開ではさらに 32 バイトを足す。Rust 1.99.1 の read_to_end は、空きが 32 バイト未満だと終端を確かめる前にも容量を増やすため、zlib と raw の最大 2 試行で、それぞれ出力量の 4 倍と 128 バイトを上限にする。LZW は、辞書とは別の出力長の 4 倍と 32 バイトを足す。追加の確保量の 16 バイトごとに Work の 1 を先に予約する。エラーを返す読み取りが書き込んだ出力も、展開器の公開の総出力量から数える。読み取りの単位が違っても、失敗までに確保する分を落とさない。予測子を当てる前と失敗までの量を使い、再展開にも同じ量を引き継ぐ。小さい予算では、以前より早く止まる。
- 単独と系列の Flate・LZW は、予測子の処理量と一時配列も先に予約する（#774）。ASCII を 1 個前置した単独の圧縮も同じ規則で扱う。引数は共通の処理で 1 回だけ読み、`F`・`Filter` と `DP`・`DecodeParms` の型ごとの優先順、未知名を含む位置、先頭 Crypt、元の文脈の参照を保つ。予測子に使う量は、Flate では容量の予約前の出力量上限、LZW では辞書とは別の出力長とする。専用の処理は追加の配列なしで、入力 1 バイトにつき Work の 8 と固定の 1 を予約する。PNG では成分を 8 ビットで処理するため、16 ビットなどの指定でも、画素のバイト数と行の長さによって専用の処理になる。
- 汎用の予測子は、入力長の 256 倍、空行の長さ、固定の 8,192 バイトを DecodedBytes に予約する。現在・前の行・書いた出力を読む成分の列と、行頭の列を 2 回複製する分の容量伸長、出力の配列も含む。空・短い入力でも空行の配列を作るので、行長を別に足す。Work は入力長の 128 倍、行長、固定の 256 を予約する。非零・整数の積・行長の既存のガードを通した引数を使い、失敗や再展開の費用も戻さない。これにより、小さい予算では以前より早く止まる。
- 展開引数の辞書の表・値・段配列も、型付き取得の前に予約する（#776）。型が違う Dict の取得でも初期表を作り、配列では未知名の引数も Object として読む。失敗した項目は次の段で再試行するため、1 個の skip 範囲だけから費用を決めない。元の tail 全体の長さと名前の数で見積もり、配列はフィルターの位置の上界だけ試行する分を数える。参照の解析が成功すれば解決に失敗しても位置が進むので、参照先の費用は再試行の倍率と分ける。既存の型別の優先順・位置・参照の文脈・ガードは保つ。
- 引数の解析は、確認 1 回と上流 2 回、暗号化では復号のための読み直しも含め 5 回分を予約する。F が名前なら、decoded_image の外部ファイル判定もその Name をもう 1 回読むため、名前の分だけ追加する。内容・フォームの診断は別に通常 2 回、暗号化で 3 回分を数え、この F の追加分は含めない。初期表・Arc・参照の包装には 2,048 バイト、キーと表の伸長には名前 1 個につき 176 バイト、名前・文字列には生バイト長の 4 倍を上界に使う。Object としての直接の stream は同じ辞書を 2 回読むため、表も 2 回、生バイト長も 8 倍にする。上流の SmallVec と確認の Stage Vec は別に数える。
- 引数の参照先は、元のファイルと展開したコンテナーの最大長、読み込み前に調べた辞書の表の上界から見積もる。型付き Array の取得は範囲を借り、取得後の生バイト列を調べてから Object を読む。数の後ろの R は、名前や文字列の中の候補も残して数え、XRef が修復の前後で対象を 2 回読む分も含める。追加確保の 16 バイトにつき Work の 1、読み取りの 16 バイトにつき 8 を予約し、確認の走査も 256 バイトずつ予算と中断を見る。get_raw が長い数を参照として試す手間も、辞書の長さから先に数える。低い予算では、展開より前の引数の予約で止まる場合がある。失敗で戻さず、再展開にも引き継ぐ。
- 複数の圧縮段では、中間ストリームの辞書と入力の写しも先に数える。厳しい Flate の展開が両方失敗する場合は、寛容な展開の内部の表も予約する。ブロック数は入力のビット数を最短のヘッダー 3 ビットで割った数を上限とし、各ブロックの表・一時の列を 512 KiB、表の生成などを 2^24 の作業で見積もる。壊れた Flate では、この保守的な上限により以前より早く止まる場合がある。寛容な Flate の内部表は、単独の段と ASCII を 1 個前置した単独の圧縮段でも、同じ規則で先に数える。固定キーの合成ストリームの 4,096 バイトの予約は、任意長の元の展開引数とは分ける。ストリームの辞書そのものなど一般の辞書の解析、Pdf::new の内部の展開や XRef の修復全体は #521 に残る。
- 系列のどこかに画像のフィルター（DCT・CCITTFax・JBIG2・JPX）があれば、hayro-syntax 0.9.0 の `decoded_data` はどの段も当てずに失敗するので、数えない。複数の段は、`F` が外部ファイルを指すときも数えない。先頭の Crypt だけを除き、途中の Crypt では止める。未知の名前でもパラメーターの位置を進め、名前でない項目で配列を読むのを終える。LZW・ASCII85 に渡る入力長を読み込み前に制限する既存の検査は変えないため、前の圧縮段の倍率を決められない LZW・ASCII85 の系列は、引き続き文書を読まない。

### 資源ごとの展開

- `Pdf::new` の前に確かめる ObjStm のうち、有効なフィルターが Flate 1 個だけのものは、8 KiB の固定長のバッファーで出力量を先に数える。名前・配列・短縮名は hayro-syntax と同じく読み、先頭の `Crypt` は適用しないので除いて判定する。既存の flate2 で zlib、raw deflate の順に試し、入力 16 バイトにつき 1、8 KiB を読む試みにつき 513 を `Work` に、展開したバイト数を `DecodedBytes` に数える。各回で中断も見る。両方が失敗したら、入力の 1,032 倍を `DecodedBytes` に、その 16 バイトにつき 1 を `Work` に先に数えてから、hayro の寛容な展開に進む。RFC 1951 の 3.2.5 では、長さと距離の符号はそれぞれ 1 ビット以上で、写す長さは 258 バイト以下なので、1 入力バイトが出すのは 8 ÷ 2 × 258 = 1,032 バイト以下。hayro-syntax 0.9.0 の寛容な展開もこの上限を守る。失敗した試みの分も戻さず、予測子を当てる前のバイト数を数える。上限内なら元のストリームを hayro で展開するので、成功時の出力は変わらない。単独 LZW とほかのストリームへの拡張は上記と下記で扱う。上記以外の複数フィルターと、hayro 内部の展開の回数・キャッシュのうち事前確認で扱えないものは #521 に残る。
- ページの内容（7.7.3.3）とフォーム（8.10）の有効な単独 Flate も、全体を展開する前に同じ確認をする。単独の内容を先に見て、なければ配列を読む。配列は参照と直接のストリームを解決し、読めない項目の後ろも読む。hayro は配列を再び展開して連結するので、再展開の分と、読めた項目の長さに空白 1 バイトずつを足した長さの倍（Vec が伸びる余りを含む）を、`page_stream` の前に `DecodedBytes` に数える。連結と伸ばす間の写しは、16 バイトにつき 3 を `Work` に数える。再展開には、予測子で短くなる前の量と、失敗した試みを含めた見積もりを使う。直接のストリームは 7.3.8.1 に反するが、hayro が読むものは同様に確かめる。
- 内容とフォームに終わりのマーカーを足す Vec と、それを Rc に写す分は、確保前に、それぞれマーカーと改行を含む長さを `DecodedBytes` に、16 バイトにつき 1 を `Work` に数える。フォームの走査のキャッシュはページ内で保つ。hayro-interpret がフォームを呼ぶたびに展開する分は、単独 Flate・LZW・RunLength と ASCII を前置した系列では、確保前に数えた量（Flate・LZW では予測子の前のバイト数）と手間を保ち、展開後に失敗するものも数える。内容の配列も、走査に続いて hayro が再展開するバイト数と手間を数える。ほかのフィルターは、これまでどおり展開後に長さを数える。
- フォント関連と ICC の単独 Flate も、固定長のバッファーで、全量の確保前に展開量・手間・中断を確かめる。対象は hayro-font 0.5.0 が読む埋め込みプログラム（Type1・MMType1 は `FontFile3`・`FontFile`、TrueType・OpenType は `FontFile2`、Type0 の最初の子孫は `FontFile2`・`FontFile3`・`FontFile` の優先順）、対応する全フォントの `ToUnicode`、Type0 の `Encoding` と最初の子孫の `CIDToGIDMap`、hayro-interpret 0.9.0 が `N` を読めた ICCBased のプロファイル。Type3 の `CharProcs` は hayro-font がストリームを保持するだけで、ここでは展開しない。対象の選択は依存の実装に合わせたもの（推定、9.7・9.9・9.10・8.6.5.5）。
- フォントの辞書のバイト列ごとに、走査の FontCache と解釈の FontCache が読む 2 回分も先に数える。プログラムと ICC のそれ自身の間接ストリームは、失敗も含め文書内で覚えるので 1 度だけ数える。文字の対応表はフォントごとに読むため、別の辞書で同じ表を使えば読み直す分を数える。直接のストリームはコンテナーの番号でまとめず、別の辞書でも確認する。フォントの途中の条件で読めなくなる場合も、後で読む候補の分を戻さない上限の見積もりにする。走査自身の TrueType 命令の事前確認と、切り抜き文字のプログラムの確認にも確保前の検査を入れる。予測子前の量と失敗した試みを保ち、字形の判定には実際の出力を使う。フォント・ICC の解析そのものの手間、画像の画素、上記以外の複数フィルターなどの残りは #521 で追う。
- hayro-interpret の解釈は、予算でも中断の合図でも止まらない。そこで、ページを渡す前に、内容のストリームを hayro-syntax の同じリーダーで走査し、hayro-interpret が解釈する手間を `Work` に、展開するバイト数を `DecodedBytes` に、たどりながら先に数える。走査は、中断の合図も見る。
- 関数（Type 0・Type 4、7.10）、メッシュのシェーディング（8.7.4）、Indexed の表（8.6.6.3）、ソフトマスクのグループ（11.6.5.2）の有効な単独 Flate も、共通の展開処理で全出力の確保前に確かめる。先頭 Crypt・短縮名・予測子・壊れた Flate の数え方は ObjStm と同じ。実際の展開後の長さと、事前確認の `Work`・`DecodedBytes` を分けて保つ。前者は標本・メッシュ・手続きの形の検査に使い、後者は解釈が資源を作り直すたびに数える。予測子で短くなる場合も、展開後に失敗する場合も、予測子の前の計上量を保つ。確認結果はそれ自身の間接オブジェクトだけページ内で再利用し、直接のストリームは使うたびに確かめる。画像の展開と、フォント・ICC の解析は対象外で、#521 に残る。
### 相互参照の表とページ順

- hayro-syntax 0.9.0 は、相互参照の表の項目が読めないか、別の番号のオブジェクトを指すと、はじめてそれを引いたときに、表をファイルの全体から作り直す（同じ番号は後ろの定義を使い、オブジェクトのストリームも展開する）。作り直すと、同じ参照が別のオブジェクトを指すので、走査が数えた後に、hayro-interpret が数えていないものを解釈しうる。そこで、走査の前に、`Pdf::new` の後で引かれうるオブジェクトをすべて引き、作り直しを済ませる。引かれうるのは、カタログとページの辞書から参照でたどれるものだけで、どのキーの値かは見ない。カタログから、続いてページの順に、辞書と配列のバイト列に書いた参照（`n g R`）を書いた順にたどり（深さ優先）、番号ごとに引く。参照は `R` の前の 2 つの数の並びの、読み始めうるすべての位置（はじめの数字までの、符号と点の位置）から、hayro-syntax の `ObjRef` で読む。hayro-syntax は、数字の前の符号と点までを数（0）として読んで次の字に進むので、配列の中の参照は並びの途中から始まり（`[--0 7 R]` は `-` と `-0 7 R`）、番号と世代番号を 1 つの並びから読むこともある（`.-0 R`）。見る位置は並びの初めの部分だけなので、手間はバイト列の長さに比例する。たどれない項目は誰も引かないので、壊れていても作り直しを起こさない。作り直すかは引く型で変わる。引く型で読めず、読み飛ばせもしない本体で作り直し、符号か点のあとに数字のない数（`-x`）は、読めても読み飛ばせない。番号ごとに、オブジェクト・辞書・配列のすべてで引く（辞書と配列の両方で読める本体はないので、読み飛ばせない本体は、どちらかで作り直す）。番号ごとに、1 と読む手間の 3 回分を `Work` に、64 バイトを `DecodedBytes` に数える。作り直す手間そのもの（ファイルの全体を読み、オブジェクトのストリームを展開する）は、予算の外にある。読むと、作り直しは見つけた「N G obj」ごとに後ろのオブジェクトを読んで確かめるので、入れ子に書いても、閉じない文字列や `endstream` のないストリームを並べても、読む量はファイルの大きさの 2 乗で増えうる（2026-11-04 に、閉じない文字列のオブジェクトを 10 万個並べた 1.4 MB のファイルで 196 秒・`Work` 184 を測った。`Pdf::new` の中なので、中断も効かない）。hayro-syntax の `objects`（表の項目を位置の順に引く）は使わない。同じ位置の項目を表（`FxHashMap`）の順に並べ、そのハッシュの値は 32 ビットと 64 ビットの環境で違うので、どの項目が作り直す前の定義を引くかで、数える量が環境で変わる。2026-11-04 に、同じ位置を指す項目の番号の組を変えた 1,260 組（どの項目にも届かない形、作り直す項目を先に引く形、後に引く形）で、ネイティブと wasm32 の `Work` が同じになることを確かめた。
- ページの木を読めない文書では、hayro-syntax 0.9.0 は、表の項目を `objects` の順に引いてページを探す（`Contents` のある辞書をページとする）。同じ位置を指す項目があると、ハッシュの順で、どの定義をページにするか、ページが見つかるかと、ページの順が環境で変わる（2026-11-04 に、ページの木のない 400 バイトほどのファイルで、番号の組を変えた 1,260 組のうち 584 組で、ネイティブ（64 ビット）と wasm32 の用紙の大きさが違った）。探したかも、読み込むときに表を作り直したかも、公開の API では分からない。そこで、ファイルの写しの後ろに、どの表にも載らない番号（2,147,483,646）の定義を足して読む。hayro-syntax は、表を作り直すと、ファイルを走査しただけの表を作るので、この番号を引けたら作り直したと分かる。足す定義は `>>` を持たず、最後に置くので、走査で辞書に飛び越されず、ほかの定義に上書きされない。hayro-syntax は最後の `startxref` をデータの全体から後ろ向きに探し、足す字は `startxref` を含まないので、ファイルと同じ位置の表を読む。表を作り直さずに読め、カタログの `Pages` が `Kids` を持つ辞書なら、ページを探していないので、そのまま使う（探すのはページの木を読めないときだけで、作り直していなければ、読み込みのときと同じ読みは同じ結果になる）。ほかの文書（読めない文書を含む）は、1 度目の文書を放してから、写しの後ろに読めない位置の `startxref`（`-1`）を足して、ファイルを走査した表で読み直す。走査した表では、同じ位置の項目のうち読めるものは 1 つで、表を作り直さないので、どの順に引いても同じ定義を選ぶ（オブジェクトのストリームの項目は、2 度書いたストリームの同じ添字の項目どうしと、ストリームそのものと添字 0 の項目で順のキーが重なるが、読める項目は 1 つで、ストリームは辞書でないので、ページの列は変わらない）。1 度目の文書は使わない。hayro-syntax の `Data` は、表を作り直しても展開したオブジェクトのストリームを番号で覚えたまま捨てないので、1 度目の文書のページの値は、作り直す前の定義を返しうる。足すバイト列は `%\ntrailer\n` で始め、ファイルの終わりで読みかけのオブジェクト（`N 0 obj` と、符号だけの数の `N 0 obj -` など）を、読めるものにしない（`%` は空白でない区切りの字なので、符号の後に置いても 0 と読み飛ばされない）。文書の情報とバージョンも、使う文書から読む。写しは、1 度に 1 つ、ファイルの大きさと数十バイトで、予算に数えない。読み直すと、表のとおりなら読めた文書が `pdf.document.invalid` になることがある（木がなく、ページの後ろの定義に `Contents` がない文書や、後ろのカタログに `Pages` がない文書）。読み直すかは表とファイルだけで決まるので、環境では変わらない。

### 読み込み前の数値と参照の検査

hayro-syntax 0.9.0 は相互参照の表を作り直す際、文字列やコメントの内側にある定義も読む。このため `Pdf::new` に渡す前に、ファイルと ObjStm の中身から名前・数・参照先の候補を拾う。個々のストリームに絞れない値には文書内の最大値を使い、安全に読めると確かめられなければ `pdf.document.unsupported` を返す。

- **整数と予測子。** `Columns`・`N`・`First` と ObjStm 内の位置は 2 の 31 乗未満に限る。予測子が有効な場合、列数・色成分数・成分のビット数が 0 なら読まない。既定値を含む最大の成分数とビット数の積は 255 以下、行の長さは 1 MiB 以下にする。
- **フィルター。** 配列の名前・参照は最大 64 個とする。LZW・ASCII85 の入力長の上限が 2 の 28 乗バイト以上、または前段や参照のためにその上限を決められない場合は読まない。上限は元の長さに、先行する ASCII85 ごとに 4 を掛けて求める。
- **展開引数。** `DecodeParms`・`DP` の配列は候補の位置ごとに 1 KiB まで読む。フィルターが使う範囲に上位の参照が 2 つある場合、直接書いたストリームや途中で切れた項目がある場合は断る。辞書の内部の参照や上位の参照が 1 つだけの配列は、この個数制限に当たらない。
- **ObjStm。** `Length`・`N`・`First`・`Filter`・`F`・`DecodeParms`・`DP` に参照を含む候補と、事前に展開したストリームに結び付かない `Type /ObjStm` は断る。暗号化した文書では、復号前に中身を検査できない ObjStm の候補があれば文書を読まない。
- **走査の費用。** 読み飛ばした空白・コメント、字句、重なった辞書を読み直す手間は `Work` に、展開や辞書・位置を覚える表は `DecodedBytes` に数える。同じ位置・深さから読んだ結果は再利用する。構文ごとの枝分かれと費用は[事前検査の実装](../../crates/zumen-pdf/src/guard.rs)、境界は[図面への変換テスト](../../crates/zumen-pdf/tests/drawing.rs)、実測値は[測定時の記録](https://github.com/zumen-jp/zumen/blob/252b878dc53338c648b35f13ba2366134bf94dae/docs/formats/pdf.md?plain=1#L72)にある。

- 暗号化した文書は、オブジェクトのストリームを使えば読まない（上）。hayro-syntax は、読み込み（`Pdf::new`）の中で中身を復号して中の位置を使い、表を作り直すときは、型の参照も解いて展開する。読み込みの後に確かめる形も試したが、それまでに中の位置を使い、作り直した表から外れたストリームの中身も覚えて使うので、確かめ漏らした（2026-11-04 の確かめで、図面が環境で変わる形と、0 で割ってパニックする形が見つかった）。hayro のテスト用の PDF 422 個では、暗号化した 15 個のうち 7 個がオブジェクトのストリームを使い、これらを読まなくなる。#521 で、上流に、中の位置を確かめて足すことを求め、取り込めたら読む。
- hayro-syntax 0.9.0 は、小数の部分が 20 桁以上で、数字を並べた値が u64 に収まる数（`0.000…0123` など）を、std の `powi` で求めた 10 の冪で割って読む。std の `powi` は、ネイティブと wasm32 で最後の桁が違うことがある（2026-11-04 に、確かめる側が、10 の 23 乗から違うことと、小数 23 桁の数で `cm` をかけたページで、線の端点と線幅が違うことを確かめた）。外からは止めていない（ファイルのバイト列と、内容のストリームと、オブジェクトのストリームの中身は、読む前の確かめか走査で見つけられるが、Type 3 の字形の手続きは、走査が展開しない）。#521 で、上流に、std の `powi` を使わないか、`str::parse` で読むことを求める。

### 描画の費用と中断

- hayro-interpret は、次のものを演算子ごとに作り直して展開するので、使うたびに数える: フォーム（`Do`）、ソフトマスクのグループと、その色空間・転送関数（`gs`）、転送関数（`gs` の `TR`・`TR2`。キーごとに作るので、両方あれば 2 回）、シェーディングのストリーム・関数・色空間（`sh` と、シェーディングのパターンを選ぶ `scn`・`SCN`）、画像と内容の中の画像の、直接書いた色空間（分版の色変換の関数と、Indexed の表）。関数は、つなぐ関数（Type 3）の中まで、辞書で書いたものもストリームで書いたものもたどる。名前で引く色空間・フォント・ICC のプロファイルは、hayro-interpret が覚えるので、作り直さない（作る手間は、ページで 1 度だけ数える）。タイルのパターンは、塗るときまで中身を展開しない。走査は、同じオブジェクトの手間をページの中で 1 度だけ求めて覚えるが、覚えるのは、資源の辞書の項目が参照で指すオブジェクトと、それ自身の間接オブジェクトのストリームだけにする。hayro-syntax の `obj_id` は、直接書いた辞書と、辞書の値や配列の項目に直接書いたストリーム（7.3.8.1 節に反するが、hayro-syntax は読む）に、それを含む間接オブジェクトの番号を返す。そこで、ストリームは、その番号で引いたストリームと辞書のバイト列が同じときだけ、それ自身の間接オブジェクトとみなす。直接書いたものは、使うたびにたどる。見分けるために引くコンテナーは、番号ごとに 1 度だけ引いて覚える（走査と装置は、文書の中で同じ表を使う）。
- hayro-interpret が作るものの大きさも、メモリの代わりに `DecodedBytes` に数える。大きさは、hayro-interpret 0.9.0 の型の大きさか、測ったメモリを、配列を伸ばすときの余りと写しを含めて倍にした（1 つずつ足して伸ばす配列は、伸ばす間に前と後の配列が同時にあるので、型の大きさの 3 倍まで使う）: メッシュのシェーディング（型 4〜7）の三角形（1 つを 1,024 バイト。型 5 は頂点ごとに 2 つまでと、頂点の 256 バイト）とパッチ（2,048 バイト）、Type 0 の関数の標本（f32 の 1 つを 16 バイト）、Type 4 の関数の手続き（作るたびに演算子の配列にするので、1 バイトを 128 バイト）、切り抜きにする文字の輪郭（経路の要素の 1 つを 512 バイト。写すときは 128 バイト）、グラフィックス状態を写すときの破線の配列（1 項目を 8 バイト）、CID フォントの幅の表（1 項目を 160 バイト）。メッシュは、使うたびに三角形とパッチをすべて作るので、頂点とパッチの数の上限を、最小のビット数（色の成分を読まないとし、型 4・5 の頂点はバイトの境から読む）から求め、1 つを `Work` の 4 とも数える。hayro-interpret は、`Function` がなければ、色の成分の数を `Decode` の座標より後ろの項目の数の半分とするので、`Decode` が座標の分だけなら、色を読まない。幅の表は、走査と hayro-interpret が、文書の間、フォントの辞書ごとにそれぞれ持つので、文書の中で 1 度だけ数える。
- hayro-interpret は、経路を塗る演算子まで配列に持ち、字形を文字列（`TJ` は配列のすべての文字列）ごとに 1 つの並びの配列にして装置に渡す。どちらの配列も、空にしても容量を持ったまま、ページの中で次の経路と並びで使い回し、ページごとに作り直す。そこで、文書の中でいちばん長い経路の要素の数（経路を作る演算子の 1 つを 1 つ、`re` は 5 つ）と、字形の並びの文字列のバイト数のうち、65,536 を超える分を、1 つ 512 バイトと数える（hayro-interpret の配列と、装置が要素にする間の写しを合わせて、経路の要素の 1 つでおよそ 340 バイト、字形の 1 つでおよそ 280 バイトを測った）。ページの中で使い回すので、フォームの呼び出しごとには数えない。数えない分の一時のメモリは、経路と字形の並びを合わせて、およそ 30 MB までになる（2026-11-04 に測った）。
- hayro-syntax は、資源を引くたびに、そのオブジェクトを読み直す。ストリームは、`Length` が合わなければ、読むたびに本体を読み進めて `endstream` を探す。hayro-interpret は、フォームを呼ぶたびに資源の辞書を読み直し、名前で引く色空間とフォントは、引くたびにオブジェクトのバイト列から表のキーを作る。関数を作るたびに関数の辞書を読み、`BDC` のたびに、名前で引く性質の辞書を、タグによらず読む。OCMD の `OCGs` は、hayro-interpret・走査・装置が、マーク付きの内容と XObject のたびに読む。そこで、資源を引く演算子（`gs`・`Do`・`sh`・`scn`・`SCN`・`cs`・`CS`・`Tf`・`BDC`）ごとに、引いたオブジェクトの大きさ（4 バイトを 1。ストリームは辞書と、`Length` が合わなければ本体。内容のストリームも同じ）を `Work` に数え、フォームを呼ぶたびに資源の辞書の、関数を作るたびに関数の辞書の、マーク付きの内容と XObject のたびに OCG か OCMD と `OCGs` の大きさも数える。関数を作るときは、数の配列（`Domain`・`Range`・`Size`・`Encode`・`Decode`・`C0`・`C1`・`Bounds`）の項目も数える（短い数の並びでは、バイト数より重い）。資源の名前が別の型のオブジェクトを指しても、hayro-syntax は読み飛ばして確かめるので、同じように数える。走査は、フォントを選ぶ（`Tf`）たびに `BaseFont` と `Subtype` を読み、直接書いたフォントは値を覚えないので、それらの参照の先も数える。
- hayro-syntax は、キーを引くたびと配列の項目を読むたびに値の参照を解き、型が違っても、読み飛ばして確かめる。読み直す辞書の値が大きなオブジェクトを指すと、使うたびに、書いた回数だけそれを読む。そこで、読み直すオブジェクト（XObject・拡張グラフィックス状態・ソフトマスク・シェーディング・パターン・関数・色空間・性質の辞書・内容のストリーム・ICC のプロファイル）と、ページの辞書を使うたびに、値の参照の先を 3 段たどり（`DecodeParms` の配列の辞書の値まで）、1 と読む手間に書いた回数を掛けて `Work` に数える。求める間は、同じ番号を段ごとに 1 度だけ引く。hayro-interpret がどのキーを読むかは見ない。資源の辞書は、hayro-syntax が引く 7 つの種類（`Font` など）の辞書までを読み、中の資源は名前で引くときに読むので、そこまでにする。`Resources` がストリームのオブジェクトを指せば、hayro-syntax はその辞書を資源の辞書として読む。親（`Parent`）は読まない。注釈（`Annots`）とビューポート（`VP`）は、外観の保持と移さない情報を診断するときに、辞書でない項目も含めて、項目を読みながら数える（注釈はページを指すので、まとめて数えると、注釈の数の 2 乗になる）。ストリームの `Length` が参照なら、読むたびにその先も読むので、ストリームを読む手間に足す（数を指すふつうの文書では 0）。`endstream` のないストリームは、読むたびにファイルの終わりまで探すので、ファイルを読み通す手間と数える。参照の先が小さい普通の文書では、ほとんど増えない（2026-11-04 に、値が 400 KB の配列を指す 70 ほどの形を、数える前の 25〜220 µs に対し、`Work` 1 あたり 0.01〜0.33 µs と測った）。
- hayro-interpret は、線と文字を描くたびに破線の配列を写し、図面モデルへの移しは、線ごとに破線から線種を作る。そこで、破線の長さ（`d` と、拡張グラフィックス状態の `D`。`q`・`Q` とともに追う）を、線と文字を描く演算子ごとに `Work` に数える。また、hayro-interpret は、`q` の後で状態を変えるとき・フォームを呼ぶとき・Type 3 のフォントの字形ごとに、グラフィックス状態を写す。写すたびに、破線の配列と、切り抜きにする文字（描画モード 4〜7、9.3.6 節）の `ET` まで貯めた輪郭も写すので、`q`（後で状態を変えるかによらない）・フォームの呼び出し・Type 3 の字形ごとに、その長さ（破線は項目の数、輪郭は経路の要素の数）を `Work` に数える。`ET` でも、貯めた輪郭を写す。
- 切り抜きにする文字は、hayro-interpret が、見える字ごとにフォントのプログラムから輪郭を作り、`ET` まで貯める。輪郭の大きさはフォントのプログラムで決まり、上限は hayro-font が使う skrifa と read-fonts の制限（TrueType の字形は 65,536 点、CFF と Type 1 は 100 万の演算）だけなので、数百バイトのフォントでも、1 字に数万の要素を持たせられる。そこで、走査も hayro-font の同じ API で、フォントと符号ごとに 1 度だけ輪郭を作り、字ごとに、経路の要素の 1 つを `Work` の 3 と 512 バイトに数える。hayro-font 0.5.0 は、輪郭を覚えず、字ごとにプログラムから作り直す。作る時間は、輪郭の大きさでなく、プログラムで決まる。TrueType の合成の字形は、部品を 2,048 本までたどり、たどるたびに字形の部品をすべて読む。CFF と Type 1 は、1 字に 100 万の演算まで動く。走査は、フォントごとに、輪郭を 1 度作る手間の上限を、埋め込んだプログラムを展開し（展開したバイト数も数える）、hayro-font と同じく skrifa で読んで求め、輪郭を作るたび（走査がはじめて作るときと、字ごと）に `Work` に数える。字形が TrueType のフォントは、2,049 ×（いちばん長い合成の字形の部品の数 + 1）+ 4,096（部品は 6 バイトを 1 つと数え、合成の字形がなければ 4,096）とし、ほかのフォントと、読めないプログラムは 65,536 とする。埋め込まないフォント（hayro-font が持つ標準のフォントで描く）は 0 とする。次の 2 つは、上限で数えると文書を読めなくなるので、その文字を切り抜きにするページを hayro-interpret に渡さず、`pdf.page.dropped` を返す（場所は、プログラムのレコード）: skrifa が字形の TrueType の命令を動かすフォント（`is_hint_reliant`。ファミリーの名前か、`cvt`・`fpgm`・`prep` の検査和で見分ける、仕様の外の慣習で、MingLiU など。輪郭を作るたびに、たどる字形ごとに 100 万の命令まで動く）と、可変の合成の字形（VARC）を描くフォント（部品ごとに、65,536 の節と変化の領域の数（65,535 まで）の積の手間で条件を評価する）。切り抜きにする描画モードは図面では少なく、塗るだけの文字には影響しない。合成の字形は、たどる数の上限で数えるので、部品を少ししかたどらないフォントでは、多めになる（2026-11-04 に測った。2,048 本をたどる形で `Work` 1 あたり 0.056 µs、CFF の 100 万の演算で 0.14 µs）。代わりに使う Helvetica で描く文字列は、hayro-interpret と同じく、ASCII のバイトだけのものしか数えない。Type 3 の字形は、輪郭を足さない。
- skrifa は、`is_hint_reliant` のフォントの字形が TrueType なら、フォントを読むときに `fpgm` と `prep` を 1 度ずつ動かす（描画モードによらない）。1 回に 100 万の命令まで動き、命令の手間は、影の領域の点の数（`maxp` の値と 4）・スタックの項目の数（`maxp` の値と 32）・定義の表の大きさ・`GETVARIATION` が積む値の数（`fvar` の軸の数。スタックの大きさまで）で決まる。定義の命令（`FDEF`・`IDEF`）が本体を読み飛ばす命令は、上限に数えない。先頭から順に読む命令の列に、飛ぶ命令（`JMPR`・`JROT`・`JROF`）がなければ、定義の命令は 1 度ずつしか動かない（関数の中の定義は、読むときに誤りになる）。飛ぶ命令があれば、値を積む命令のデータの中のバイトにも入れ、関数の呼び出しで何度でも動かせる。そこで、フォントを読む前に、プログラムのストリームごとに 1 度、走査と hayro-interpret が読む 2 回分を数える。`Work` は、空でないプログラムごとに、100 万 ×（8 + 点の数 ÷ 32 + 項目の数 ÷ 1,024 + 定義の数 ÷ 256 + 軸の数 ÷ 128）に、定義の命令を動かせる回数の見積もり（呼び出しで動かす 100 万 ÷ 4 と、後ろへ飛ぶ回数の上限の 2 倍の和。100 万 ÷ 2 まで）× いちばん長い本体の命令の数 ÷ 16 を足したもの（飛ぶ命令がなければ、足さない。`prep` は `fpgm` の関数を呼べるので、どちらかの長いほう）。`DecodedBytes` は、表の大きさ（定義は 1 つ 16 バイト、スタック・`cvt`・記憶域は 1 項目 4 バイト、影の領域は 1 点 17 バイト）。どちらも大きめに数えるので、ふつうのプログラムでは多めになる。定義の回数は上限ではなく、定義を続けて並べた所へ呼び出しで飛ぶと、もっと動かせる（2026-11-04 に、確かめる側が、50 個並べて 130 × 130 回呼ぶ形で、1 回の実行で 84 万 5,000 回動くことを確かめた。式の見積もりは 25 万 600 回）。そのときも、1 あたりの手間は下の幅に収まる。既定の予算（`Work` 100 億）で、飛ぶ命令のないフォントは 1 つに 3,200 万ほど、Windows のフォント 287 個の本体の長さ（中央値 229、最大 3,849 命令）で見積もると、飛ぶ命令のあるものは 1 つに 5,000 万〜3 億ほどを使うので、命令に頼るフォントは文書の中でおよそ 30〜300 個まで読める（2026-11-04 に測った。重い命令の並びで `Work` 1 あたり 0.07〜0.11 µs、定義の読み飛ばしで 0.04 µs（定義を続けて並べた所へ飛ぶ形では 0.34 µs まで）、`GETVARIATION` で 0.06 µs、`PUSHB`・`POP` の並びで 0.003 µs）。命令を動かさないフォントと、空のプログラムは数えない。
- 装置は、塗りと線は演算子ごとに、文字は文字列ごとに、色を 1 度だけ RGB にする（線を部分パスで分けても、文字を字の間で分けても、分けた要素に同じ色を使う）。hayro-interpret は、Separation・1 成分の DeviceN・Indexed の色空間では、はじめて色を RGB にするときに 256 色の表を作り、多成分の DeviceN では、色を RGB にするたびに色変換の関数を当てる。転送関数は、状態を当てるたびに 256 個の値に当てて表を作る。そこで、関数を 1 度当てる手間を多めに見積もり（Type 0 は、出力ごとに 2 の（大きさが 1 より大きい入力の数）乗の端の標本を足し、Type 2 は出力の数と 1、Type 3 はつなぐ関数の数と、その中でいちばん重い関数、Type 4 は手続きのバイト数）、表を作る手間（256 回）と、塗るたびの手間を `Work` に数える。
- `Work` は、簡単な演算子を 1 とし、重い演算子に重みを付ける: フォームを 1 回呼ぶと 50、`gs`・画像（`Do` と内容の中の画像）・`sh` は 16、文字列の 1 バイトは 8（切り抜きにする描画モード 4〜7 は 40 と、輪郭の経路の要素の 1 つに 3、写すときは 1）、経路を塗るか線を描く演算子は 6（`B` などは 12）、マーク付きの内容の始まり（`BDC`）は 4、メッシュの頂点かパッチの 1 つは 4、CID フォントの幅の 1 項目は 2、関数を作るときに読む Type 0 の関数の標本は 8 個を 1、関数の数の配列は 1 項目を 1、Type 4 の関数の手続きは 4 バイトを 1。hayro-interpret 0.9.0 を release で build し、同じ演算子を何万回も並べたページを解釈して測った比で決めた（2026-11-03・2026-11-04）。重みを付けると、`Work` の 1 あたりの時間は、測った機械と演算子（パス・塗り・線・色・フォーム・`gs`・画像・`sh`・メッシュ・マーク付きの内容・文字・切り抜きにする文字の輪郭とフォントのプログラム・TrueType の命令・大きな辞書と数の配列を引く演算子・読み直す辞書の値の参照の先・破線・幅の範囲）で 0.05〜0.35 µs になり、多くは 0.1〜0.3 µs になる。関数を当てる手間・状態の写し・`OCGs` の読み直し・値の参照の先・メッシュの頂点の数・合成の字形をたどる数・TrueType の命令・字形の Unicode は多めに数えるので、これらの多いページでは、1 あたりの時間がもっと短い。
- hayro-interpret は、関数（つなぐ関数の `Functions`、7.10.4 節）と色空間（Indexed・Separation・DeviceN・Pattern の基の色空間と、ICCBased の `Alternate`、8.6 節）を、深さの上限なしに再帰して作る。長い鎖ではスタックを使い切ってプロセスが落ち、パニックでないので捕まえられない。Type 4 の関数（7.10.5 節）の手続き（`{` `}`）の入れ子も、同じく深さの上限なしに再帰して読み、当てる。また、hayro-font は、CID フォントの幅（`W`・`W2`、9.7.4.3 節）の範囲の CID を 1 つずつ表に入れるので、数十バイトの指定から、範囲に比例した時間とメモリを使う。Type 0 の関数（7.10.2 節）は、標本の位置を f32 で求めるので、大きさ（`Size`）が 2 の 24 乗（16,777,216）を超えると、丸めた位置が標本の外を指してパニックする。格子のメッシュ（型 5、8.7.4.5.6 節）は、行の頂点の数（`VerticesPerRow`）が 0 だと、頂点を読まずに行を足し続けて、メモリを使い切る。Type 0 の関数の標本とメッシュ（型 4〜7）は、展開した長さを 8 倍し、読む位置をビットの数の `usize` で持つので、2 の 29 乗（512 MiB）からの長さは、32 ビットの環境であふれる（2026-11-04 に、確かめる側が、2 の 29 乗バイトに展開する関数で、ネイティブと wasm32 の図面が違うことを確かめた）。そこで、走査で、16 段より深い入れ子の関数か色空間（転送関数・ソフトマスク・シェーディング・パターン・`cs`・`CS`・画像・内容の中の画像が使うもの）か、64 段より深い手続きの Type 4 の関数（コメントの中の括弧は数えない）か、大きさが 2 の 24 乗を超えるか、展開した長さが 2 の 29 乗からの Type 0 の関数か、行の頂点の数が 0 の格子のメッシュか、展開した長さが 2 の 29 乗からのメッシュ（型 4〜7）を使うページと、幅の項目が 2 の 18 乗（262,144）より多い CID フォントか、文字の範囲（`FirstChar`・`LastChar`）の値が 2 の 18 乗を超える単純なフォントを使うページは、hayro-interpret に渡さない（hayro-font でフォントを読む前に数える）。hayro-font は、単純なフォントの `FirstChar` の数だけ幅の表を伸ばすので、数十バイトの指定から、値に比例した時間とメモリを使う。値は環境の大きさの整数で読むので、2 の 32 乗からの値は、32 ビットの環境で読めず、幅が変わる。範囲に収まるフォントでも、`FirstChar` が 256 を超えれば、その数を `Work` に、その 32 倍を `DecodedBytes` に、文書の中で 1 度だけ数える。そのページはシートにするが、中身は移さず、`pdf.page.dropped` を返す。場所は、理由の関数・フォント・メッシュのレコード（直接書いたものは、それを含む間接オブジェクトのレコード。色空間の入れ子は、ページの内容のストリーム）にする。そのページで走査が見つけた、ほかの診断は返さない。hayro に上限を求めることは、#521 で扱う。
- フォームが次の段のフォームを何度も呼ぶと、解釈する数は段の数の冪で増える。同じフォームを同じ文脈（深さ・資源の持ち主・走査が追うグラフィックス状態）で呼ぶ所は 1 度だけ走査し、覚えた手間をまとめて数えるので、走査の手間は段の数に比例する。走査が返した中の診断（`pdf.text.dropped` など）も覚え、呼んだ回数だけ件数を足す。ページごとに 1 件の診断（`pdf.font.missing` など）は、足さない。
- マーク付きの内容の入れ子（14.6 節）は、hayro-interpret と同じく、ページの中で 1 つの重なりとして追い、フォームの中と外で分けない。閉じない `BDC` や、外の入れ子を閉じる `EMC` を持つフォームは、呼ぶ所の入れ子で見え方が変わるので、手間を覚えず、呼ぶたびにたどる。
- 解釈を始めた後は、hayro-interpret を途中で止められない。要素を描くときと、ページを解釈した後に中断の合図を見て、中断を返す。中断してから止まるまでの時間は、長くてもそのページの解釈の時間になる。解釈の時間は、走査で数えた `Work` に、測った演算子ではおよそ比例する（`Work` 1 あたり 0.05〜0.35 µs）が、測っていない入力の形では、もっとかかりうる。今の既定の上限（`Work` 100 億、[予算と中断](../architecture.md#予算と中断) の仮の既定値）では、1 ページで十数分から 1 時間ほどになりうる。すぐに止めたい呼び出し側は、`Work` の上限を小さくするか、ホストの手段（Worker を止めるなど、[予算と中断](../architecture.md#予算と中断)）で止める。解釈の途中で止める口は、#521 で hayro に求める。
- hayro-interpret は、ページごとにカタログと表示の設定を読み直す。そのバイト数を、ページごとに `Work` に数える。
- 図面モデルへの移しは、さらにパス・字形の並び・画像ごとに `Work` を、要素ごとに `Elements` を使う。止めたら、そのページの最初の内容のストリームを場所にする。hayro-interpret は、フォームを呼ぶたびに中身を解釈し直すので、要素は小さいファイルからも指数的に増える。そこで、図面モデルのメモリも `DecodedBytes` に数える。要素の 1 つを 2,048 バイト（要素の配列を伸ばす間の写しを含めて測った、およそ 1.3〜1.5 KB を多めにした）とし、形が持つ配列の倍（作る間の写しと、配列の余りの分）を足す。配列は、項目の数と、64 ビットの環境の型の大きさ（折れ線の頂点 32 バイト、スプラインの制御点 24 バイトと節点 8 バイト、ハッチングの輪 64 バイトと輪の辺 168 バイト）から求め、文字の様式の名前とアンダーレイの資源の名前はバイト数で数える。予算は環境によらず同じに数えるので、32 ビットの環境でも同じ大きさを使う。字形の Unicode（ToUnicode の CMap の写す先、9.10.3 節）は長さが決まっておらず、1 つの符号を数万字に写せる。装置は、字形ごとの Unicode の配列・同じ並びかを見るキー・文字の中身の 3 つに写すので、字形ごとに、写す前に 1 バイトを 4 バイトと、16 バイトを `Work` の 1 に数える。2026-11-04 に、曲線の塗りと線、長い写し先で測ったメモリは、数えた量の 0.5〜0.75 倍だった。既定の予算では、文書の中でおよそ 100 万の要素まで移す。超えると、文書の全体を `budget.decoded-bytes.exceeded` で止め、部分の結果は返さない。要素のメモリの数え方・code・部分の結果は、#559 で決める。
- ページラベルの数の木は深さ 32 まで、文字のページラベル（`A`〜`Z`、`AA`…）は 64 文字までたどる。同じ参照は、番号を見てから解くので 2 度解かず、直接書いた節（7.9.7 節では、`Kids` の項目は間接参照）は、それを含む節をたどるときに 1 度だけ読む。hayro-syntax 0.9.0 は、読んだ辞書ごとにキーの数に比例する表を作るので、範囲の辞書は持たず、値（`P`・`St`・`S`。`S` は 1 バイトの名前だけで、長い名前は書き方のないものとする）だけを持つ。範囲の 1 つを 256 バイトと `P` のバイト数で `DecodedBytes` に数える。`Nums` の項目は、参照を解くたびに読み直すので、読むバイト数を `Work` に数える。ラベルはページごとに作り、図面モデルに写すので、ページごとに、`P` のバイト数を `Work` に、その 1 バイトを 6 バイト（UTF-8 で 3 バイトまでになり、写す分を合わせる）と 256 バイトを `DecodedBytes` に数える。

### 予算の外に残る処理

- 予算の外の作業は、ストリームの展開そのもの（上の ObjStm・内容・フォーム・描画資源・フォント・ICC の単独 Flate・LZW・RunLength と、上記の ASCII を前置した系列を除き、展開してから数える）・`Pdf::new` の中の読みとメモリ（ページの木の節とページの値。数えるのは読んだ後になる。hayro-syntax 0.9.0 の `Page::new` は、ページごとに資源の 7 つの種類の辞書を読んで文書の間持つので、同じ大きな資源の辞書を多くのページが指すと、メモリはページの数とキーの数の積で増える。2026-11-04 に、確かめる側が、500 ページ × キー 5,000 の 96 KB のファイルで 1.3 GiB、1,000 ページ × キー 7,000 の 166 KB のファイルで 2.7 GiB を測った。外から止めるには L1 の数で見積もることになり、ふつうの大きな文書も断るので、止めていない）・相互参照の表の作り直し・オブジェクトのストリームの展開（hayro-syntax 0.9.0 は、どのストリームを展開したかを返さないので数えない。文書の間持つ量は、ストリームの展開と同じく、圧縮の比とファイルの大きさで決まる。2026-11-04 に、1 MB のファイルで 1.3 GiB、3 MB のファイルで 5 GiB を測った）・読み飛ばす空白とコメント（オブジェクトの前後と、`Length` が合わないストリームの `endstream` の前）と、読んだ値から読んだ長さが分からない定義を読む手間（hayro-syntax 0.9.0 は、読んだ長さも項目の位置も返さない。数でも名前でもない字の並びは `null` と読み、本当の `null` と見分けられないので、短いものとして数える。読み飛ばせても数として読めない並び（`5-333…3.2`）は引けないので 0 と数える。長い数・空白だけの 16 進の文字列・行の継続だけの文字列は、読んだ後の値の大きさで数えるので、読んだ長さより少なく数える。どれも読む回数とファイルの大きさの積で増え、`Work` 1 あたりの時間に上限がない。2026-11-04 に、1 MiB の空白の前のオブジェクトを `gs` で 1,000 回引いて 1.2 秒・`Work` 1 あたり 60 µs、8 MiB で 9 秒・446 µs、400 KB の字の並びを `Do` で 1,000 回引いて 1.3 秒・970 µs を測った。確かめる側は、400 KB の読めない数・長い数・空白だけの 16 進の文字列を `Do` で 1,000 回引いて 1.2〜2.9 秒を測った）・フォントの解析（単独 Flate・LZW・RunLength と、ASCII を前置した系列の展開は上のとおり先に数える。CID フォントと単純なフォントの幅の表だけは、項目の数（単純なフォントは文字の範囲の値）をフォントごとに先に制限し、表のメモリを文書の中で数える。切り抜きにする文字に使うフォントは、走査もプログラムを展開して数える。TrueType の命令の手間は、上で数える）・ICC のプロファイルの解析・曲線の平坦化。hayro-syntax 0.9.0 の展開は出力の大きさに上限がないので、事前の確認の対象外では、小さいファイルから大きく展開するストリームで、予算より先にメモリを使う。[予算と中断](../architecture.md#予算と中断) の「依存の中の作業は、入力の大きさで先に制限する」には、まだ合っていない。止め方は #521 で決める。

## 図面モデルへの変換

### ページ

- ページを、順に図面のシートにする。名前はページラベル（12.4.2 節）とし、ラベルのないページは名前を持たない。ページの木（7.7.3.2 節）の `Kids` の項目のうち、辞書に読めないもの（数・`null`・入れ子の深すぎる値を持つ辞書など）と、たどった節かページをもう一度指す参照は、hayro-syntax 0.9.0 がページにも節にもせずに飛ばす。同じ規則で木をたどり直し、飛ばした項目を、その項目を持つ節（直接書いた節は、それを含む間接オブジェクトの節）のレコードを場所にした `pdf.page-tree.dropped` で返す。件数は飛ばした項目の数。`Type` が `Pages` でない辞書はページとみなす。`Kids` を配列に読めない（ない場合を含む）`Pages` の子の節も、hayro-syntax は下のページごと飛ばすので、その節のレコードを場所にして 1 つ数える（`Kids` は中間の節に必須の項目で、7.7.3.2 節の表 30 にある）。`Kids` がないと、`Count` が 0 でページを失っていなくても、ページを持つかが分からないので数える。`Kids` が空の配列なら数えない。カタログの `Pages` の参照の先に `Kids` の配列がなければ、hayro-syntax は木をたどらずにファイルからページを探すので、数えない。たどる手間は、項目ごとに `Work` を 1 と読むバイト数、参照ごとに `DecodedBytes` を 64 バイト数える（#555）。
- 大きさは、クロップボックスとメディアボックスの重なり（14.11.2 節）を、`UserUnit`（7.7.3.3 節）と `Rotate`（時計回りに 90 度ずつ）を当てて mm にする。1 pt は 25.4/72 mm。メディアボックスのないページと、大きさのない範囲（辺が 1/4096 pt 以下）は A4（210 × 297 mm）とし、1 pt より短い辺は 1 pt とする（推定。hayro-syntax の `Page::base_dimensions` と同じ決め方）。
- 座標は、表示の向きに回した用紙の mm で、クロップボックスの左下を原点、Y を上にする。hayro には 1/1024 mm を 1 装置単位として渡す。

### 線と塗り

- 線を引くパスは、部分パス（8.5.2 節）ごとに要素にする。線分 1 本は線、曲線を含むものはスプライン（3 次のベジェ曲線をそのまま持つ）、ほかは折れ線にする。2 次の曲線は、同じ形の 3 次の曲線にする。閉じた部分パスは、閉じた折れ線にする。曲線を含む閉じた部分パスは、閉じる線分も同じ形の 3 次の曲線にした、閉じたスプラインにする。
- hayro は、長方形の形のパス（`re` と、`m`・`l` で描いた軸に平行な長方形）を、角の座標にして渡す。そのため、左下の角から反時計回りの閉じた折れ線にし、元の始点と向き（8.5.2.1 節）は移らない。破線の位相は、元の始点からずれうる（推定）。
- 線の端（8.4.3.3 節）とつなぎ（8.4.3.4 節）の形と、マイターの限度（8.4.3.5 節）は、図面モデルが持たないので移さない。開いた部分パスの端が突き合わせでないか、線分が 2 つ以上か閉じた部分パスのつなぎがマイターでなければ、`pdf.stroke.approximated` を返す。丸い端やつなぎを使う図面（CAD の出力に多い）では、ほぼいつもこの警告が出る。長さのない部分パスの丸い端（点）は、長さのない線になる。
- 座標・線の太さが有限でない要素（大きすぎる変換など）は移さず、`pdf.geometry.dropped` を返す。
- 線の太さは、ユーザー空間の太さに、変換の行列式の絶対値の平方根を掛けて mm にする（推定。斜めに伸ばす変換では、向きで太さが変わる）。
- 破線（8.4.3.6 節）は、長さの並びを mm にした線種にする。名前は `[2.117 1.058]` のように mm の小数 3 桁で、実線は `[]` とする。奇数個の並びは 2 回繰り返す。すべて 0 なら実線にする。位相が 0 でなければ、位相を移さず `pdf.dash.approximated` を返す。hayro が 0 の代わりに置く 0.01 以下の長さは、0（点）に戻す。
- 塗りは、部分パスを輪にした塗りつぶしのハッチングにする（輪の中の輪を交互に埋める）。非ゼロ回転数の規則（8.5.3.3 節）で塗った形は、輪が 2 つ以上か、単純な輪と確認できなければ、`pdf.fill-rule.approximated` を返す。面積のない塗りを hayro は 1 装置単位の線にするので、1/1024 mm の線になる。
- 単一の輪は、終点と始点を結ぶ辺も含めて、隣り合わない辺の外接矩形を比べる。曲線を含むか、外接矩形が重なるか、4,096 組までで確認できなければ、単純な輪と確認できないものとする。交差そのものは計算しないので、自分と交わらない輪にも診断を返すことがある。確認によって境界の形・要素の数と順・ID は変えない。非ゼロ回転数の塗りを保つ実装と、#520 のほかの残件は、未対応のままである。
- 輪の確認では、辺の数を先に `Work` に数え、辺の組を比べる直前に `Work` を 1 使う。確認用の配列は新しく確保しない。予算超過や中断では、出所を持つ診断を返して停止し、図面を返さない。
- 塗りと線の両方（`B` など）は、ハッチングと線の 2 つの要素にする。

### 色と透明

- 色は、色空間の系統（8.6 節）ごとに、四則演算だけで RGB にする。
  - DeviceGray・DeviceRGB は、そのままの値にする。
  - DeviceCMYK は、10 章の換算（赤 = 1 − min(1, シアン + 黒) など）にし、`pdf.color.approximated` を返す。
  - CalGray・CalRGB は、灰色・RGB の成分として読む。ICCBased は、成分の数（1・3・4）の装置の色空間として読む（8.6.5.5 節の `Alternate` の既定と同じ）。どちらも `pdf.color.approximated` を返す。ただし hayro は、sRGB とみなすプロファイル（ヘッダーの機器の型が `sRGB`）を DeviceRGB として、moxcms で読めないプロファイルを `Alternate` か成分の数の装置の色空間として渡すので、それらは装置の色空間と同じ扱いになる（推定）。読めるかは moxcms のバージョンで変わりうるので、moxcms のバージョンも固定する。
  - Lab・Indexed・Separation・DeviceN と、読めない系統は、レイヤの色にして `pdf.color.dropped` を返す。どちらの診断も、系統の名前を `space` に持つ。
- 不透明度（`ca`・`CA` と、透明のグループの不透明度）は、掛け合わせて透過性にする。不透明ならレイヤに従う。ソフトマスクと、通常でない合成の方法（11.3・11.6.5 節）は、移さず `pdf.transparency.approximated` を返す。パスと文字の状態のもの、透明のグループのもの、画像の `SMask`・`Mask`・`SMaskInData` を含む。
- 転送関数（`TR`・`TR2`、10.4 節）を持つ拡張グラフィックス状態をページが使うと、hayro は関数を当てた色を DeviceRGB で渡す。その値はバージョンと環境で変わりうるので使わず、そのページの色をすべてレイヤに従わせて `pdf.transfer.dropped` を返す。どの要素に効くかは渡されないので、ページごとに決める。関数を外す名前（`Identity`・`Default`）は、関数を使わないものとみなす。
- シェーディング（`sh` と、シェーディングのパターン）とタイルのパターンで塗った形は移さず、`pdf.shading.dropped`・`pdf.pattern.dropped` を返す。

### 文字

- 字形の並び（hayro が 1 回に渡す、同じフォントの字形）を、字形の原点の間がフォントの送り（`Widths`・`W`、9.2.4 節）から 0.5 em より大きくずれる所で分け、分けた範囲ごとに 1 つの文字にする（推定）。`TJ` の大きな隙間で並べた表の列は、別の文字になる。字間（`Tc`）を 0.5 em より広げた題名なども、1 字ずつの文字になる。位置は保つが、1 つの文字としては探せない。図面モデルは字間を持たないので、2 点の間に合わせて 1 つの文字にするかは、公開サンプル（#519）で確かめてから決める（#520）。分けた範囲の中に 0.05 em より大きなずれ（`TJ` の数・`Tc`・`Tw`、9.4.3・9.4.4 節）があれば、字形ごとの位置を移さず、フォントの送りで並べた文字にして `pdf.glyph-position.approximated` を返す（推定）。
  - 横書きの送りの向きの長さは、hayro が字形の幅を合わせる伸縮に依らないよう、em の高さを単位にして比べる。フォントの幅の 1 em の長さ（水平の伸縮 `Tz` を含む）は、分けるときは、最初の字形の x 軸と、字形の間の送りの中央の値（数が偶数なら大きいほう）の小さいほうから求める。詰めた所が半分あっても、詰めていない所では分けない。
  - ずれを見るときは、分けた範囲の字形の x 軸がすべて同じなら、その x 軸（文字の幅の倍率と同じ）から求めるので、すべての字形の間に同じだけ足した字間（`Tc` や、同じ数を並べた `TJ`）も診断する。埋め込みのないフォントを代わりのフォントで読むと、hayro は字形ごとに違う伸縮で幅を合わせることがある。そのときは送りの中央の値から求めるので、すべての字形の間に同じだけ足した字間は見えない。字形の間が 1 つなら、最初の字形の x 軸から求めるので、伸縮が 1 から遠い代わりのフォントでは、ずれを見誤りうる。伸縮がどの字形でも同じで 1 でないとき（同じ字形だけの並びなど）は、伸縮も、ずれとして診断する（伸縮は幅の倍率に入るので、移した文字の長さは PDF と違う）。
  - 縦書きは、縦の送りを 1 em（`DW2` の既定）とみなし、送りの向きだけを比べる。
- 中身は、字形の Unicode（`ToUnicode`・エンコーディング・字形の名前、9.10 節）をつないだもの。Unicode に戻せない字形は U+FFFD にし、`pdf.glyph.dropped` を返す。空白だけの並びは移さない。
- 位置は最初の字形の原点とし、横書きは左・基準線に合わせる。縦書きは、縦の原点（字形の空間の `(500, 880)`。横の幅を 1,000、`DW2` を既定の `[880 −1000]` とみなす、9.7.4.3 節、推定）を、中央・上に合わせる。hayro は、字形ごとの原点の移動（横の幅の半分と `DW2`・`W2`）を字形の変換に入れるが、移動の量を渡さない。そのため、横の幅が 1,000 でない字形や、`DW2`・`W2` が既定と違うフォントでは、基点がずれる。解釈の前の走査で、選んだフォント（`Tf` と、拡張グラフィックス状態の `Font`）の子孫のフォントの `DW`・`W`・`DW2`・`W2` の値を見て、既定と違いうるフォントで見える文字を描けば、`pdf.vertical-origin.approximated` を、ページとフォントごとに 1 件返す（#520）。フォントを選ぶ所が見えなくても、hayro と同じく選んだとみなす。高さは em の大きさ（字形の空間の 1,000 単位）を、基準線に直交する向きで測った mm にする。
- 回転は基準線の向き、幅の倍率は基準線の向きの em の長さと高さの比（水平の伸縮 `Tz` を含む）、斜体の角度は em の上向きの傾きとする。行列式が負の変換（鏡に映した文字）は、基準線の向きのまま、上下を裏返す。埋め込みのないフォントを代わりのフォントで読むときは、hayro が字形の幅を合わせる伸縮も、幅の倍率に入る（#520）。
- 座標が有限でない文字と、大きさのない文字（`0 Tf`・`0 Tz`・特異な行列）は移さず、`pdf.geometry.dropped` を返す。
- 描画モード（9.3.6 節）が塗りと線の両方なら 1 つの文字に、見えない文字（モード 3）なら透過性 0 の文字にする。
- 文字スタイルの名前は、フォントの `BaseFont` から部分集合の前置き（`ABCDEF+`）を除いたものにする。縦書きは `@` を前に付ける。名前を得られるのは、Type 0 と、埋め込んだ TrueType のフォントだけ。hayro が名前を渡さないフォント（Type 1・埋め込みのない TrueType・代わりの Helvetica）と、UTF-8 でない名前は、文字スタイルを空にして `pdf.font-name.dropped` を返す。Type 1 は `BaseFont` に名前があるが、hayro は字形にフォントの辞書を付けないので、名前を移せない。標準の 14 のフォントの文字には、いつもこの警告が付く（#520）。太字は重さが 700 以上、斜体はフォントのフラグによる。
- Type 3 のフォントの字形（9.6.4 節）は、形を移さず書体のない文字にし、`pdf.type3.approximated` を返す。
- hayro は、資源にないフォントを選んだ文字と、フォントを選ばずに `Tj`・`TJ` で描いた文字と、読めないフォントの文字を、Helvetica で読む。解釈の前の走査で、`Tf` の名前を資源と突き合わせ、hayro と同じ crate（hayro-font）でフォントを読んでみて、`pdf.font.missing`（資源の名前）と `pdf.font.unsupported`（`BaseFont`）を、ページとフォントごとに 1 件返す。フォントを選ばずに描いた文字は、`pdf.font.assumed` をページごとに 1 件返す。hayro は、見えない所の `Tj`・`TJ` でも Helvetica を選ぶので、その後ろの見える文字でも返す。場所は、フォントのオブジェクトのレコード（なければ、ページの内容のストリーム）にする。
- Helvetica で読む文字列は、ASCII のバイトだけのものしか描かれない。フォントを選ばずに `'`・`"` で描いた文字列は描かれない。描かれない文字列は移さず、`pdf.text.dropped` を返す。

### 画像

- 画像（8.9 節）は、画素の格子のアンダーレイにする。左下・右下・左上の角は、画像の空間の単位の正方形を変換した位置にする。画像の XObject は、資源の名前を間接参照（`5 0 R`）にし、そのオブジェクトのレコードを定義にする。内容の中の画像（`BI … EI`）と、資源の辞書に直接書いた画像（7.3.8.1 節に反するが、hayro-syntax は読む）は、名前を持たない。
- 色を塗る画像（`ImageMask`、8.9.6.2 節）の色は、マスクを展開しないと得られないので移さず、レイヤの色にして `pdf.image-mask.approximated` を返す。

### OCG とレイヤ

- OCG（optional content group、8.11 節）を、カタログの `OCProperties` の `OCGs` の順にレイヤにする。名前は `Name` の文字列とする。OCG の外の内容は、レイヤ `0` に置く。
- 既定の設定（`D`）の `BaseState`・`ON`・`OFF` で隠れるグループは、見えない・印刷しないレイヤにする。hayro は隠れたグループの内容を塗らないので、`pdf.optional-content.dropped` をグループの名前とともに返す（#520）。`Locked` のグループは、編集できないレイヤにする。印刷の可否は、表示と同じとみなす（推定。`Usage` の辞書は読まない）。
- OCMD（optional content membership dictionary、8.11.2.2 節）で見えるかは、hayro と同じく `OCGs` と `P` で決める（`VE` は読まない、#520）。見える内容は、最初の OCG のレイヤに置き、`pdf.optional-content.approximated` を返す。隠れる内容は、hayro が塗らないので移さず、`pdf.membership.dropped` を返す。
- 画像の XObject（`/OC`、8.11.3.3 節）は、ページ本体と注釈の各描画期で、見えるすべての呼び出しが、同じ登録済みの単一 OCG に属すると確認できれば、そのレイヤに置く。画像自身の指定と、外側のマーク付きの内容・フォームの指定を合わせて確かめる。同じ OCG の重なりは単一のまま扱い、フォームの内側の画像も対象にする。画像の境界・数・順序・出所・ID は保ち、レイヤと要素のハッシュは保持した値に応じて変わる。ページ本体と注釈では表を分け、注釈を加えたことでページ本体のレイヤを変えない。
- 異なる OCG の重なり、OCMD、未登録や解けない指定、同じ画像の異なる表示条件での共用は、単一レイヤで保持できたと扱わない。その画像のレイヤは従来のマーク付きの内容から決め、XObject の指定を保てない診断 `pdf.optional-content.approximated` を残す。原本のストリームを特定できない直接の画像も、この確認の対象にしない。既定で隠れる内容は、引き続き hayro が描かない。
- フォームの呼び出しのキャッシュには表示条件も含める。同じフォームを別の条件で呼ぶ場合を同じ結果として再利用しない。画像の表示条件の表と診断の記録は、確保する前に作業量と展開量を予算へ数える。後処理で予算が尽きたときも、走査で見つけた診断は返す。装置は走査で確定した表を使い、OC 辞書を読み直さない。
- フォーム自身の OCG を、線や文字を含む内容全体のレイヤとして保持することは、まだしない。フォーム自身や、画像で単一レイヤに保てない指定の診断は残す。hayro が描く XObject だけを数える。

### 切り抜き

- 切り抜きのパス（8.5.4 節）は、外接矩形だけを見る。要素の外接矩形が切り抜きの外なら移さず `pdf.clip.dropped` を、かかるなら切らずに移して `pdf.clip.approximated` を返す（推定。切り抜きの形ではなく外接矩形で比べる）。文字の外接矩形は、字形ごとの em の箱（字形の空間の `(0, −200)`〜`(1000, 1000)`、推定）を合わせたもの。ページの見える範囲も、切り抜きとして扱う。
- 切り抜きと比べてから色を決めるので、切り抜きで移さない要素には、色・透明の診断を返さない。

### 注釈の通常外観

- 注釈の通常外観（`AP/N`、12.5.5 節）は、hayro-interpret 0.9.0 の選択に合わせる。`N` がストリームならそれを使い、状態の辞書なら `AS` の名前が指すストリーム、なければ `Off` のストリームを使う。ロールオーバーと押したときの外観は選ばない。
- 外観の `BBox` に `Matrix` を当てた外接矩形を、注釈の `Rect` に合わせて拡大縮小・移動する。ページの回転・クロップ・単位も当てる。資源は外観自身の `Resources`、なければページの資源を使い、内部のフォームの資源の上書きも保つ。これは pinned hayro の実装に合わせた扱いである。
- 全ページの本体を先に描き、線種・文字様式の既存の ID を確定してから、注釈をページ・`Annots` の配列の順に加える。各ページでは本体の末尾へ足し、既存の図形・スタイル・出所・ID と、様式の順を保つ。要素の出所は、本体と同じページの最初の内容のストリームとする。注釈ごとの詳細な出所の通知は #520 に残る。
- ページ本体と注釈は別の Context と走査で扱う。本体の不釣り合いな状態や表示条件、注釈の走査拒否は、もう一方へ混ぜない。注釈の描画期では、外観と内部フォームの切り抜きの境界で文字の重複判定を初期化し、別の外観の文字を 1 つにしない。同じ並びを塗りと線で描く文字は、引き続き 1 つにする。
- `F` の Hidden（2）・NoView（32）が立つ注釈は描かず、従来の未対応診断を残す。それ以外の全注釈で、通常外観の選択・有限で非ゼロの配置・展開・内容の終了・`q/Q` とマークの釣り合い・再帰と資源の安全性を確かめられたときに、注釈の描画を有効にする。注釈自身の `OC`、外観なし、不正な配置や内容、走査拒否が混ざると、そのページの注釈群を描かず、従来の `pdf.annotation.unsupported` を返す。本体は保つ。外観自身と内部の OCG は、既存の表示・近似の規則を使う。
- 外観だけを図形へ移した注釈は、種類（`Subtype`）ごとに `pdf.annotation.drawn` を返す。注釈の内容・返信・操作などの情報は保持しない。注釈の両診断の場所は、注釈の辞書のレコード（間接オブジェクトでなければページ）にする。
- 追加の Context のカタログ再読、注釈の選択・配置、外観と内部資源の解釈・再展開を予算へ数える。保留するページの固定部分と配列を伸ばす間の写し、再開する Context の固定部分は、ページごとに `DecodedBytes` を 8,192 バイト先に数える。表・scalar・報告済みの診断の写しも確保前に予約し、予算不足と中断は文書全体を止める。外観の診断は本体の描画後まで保留し、採用しなかった外観の診断は返さない。
- 外観の内容は、scalar の写しとして長さの 16 倍、辞書の表の上限として `/` の数の 512 倍を予約する。`q` は、可変長の状態に加えて、走査と解釈器の状態スタックの固定分を 512 バイトずつ先に数える。使用する資源の scalar は、通常 3 段・フォント 8 段まで型付きで事前確認し、末端に未確認の参照が残れば、そのページの注釈群を見送る。確認できない値を黙って解釈する範囲には広げない。

### 移さないもの

- 計測の辞書を持つビューポート（`VP`・`Measure`、12.9 節）の縮尺は移さず、`pdf.measure.unsupported` を返す（#520）。

### ID と出所

- 要素の出所は、そのページの最初の内容のストリームのレコードにする。内容のストリームがなければ、ページのオブジェクトのレコードにする。ID は、出所のレコードと描いた順から、[ID と編集の前提条件](../../schema/README.md#id-と編集の前提条件) の規則で作る（`sheet/0/r7`、`sheet/0/r7/1`…）。
- 要素の診断は、同じ code と値の最初の 1 件にだけ、そのページの出所を添える。
- オブジェクトのストリーム（7.5.7 節）の中のオブジェクトは、L1 のレコードを持たない。そのため、その中のページ・内容のストリーム・注釈・画像の出所と診断の場所は、空か、外側のページの出所になる（#520）。

### 文書の情報

- 文書の情報の辞書（14.3.3 節）の `Title`・`Author`・`Subject`・`Keywords`・`Creator`・`Producer` を文字列に、`CreationDate`・`ModDate` を ISO 8601 の日時に、ページの数を数にして、図面の拡張 `pdf.document`（バージョン 1）に持つ。拡張のバージョンの名前は、PDF のバージョン（ヘッダー（7.5.2 節）と、カタログの `Version`（7.7.2 節）の新しいほう）とする。時差を書かない日時（UT との関係が分からない、7.9.4 節）は、hayro-syntax が `Z` と見分けないので `+00:00` にする（推定）。

## 書き戻し

- L1 の `write` は、レコードのバイト列と、その間のバイト列をそのまま並べ、読んだバイト列と同じものを返す。
- 図面モデルの変更を PDF に書き戻す（apply・lower）ことは、しない。

## 確かめた度合い

| 形式 | 向き | 段 |
| --- | --- | --- |
| `pdf` | 読み | `external` |
| `pdf` | 書き | `synthetic` |

読みは外部リーダーと照合した範囲、書きは元のバイト列を保つ往復を自前で確かめた範囲を示す。[段の定義](../../formats/README.md#確かめた度合い)と[台帳の根拠](README.md#format-pdf)を参照。

### pdf.js で照らした値

- 合成の 2 ページと PDFium の公開サンプル 4 個で、ページ寸法、文字の内容と位置、経路数・画像数を pdf.js 6.5.438 と比較した。回転・クロップ・単位、フォーム、非表示の OCG を含む。シーンは図面モデルから生成できるところまで確かめた。[外部照合のテスト](../../crates/zumen-pdf/tests/external.rs)は毎晩の CI で実行する。
- 注釈は選んだ通常外観の配置と線を比較した。`AS` で選べないときの `Off` と、外観自身の `OC` で隠れる場合は、両実装の異なる結果を固定した。画像の OCG は表示条件と見える画像数、単一輪の塗りは `f` と `f*` の規則を照合した。zumen は両方の塗りを同じハッチングに写す。
- Type 3 の字形とソフトマスクでも両者の値と診断を記録している。色・透明度・字形の見え方、一般の PDF の文字列の分け方、基準になるソフトでの表示は未照合。書いた PDF を外部アプリで開く検証も残る。[照合の手順と既知の差](../../xtask/verify/pdfjs/README.md)

### 予算・ID・中断のテスト

- ObjStm・ページ内容・フォームの Flate は、2 MiB に展開する合成入力を 32 KiB の予算で止める。関数・描画資源・フォント・ICC と、ASCII 前置・LZW・RunLength・複数段の各系列は、64 KiB に展開する入力と 32 KiB の予算を使う。対象の系列は 22 種類の入口で、正常・損傷・再利用、予算の境界と中断を調べる。画像フィルターや外部ファイルを指す系列は展開しない経路も確かめる。[展開・資源・フォントのテスト](../../crates/zumen-pdf/tests/)
- 出力の容量、予測子の一時配列、展開引数は別々に予約する。それぞれの予約で予算がちょうどのときと 1 不足のときを比べる。実確保は合成入力で観測した範囲に限る。条件と検査は[出力容量](../../crates/zumen-pdf/tests/allocation_growth.rs)、[予測子](../../crates/zumen-pdf/tests/predictor_allocations.rs)、[展開引数](../../crates/zumen-pdf/tests/metadata_allocations.rs)にある。
- L1 は `stops_at_same_place`・`survives`・`ids_match`、図面への変換は停止位置と ID を検査する。注釈と画像の OCG は既存要素・様式・ID、診断の場所、中断後の再試行も比べる。[ID の期待値](../../crates/zumen-pdf/tests/ids/pdf.txt)、[注釈](../../crates/zumen-pdf/tests/appearance.rs)、[画像の OCG](../../crates/zumen-pdf/tests/image_ocg.rs)、[読み取りから変換までの fuzz](../../fuzz/fuzz_targets/pdf.rs)

### ネイティブと wasm の一致

公開 PDF 336 個でネイティブと wasm32-wasip1 の図面のハッシュ・診断・予算が一致した。合成入力では wasm32-unknown-unknown と図面・診断・予算・停止を比較した。出力容量は 6,192 件、予測子は 10,564 件、展開引数は 9,792 件。十分な予算では変更前の図面・診断・ID も照合した。これらは手元での測定で、API の適合テストは [#518](https://github.com/zumen-jp/zumen/issues/518)、実図面での速度と予算の既定値は [#521](https://github.com/zumen-jp/zumen/issues/521) で追う。[入力・実測値・ハッシュ](https://github.com/zumen-jp/zumen/blob/252b878dc53338c648b35f13ba2366134bf94dae/docs/formats/pdf.md?plain=1#L217)

## 公開サンプル

`samples/pdf/` に、PDFium の Type 3・OCG・ソフトマスク・LZW と JPX の 4 ファイルを置く（2026-11-06、BSD-3-Clause）。3 つは公開された `.in` を、同じリビジョンの `fixup_pdf_template.py` で PDF にした。出所と変換の内容は `samples/ledger.toml`、ライセンスの全文は `licenses/pdfium.txt` にある。PDFium のコードとツールは入れない。

CAD が出力したベクターの図面は、まだない。2026-11-03 に CC0・パブリックドメインの図面と Wikimedia Commons の建築の図面の分類を探した。Commons の PDF は主にスキャンした本で、ライセンスを書かない図面の配布と素材の販売は、[公開サンプルの条件](../../samples/README.md) に合わない。2026-11-06 には `pdf-association/pdf20examples` も確かめたが、元の `LICENSE.md` は CC BY-SA 4.0 なので入れない。`samples/dwg` の CC0 の図面を PDF に印刷する候補は、利用者が AutoCAD の利用を許したときに進める。
