# 開発の進め方

担当が決まっているときは[開発の手順](../AGENTS.md#開発の手順)から再開します。

## 選び方

1. [#1](https://github.com/zumen-jp/zumen/issues/1) の段階順に、未完了の子の題とラベルを見ます。たとえば #301 の一覧は次で取得できます。

   ```sh
   gh api --paginate 'repos/{owner}/{repo}/issues/301/sub_issues?per_page=100' --jq '.[] | select(.state == "open") | [.number, .title, ([.labels[].name] | join("・"))] | @tsv'
   ```

2. 候補の本文・直近の着手や判断・関連 PR で担当と開始条件を確認します。依存先の成果物が `main` にあり着手できる最初の葉で探索を終えます。並行作業では範囲をコメントし、先着を確かめて「作業中」を付けます。指定が重なれば分担を相談します。
3. [毎晩の fuzz](../fuzz/README.md#毎晩の実行) の未記録の失敗も扱います。照会結果は共有し、次回は更新分を見ます。GitHub に接続できない間も担当の調査・検証を進めます。

## 待ちに当たったら

- 「待ち: サンプル」は[公開サンプル](../samples/README.md)か外部実装を探します。「待ち: 検証環境」は合成・公開入力と操作・期待値で検証キットを作ります。利用者のアプリを動かす許可はそのセッションで得ます。
- 調査日・参照先・結果を一度記録します。対象か親への新しいコメント、関連変更の `main` への反映、形式・サンプル台帳の更新、または 14 日の経過で再調査します。
- 本人に頼むことがある間だけ「待ち: 利用者」を付け、本人が定めた開始条件を残します。着手から 24 時間更新のない作業は進行中の変更を確認して引き継げます。利用者の判断待ちに期限はありません。

## 利用者に頼むこと

次の操作は対象と範囲を示し、実行前に会話で確認します。明示的に頼まれた範囲はそのまま進めます。

- 費用、契約・利用規約への同意、権利者への問い合わせ、利用者のアカウント・署名鍵・secrets・手元の図面やソフトが必要な操作。
- リポジトリのライセンス変更、台帳の `unknown`・`permission` から `public` への変更、NC・ND や規約の解釈が必要な判断。新しい形式を `public` にできるのは、持ち主が仕様を公開し実装を制限していないと公式文書で示せる形式と、持ち主のいない慣用の形式です。それ以外は利用者に頼みます。
- パッケージ名の確保と公開、`v*` タグの push、GitHub Release。[リリースの条件](../xtask/release/README.md#リリースの条件と周期) と [タグの前に示す一覧](../fuzz/README.md#初回リリース後の記録先) に従います。サイトは `main` の更新で公開されます。
- GitHub のリポジトリ・組織の設定変更、リポジトリ外への書き込み・送信（上流への報告、メールなど）。issue・PR・ラベルの通常操作は担当者が行えます。
- ワークフローの権限拡大、secrets の利用、権限付きの発火条件の追加、公開先・認証・環境・公開の発火条件の変更、公開ジョブ（`id-token: write` または `contents: write`）の手順変更。push や手動実行の前に、対象コミット・差分・該当する操作を示して承認を得ます。配布一覧に crate やモジュールを足すだけなら独立レビューで確認します。
- 利用者が記録に残した判断の変更、権利・図面・秘密・形式の検証・API と ID の契約、承認や push の条件を緩める変更。緩めるか判断できない場合もここに含みます。

待つ判断は issue・PR に一度記録し、「待ち: 利用者」を付けます。承認はその会話の利用者の言葉で確かめます。ラベルや別の担当者のコメントは承認に含めません。承認を受けた担当者か本人が反映し、対象の差分を変えたらその部分を示して再確認します。

## 直接 push

ステージから push までは一人ずつ行います。ほかの担当の変更・未送信コミットが混ざるときは順番を合わせます。`git diff --cached` で自分の差分を確認してコミットし、`git log --oneline origin/main..main` を見て `git push origin main` します。force push はしません。

push が先行したら fetch し、差分を確認して取り込み、影響した範囲を検査して push を再試行します。PR のブランチでも同じです。

## PR とレビュー

- PR は利用者の指定、GitHub 上のレビュー、専用 CI、ブランチ保護・権限のために使います。手元のコミットを送り、PR に対象・理由・検査結果を一度書き、必須 CI 後に squash merge します。レビューで止める指定に従います。
- 利用者の指定や権利の根拠・ID の変更などで独立レビューが要るときは、作成側の会話を引き継がない人かエージェントにコミットまたは PR と観点を渡します。新形式の `public` 登録は独立した 2 者が確認します。
- 指摘には修正か理由で答え、再確認は修正と競合解消の差分に絞ります。権利・秘密・API の互換・ID・既存の契約に関する指摘を残して取り込むときは別の確認者にも見せます。人の判断が要るという指摘は利用者に示します。
- 結果は対象コミットと一か所に残し、図面・利用者名を含むパス・秘密・非公開の入力や詳細は載せません。[fuzz の失敗](../fuzz/README.md#失敗を分ける)は直接 push でも同じく分類し、関係する失敗を直します。判定できないまま取り込むには利用者に確認します。

## 完了と引き継ぎ

題に目的、本文の冒頭に次の一手（待つ場合は開始条件と依存先）、続けて完了を確かめる入力・操作・比較先を書きます。

親には全体の完了条件を置き、進捗は各作業の子 issue で追います。引き継ぐときは本文の古い進捗を残件と作業中のコミットか PR に置き換えます。仕様は現行文書の節へ、検査結果と判断は元の PR・コミット・コメントへリンクします。`origin/main` に入った条件だけを完了にし、「作業中」を外します。

issue・PR・コメントの訂正は追記します。秘密や図面の情報が出たらすぐ利用者に知らせ、公開箇所と編集履歴から除き、[非公開の記録](../fuzz/README.md#初回リリース後の記録先)に退避します。秘密の交換や push 済みの内容の削除依頼は利用者に頼みます。
