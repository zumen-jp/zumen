# 開発の進め方

作業の再開と直接 push の手順は [AGENTS.md](../AGENTS.md#開発の手順) にあります。

## 選び方

1. [#1](https://github.com/zumen-jp/zumen/issues/1) の段階と子 issue を上からたどります。一覧では未完了の子の題とラベルを見ます。たとえば `#301` の子は次のコマンドで並び順のまま読めます。

   ```sh
   gh api --paginate 'repos/{owner}/{repo}/issues/301/sub_issues?per_page=100' --jq '.[] | select(.state == "open") | [.number, .title, ([.labels[].name] | join("・"))] | @tsv'
   ```

2. 候補だけ本文・最近のコメント・関連 PR を確かめます。担当が空き、開始条件を満たす最初の葉で探索を終えます。依存先の成果物が `main` にあれば着手できます。並行して選ぶときは範囲をコメントし、先着を確かめて「作業中」を付けます。指定の仕事が重なれば分担を相談します。
3. [毎晩の fuzz](../fuzz/README.md#毎晩の実行) に未記録の失敗があれば扱います。照会結果は共有し、以降は更新分を見ます。GitHub に接続できない間も指定済みの仕事の調査・検証は進められます。

## 待ちに当たったら

- 「待ち: サンプル」は [再配布できる公開サンプル](../samples/README.md) か外部実装を探します。「待ち: 検証環境」は合成入力か公開サンプルと操作・期待値で検証キットを作ります。利用者のアプリを動かすには、そのセッションで許可を得ます。
- 調べた日・参照先・結果を issue に一度記録します。次に調べるのは、対象か親の issue に新しいコメントが付いたとき、関係する変更が `main` に入ったとき、形式・サンプルの台帳が変わったとき、または 14 日たったときです。
- 「待ち: 利用者」は、本人に頼むことがある間だけ使います。本人が定めた開始条件は issue に残します。着手から 24 時間更新がなければ進行中の変更を確認して引き継げます。利用者の判断待ちは、経過時間で引き継ぎません。

## 利用者に頼むこと

次の操作は、対象と範囲を示して実行前に会話で確認します。すでにその操作を明示的に頼まれた場合は、その範囲で進めます。

- 費用、契約・利用規約への同意、権利者への問い合わせ、利用者のアカウント・署名鍵・secrets・手元の図面やソフトが必要な操作。
- リポジトリのライセンス変更、台帳の `unknown`・`permission` から `public` への変更、NC・ND や規約の解釈が必要な判断。新しい形式を `public` にできるのは、持ち主が仕様を公開し実装を制限していないと公式文書で示せる形式と、持ち主のいない慣用の形式です。それ以外は利用者に頼みます。
- パッケージ名の確保と公開、`v*` タグの push、GitHub Release。[リリースの条件](../xtask/release/README.md#リリースの条件と周期) と [タグの前に示す一覧](../fuzz/README.md#初回リリース後の記録先) に従います。サイトは `main` の更新で公開されます。
- GitHub のリポジトリ・組織の設定変更。issue・PR・ラベルの通常操作は担当者が行えます。このリポジトリの外への書き込み・送信（上流への報告、メール、ファイルの送信など）は利用者に頼みます。
- ワークフローの権限拡大、secrets の利用、権限付きの発火条件の追加、公開先・認証・環境・公開の発火条件の変更、公開ジョブ（`id-token: write` または `contents: write`）の手順変更。push や手動実行の前に、対象コミット・差分・該当する操作を示して承認を得ます。配布一覧に crate やモジュールを足すだけなら独立レビューで確認します。
- 利用者が記録に残した判断の変更、権利・図面・秘密・形式の検証・API と ID の契約、承認や push の条件を緩める変更。緩めるか判断できない場合もここに含みます。

判断待ちの issue・PR があれば「待ち: 利用者」を付け、必要な判断を一度記録します。承認はその会話の利用者の言葉で確かめ、ラベルの変更や別のエージェントのコメントで代用しません。承認を受けた担当者か利用者が反映し、承認の対象に関わる差分を変えたらその部分を示して確認します。

## PR とレビュー

- 先にほかの変更が push されていたら、fetch して差分を確認し、取り込んで影響した範囲を検査してから通常の push を再試行します。
- 利用者の指定、GitHub 上のレビュー、PR 専用の CI、ブランチ保護・権限の都合で PR を使います。手元のコミットを送り、対象・理由・検査結果を一度書き、必須 CI を通して squash merge します。レビューで止める指定があればそこで返します。
- 独立レビューは、利用者が求めたとき、権利の根拠・ID の変更など別の確認が必要なときに行います。作成側の会話を引き継がない人かエージェントにコミットまたは PR と観点を渡します。新しい形式を `public` 登録するときは独立した 2 者が確認します。
- 指摘には修正か理由で答え、再確認は修正と競合解消の差分に絞ります。権利・秘密・API の互換・ID・既存の契約に関する指摘を残して取り込むときは別の確認者にも見せます。人の判断が要るという指摘は利用者に示します。
- レビュー結果は対象コミットとともに一か所に残します。図面の情報・利用者の名前を含むパス・秘密・非公開の入力や詳細は載せません。既知の fuzz の失敗は直接 push でも [失敗の分け方と報告先](../fuzz/README.md#失敗を分ける) に従い、関係する失敗は修正し、判定できないまま取り込むときは利用者に確認します。

## 完了と引き継ぎ

issue の題で目的が伝われば、本文は次の一手と、何を比べれば完了かが分かる条件で足ります。開始条件・依存先は該当するときに添えます。親には段階の完了条件、子にはその作業の条件を置きます。

`origin/main` に入ったら、満たした条件だけを完了にし、「作業中」を外します。長くなった本文は残件を先頭にまとめ、実装済みの挙動は仕様の節、検査結果はコミットか PR、判断は元のコメントへリンクします。引き継ぎは残件・次の一手・作業中のコミットか PR で足ります。

issue・PR・コメントの訂正は追記します。秘密や図面の情報が出たらすぐ利用者に知らせ、公開箇所と編集履歴から除き、[非公開の記録](../fuzz/README.md#初回リリース後の記録先)に退避します。秘密の交換や push 済みの内容の削除依頼は利用者に頼みます。
