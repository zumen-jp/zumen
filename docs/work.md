## 選び方

1. 利用者の依頼と、この作業場所に適用される `AGENTS.md` を読む。利用者が指定した作業は、下の順より優先する。
2. 手元の変更を確認し、`origin/main` を取得する。進行中の変更を上書きしない。
3. 段階の issue を順に開き、子 issue を上から見る。子 issue が子を持つなら、その中を同じ順に見る。
4. 閉じていない葉の issue のうち、「待ち: 利用者」と「作業中」のラベルがなく、依存で止められていない最初のものを選ぶ。「待ち: 試料」「待ち: 検証環境」が付いていれば、その issue では、まず待ちを減らす（下の「待ちに当たったら」）。本文の開始条件と、関連する開いた PR も確かめる。依存する issue 全体が閉じる必要はなく、開始条件に書かれた成果物が main に入っていればよい。
5. 最初に「対象 issue」「今回作るもの」「検査方法」を示す。大きな issue は、子 issue に分けるか、完了の条件の一部を満たす PR に分ける。

GitHub を確認できない場合は、候補と未確認の点を報告する。指定済みの作業の調査やローカルの検証は進められるが、未着手と断定して別の作業を選ばない。

## 待ちに当たったら

飛ばす前に、待ちを減らします。待ちを減らす作業も、着手と同じく名乗ります。

| 待ち | すること |
| --- | --- |
| 試料 | 決定 0171 の条件に合う公開サンプルを探し、あれば `samples/` に足す（[決定 0171](decisions/0171-public-samples-in-git.md)）。決定 0019 と台帳で入れないとしたもの（国土地理院のデータなど）は除く。外部の実装で読めるなら、その実装と照らす |
| 検証環境 | 確認の束を作り、issue に置く。束に入れるのは、試験で作るファイルか `samples/` のファイルと、それを作るコマンド・開く手順・期待する結果だけ。受け取った図面と、そこから作ったファイル・名前・画面の写しは置かない。利用者の手元のソフトは、そのセッションで利用者がアプリの利用を許したときだけ、束のファイルを開くのに使う |

- 試みた日と、探した所・結果を issue に書く。それより後に新しい手がかりがなければ、次からは飛ばしてよい。
- 判断に当たったら、人を待つもの（`AGENTS.md` の「並行して進める」）に当たらなければ、エージェントが決める。決定の記録にする判断は、その PR に選択肢と理由を書き、マージの後にラベルを外す。記録にしない判断は、issue のコメントに選択肢と理由を書いてから外す。
- 人を待つものに当たったら、ラベル「待ち: 利用者」を付け、利用者に頼むことを開始条件に具体的に書く。

## 着手するとき

- 対象 issue のコメントで名乗る。ブランチ・worktree・時刻を書く。
- 名乗ったあとに読み直す。いちばん早い名乗りだけが進め、後の側は名乗りを取り下げて別の issue を選ぶ。
- 名乗りが通ったら、ラベル「作業中」を付け、本文の「着手・引き継ぎ」に、作業ブランチ・担当する範囲を書く。PR を作ったら、そのリンクを書く。
- 同じ issue か、同じ crate・同じ形式の文書を主に変える開いた PR があれば、着手しない。一覧・台帳・生成物（決定の一覧・`catalog/`・スキーマの版・適合試験のハッシュの一覧・`Cargo.lock`）が重なるのは構わず、マージの前に解く。worktree を分ける。
- 古い着手は、関連する PR とブランチの状態を確かめてから扱う。名乗りから 24 時間、PR・ブランチ・名乗りの更新がなければ、引き継ぐと名乗って引き継げる。

## 互いに確かめる

PR は、作った側と別の確かめる側が確かめてからマージします。

- 確かめる側は、作った側の会話を引き継がないエージェント（新しいセッションか、会話を渡さないサブエージェント）か、人にする。
- 依頼には、PR の番号と確かめる観点だけを渡し、作った側の見立ては渡さない。確かめる側は読むだけにし、自分で直さない。
- 観点は、差分と issue の完了の条件、`AGENTS.md` の「範囲と権利」「図面と秘密」「守る約束」、仕様の節、試験、依存のライセンス、表記。決定の記録なら、選択肢が実際にあるか、採用済みの決定と食い違わないかも見る。
- 結果は、確かめた head の commit と確かめる側の種類を添え、手を加えずに全文を PR のレビューのコメントに貼る。
- 作った側は、指摘のすべてに答える（直すか、直さない理由を書く）。権利・秘密・境界の互換・ID・採用済みの決定との食い違いの指摘を直さずにマージするなら、別の確かめる側にも見せる。直したあとの差分も、確かめる側に見せる。
- 新しい形式の権利を `public` とする PR は、確かめる側を 2 つにし、別々に確かめる。
- CI の通過は、この確認の代わりにしない。

## 完了したとき・途中で引き継ぐとき

- PR の「対象と残る作業」に、対象 issue・満たした条件・残る条件を書く。issue の条件をすべて満たすときだけ `Closes #番号` を使う。
- 形式・版・向きを足す issue は、`AGENTS.md` の「範囲と権利」の条件（外部の実装との照合・公開サンプル・fuzz の対象とテストキットの契約試験・確かめた度合いの節）をそろえて閉じる。
- マージの前に、最新の `origin/main` を取り込み、生成物を作り直し、CI を通し直す。指摘に答え、直したあとの差分の確認が済み、CI が通ったら squash merge する。
- マージを確かめてから、issue の完了の条件のチェック欄と次の一手を直し、ラベル「作業中」を外す。PR が閉じただけなら、完了と扱わない。できたことの経過は PR に書き、issue の本文に積まない。
- 中断するときは、issue の本文に「できたことと PR・ブランチ」「残る条件」「検査結果」「待っているもの」「次の一手」を書き、ラベル「作業中」を外す。待つものが issue でなければ、待ちのラベルを付ける。
- 設計の issue を閉じても実装が残るなら、実装の issue に関連づけるか、新しい issue を作る。閉じた issue の本文だけに残件を置かない。
- 新しく見つけた仕事は、ひな形で issue を作り、目的・範囲・開始条件・完了の条件・参照を書いて、段階の issue の子に置く。ほかの issue の成果物を待つなら、依存（blocked by）を付ける。
- 優先順を変えるときは、子 issue を並べ替え、理由を親の issue にコメントで書く。

着手できる issue がなければ、開いた issue と採用済みの決定の残件を確かめます。追跡漏れなら issue を補います。待ちを減らせない issue と「待ち: 利用者」の issue だけが残るなら、試みたことと残る待ちを利用者に伝えます。
