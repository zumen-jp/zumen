## 選び方

1. 利用者の依頼と、この作業場所に適用される `AGENTS.md` を読む。利用者が指定した作業は、下の順より優先する。
2. 手元の変更を確認し、`origin/main` を取得する。進行中の変更を上書きしない。
3. 段階の issue を順に開き、子 issue を上から見る。子 issue が子を持つなら、その中を同じ順に見る。
4. 閉じていない葉の issue のうち、待ちと作業中のラベルがなく、依存で止められていない最初のものを選ぶ。待ちのラベルが付いた issue は、飛ばす前に、下の「待ちに当たったら」を行う。本文の開始条件と、関連する開いた PR も確かめる。依存する issue 全体が閉じる必要はなく、開始条件に書かれた成果物が main に入っていればよい。
5. 最初に「対象 issue」「今回作るもの」「検査方法」を示す。大きな issue は、子 issue に分けるか、完了の条件の一部を満たす PR に分ける。

GitHub を確認できない場合は、候補と未確認の点を報告する。指定済みの作業の調査やローカルの検証は進められるが、未着手と断定して別の作業を選ばない。

## 待ちに当たったら

飛ばす前に、待ちを減らします（[決定 0253](decisions/0253-parallel-agents-and-cross-review.md)）。

| 待ち | すること |
| --- | --- |
| 試料 | 再配布できる公開の試料を探し、あれば `samples/` に足す（[決定 0171](decisions/0171-public-samples-in-git.md)）。外部の実装で読めるなら、その実装と照らす。見つからなければ、探した所と結果を issue に書く |
| 検証環境 | 開くファイル・手順・期待する結果をそろえた確認の束を作り、issue に置く。利用者の手元のソフトは、利用者がアプリの利用を許せば、画面の操作で使う |
| 判断 | 下の「人を待つもの」に当たらなければ、選択肢と理由を書いて決め、ラベルを外す |

人を待つのは、次のことだけです。

- 権利者への問い合わせ、契約・規約への同意、費用のかかること
- アカウント・署名の鍵・secrets、パッケージの名前の確保と公開
- リポジトリと GitHub の設定の変更
- 利用者の手元にしかないもの（受け取った図面、利用者のライセンスで動くソフト）を使う確認

待ちを減らせなければ、待っているものを開始条件に具体的に書き、次の issue へ進みます。

## 着手するとき

- 複数のエージェントが同時に動く。着手を決めたら、すぐに対象 issue にラベル「作業中」を付け、本文の「着手・引き継ぎ」に、作業ブランチ・担当する範囲を書く。PR を作ったら、そのリンクを書く。
- 付ける前に、ほかのエージェントが付けていないか、同じファイルを変える開いた PR がないかを確かめる。worktree を分ける。
- 古い着手の記録は、関連する PR とブランチの状態を確かめてから扱う。経過時間だけで、担当が空いたと判断しない。

## 互いに確かめる

PR は、作ったエージェントと別のエージェントが確かめてからマージします（決定 0253）。

- 確かめる側は、作った側の会話を引き継がない。新しいセッションか、会話を渡さないサブエージェントにする。
- 確かめる側は、差分と issue の完了の条件を照らし、仕様の節・試験・予算・診断・決定性・権利・表記を見る。決定の記録なら、選択肢が実際にあるか、採用済みの決定と食い違わないかも見る。
- 確かめた点と結果を、PR のレビューのコメントに書く。指摘は、作った側が直すか、直さない理由を書く。
- CI の通過は、この確認の代わりにしない。

## 完了したとき・途中で引き継ぐとき

- PR の「対象と残る作業」に、対象 issue・満たした条件・残る条件を書く。issue の条件をすべて満たすときだけ `Closes #番号` を使う。
- 形式を読む・書く issue は、外部の実装との照合・公開の試料・fuzz の対象とテストキットの契約試験・確かめた度合いの節をそろえて閉じる（`AGENTS.md`）。
- マージを確かめてから、issue の完了の条件のチェック欄と次の一手を直し、ラベル「作業中」を外す。PR が閉じただけなら、完了と扱わない。できたことの経過は PR に書き、issue の本文に積まない。
- 中断するときは、issue の本文に「できたことと PR・ブランチ」「残る条件」「検査結果」「待っているもの」「次の一手」を書き、ラベル「作業中」を外す。待つものが issue でなければ、待ちのラベルを付ける。
- 設計の issue を閉じても実装が残るなら、実装の issue に関連づけるか、新しい issue を作る。閉じた issue の本文だけに残件を置かない。
- 新しく見つけた仕事は、ひな形で issue を作り、目的・範囲・開始条件・完了の条件・参照を書いて、段階の issue の子に置く。ほかの issue の成果物を待つなら、依存（blocked by）を付ける。
- 優先順を変えるときは、子 issue を並べ替え、理由を親の issue にコメントで書く。

着手できる issue がなければ、開いた issue と採用済みの決定の残件を確かめる。追跡漏れなら issue を補う。人を待つものだけが残るなら、その点を利用者に伝える。
