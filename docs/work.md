利用者から作業を任されたエージェントと開発者の入口です。計画は [全体計画 #1](https://github.com/zumen-jp/zumen/issues/1) の下の issue で持ちます（[決定 0174](decisions/0174-plan-in-issues.md)）。複数のエージェントが同時に進め、人を待つのは人にしかできないことだけにします（[決定 0254](decisions/0254-parallel-agents-and-cross-review.md)）。この文書は、その読み方と手順だけを書きます。

## 選び方

1. 利用者の依頼と、この作業場所に適用される `AGENTS.md` を読む。利用者が指定した作業は、下の順より優先する。
2. 手元の変更を確認し、`origin/main` を取得する。進行中の変更を上書きしない。main の最新の毎晩の fuzz が落ちていたら、その失敗の issue があるかを確かめ、なければ作る（[決定 0261](decisions/0261-fuzz-outside-required-checks.md)、確かめ方は `fuzz/README.md` の「落ちたとき」）。
3. 段階の issue を順に開き、子 issue を上から見る。子 issue が子を持つなら、その中を同じ順に見る。
4. 閉じていない葉の issue のうち、「待ち: 利用者」と「作業中」のラベルがなく、依存で止められていない最初のものを選ぶ。「待ち: 利用者」の issue に当たったら、開始条件を見直す。「待ち: 試料」「待ち: 検証環境」が付いていれば、その issue では、まず待ちを減らす（下の「待ちに当たったら」）。本文の開始条件と、関連する開いた PR も確かめる。依存する issue 全体が閉じる必要はなく、開始条件に書かれた成果物が main に入っていればよい。開始条件を満たしていなければ、飛ばす。
5. 最初に「対象 issue」「今回作るもの」「検査方法」を示す。大きな issue は、子 issue に分けるか、完了の条件の一部を満たす PR に分ける。

GitHub を確認できない場合は、候補と未確認の点を報告する。指定済みの作業の調査やローカルの検証は進められるが、未着手と断定して別の作業を選ばない。

## 待ちに当たったら

飛ばす前に、待ちを減らします。待ちを減らす作業も、着手と同じく名乗ります。

| 待ち | すること |
| --- | --- |
| 試料 | 決定 0171 の条件に合う公開サンプルを探し、あれば `samples/` に足す（[決定 0171](decisions/0171-public-samples-in-git.md)）。決定 0019 と台帳で入れないとしたもの（国土地理院のデータなど）は除く。外部の実装で読めるなら、その実装と照らす |
| 検証環境 | 確認の束を作り、issue に置く。束に入れるのは、試験で作るファイルか `samples/` のファイルと、それを作るコマンド・開く手順・期待する結果だけ。受け取った図面と、そこから作ったファイル・名前・画面の写しは置かない。利用者の手元のソフトは、そのセッションで利用者がアプリの利用を許したときだけ、束のファイルを開くのに使う |

- 試みた日と、探した所・結果を issue のコメントに書く。次のどれかが出るまでは、次からは飛ばしてよい: その issue か親の issue への新しいコメント、関係する PR のマージ、台帳（`formats/ledger.toml`・`samples/ledger.toml`）の変更、前の試みから 14 日が過ぎること。
- 作業の中で判断に当たったら、人を待つもの（`AGENTS.md` の「並行して進める」）に当たるかを見る。当たらなければ、エージェントが決めて進める。決定の記録にする判断は、その PR に選択肢と理由を書き、記録にしない判断は、issue のコメントに選択肢と理由を書く。
- 人を待つものに当たったら、ラベル「待ち: 利用者」を付け、利用者に頼むことを開始条件に具体的に書く。人を待つものとほかの作業が混ざるなら、人を待つものを別の issue に分ける。PR が人を待つものを含むなら、PR にも「待ち: 利用者」を付け、一覧のどの項に当たるかと中身を本文に書く。ラベルは、マージか閉じるまで外さない。workflow の項に当たる変更は、push の前に差分と当たる項を利用者に示し、会話で認めてもらう。PR を開く前は、PR の番号と head の代わりに、ブランチの名前と push する commit を示す。開いたあとは、PR の番号と push する commit を示す。PR の全体の差分と当たる項のすべてを示したときは、これをその PR の承認とする。PR を開いたら、その承認を PR に書く。認める前に、そのブランチで workflow を手で走らせない。
- 選ぶ順で「待ち: 利用者」の issue に当たったら、開始条件とコメントを読む。人を待つものに当たらなければ、理由をコメントに書いてラベルを外し、選ぶ。利用者の判断の記録（日付と言葉）があれば、その判断に従う。利用者が何かを待つと決めたもの（要望が来るまで待つなど）は、待つものを開始条件に書き、利用者に頼むことが残っていなければ、ラベルを外す。判断を変えて先に進めたいなら、ラベルを付けて利用者に頼む。

## 着手するとき

- 対象 issue のコメントで名乗る。ブランチ・worktree のフォルダーの名前・時刻を書き、絶対パスは書かない。決定の記録を書くなら、使う番号も書く。
- 名乗ったあとに読み直す。いちばん早い名乗りだけが進め、後の側は名乗りを取り下げて別の issue を選ぶ。
- 名乗りが通ったら、ラベル「作業中」を付け、本文の「着手・引き継ぎ」に、作業ブランチ・担当する範囲を書く。PR を作ったら、そのリンクを書く。
- 同じ issue か、同じ crate・同じ形式の文書を主に変える開いた PR か名乗りがあれば、着手しない。一覧・台帳・生成物（決定の一覧・`catalog/`・スキーマの版・適合試験のハッシュの一覧・`Cargo.lock`）が重なるのは構わず、マージの前に解く。worktree を分ける。
- 利用者が指定した issue に、ほかの名乗りがあれば、利用者に伝えて指示を待つ。24 時間の更新がない名乗りは、引き継いでよい。
- 古い着手は、関連する PR とブランチの状態を確かめてから扱う。名乗りから 24 時間、PR・ブランチ・名乗りの更新がなければ、引き継ぐと名乗って引き継げる。前の PR とブランチは消さない。「待ち: 利用者」の issue と PR は、24 時間では引き継がず、利用者に確かめてから引き継ぐ。
- 決定の番号は、開いた PR と、名乗りに書かれた番号を見て選ぶ。issue のない作業は、先に issue を作り、その issue で名乗る。番号だけを早く押さえたいときは、下書きの PR を開いてもよい。ぶつかったら、後にマージする側が付け替え、古い番号でその決定を指す開いた PR・issue と main のファイルを探して、直すか知らせる。
- issue・PR・コメントは消さず、閉じるか、新しいコメントで直す。名乗りと、確かめた結果のコメントは、書き換えない。秘密や受け取った図面の情報が入ったら、すぐ利用者に伝える。コメントは消すか、伏せたうえで編集の履歴から前の版を消す。名乗りと確かめた結果のコメントは、消さずに、その所だけを伏せる。本文のように消せないものも、伏せたうえで、編集の履歴から前の版を消す（エージェントが消せなければ、利用者に頼む）。消した所か伏せた所と理由は、秘密を書かずに新しいコメントに書く。push した commit・ブランチの名前・題に入ったものは、force push や題の変更では GitHub から消えないので、GitHub に消してもらうかを利用者に決めてもらう。secrets は、利用者に替えてもらう。

## 互いに確かめる

PR は、作った側と別の確かめる側が確かめてからマージします。

- 確かめる側は、作った側の会話を引き継がないエージェント（新しいセッションか、会話を渡さないサブエージェント）か、人にする。
- 依頼には、PR の番号と確かめる観点だけを渡し、作った側の見立ては渡さない。2 回目からは、前の結果と作った側の答えを渡してよい。確かめる側は読むだけにし、自分で直さない。
- 観点は、差分と issue の完了の条件、`AGENTS.md` の「範囲と権利」「図面と秘密」「守る約束」、仕様の節、試験、依存のライセンス、表記。人を待つものに当たる所がないかと、当たるなら、PR にラベル・当たる項・その中身があるかも見る。利用者が認めた記録があれば、記録の範囲が当たる項のすべてを含むかと、認めた head のあとに当たる項に関わる変更がないかも見る。記録がまだないことは、指摘にしない。記録は、マージする側も確かめる。決定の記録なら、選択肢が実際にあるか、採用済みの決定と食い違わないかも見る。
- 依頼には、結果に書かないもの（受け取った図面のファイル名・顧客の名前・図面の中身・秘密の値・利用者の名前を含むパス）も書く。試験の出力は、件数・code・ハッシュに限って書いてもらう。
- 結果には、指摘ごとに重さ（重・中・軽微）を付けてもらう。結果は、確かめた head の commit と確かめる側の種類を添え、手を加えずに全文を PR のレビューのコメントに貼る。書かないものが入っていたら、そこだけを伏せ、伏せた所と理由を書く。
- 作った側は、指摘のすべてに答える（直すか、直さない理由を書く）。権利・秘密・境界の互換・ID・採用済みの決定との食い違いの指摘を直さずにマージするなら、別の確かめる側にも見せる。人を待つものに当たるという指摘は、作った側が当たらないと考えても、人を待つものとして扱い、利用者に示す。
- 直したあとの差分も、確かめる側に見せる。重と中の指摘がなくなったあとの軽微の直しと、生成物・ハッシュの一覧・一覧の中の位置だけを直す main の取り込みは、確かめ直さない。衝突を解くために、PR の側で番号・文・コードを変えた取り込みは、その差分（`git show --remerge-diff <取り込みの commit>`）を見せる。
- 確かめ直しは、直した差分と答えを主に見る。直した差分の外から出た新しい指摘のうち、重のものと、権利・秘密・人を待つものに関わるものは、その PR で直す。ほかは、追跡先の issue に回してよく、答えにその issue を書く。
- 新しい形式を `public` として足す PR は、確かめる側を 2 つにし、別々に確かめる。足せるのは、持ち主が仕様を公開し、実装を制限していないことを公式の文書で示せる形式と、持ち主のいない慣用の形式（区切ったテキストなど）だけ。ほかは、権利の判断として人を待つ。台帳にある形式の版違い・別名は、新しい形式として扱わない。
- CI の通過は、この確認の代わりにしない。

## 完了したとき・途中で引き継ぐとき

- PR の「対象と残る作業」に、対象 issue・満たした条件・残る条件を書く。issue の条件をすべて満たすときだけ `Closes #番号` を使う。
- 形式・版・向きを足す issue は、`AGENTS.md` の「範囲と権利」の条件（外部の実装との照合・公開サンプル・fuzz の対象とテストキットの予算・ID の契約試験・確かめた度合いの節）をそろえて閉じる。
- マージの前に、最新の `origin/main` を取り込み、生成物を作り直し、CI を通し直す。指摘に答え、直したあとの差分の確認が済み、CI が通ったら squash merge する。PR で fuzz が流れたら、その結果も通ってからマージする。見つけた入力のある失敗は、その入力が PR の最新の head で落ちないと確かめるまで、流し直しや新しい commit の実行が通っても、通ったとしない。fuzz の失敗のうち、PR の変更と関係のないもの（main の上でも同じように落ちるもの）では、マージを止めない。マージの前に issue にし（見つけた入力は最小にして貼る）、PR の本文に書き、早めに直す（[決定 0261](decisions/0261-fuzz-outside-required-checks.md)、確かめ方は `fuzz/README.md` の「落ちたとき」）。人を待つものを含む PR は、利用者に PR の番号・head・当たる項を示し、その PR について会話で認めてもらう（workflow の項に当たる PR は、push の前の承認で PR の全体の差分と当たる項のすべてを示したときに、それをその PR の承認とする）。認めた日・head・範囲・利用者の言葉を PR に書き、認めた会話のエージェントか利用者がマージする。認めた head と比べて、PR の側で当たる項に関わる所（緩める変更の項なら、その項が守る範囲の文）を変えたら、強める向きでも、変えた所を示して認め直してもらう（main の取り込みで入っただけの変更は除く）。前からある一般の指示や、ラベルが外れたこと・GitHub のコメントを、利用者が認めたとはみなさない。PR の記録だけを読んだエージェントは、マージせずに利用者に確かめる。
- マージを確かめてから、issue の完了の条件のチェック欄と次の一手を直し、ラベル「作業中」を外す。PR が閉じただけなら、完了と扱わない。できたことの経過は PR に書き、issue の本文に積まない。
- 中断するときは、名乗りを取り下げたと issue のコメントに書く。issue の本文に「できたことと PR・ブランチ」「残る条件」「検査結果」「待っているもの」「次の一手」を書き、ラベル「作業中」を外す。待つものが issue でなければ、待ちのラベルを付ける。ただし、利用者が待つと決めたもので、利用者に頼むことが残っていなければ、ラベルを付けずに開始条件に書く。
- 設計の issue を閉じても実装が残るなら、実装の issue に関連づけるか、新しい issue を作る。閉じた issue の本文だけに残件を置かない。
- 新しく見つけた仕事は、ひな形で issue を作り、目的・範囲・開始条件・完了の条件・参照を書いて、段階の issue の子に置く。ほかの issue の成果物を待つなら、依存（blocked by）を付ける。
- 優先順を変えるときは、子 issue を並べ替え、理由を親の issue にコメントで書く。

着手できる issue がなければ、開いた issue と採用済みの決定の残件を確かめます。追跡漏れなら issue を補います。待ちを減らせない issue と「待ち: 利用者」の issue だけが残るなら、試みたことと残る待ちを利用者に伝えます。
