# 文書エンジンの設計

文書エンジンは、開いた図面をメモリに持ち続け、変更を差分で当てる、コアの中の実装です。図面を対話で直すときに、1 つの操作にかかる時間が、図面の大きさではなく変更の大きさで決まるようにします。作業は [#878](https://github.com/zumen-jp/zumen/issues/878) で追います。

形式非依存の基盤（ページ配列・塊ごとの版・トランザクション・取り消し・空間索引・64 要素ブロックの差分追跡・依存辺）は [`crates/zumen-live`](../crates/zumen-live) に置き、形式別の 1 レコード読み書きは各 L1 crate（DXF と DWG は `crates/zumen-acad`）に置きます。測定と等価検査のハーネスはコアのワークスペースの外の [bench/live](../bench/live/README.md) にあります。公開の API にはまだ何も足していません。`Session` は、変換した図面モデルを常駐させ（[セッションの常駐の図面モデル](#セッションの常駐の図面モデル)）、DXF・DWG・JWW・SXF の `apply` と、IFC の `building_apply` を文書エンジンで当てます（[セッションの文書エンジン](#セッションの文書エンジン)）。

## 決まっていること

2026-11-13 に、利用者が次の 2 つを決めました。

- 対話の編集の本線は、文書エンジンを今の実装と並べて作り、形式を移す道にする。今の実装に手当てを重ねる道は、本線にしない。
- 文書エンジンは、wasm32 の 1 スレッドの制限に合わせて設計しない。

2026-11-15 に、試作の結果にもとづき、利用者が次の 3 つを決めました。

- 文書エンジンを採用して本実装に進める。
- 形式非依存の基盤を `crates/zumen-live` とし、形式別の差分読み書きは各 L1 crate 側に置く。
- 差分で更新する表示のバッファーと、後ろに足す保存の契約を、[契約](#契約)のとおり定める。

2026-11-17 に、`Session` を文書エンジンに載せ替えるにあたり、利用者が次の契約を決めました。

- 文書エンジンで答える `Session` の op は、予算の使い方と、予算で止まる所が、文書エンジンの仕事に従ってよい。
- 止まらない大きさの予算では、ほかは変えない。結果の JSON・保存するバイト列・ID とハッシュ・予算でない診断（code・値・場所・順）は、今までと同じにする。
- 止まったときと中断したときは、文書を変えない。出力は、環境とスレッドの数に依らず同じにする。

## 今の実装との関係

「今の実装」は、要求のたびにファイルモデルから図面モデルとシーンを作る、今のコアの動かし方を指します（[コアの設計](architecture.md#モデルと依存)）。

- API は変えない。JSON のメッセージ・各言語のバインディング・適合テストはそのまま使う。`Session` は、文書エンジンに移した形式から、その上に載せ替える（[セッションの文書エンジン](#セッションの文書エンジン)）。
- 移し終えるまで、新しい op と、形式の読み書きの追加は、今の実装に足す。文書エンジンを待たない。
- `Session` は、変換した図面モデルを常駐させる（[セッションの常駐の図面モデル](#セッションの常駐の図面モデル)）。読み取りは、文書エンジンに載せ替えた形式でも、常駐の図面モデルで答える。
- 今の実装は、文書エンジンの結果を照らす先になる。同じ変更で、同じバイト列・ID・ハッシュ・診断を返すことを、オブジェクトの種類ごとに確かめる（[今の実装との等価](#今の実装との等価)）。
- 今の実装への手当て（#708。P21 の `apply` である #709 は完了）は、文書エンジンと別に進める。サーバーで `apply` を呼ぶ使い方に、すぐ効く。
- 形式非依存の基盤は `crates/zumen-live` に置き、形式別の差分読み書きは各 L1 crate に置く。測定と照合の試作は `bench/live` の独立した package に置く。

### セッションの常駐の図面モデル

`Session` は、DXF・DWG・JWW・SXF の文書について、ファイルモデルと一緒に、変換した図面モデルを持ち続けます。読み取りの応答・予算・診断は、要求のたびに変換し直していたときと同じです。

- 図面モデルが要る読み取り（`drawing`・`entities`・`tables`・`scene`・`render`・`lift`・`measure` など）で最初に変換したとき、その変換が予算の単位ごとに使った量・深さの余裕・届いた診断を、`zumen_base::Replay` に記録する（`Cx::record`）。変換を最後まで通せたときだけ記録し、図面モデルと一緒に持つ。
- 次の読み取りでは変換し直さず、記録を当てる（`Cx::replay`）。単位ごとに使った量を一度に使い、届いた順にまとめた診断を足す。届いた順にまとめる収集先では、まとめた診断を足しても、元の報告を 1 件ずつ足したのと同じ件数・場所・値・順になる。当てる手間は診断の種類の数に比例し、図面の大きさに依らない。
- 記録を当てるのは、その呼び出しの予算で変換が最後まで通ると分かるときだけにする。条件は、単位ごとの残りが記録した量以上、深さの余裕が記録したとき以上、予算が止まっていない、中断の合図がない、収集先が届いた順にまとめる同じ場所の数のもの、の 5 つ。当てられないときは今までどおり変換し直すので、止まる所（単位・`limit`・`requested`）と止まる前の診断も変わらない。入力順に診断を集める op（`convert` など）や明細を捕捉する中の変換も、変換し直す。
- 記録するのは、変換が予算の残りや収集先の中身を読んで動きを変えない形式に限る。DXF・DWG・JWW・SXF の変換で確かめた。プラグインと図面モデルのバイナリの文書は、もとから変換せずに貸す。SIMA と TIFF は常駐させない。
- 中断の合図は、記録を当てる前に一度だけ確かめる。当てている途中に届いた合図は、変換を終えた直後に届いたのと同じ扱いになり、op の次の確かめで止まる。合図が届いた時点で止まる所が環境で変わるのは、今までと同じ。
- `apply` は、常駐の図面モデルを複製せずに移して使う。当てたら捨て、次の読み取りで作り直して記録し直す（文書エンジンで当てた文書は、文書エンジンから組み立てる。[セッションの文書エンジン](#セッションの文書エンジン)）。ハンドルを持たない DXF を文書エンジンで当てたときは、ID のずれを調べるために変換した図面モデルを記録して持つ。断られたとき・止まったときは文書を変えないので、常駐の図面モデルを戻す。ファイルモデルを書き換える経路は、常駐の図面モデルと文書エンジンを捨てる関数を通さないと書き換えられない。
- 変更を常駐の図面モデルへ差分で当てることは、まだしない。
- 常駐の図面モデルの分だけ、開いた文書のメモリが増える。

### セッションの文書エンジン

`Session` は、ASCII の DXF と DWG（R2007 を除く）の `apply` を `AcadLive` で、JWW の `apply` を `JwwLive` で、SXF（SFC・P21 と、それを入れた P2Z・SFZ）の `apply` を `SxfLive` で、IFC（IFC-SPF と ifcZIP）の `building_apply` を `IfcLive` で当てます。契約は、2026-11-17 の決定（[決まっていること](#決まっていること)）のとおりです。

- 文書エンジンは、文書の最初の `apply` で、ファイルモデルから作る。ASCII の DXF は書き出したバイト列から開き、DWG はファイルモデルの写しから開く。JWW と SXF はファイルモデルから作る。SXF は、今までの経路と同じく属性ファイル（SAF）を結ばない図面モデルで要素のハッシュを比べるので、属性ファイルを渡さずに作る。作る仕事は、その `apply` の予算で数え、作る途中の診断は返さない。作ったあとは、文書を閉じるか、ほかの経路でファイルモデルを書き換えるまで持ち続ける。
- 当てるときは、まず変更の一覧が持つ文書のハッシュを、セッションが持つ今のハッシュと比べる。違えば今までの経路に任せ、同じ診断で断る。同じなら、確かめ済みとしてハッシュを外して文書エンジンに渡す。文書エンジンは変更を差分で当て、全体を書く保存で、今までの経路と同じバイト列を返す。DWG は、今までの経路と同じく当てる前にオブジェクトの表を作り、型どおりに読めないオブジェクトの診断を別に集める。文書エンジンの診断も別に集め、文書エンジンが保存したバイト列を読み直して書き戻しの参照で当てたとき（`AcadLive::apply_rereading` が真）は、参照が同じ診断を返すので表の診断を捨てる。差分の経路と空の変更では、表の診断を前に足す。`apply` の診断は届いた順にまとめるので、まとめたものを移しても件数・場所・順は今までの経路と同じになる。文書エンジンが止まった理由の診断を足さずに返したときは、`Session` が足す。
- JWW と SXF は、文書エンジンの診断を別に集め、当てたときと止まったときだけ移す。断ったときは診断を捨て、文書エンジンを持ち続けたまま、同じ要求を今までの経路で当て直す。`SxfLive` には、今までの経路なら当てられる変更を断るもの（P21 で文書エンジンが足したレイヤに入る要素を除く変更など）があるためである。文字の要素の変更と、レイヤの変更・追加は、SFC・P21 とも文書エンジンで当て、今までの経路と同じバイト列になることを試験で確かめる。当て直すと、文書エンジンの仕事の分だけ予算を多く使い、今までの経路で当てたら文書エンジンを捨てる。P2Z・SFZ は、今までの経路と同じく保存したバイト列をアーカイブに入れ、アーカイブのバイト列のハッシュを返す。読み直すのは中の SXF のファイルだけで、アーカイブと属性ファイルは持ち続ける。
- 当てたあとは、ファイルモデルを読み直さない。文書の正は、文書エンジンと、それが保存したバイト列になる。保存したバイト列は応答の blob と同じもの（P2Z・SFZ はアーカイブに入れる前の中の SXF のファイル）で、文書エンジンを捨てたときもここから読み直せる。アーカイブと属性ファイル（SAF）は、開いたときのものを持ち続ける。
- 図面モデルが要る読み取りは、文書エンジンの `drawing` で組み立てる。保存したバイト列を読み直して変換したときと同じ図面モデルと変換の診断を返すので、結果は変わらない。予算の使い方と止まる所は、文書エンジンの仕事に従う（2026-11-17 の決定）。最後まで通せたら、今までどおり記録して常駐させる。DWG（文書エンジンは DXF として変換するので、診断の code が違う）と、属性ファイルを結んだ SXF（文書エンジンが属性ファイルを結ばない）は、ファイルモデルを読み直して変換する。
- ファイルモデルが要る op（形式の詳細・書き出し・R2004 の DWG の `convert`・今までの経路の `apply`・DWG の文書エンジンで当てる前のオブジェクトの表）は、初めて要るときに保存したバイト列から読み直す。読み直しの予算は呼び出し元と共有し、診断は返さない（開いたときと当てたときに返している）。止まったときと読めなかったときだけ理由を返す。読み直したファイルモデルは、次に文書を変えるまで持ち続ける。読み直しの仕事は常駐の図面モデルの記録に入れない。入れると、記録を当てるたびに読み直した分まで予算を使う。
- 文書エンジンが断ったとき・止まったときは、文書エンジンの状態も変わらないので持ち続ける。当てたあとの保存・ハッシュ・読み直しで止まったときは、文書エンジンを捨てる。どちらでも、ファイルモデル・ハッシュ・blob は変えない。取り消しの記録は、当てるたびに捨てる（`undo` は前の版のバイト列を開き直す今までの経路のまま）。
- 次の場合は、今までの経路で当てる。バイナリの DXF（文書エンジンに差分の経路がない）、R2007 の DWG（書き戻せない）、ハッシュが今と違う要求、同じ要求の中の新しい表を指す `apply`（表を順に準備する経路）、文書のハッシュを持つ P2Z・SFZ への要求（今までの経路は、アーカイブではなく中の SXF のバイト列のハッシュと比べて古いと断る）、文書エンジンを作れなかった文書、JWW・SXF の文書エンジンが断った変更（上のとおり当て直す）、プラグインの文書（載せ替えていない）。IFC で今までの経路に任せる場合は、下の IFC の項にまとめる。
- `Cx::record` と `Cx::replay` は、読み取りで持ち続ける。読み取りは常駐の図面モデルで答えるので、変換し直さずに同じ予算と診断を返すために要る。
- 文書エンジンで当てると、予算の使い方が今までの経路と変わる。最初の `apply` は文書エンジンを作る分だけ多く使い、次からは、ファイルモデルの写しと変更の当て方の分が変わる。止まる所も変わる。常駐の図面モデルの試験は、文書エンジンを持ち続けたまま、常駐の図面モデルだけを捨てて比べる。
- 今までの経路で当てた要求が断られたとき・止まったときは、ファイルモデルが変わらないので、文書エンジンを持ち続ける。今までの経路で当てたら、文書エンジンを捨て、次の `apply` で作り直す。
- 2026-11-17 に、`samples/dwg/zumen-layout-r2018_ascii.dxf` と `zumen-layout-r2018.dwg` に線を足した図面で、ネイティブのリリースのビルドで測った（7 回、2 回目からは中央値、単位はミリ秒）。1 件を動かす `apply` は、次の表のとおり。`apply` のあとの `entities`（1,000 件）は、変換し直すので、どちらも同じ（1 万件で 24〜27）。

  | 図面 | 今までの経路（最初・次から） | 文書エンジン（最初・次から） |
  | --- | ---: | ---: |
  | DXF ＋1,000 | 8.8・9.0 | 5.9・2.2 |
  | DXF ＋1 万 | 79.8・78.7 | 35.5・17.0 |
  | DWG ＋1,000 | 11.8・12.0 | 9.7・5.5 |
  | DWG ＋1 万 | 93.1・90.5 | 46.6・29.2 |

  次からの `apply` に残る時間は、全体の保存・ハッシュ・ファイルモデルの読み直し（DWG はオブジェクトの表も）で、図面の大きさに比例する。この表は、当てたあとにファイルモデルを読み直していたときのもの。読み直しをやめた 2026-11-18 に、同じ端末で前後を 2 回ずつ測ると、DXF ＋1 万の次からの `apply` は約 21 ms から約 11 ms に、続く `entities` は約 32 ms から約 13 ms になった。DWG はオブジェクトの表を作るので、ほぼ変わらない。
- JWW と SXF は、2026-11-17 に、`samples/jww/ezjww-geometry.jww` と `samples/sxf/ezsxf-writer-all-features.sfc` に、今までの経路で線を足した図面で、同じように測った。動かすのは、文書エンジンで当てられる元の図面の要素の 1 件。

  | 図面 | 今までの経路（最初・次から） | 文書エンジン（最初・次から） |
  | --- | ---: | ---: |
  | JWW ＋1,000 | 4.3・4.5 | 1.5・0.3 |
  | JWW ＋1 万 | 50.6・46.5 | 13.8・2.4 |
  | SFC ＋1,000 | 8.3・8.0 | 6.2・1.0 |
  | SFC ＋1 万 | 81.3・80.7 | 60.7・9.1 |

  SFC の最初の `apply` は、文書エンジンを作る仕事が大きく、今までの経路との差が小さい。P21 は、線を足せる公開サンプル（線種の表を持つもの）がないので測っていない。
- IFC（IFC-SPF と ifcZIP）の `building_apply` は、最初の `building_apply` で `IfcLive` を作り、建物モデルの文書に持たせる。ifcZIP は中の IFC-SPF のファイルモデルの写しから作り、当てたら、今までの経路と同じく保存したバイト列をアーカイブに入れ直す。文書のハッシュと要素の ID・ハッシュ・値の確かめは、今までの経路と同じ準備（`building::prepare`）で済ませ、確かめた変更だけを文書エンジンに渡す。当てたら、保存したバイト列（`IfcLive::save_spf`）を今までの経路と同じ仕上げ（`building::finish`）で読み直し、結果と blob を作る。建物モデルを作り直す経路（今までの経路の `building_apply`・開き直し・閉じる）は、文書エンジンを持たない新しい建物モデルを作るので、文書エンジンは自然に捨てられる。
- IFC で今までの経路に任せるのは、次の場合。文書エンジンが断った変更（L1 が断る型名・値の種類など。診断を捨て、文書エンジンを持ち続けたまま今までの経路で当て直し、その診断を返す）、文字コードの指定が `auto` で手がかりから CP932 で読むファイル（今までの経路は書き戻したファイルの手がかりを読み直すので、手がかりの文字列を書き換えると読み方が変わる。文書エンジンは開いたときの読み方を保つので作らない）、文書エンジンを作れなかったファイル、プラグインの建物の文書（IFC のファイルモデルを持たない。準備で今までと同じく断る）。ハッシュが今と違う要求と、要素が古い・ない変更は、準備で同じ診断で断る。
- 比べて直したこと。`IfcLive` は、セットとプロパティの名前を文字コードを見ずに比べていた。今までの経路（`zumen_ifc::apply`）は、ファイルの文字コード（指定と手がかり）で読んだ名前で比べるので、CP932 の名前のセットに足すときに、新しいセットを作るか既存のセットに足すかが変わった。文書エンジンも作ったときの文字コードで読んで比べるように直し、`crates/zumen-ifc/tests/live.rs` に、`auto`・`shift_jis`・`iso_8859_1` で `apply` とバイト列が同じことを確かめる試験を足した。
- IFC は、2026-11-17 に、`samples/ifc/rinya/wood-office-architecture.ifc`（1.8 MB）と、適合テストの `building_apply` の IFC に、それぞれ自分のプロパティセットを持つ壁を足した合成の図面で、同じように測った。変更は、最後の要素の名前を変える属性の変更の 1 件。7 回とも新しいセッションで開き、最初の `building_apply` の中央値と、続く 7 回の中央値を取った。

  | 図面 | 今までの経路（最初・次から） | 文書エンジン（最初・次から） |
  | --- | ---: | ---: |
  | 木造の事務所（公開サンプル） | 108.8・110.4 | 169.0・82.1 |
  | 合成 ＋1,000（0.28 MB） | 18.1・16.9 | 26.3・14.1 |
  | 合成 ＋1 万（2.9 MB） | 191.9・190.8 | 292.7・158.8 |

  最初の `building_apply` は、文書エンジンを作る分だけ遅い。次からの `building_apply` に残る時間のほとんどは、保存したバイト列からの建物モデルの読み直しとハッシュで、図面の大きさに比例する。正を建物モデルの文書のままにする限り、ほかの形式より短くならない。
- 予算の使い方が変わるので、適合テストの `civil` の手順 10（空の変更を作業の上限 543 で当てる）の止まる所が、`requested` 563 から 570 に変わった。`hashes.txt` の応答のハッシュを作り直した。ネイティブと wasm で同じ値になる。
- `crates/zumen-abi/src/session/building_ops/tests.rs` で、公開サンプル（`samples/ifc/nakano/nakano_Outside.ifc`・`samples/ifc/text2bim/sample_model.ifc`）と適合テストの IFC、そのうち 2 つを入れた ifcZIP について、今までの経路だけを使うセッションと、`building_apply` の結果・blob・読み取り（`building`・`building_elements`）の応答が同じことを確かめる。変更の種類は、プロパティ（新しいセット・既存のセットの書き換え・実数・整数・真偽・論理・引用符と逆斜線と絵文字を含む文字列）・属性（名前・説明・空）・空の変更・断られる変更を混ぜた一覧・L1 が断る変更・文書のハッシュの違い。文字コードの手がかりを持つファイルを、指定なし・`auto`・`iso_8859_1`・`shift_jis` で開いても比べる。断られたあとも文書エンジンを持ち続け、開き直すと捨てることと、どの予算の種類と上限で止まっても文書を変えず、止まった理由の診断だけを返すことも確かめる（予算の試験は `sample_model.ifc` を除く）。
- `crates/zumen-abi/src/session/resident/tests.rs` で、公開サンプルの ASCII の DXF（R12・R2000・R2007・R2018）と DWG（R2000・R2004・R2013・R2018）、JWW（`ezjww-geometry.jww`）、SFC（`ezsxf-writer-all-features.sfc`）、適合テストの P2Z・SFZ とその中の P21・SFC、属性ファイルを持つ P2Z（`open_sxf_saf`）について、今までの経路だけを使うセッションと、`apply` の結果・blob・読み取りの応答が同じことと、どの予算で止まっても文書を変えないことを確かめる。変更の種類（除く・色が変わる変更と変わらない変更・置き換え・動かす・レイヤ・レイヤを足す・点の表し方・空の変更・断られる変更を混ぜた一覧・`max_places`、JWW と SXF の色・紙空間への追加・空間をまたぐ追加）ごとに比べ、属性ファイルを結んで開いた SFC でも比べる。公開サンプルごとに、文書エンジンで当てた `apply` があることも確かめる。型どおりに読めないオブジェクトを持つ DWG（適合テストの `entity_details_formats`）、ハンドルが重複する DXF（EOF の後ろに読まないバイトを持つものも）、ハンドルを持たず ID がずれる R12 の DXF も使う。
- 独立した確かめ（2026-11-17）で見つかった違いと直したこと。
  - 差分の経路が、除いた図形と値の変わらない図形でも `$EXTMIN`・`$EXTMAX` を広げていた。参照（`dxf::write_back`）は、値を変えた図形と足した図形だけで広げる。範囲が空の図面と、範囲の Z がわずかに負の図面で違いが出た。文書エンジンと参照の比較（`equivalence.rs`）は、この 2 つの変数を持つ ASCII の DXF を使っていなかったので、`text_alignments.dxf` と `zumen-layout-r2000_ascii.dxf`・`r2018_ascii.dxf` で確かめる試験を足した。
  - DWG の型どおりに読めないオブジェクトの診断を、参照の経路に入った `apply` で 2 回数えていた。
  - ハンドルが重複する DXF の空の `apply` を、文書エンジンが通していた。参照は `change.edit.unsupported`（`duplicate_handle`）で断るので、文書エンジンも空の変更を参照の経路に任せる。
  - 保存したバイト列を読み直す経路と、書き戻しの参照（今までの経路）は、変換の診断を捨てる収集先で読み直し・作り直しをする。そこで予算か中断で止まると、止まった理由の診断が呼び出し元に届かなかった（#878 への独立レビューの報告、2026-11-16）。捨てる収集先の結果を渡す所で、止まった理由を呼び出し元へ報告する。文書エンジンの予算の試験は、止まったときに理由の診断があることも確かめる。
  - `JwwLive` は、足す図形のクラスの区分をトランザクションの前に作り、断ったときと止まったときにも残していた。作った区分を除くように直し、`zumen-jww` の等価の試験に、止まる所を変えて確かめる試験を足した（JWW の載せ替え、2026-11-17）。
  - SXF の今までの経路は、変換を診断を捨てる収集先でするので、変換で止まると止まった理由の診断を返さなかった。`Session` が足す（同上）。
  - ハンドルを持たない R12 の DXF で、除いたあとの置き換えが古いハッシュとして断られる疑いは、紙空間の図形・ブロック・挿入の並びを変えた合成の図面と、断られる追加を挟む手順で再現しなかった（R12 の紙空間の図形は図面モデルに入らない）。上の試験に、その手順を残す。

### コアで測った値

## 今の実装で届かない理由

時間が図面の大きさに比例するのは、個々の処理が遅いからではなく、要求ごとに図面の全体を作る動かし方によります。

- セッションが持ち続けるのは、ファイルモデルと、変換した図面モデルと、DXF・DWG・JWW・SXF の文書エンジンである（[セッションの文書エンジン](#セッションの文書エンジン)）。読み取りは変換し直さないが、`apply` は 1 件の変更でも、全体の保存と、ファイルモデルの読み直しをし、次の読み取りでもう一度変換する。
- `apply` は、変更が 1 件でも、図面の全体を何度も作る。DXF では、図面モデルへの変換を 3 回、オブジェクトの表を 3 回、ファイルモデルの写しを 1 回作る。文書のハッシュを付けると、ファイルの全体の書き出しとハッシュの計算を 2 回する（当てる前の確かめと、当てたあと）。DWG は、ファイルモデルの写しが 2 回になる。
- ID から要素を引く索引を持ち続けない。`apply` のたびに、文字列の ID をキーにした表を、全部の要素から 2 回作る。範囲で選ぶ `entities` も、図面モデルへ変換してから全部の要素を見る。
- 1 つの図面を、ファイルのバイト列・ファイルモデル・オブジェクトの表・図面モデル・シーンの 5 つの形で、それぞれ全体を作る。10 万要素の wasm のメモリは 285〜409 MiB になる（[測ったこと](editor.md#測ったこと)）。
- シーンは、変更のたびに全体を作り直し、表示部品へ全体を渡し直す。曲線はシーンを作るときの許容差で折れ線にするので、拡大して細かく見るにはシーンを作り直す。
- 読み取りは JSON で、`entities` は 1 回に 10,000 件までである。続きを読むたびに、図面モデルへ変換し直す。
- 読み取り・変換・書き出しは、1 つのスレッドで動く。
- 手当て（#708 の、図面モデルの使い回しなど）で減るのは回数で、図面の大きさへの比例は残る。効きは 2〜4 倍と見ている（見立てで、測っていない）。

## 形

次の 3 つを原則にします。

- 仕事の量を、変更の大きさに比例させる。
- 図面を 1 つの表で持ち、ファイルモデル・図面モデル・表示は、その表から導く。
- 残す結果（書き出すバイト列・ID・ハッシュ・診断）は、今の契約をそのまま守る。

### 1 つの表で持つ

- オブジェクトを、列ごとの配列で持つ。種類・元のバイト範囲・ハンドル・レイヤ・色の列と、種類ごとの形の列、頂点・文字列・解釈しないバイト列の置き場に分ける。行の番号は、詰めた 32 bit の整数にする。
- 中では行の番号で引く。文字列の ID（`space/0/h2D9` など）は API の境で作り、ハンドルから行の番号への索引を持ち続ける。
- ファイルモデル（L1）と図面モデル（L2）は、同じ表の 2 つの見え方にする。L2 が L1 の型に依らないという層の向きは、見え方の型で保つ。

### バイト列を持ち、要るときに解釈する

- 元のファイルのバイト列を持ち続け、オブジェクトごとにバイト範囲を覚える。型のある値への復号は、表示・選択・変更で要るときにする。
- 触れていないオブジェクトは、保存のときに元のバイト列を写す。「触れたレコードだけを書き換える」（[書き出しの経路](architecture.md#書き出しの経路)）と同じ結果を、全体を作り直さずに得る。
- 解釈しない種類は、バイト範囲と、ほかのオブジェクトへの参照だけを持つ。

### 変更の記録と取り消し

- 変更はトランザクションで当て、当てる前の値を変更の記録に残す。確かめてから反映し、失敗したら何も変えない。
- 取り消しは、記録にある前の値を戻す。逆の操作を当てないので、浮動小数の丸めやハンドルの付け直しで元に戻らないこと（[`apply` で直すときの性質](editor.md#apply-で直すときの性質)）が起きない。
- 変更の記録をファイルに足していくと、異常終了のあとに、最後の変更まで戻せる。
- 版は、表を塊（4,096 行など）に分け、変わった塊だけを写して持つ。前の版を読む仕事（保存・書き出し・チェック）と、次の変更を、並べて動かせる。

### 保存

- 全体を書く保存は、変わっていない範囲に元のバイト列を写し、変わったオブジェクトだけを符号化し直す。バイト列は、今の実装が同じ変更を当てて書くものと一致させる。
- 後ろに足す保存（DWG など）を設ける場合は、全体を書く保存とバイト列が違ってよく、読み直した図面モデル・ID・ハッシュ・診断が一致すること、および同じ入力・操作の列なら環境間で同じバイト列になることを契約とする（[差分で更新する表示と後ろに足す保存](#差分で更新する表示と後ろに足す保存)）。
- 対話の入口では、文書が古くなっていないかを版の番号で確かめる。JSON の `apply` は、今と同じく文書のハッシュを受け取り、返す。このときは全体を書いてハッシュを求めるので、時間は図面の大きさに比例する。

### 表示

- 表示のためのバッファー（種類ごとのインスタンスの列）を持ち続け、変わった行だけを直す。
- 円と円弧は中心・半径・角度のまま持ち、折れ線にするのは描く側でする。座標は、塊ごとの原点からの 32 bit の浮動小数にする。レイヤの表示と色は、表を引いて決める。ブロックと字形は、インスタンスで描く。
- 決定的なシーンの blob と、コアが描く画像（SVG・PNG）は、書き出しの結果としてそのまま残す。

### 表示差分の通信

`zumen-live::display_wire` は、表示の 13 列を全体または 64 要素の塊として写します。文書エンジンを常駐させる子プロセスの入口で使う共通部品です。`encode` は変更フラグを消しません。通信する側は文書の前後の版を別に運び、受信側が反映した版を確認してから `Display::clear_dirty` を呼びます。送信中に次の編集をする場合は、その編集のフラグを消さないよう、版ごとに差分を保持する必要があります。

パケットは `ZLDP` の 4 バイト、版 `u16 = 1`、全体なら `u16 = 1`・差分なら `0`、全長 `u32`、列数 `u32 = 13` で始まります。数値はすべて little endian です。各列には、列番号・1 要素の 32 bit 値の数・反映後の要素数・塊の数をそれぞれ `u32` で置きます。各塊は、先頭の要素番号 `u32`、要素数 `u32`、値の順です。先頭は 64 の倍数で、要素数は 64、列の末尾だけ 1〜63 になります。列も塊も番号の昇順で、重複はありません。浮動小数点は `f32` のビット列を保ちます。

| 列番号 | 値 | 1 要素の 32 bit 値の数 |
| --- | --- | --- |
| 0・1・2 | 線分の座標・持ち主・画層と色 | 8・1・2 |
| 3・4・5 | 円弧の座標と角・持ち主・画層と色 | 7・1・2 |
| 6・7・8 | 文字の位置と姿勢・持ち主・画層と色 | 8・1・2 |
| 9・10・11・12 | 挿入の位置と尺度・定義と格子数・持ち主・画層と色 | 9・3・1・2 |

全体にはすべての値を含め、差分でも全列の長さを含めます。塊がない列も、縮んだ長さを反映します。パケットと反映後の全列は、それぞれ 1 GiB を上限にします。共有 `Cx` で、入力・出力のバイト数、走査・値のコピー、塊の数を数えます。受信する `Packet::parse` は全体を検査してから元のバイト列を借りるため、途中まで検査した値を表示へ反映しません。

この部品には、文書の版と行の ID、描画順、画層・文字・記号の定義は含めません。画層の表は、各エンジンの `display_layers` が、表示のスタイルの画層の値と図面モデルの `Layer` の組で返します。`zumen live --stdio` と Node.js の `openLiveProcess` は、`AcadLive`・`JwwLive`・`SxfLive` を常駐させ、版と受領確認を伴う表示、表示の画層の表、行を指定する移動、取り消し・やり直し、保存、現在の ID とハッシュ、診断を運びます。[文書の IPC](../bindings/cli/live.md)で、通信の上限と共有予算、編集確定後に表示だけが停止した場合の再取得を定めます。

残りの形式、描画順と表示定義、移動以外の編集、Electron の表示への組み込み、往復の性能検査は続けて実装します。既存のシーンや保存のバイト列は変更しません。

`cargo fuzz run display_wire` は、任意のバイト列の検査と、任意の `f32` のビット列を含む最大 256 行の書き出しを流します。通常の予算と小さい入力・確保・レコード・作業量の上限で、結果と使用量が繰り返して一致することを確かめます。

### 問い合わせ

- 文書エンジンの入口は、型のある、写しを作らない読み取り（列の切り出し）にする。JSON の `Session::call` は、その上に載せ替える。メッセージは変えない。
- 範囲で選ぶための空間の索引を持ち続け、変更のたびに、変わった行だけを直す。

`AcadLive::seen_of_row` は、表示の行から現在の正規 ID と要素のハッシュを取得します。出所のレコード番号・バイト位置はハッシュに入らないため、保存位置の全体対応表は作りません。文字列と要素のコピー、走査、ハッシュ計算は呼び出し元の予算を使います。削除済み・範囲外の行は値を返さず、停止時は文書と表示の変更フラグを保ちます。

一意なハンドルでは図面全体を走査しません。キーなし・重複ハンドルでは既存の ID 表を逆引きするため、その件数に比例した走査が残ります。行番号は現在の版だけで使い、全体を作り直す編集や履歴の復元をまたぐ呼び出しは、呼び出す側が文書の版を確かめます。ID の生成規則と `Seen` による編集の前提条件は変えません。

`AcadLive::select_rect_with_cx` は、モデル空間の囲む箱と矩形が接触・交差する生存行を昇順で集めます。空間索引の走査、結果 1 行につき要素数 1・論理サイズ 4 バイト、整列と生存判定を呼び出し元の予算へ計上します。停止時は出力先の元の内容を保ち、文書・表示・履歴を変更しません。従来の予算なしの `select_rect` と選択条件・順序は同じです。共通の索引を使う JWW の選択にも、結果の確保と整列の検査が加わります。

`JwwLive`・`SxfLive` にも、行で引く同じ形の `select_rect_with_cx`・`seen_of_row` と、行の空間の座標から表示（用紙）の座標への変換を返す `sheet_of_row` があります。常駐 IPC は、表示の座標で届いた移動を `sheet_of_row` で行の座標に直して当てます。SXF の実寸の空間で、空間を置いたビューがないか 2 つ以上ある行は変換が決まらず、移動を断ります。試験では、行の ID とハッシュが `drawing` の要素のものと一致すること（1・4 スレッド、移動を挟んだ 2 回）と、選択が `select_sheet` と同じ要素を返すことを確かめています。

常駐 IPC の `Select` と Node.js の `select` でも同じ選択を使います。文書の版を先に確かめ、全結果の符号化が成功した場合だけ行を返します。全域では結果数に比例する領域と、走査・整列の作業が必要です。形状そのものとの交差や画層の表示状態による除外は別の処理です（[通信と検査](../bindings/cli/live.md)）。

### 並列

- 64 bit・複数のスレッド・共有メモリを前提にする。
- 復号と、導くもの（表示のバッファー・索引）は、オブジェクト 1 つと、表（レイヤ・スタイル・ブロック）への参照から決まる関数にする。分けて流し、入力の順に集めるので、結果はスレッドの数に依らない（[決定性](architecture.md#決定性)）。
- wasm32 の 1 スレッドでも、同じ結果を返す。速さは、そこに合わせない。

DXF の平面図形は、入力位置を最大 16,384 件ずつ区切って復号します。結果は 256 件のページへ直接置き、入力順に表示用の値へ移します。使い終えたページは解放し、全件の復号結果を別の配列に集め直しません。DWG の復号済みの平面図形にも、同じページ単位の解放を使います。モデル・用紙・ブロック定義を通じて一意なハンドルは、ID の重複回数と出所の共有を調べる一時表から除きます。これらの検査に使った表は表示の構築前に解放します。一般図形・用紙・属性の処理順と、論理サイズで数える予算・診断の順は変えません。

### 依存

- 寸法と測る相手、ハッチングと境界、ブロックと属性のような依存を、表の中に辺として持つ。変更のあとは、依存する側だけを作り直す。
- 建物モデルの要素どうしの依存（壁と開口など）も、同じ形で持てるようにする。

`AcadLive` は、図形自身の参照と、別レコードの DIMASSOC・リアクターから得た依存元を分けて持ちます。図形だけを読み直す編集でも、外部から得た依存辺を保ちます。この依存元の列は履歴の状態間で共有し、保持するバイト数と編集時の走査を予算に計上します。合成 DXF の寸法・引出線で、編集・取り消し・やり直し後の依存辺と、保持モデル・逐次 `apply` の保存バイト列を照合しています。連想の合成 DXF では、測る相手と依存する側（寸法・連想ハッチング・引出線と注記）のそれぞれに移動・色・線種の尺度・削除を当てます。1 つずつ当てたときと続けて当てたときの両方で、結果・診断・保存・保持モデルを逐次 `apply` と照合します。依存辺は、編集・取り消し・やり直しのたびに、保存したバイト列を開き直したものと一致します（1・4 スレッド）。DWG では、公開の R2000 の DWG に書き戻した引出線と注記で同じ照合をしています。DWG の読み込みもリアクターと DIMASSOC の参照（330・331）を DXF と同じ値で置くので、公開の R2004・R2018 の弧長寸法の DWG では、円弧から弧長寸法への辺を DXF と同じに持ちます（1・4 スレッド）。DWG の書き戻しは連想ハッチングを足せないので、DWG の連想ハッチングの照合はまだありません。

`IfcLive` は、要素どうしの依存（空間の包含・相対配置・型・材料・開口の穴と充填・グループ・通り芯・区画・プロパティの要素参照）を同じ依存グラフに持ちます。今の変更（プロパティの値、名前と説明）は、プロパティの要素参照だけを変えられます。合成 IFC の階・壁・開口・扉・扉の型・室のそれぞれに、プロパティを足す・名前を変える・説明をなくす変更を当て、室のプロパティの要素参照を文字列に変えます。1 つずつ当てたときと続けて当てたときの両方で、結果・診断・保存・保持モデルを逐次 `apply` と照合します。依存辺は、変更・取り消し・やり直しのたびに、保存したバイト列を開き直したものと一致します（1・4 スレッド）。依存辺が変わるのは、要素参照を文字列に変えたときだけです。

空間・要素・関係を足す・除く・置き直す変更（[#897](https://github.com/zumen-jp/zumen/issues/897)）は、要素の差分では当てません。`IfcLive::apply` は、この変更を含む一覧を今までの経路（`zumen_ifc::apply`）で今の状態に当て、書き直したバイト列から状態を作り直します。保存・保持モデル・ID・ハッシュ・依存辺・変換の診断は、保存したファイルを開き直したものと同じです。前の状態は取り消しのために持ち、取り消し・やり直しは差分の履歴と同じ順で状態を行き来します。仕事とメモリは文書の大きさに比例します。`crates/zumen-ifc/tests/author.rs` で、IFC2X3・IFC4・IFC4X3 の合成入力について、差分の変更と構造の変更を混ぜた列と、取り消し・やり直し・戻ってから当てる変更を、今までの経路と開き直したものに照らしています。

`JwwLive` は、ブロック定義から最上位の挿入要素を逆引きします。定義内の要素の囲む箱をモデル座標で保持し、変更した定義の箱を集計して、参照する挿入要素の箱と空間索引を同じトランザクションで更新します。集計と依存先の走査は予算を共有し、取り消し・やり直しでは記録した箱の差分を戻します。合成 JWW の移動・削除で、回転と尺度が異なる複数の挿入の選択結果、保持モデル、保存バイト列、予算で停止したときの状態と履歴を照合しています。

`SxfLive` は、変更した作図部品と依存する部品の囲む箱を一度空にしてから、開いた直後と同じ順に作り直します。循環する定義でも前の箱が再計算に残りません。箱の変更前後を同じ履歴に保存し、取り消し・やり直しでは記録した値を戻します。並べ替え・集計・一時確保と復元の確保は、反映前に共有予算で検査します。部品を変えない編集では、部品の箱の表をコピーしません。部品の変更時は表全体のコピーと並べ替えが残るため、性能目標の検証は別に行います。

合成 SFC の循環・入れ子の部品と部分図で、移動・削除・取り消し・やり直し後の保持モデル、保存、箱、選択を照合しています。上限直前・上限一致・使用済みの予算と中断では、停止時に表示の変更フラグと履歴も変わらないことを確かめています。1・4 スレッド、およびネイティブと wasm32-wasip1 で、保存・モデル・診断・予算使用量・履歴の比較記録が一致しています。

### 予算・中断・診断

履歴とトランザクションの確保予算は、ポインター幅に依らない論理バイト数で見積もります。行と形式別の差分は `INLINE_BYTES` に本体の大きさを指定し、可変長部分も環境共通の単位で数えます。取り消し履歴の上限にも同じ見積もりを使います。

AcadLive のモデル空間とブロック定義内の編集では、要素を複製する前に予算を検査し、図形を持ち上げ直す作業と一時的な値・文字列も呼び出し元の `Cx` で数えます。診断を一時的に分ける場合も、予算と中断トークンは共有します。DXF のタグ履歴は、タグを 64 バイト、操作を 128 バイトとして、値の長さを足します。実際の構造体の大きさや `Vec` の確保容量は、予算や取り消し履歴の上限に使いません。

DWG の編集で符号化し直したレコードを復号する入口も、呼び出し元の予算と中断を使います。復号する前にビット列の長さから作業量と一時領域を見積もり、復号後に値の件数と文字列・バイナリの長さを数えます。表から補う画層・線種・スタイル・登録アプリケーション・拡張データの画層名、色見本、ブロックの値、種類・セクション名は、コピーの前にも検査します。値 1 件を 64 バイトとし、可変長部分は長さを加えます。省略する既定の名前、未参照の表、余分な確保容量は数えません。後で参照不足により捨てる拡張データも、実際にコピーする分を数えます。配置と診断の順序は従来の読み取りと共有します。予算不足や中断は編集の停止として返し、全体を読み直す経路へ進みません。この論理サイズは実際の最大確保量を証明するものではなく、復号全体の確保量は引き続き監査します。

編集対象の元レコードの復号も同じ予算検査を使います。変更済み・追加済みレコードは、種類・セクション名・符号化したバイト列・値とその文字列やバイナリを、コピーする前に数えます。実際の確保容量によって使用量は変わりません。取得中の停止は編集の停止として呼び出し元へ返し、保持しているレコードと履歴を変更しません。

- 予算と中断は、トランザクションごと、後ろで動く仕事（開く・保存・索引）ごとに持つ。並列でも入力の順に予算を使い、止まる位置を同じにする（[予算と中断](architecture.md#予算と中断)）。
- 診断は、今の実装と同じ code・場所・値を返す。カタログは共用する。

## 契約

### 変えないもの

- 同じ入力・設定・予算なら、書き出すバイト列・領域モデル・シーンの blob・コアが描く画像・診断の順と停止位置が、ネイティブと wasm で一致する（[決定性](architecture.md#決定性)）。
- 予算と中断、入力でパニックしないこと、診断のカタログ、版をまたいで保つ ID、形式の権利の台帳。

### 今の実装との等価

文書エンジンに移した種類と操作について、次の 3 つを確かめます。

1. 全体を書く保存のバイト列が、同じ変更の列を、今の実装の `apply` に 1 つずつ当てた結果と同じである。
2. 文書エンジンが保持する図面モデル・ID・ハッシュ・診断が、保存したバイト列を今の実装で読み直した結果と同じである。
3. 取り消したあとの状態が、変更の前と同じである。全体を書く保存のバイト列も同じになる。

照らす先を「1 つずつ当てた結果」にするのは、今の実装が変更ごとにファイルを書き戻し、途中の状態（進めた `$HANDSEED` など）が結果に残るためです。

2 では、保存前に文書エンジンが保持する値を比較に使います。同じバイト列を今の実装で読み直すだけでは、保持している値の一致を確かめられません。試作は、DXF と DWG の扱う範囲（モデル空間の 6 種類）について、保存・開き直しをせずに保持している要素の ID・種類・画層・ハッシュ・囲む箱、表示のバッファーの値、画層・線種の表、範囲で選ぶ結果、開いたときの診断を、今の実装の `entities`・`tables`・`scene`・選択・診断と直接照合しています（画層と線種の ID は、開き直したときの振り直しに合わせて比べます）。残りの図形の種類での照合はこれからです（[まだ確かめていないこと](#まだ確かめていないこと)）。

DXF の本実装では、要素の追加・削除により移動する出所のレコード番号も、保存前の保持モデルと保存後の読み取りで照合しています。属性を持つブロックの追加、表やブロック定義が ENTITIES セクションの後ろにある図面も含め、今の実装の逐次 `apply` との保存バイト列の一致、`undo`・`redo` 後の保持モデルと保存バイト列の一致を確かめています。

合成の DXF では、MTEXT・POINT・ELLIPSE・DIMENSION・LEADER の移動と置き換え、SPLINE の制御点の置き換え、SOLID・HATCH の属性変更と削除、ペーパー空間とブロック定義内の要素の移動・置き換え・削除も、1 スレッドと 4 スレッドでこの 3 つを照合しています。画層・文字スタイル・線種・寸法スタイルの表の追加・置き換え・削除と、TABLES セクションのない図面で最初に画層を指す要素を削除した場合も含みます。SPLINE・SOLID・HATCH の移動は、今の実装と同じ診断で断り、状態と取り消しの履歴を変えないことを確かめています。1 要素ずつ取り出す場合も、出所と参照のレコード番号を全体のモデルと同じ規則で補正します。

DWG は、保持する形状を使い、全体保存と共通の変更手順・オブジェクト長・マップの区切り・ヘッダーの伸縮から、保存後の出所バイト範囲を求めます。元のバイト列を借り、変更したデータと位置を一時的に持ちます。保存したファイルを読み直したり、全体の図面モデルを復号したりはしません。R2000 の前後リンクは、既存の更新器へ渡すため、オブジェクトのデータを一時的にコピーします。出所の計算は共有 `Cx` の予算と中断に従い、編集確定・選択・取り消しの経路では実行しません。

DWG の出所を伴う単体取得には `element_with_source` を使います。`element_of_row` は保持時の位置を返します。全体取得と単体取得の出所は同じ規則で補正します。出所の取得には全レコードと変更列の走査が残り、単体取得の時間が図面の大きさに依らないことは、まだ示していません。

DWG の 4 規模は、ネイティブの 1・4 スレッドと WASI で、保存前のモデル全体・保存・undo・redo が一致しました。範囲と結果は[出所の再検証](../bench/live/results/dwg-source-2026-11-16.md)にあります。

DWG の公開サンプルと合成の操作では、R2000・R2004・R2018 の画層・文字スタイル・線種・寸法スタイルの追加・置き換え・削除、ペーパー空間の追加・移動・置き換え・属性変更・削除、ブロック定義内の移動・置き換え・属性変更・削除を、1・4 スレッドで逐次 `apply` と照合します。MTEXT・POINT・ELLIPSE・SPLINE の追加・属性変更・置き換え・削除、移動できる図形の平行移動も含みます。LEADER は、矢印と既存の寸法スタイルを指定した追加・属性変更・平行移動・置き換えを照合します。

R2000・R2018 の連想しない HATCH の追加・属性変更、R2004・R2018 の SOLID の属性変更・削除と ARC_DIMENSION の平行移動・属性変更・置き換えも照合します。今の実装が拒否する操作では、成否・診断の全項目が一致し、モデル・保存バイト列・履歴が変わらないことを確かめます。DWG の追加要素も、既存の要素と共通の削除条件で検査します。

表・ペーパー空間の要素の追加と削除・画層の順が変わる削除などは、全体を書いて読み直す経路で照合したものです。ペーパー空間の要素の移動・属性変更・置き換えは、ASCII DXF と DWG（R2000・R2004・R2018）で差分の経路を通ることも確かめています。差分だけの作業量や性能目標に届いたことは、この検査では示していません。

JWW の公開サンプルの線・円・曲線・点・ソリッド・寸法は、移動・属性変更・置き換え・削除の成否と診断の全項目、保持モデル、保存バイト列、取り消し・やり直しを、1 スレッドと 4 スレッドで今の実装と照合しています。今の実装が断る操作は、同じ診断で断り、状態と履歴を変えないことを確かめます。文字の追加・置き換え・移動・色の変更と、レイヤの改名・状態の変更・追加も文書エンジンで当て、文字の長さが変わると一覧を数え直して書き、レイヤはヘッダーのレコードを書き直します。合成 JWW で、今の実装と保存バイト列・保持モデル・適用の結果・診断と、取り消し・やり直しを照らしています（#861）。この照合は、全種類や性能目標の達成を示すものではありません。

SXF は、削除した基底レコードと追加するレコードの順序から、保存後の出所レコード番号を求めます。`drawing` で保持モデルを取り出すときに、要素・表・部分図・作図部品・拡張と、要素間の参照を補正します。この補正に保存や読み直しは使いません。公開 SFC、用紙フィーチャのない合成 SFC、共有の座標とスタイルを持つ合成 P21 で、追加・削除の列、保存前のモデル全体、多段の取り消し・やり直しを、1 スレッドと 4 スレッドで照合しています。単体の要素は `placed_with_source` で、同じ出所と参照の補正を受けた値を取り出せます。コピーと補正は共通の予算・中断に従います。内部の保持値を借りる `placed` は、補正前の出所を保ちます。追加・削除・取り消し・やり直しの各段で、単体取得も全体モデルと照合しています。

SXF の保持モデルの取得では、未集約の変換診断を保存順の場所で報告します。要素の診断は変更・取り消しと同じ行に保持し、未定義の線種は最初の使用箇所、用紙の後にある要素の診断は最初の生存要素へ対応させます。P21 の参照欠落と重複する画層への所属は現在の参照で確かめ、SAF の診断は現在の拡張との結合から作ります。表示する場所の件数は取得時に選び、開いたときの上限に制限しません。公開 SFC と合成入力で、診断の全項目、属性変更・削除・取り消し・やり直し、予算停止時の状態の保持を照合しています。編集を拒否する診断の場所も保存順に補正します。

線種の使用順は、部分図・作図部品を定義順に読んだ後に用紙を読む、従来の変換の順序で保持します。作図グループの展開、空・非表示の複合曲線も区別し、最初の使用要素を除いた後の警告と線種表の名前・順序を求めます。用紙フィーチャの後に要素がある場合も、追加要素を保存先と同じ位置に挿入します。合成 SFC の変更・取り消し・やり直しで、診断全項目、保持モデル全体、保存バイト列と、入れ子のビューを含む描画順を 1・4 スレッドで照合しています。この初期走査と取得は共通の予算・中断に従います。全種類での照合と性能の検証は残っています。

IFC の変更文は、確定前に呼び出し元の `Cx` で一度読み、建物モデルの更新と IDS の属性取得で共有します。文と解析結果を同じ履歴で保持し、取り消し・やり直しでも対応を保ちます。共有プロパティの変更・数量セットの改名・属性変更の列で、予算停止時の原子性、保存・保持モデル・ハッシュ、IDS の値と作業量、取り消し・やり直しを照合しています。この合成入力ではネイティブと wasm32-wasip1 の保存・モデル・ハッシュ・診断・全予算種別の使用量・履歴の見積もりも照合します。建物要素全体の依存伝播と性能の検証は残っています。

2026-11-17、`IfcLive::report_lift_diagnostics` を足しました。保存したバイト列を今の実装で読み直して建物モデルに変換したときと同じ変換の診断を報告します。開いたときの変換の診断を状態に持ちます。書き直した文がどれも、参照・型の名前・列挙・省略の並びを変えず、診断の場所のインスタンスでもなく、インスタンスを足していないときは、持っている診断の場所を、書き直した文の長さの差だけ移して返します。仕事は書き直した文と診断の数に比例します。ほかの変更があるときと、文字の手がかりから CP932 で読んだときは、保存して読み直して変換します。使われないインスタンスの診断（`ifc.entity.dropped`）や単位の診断は、参照や値の型が変わると変わるためです。試験では、合成入力と公開サンプル（`nakano_Outside.ifc`）の変更・取り消し・やり直しのたびに、読み直した変換の診断と一致することを、1・4 スレッドで確かめています。`Session` の読み取りは、これまでどおりファイルモデルから答えます。

IFC の単一プロパティを変えたときは、保持する詳細プロパティも同じ履歴で更新します。共有セットと値の複製先の番号を追い、上下限・値の列・列挙の選択肢・複合の構造と出所を保ちます。セットの改名・説明の変更、型に付くセット、重複した根と複合の子も対象です。モデル全体の保存・再読を使わず、保持する詳細の構造と変更文から更新します。詳細値に含まれる要素参照も依存辺へ反映します。モデルをコピーする前に作業量・確保量・値の入れ子の深さを検査し、取り消し・やり直しでは履歴と版の変更前に検査します。保持モデルの履歴サイズは、文字列や値の長さから求めた環境共通の論理バイト数です。形状・表示を含む建物モデル全体の照合と、編集経路全体の確保量の監査は続けます。

ドア・窓の枠とパネルの定義済みプロパティも、通常のプロパティを編集した後に保ちます。属性の位置・名前・型と IFC2X3 の版の補正は、従来変換と共通の表から読みます。関係経由と型への直接付与、重複する参照、改名と説明の変更を、IFC2X3・IFC4・IFC4X3 の合成入力で照合します。単位の有無と解釈できない属性値を含め、保持モデル・ID・ハッシュ・編集時の診断・保存・多段の取り消しとやり直しを比較します。取得時の診断全体の追従は、引き続き残件です。

依存先を求める共通の走査は、探索から並べ替えまでの作業と一時確保を呼び出し元の予算で数えます。循環を含めて同じ順で返し、影響しない上流の要素数では作業量が変わらないことを確かめます。IFC は構造とプロパティから参照を集める際も共有の予算を使い、入れ子の値に深さ制限を適用します。共有プロパティの参照を外す合成例で、依存先・保持モデル・保存・取り消し・やり直しと、予算停止時に状態を保つことを照合しています。

共通トランザクションは、依存辺を履歴へコピーする前に作業量と確保量を検査します。辺の追加・削除と取り消し・やり直しも、反映を始める前に必要な量を検査します。重なり合う辺と循環を持つ例で、上限直前・上限一致・使用済みの予算・中断を試し、停止時に表・ハンドル索引・依存グラフ・履歴が変わらないことを確かめています。無関係な依存行を 1 万件足しても、この検査の使用量は変わりません。

### 差分編集の fuzz

[5 形式の fuzz](../fuzz/README.md#target) は、本実装の読み込み・編集・保存・保持モデルの取得・取り消し・やり直しを直接呼びます。有限の予算、小さい作業量、中断で停止位置を比べ、停止時の原子性と履歴による状態の復元を確かめます。保存・保持モデル・診断・予算の使用量は、同じ入力を 1・4 スレッドで 2 回ずつ実行して比較します。全種類の今の実装との等価と環境間の一致を、この検査だけで示すものではありません。

### 差分で更新する表示と後ろに足す保存

次の 2 つは、2026-11-15 の利用者の判断で定めた契約です。

- **差分で更新する表示のバッファー**: 行の並びが変更の履歴に依るため、同じ図面でも開き直した直後に作った表示のバッファーとのスロット順のバイト列一致は求めない。描く結果（要素ごとの値と描画順）が一致すること、および同じ入力・設定・操作の列なら環境間で同じになることを契約とする。従来の `scene` の blob と、コアが描く画像（SVG・PNG）は、これまでどおりバイト列まで一致させる。
- **後ろに足す保存**: 全体を書く保存は、今の実装とのバイト列一致を必須とする。後ろに足す保存を設ける場合は、全体を書く保存とバイト列が違ってよく、読み直した図面モデル・ID・ハッシュ・診断が一致すること、および同じ入力・設定・操作の列なら環境間で同じバイト列になることを契約とする。

## 進め方

1. 縦に 1 本通す試作を作る（#878）。DXF から始め、DWG（R2000・R2018）に進む。線・折れ線・円・円弧・文字・画層・ブロックの挿入について、開く、表示のバッファーを作る、1 件を動かす、取り消す、保存する、範囲で選ぶ、を通す。bench/editor の図面で、今の実装と時間とバイト列を比べる。DXF と DWG（R2000・R2018）の縦 1 本、差分で更新する表示のバッファーと GPU での表示、動かす場所の比較まで試作を終えた（[試作で測った値](#試作で測った値)）。
2. 次の 3 つがそろえば、採る。試作の範囲で 3 つとも満たし、採らない条件には当たらなかったため、2026-11-15 に採用が決まった。
   - 確定・選択・取り消しの時間が、1 万要素と 100 万要素で同じ桁になる。
   - 開いて表示するまでの時間が、今の実装の 5 分の 1 以下になる。
   - 全体を書く保存のバイト列が、公開サンプルと合成の図面で、今の実装と一致する。
3. 多くの種類で、書き戻しに図面の全体の解釈が要ると分かったら、採らない。そのときは、今の実装に、持ち続ける図面モデルを足す道（#708 の先）に戻す。
4. 採ったあとは、次の順に移す。`crates/zumen-live` の表・版・トランザクション・取り消し。DXF と DWG の主な種類と、等価の照らし合わせ。差分で直す表示。残りの種類と、JWW・SXF・IFC（形式ごとに並行して進められる）。`Session` の載せ替え（変換した図面モデルの常駐と、DXF・DWG・JWW・SXF の `apply`、IFC の `building_apply` は済んだ）。依存。

## 目標の値

100 万要素の図面での、ネイティブの目標です。測った値ではありません。試作の値は[試作で測った値](#試作で測った値)にあります。

| 操作 | 目標 |
| --- | --- |
| 開いて最初に表示する | 1 秒以内。見えている範囲は 300 ms 以内 |
| 確定・選択・取り消し | 1 ms 以内。図面の大きさに依らない |
| 保存 | 後ろで動かし、操作を止めない |

## まだ確かめていないこと

- 解釈を一部にとどめたまま、残りの種類と変更でも今の実装と同じバイト列を書き戻せるか。DXF と DWG（R2000・R2018）のモデル空間の 6 種類を、動かす・足す・除く・属性を変える変更では、図面の全体を作り直さずに差分で書き戻せた（[試作で測った値](#試作で測った値)）。本実装の DXF で照合した範囲は[今の実装との等価](#今の実装との等価)に記す。ASCII DXF と DWG のペーパー空間の要素は、移動・属性変更・置き換えを差分で書き戻し、逐次 `apply` と照合した。ペーパー空間の要素の追加・削除、属性を持つブロック参照・寸法・表、厚さなどの拡張情報が変わる変更は、全体を作り直す経路で当てる。表を差分だけで直すことと、残りの種類・操作を DWG でも照らすことは残っている。
- 要素のハッシュを、変更のたびに差分で保てるか。試作は、検査のときに生きている画層・線種の ID を今の実装と同じ順で振り直してハッシュの一致を確かめた。TABLES セクションのない図面では、ある画層を最初に指す図形を除くと、指していない要素のハッシュも変わる。本実装では、TABLES セクションのない ASCII DXF のモデル空間の編集で、表にない画層・線種の順を最初に指す図形の位置から差分で求め直し、ID・ハッシュ・取り消しを全体を読み直す経路と一致させた。ブロック定義・ペーパー空間が使う ID が動く変更、決め手の位置が分からない変更、バイナリ DXF・DWG は、引き続き全体を作り直す経路で当てる。
- DWG の後ろに足す保存（試作は R2000 の部分書き換えと R2004〜R2018 のコンテナー再構築による全体の保存だけを実装した）。
- 寸法・ハッチング・実際の文字の字形を入れた表示のバッファーの大きさと GPU 表示の時間（試作の WebGPU 測定は、線分・円弧・ブロック定義の線分展開・文字の矩形枠まで）。
- 変更ごとの診断と予算・中断の検査を入れた時間。
- 共有メモリ wasm で DWG を並列に開くときの、アロケーターの大域ロックを避ける作業領域の持ち方（DXF は 12 スレッドで 3.3 倍速くなったが、DWG はレコードごとの一時確保が競合した）。
- 残りの図形の種類について、文書エンジンが保持する形・表示のバッファー・範囲で選ぶ結果・診断を、今の実装と直接照らすこと。
- 入力でパニックしないこと。[差分編集の fuzz](#差分編集の-fuzz) で本実装を継続して検査する。入力と操作の組み合わせをすべて試したことや、任意入力で停止することの証明にはならない。
