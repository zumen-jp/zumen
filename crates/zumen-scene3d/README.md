# 3D のシーン

建物モデルの形を評価し、開口を引いたメッシュ・配置・要素 ID を ZMS3 の列へ詰めます。配置の正本は [scene3d.toml](../../schema/scene3d.toml)、選択・座標・許容差は [3D のシーンの契約](../../schema/README.md#3d-のシーンの契約)にあります。

Rust では、形を保持する Building を build に渡し、encode でバイト列にします。IFC の通常の Lift は属性だけを取得するため、形には IfcFile::lift_geometry を使います。read は元のバイト列を借用し、列の範囲・有限値・参照・文字列・ID の重複を検査します。いずれも Cx で予算と中断を受けます。共通 API では scene3d の要求と take で同じ結果を取得できます。

## 公開 IFC での計測

2026-11-16、Windows 11 x64、Rust 1.99.1 MSVC の release ビルドで、[公開 IFC 12 件](../../samples/ifc/README.md)を測りました。入力は属性と形を lift してから L1 を捨て、同じ Building から塊と許容差を変えています。許容差の既定値を求める予備評価を 1 回行い、その値の 1・4・16 倍と、塊の目安 256・1024・4096 の組を 1 回目と 3 回目は順に、2 回目は逆順にして 3 回ずつ測りました。

下表は許容差 1 倍・塊 4096 の結果です。時間は形の評価・シーン作成・符号化の合計の中央値で、読む時間・lift・予備評価を含みません。確保量は入力の Building を除いた System アロケーターの追加確保の最大値です。OS の常駐量や予算の論理量ではありません。別のビルドも動く端末で測った参考値で、数 % の時間差を性能の優劣の根拠にはしません。

塊だけを変えた 12 件の合計は、256 で 45 塊・2,817,514 バイト、1024 で 18 塊・2,816,106 バイト、4096 で 13 塊・2,815,850 バイトでした。共有するメッシュと三角形の数は変わりません。4096 を既定として採用し、1 要素は分けず、配置の f32 化の誤差が許容差の 1/4 を超える手前で原点を区切ります。256 と 1024 は Rust の Options で選べます。描画時のカリングやフレーム時間はこの測定に含めず、表示部品で別に確かめます。

4096 で許容差を 1・4・16 倍にした合計は、それぞれ 75,816・75,792・75,780 三角形、2,815,850・2,815,274・2,814,986 バイトでした。直線と既存の面分割が多いこのサンプルでは削減量が小さいため、固定の LOD の段や自動切り替えは設けず、1 倍を既定にします。粗いシーンは利用側が明示した許容差で別に作ります。曲線の許容差を小さくすると点が増えることは、円柱の解析的な合成入力でも確認します。

座標・ID・列の正しさは合成入力の期待値で、環境間の一致は共通 API の全応答と blob のハッシュで確かめます。この測定は外部実装との一致率ではありません。形の体積についての照合は [形状評価の記録](../../bench/kernels/README.md)に分けています。

再測定は公開入力を指す ZUMEN_SAMPLES を設定し、相対パスを辞書順に渡します。確保量は 64 GiB、作業量は 100,000,000,000 の予算を明示します。例は入力番号と件数・時間だけを出し、入力名・要素 ID・属性値を出しません。

    cargo run --release -p zumen-scene3d --example ifc_scene -- <相対パス...>

予算の上限 0、中断、不正な形では、部分的な blob を返しません。読み手は全 prefix の切り詰め、列の型・長さ・参照・NaN・ID の重複、未知の追加セクションを検査し、fuzz の scene3d でも同じ入口を使います。
